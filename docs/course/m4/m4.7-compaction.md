# M4.7 · Compaction before and after

> **Ticket:** [#62](https://github.com/Dfscashline21/sideline/issues/62) ·
> **Mode:** hand · **Time:** 2 to 3 hours ·
> **Needs:** M4.3, M4.4 (the bucketed season), M4.6 (snapshots)

## Why this matters

"Small files" is the most common lakehouse performance problem in real
life, and a favourite interview question because it connects everything:
streaming and frequent loads create them, fine partitioning multiplies
them, every file costs a metadata entry and an open, and the fix
(compaction) interacts with snapshots, time travel and storage cost.

You've already created small files without trying: M4.4's bucketed
season. Now you'll create them on purpose, measure the damage, and fix it.

## What you'll produce

- A table with many small files, made the way real pipelines make them.
- `ingestion/sideline_ingestion/lakehouse/compact.py`: rewrites a
  partition range into few files in one commit.
- A table in `docs/notes/m4.md`: file count, snapshot count, query time,
  before and after, plus what happened to storage.

### 3. Write the compaction (45 min)

Compaction is "read these files, write the same rows as fewer, bigger
files, swap them in one atomic commit". Readers never see a half-done state.

<details>
<summary>Hint 2 · Approach</summary>

PyIceberg 0.12 has no `rewrite_data_files` (Spark has, as a stored
procedure, and you'll meet it in M7). You can build the same operation
from what you know: `overwrite(rows, overwrite_filter=<partition range>)`
where `rows` is a scan of that same range. Do it **one partition range
at a time** (a month) so memory stays bounded and each commit is small.

Only compact partitions that need it: skip months whose file count is
already low. Pass the threshold as an argument.

</details>

<details>
<summary>Solution (open only after you have your own)</summary>

```python
"""Compact raw.pbp-style tables month by month: many small files -> few large ones."""

import argparse
import datetime as dt

from pyiceberg.table import Table

from sideline_ingestion.lakehouse.catalog import get_catalog


def month_starts(first: dt.date, last: dt.date) -> list[dt.date]:
    months, current = [], first.replace(day=1)
    while current <= last:
        months.append(current)
        current = (current + dt.timedelta(days=32)).replace(day=1)
    return months


def compact_month(table: Table, start: dt.date, min_files: int) -> tuple[int, int]:
    end = (start + dt.timedelta(days=32)).replace(day=1)
    month_filter = f"game_date >= '{start}' and game_date < '{end}'"
    scan = table.scan(row_filter=month_filter)
    files_before = len(list(scan.plan_files()))
    if files_before < min_files:
        return files_before, files_before
    # Same rows, rewritten as few files, swapped in one commit.
    table.overwrite(
        scan.to_arrow(),
        overwrite_filter=month_filter,
        snapshot_properties={"sideline.change": "compaction"},
    )
    return files_before, len(list(table.scan(row_filter=month_filter).plan_files()))


def main() -> None:
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("table")
    parser.add_argument("--start", type=dt.date.fromisoformat, required=True)
    parser.add_argument("--end", type=dt.date.fromisoformat, required=True)
    parser.add_argument("--min-files", type=int, default=10)
    args = parser.parse_args()
    table = get_catalog().load_table(args.table)
    for month in month_starts(args.start, args.end):
        before, after = compact_month(table, month, args.min_files)
        print(f"{month:%Y-%m} files {before} -> {after}")


if __name__ == "__main__":
    main()
```

Note the filter is on `game_date`, the partition source column, so the
overwrite removes whole files. A filter on a non-partition column would
force partial rewrites (M4.6).

</details>

Run it on `raw.pbp_small`, then on M4.4's bucketed season in `raw.pbp`.

✅ **Checkpoint:** the file count drops. Row counts are identical before
and after (check!). Query time drops.

### 4. Find out where the old files went (30 min)

Count files in MinIO under the table's `data/` prefix (MinIO console, or
`mc ls --recursive`). Compare with `len(table.inspect.files())`.

<details>
<summary>Hint 3 · Why storage didn't shrink</summary>

The old small files are still referenced by **older snapshots**: time
travel to before the compaction must keep working. Storage only shrinks
after you expire those snapshots:

```python
table.maintenance.expire_snapshots().older_than(
    dt.datetime.now(dt.timezone.utc) - dt.timedelta(days=7)
).commit()
```

Use a **timezone-aware** datetime. Then count again: in PyIceberg 0.12
the snapshots disappear from metadata, but the unreferenced files are
**still in storage**. Deleting files that no snapshot references
("orphan files") is a separate maintenance job: Spark's
`remove_orphan_files` procedure, or a careful script that lists storage
and diffs it against `table.inspect.all_files()`. Never delete files a
live snapshot references.

</details>

Fill in the "After expiry" row. Then write your retention policy for
`raw.pbp` in one sentence: how many days of time travel, and why.
Remember M4.6 depends on it.

## Gotchas

- **Compaction is a commit.** It conflicts with concurrent writers to the
  same partition. Real systems compact older partitions that are no
  longer being written.
- **Compaction doesn't change what M4.4 decided.** If 16 buckets per
  month means ~16 files of 4k rows each even when compacted, the
  partition spec is too fine for the data volume. Compaction can't merge
  across partition boundaries.
- **Measure the same query before and after**, same harness, same
  threads. Write the conditions down; M4.8 reruns all of this.
