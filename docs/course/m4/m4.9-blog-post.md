# M4.9 · Blog post: Iceberg on basketball data

> **Ticket:** [#64](https://github.com/Dfscashline21/sideline/issues/64) ·
> **Mode:** hand · **Time:** 4 to 6 hours over two or three sittings ·
> **Needs:** M4.8 (numbers and charts)

## Why this matters

This is M4's portfolio artifact. A recruiter skims it; a hiring manager
reads the first two paragraphs; a senior engineer checks your method
section. One honest, specific post beats ten generic "what is Iceberg"
articles, because yours has **real data, measured numbers, and a
trade-off you found yourself** (finer partitions pruned better and made
small files).

Writing it by hand is the point: explaining it clearly is the same skill
as M4.11's closed-book check.

## What you'll produce

- A published post on your site or LinkedIn (article, not a feed post).
- The draft kept in `docs/blog/m4-iceberg/post.md`.
- A link from the README's "Numbers" or "Decisions" section (M0.6).

## Steps

### 1. Pick one story (20 min)

Don't write "everything I did in M4". Pick the thread with the most
surprising measured result, and let the other experiments support it.
Candidate angles:

- "Partitioning finer made my queries prune 15x more files and run no
  faster": the small-files trade-off, with compaction as the fix.
- "Correcting one rebound rewrote a month of data": copy-on-write vs
  merge-on-read, with time travel showing both versions.
- "25 seasons, 14 million plays, and a schema that changed three times":
  schema evolution and historical NULLs.

Write one sentence: *"After reading this, an engineer will know ___."*

### 2. Outline (30 min)

A structure that works for technical posts:

1. **Hook** (2 to 3 sentences): the surprising result, with a number.
2. **Setup**: the data (source, rows, seasons), the stack (Iceberg REST
   catalog, MinIO, PyIceberg, DuckDB), one diagram.
3. **The experiment(s)**: what you changed, what you measured, the chart.
4. **Why**: the mechanism, using the metadata tree. This is where you
   show depth.
5. **What I'd do in production**: the decision you'd make and its cost.
6. **Method and reproducibility**: hardware, versions, N runs, median,
   variation, and the link to your repo and `make bench-m4`.

### 3. Draft (2 to 3 hours)

Write it in `docs/blog/m4-iceberg/post.md`. Rules:

- **Every number traces to `results.csv`.** If it isn't in the CSV,
  either add it to the harness or remove it from the post.
- **Explain one mechanism properly** rather than five shallowly. Draw on
  your M4.1 tree.
- **Name the limits.** Laptop, one-month subsets, a local MinIO, tiny files
  compared with production. Saying so builds trust.
- **Plain words.** If a sentence needs "leverage", "robust" or
  "seamless", rewrite it.

### 4. Review (by a human, then an agent for typos only)

Ask a friend or colleague to read it and tell you the one thing they'd
remember. If it's not the thing from step 1, revise the hook and the
headings.

An agent may then check spelling and grammar. Prompt it to **list**
issues, not rewrite: the voice must stay yours.

### 5. Publish and link (30 min)

- Publish on your site or as a LinkedIn article. Use the charts from
  `docs/blog/m4-iceberg/`.
- Add the link to the README (M0.6's "Numbers" or "Decisions" section).
- Commit the final markdown with the published URL at the top.

```bash
git switch -c m4.9-blog
git add docs/blog/m4-iceberg/post.md README.md
git commit -m "M4.9: Iceberg on basketball data blog post"
gh pr create --fill        # Closes #64
```

## Gotchas

- **Don't publish secrets in screenshots**: no `.env` values, no MinIO
  console showing credentials.
- **Don't overclaim.** "Iceberg is 16x faster" is wrong; "compacting 222
  files into 1 made this query ~16x faster on my laptop" is right.
- **LinkedIn compresses images.** Export charts at 2x resolution with
  large fonts.
