# M4.8 · Benchmark harness and charts

> **Ticket:** [#63](https://github.com/Dfscashline21/sideline/issues/63) ·
> **Mode:** agent: the agent drafts, you review it like a junior's PR ·
> **Time:** 3 hours · **Needs:** M4.3 to M4.7 (all their timings in `docs/notes/m4.md`)

## Why this matters

Right now your M4 numbers were measured by hand, on different days, in
slightly different ways. A blog post built on them invites the first
question any sceptical reader asks: *"How do I reproduce this?"* One
command that rebuilds every number and chart is the answer, and the
habit (benchmarks as code, not screenshots) is what separates an
engineering write-up from an anecdote.

## What you'll produce

- `ingestion/benchmarks/m4/run.py` (plus any helpers), runnable as
  `make bench-m4`.
- `ingestion/benchmarks/m4/results.csv`: every measurement, one row each,
  with its conditions.
- Charts in `docs/blog/m4-iceberg/`, ready for M4.9.

## Steps

### 1. List what must be reproduced (30 min, by hand)

From your notes, list every number the blog will cite. For each one,
write: the query, the table state it needs, and the metric (median ms,
files planned, file count, bytes). Typically:

| Experiment | States compared | Metrics |
|---|---|---|
| Baseline (M4.3) | `raw.pbp`, month partitions | player query: median ms, files planned |
| Partition evolution (M4.4) | old spec season vs new spec season | team query and player query: ms, files planned, files per season |
| Schema evolution (M4.5) | before vs after adding columns | read time of the old snapshot vs current (optional) |
| Time travel (M4.6) | snapshot before vs after correction | read time by snapshot vs by timestamp (optional) |
| Compaction (M4.7) | per-game commits vs compacted vs expired | files, snapshots, bytes, ms |

This list is the spec. The agent doesn't decide what to measure; you do.

### 2. Decide the rules for a fair benchmark (20 min, by hand)

Write these into your spec:

- **Never mutate `raw.pbp`.** The harness builds its own tables in a
  `bench` namespace (for example `bench.pbp_month`, `bench.pbp_small`)
  from `raw.pbp`, and drops them at the end. Or it pins reads to fixed
  snapshot IDs.
- **Warm-up run discarded, then N runs, report the median** (and min/max,
  so readers see the spread).
- **Record conditions on every row**: date, machine, DuckDB/PyIceberg
  versions, threads, row count of the table measured.
- **Same query text** for before and after, stored in one place.
- **Idempotent**: running it twice gives the same table states and
  similar numbers.

### 3. Prompt the agent

> Write a benchmark harness for this repo at `ingestion/benchmarks/m4/`,
> runnable via a new Make target `bench-m4`. It reproduces the
> experiments in this spec: *(paste your table from step 1 and rules
> from step 2)*. Use PyIceberg via
> `sideline_ingestion.lakehouse.catalog.get_catalog()` for writes and
> DuckDB (attached to the same REST catalog) for timed reads. Reuse
> functions from `sideline_ingestion.lakehouse` (`load_pbp`,
> `evolve_partitions`, `compact`) instead of reimplementing them. Write
> all measurements to `results.csv`, then render charts with matplotlib to
> `docs/blog/m4-iceberg/*.png`. Every function typed for mypy. Read
> `AGENTS.md` first.

Add matplotlib as a dev dependency (`uv add --dev matplotlib`). It's
a reporting tool, not part of the pipeline.

### 4. Review it like a pull request

| Review question | What a good answer looks like |
|---|---|
| Can it damage `raw.pbp`? | Writes only to `bench.*`; any reads of `raw.pbp` are reads |
| Where does timing start and stop? | Around the query execution and `.fetchall()` only, not table setup or chart rendering |
| Is the warm-up excluded? | Yes, and N is a named constant |
| Are before/after measured with identical query text? | One query string per experiment, parameterised by table or snapshot |
| Does it reuse your lakehouse functions? | Imports them; doesn't copy-paste a second version of the loader |
| What happens on a second run? | `bench.*` tables recreated from scratch; no "table already exists" crash |
| Do the charts say what they measure? | Axis labels with units, title, and conditions (machine, N runs, median) in a caption or footnote |
| Does a chart lie? | Bar charts start at zero; log scale only if labelled; file counts and times not mixed on one axis |

<details>
<summary>Hint · Things agents commonly get wrong in benchmarks</summary>

- Timing the first run (cold cache) and calling it the result.
- Using `time.time()` instead of `time.perf_counter()`.
- Measuring with different `threads` settings across experiments.
- Silently reusing a table from a previous run that's in a different
  state (compacted already, so "before" equals "after").
- Generating charts with default matplotlib styling that truncates the
  y-axis, making a 5% difference look like 5x.

</details>

### 5. Run it twice and compare (30 min)

```bash
make bench-m4
cp ingestion/benchmarks/m4/results.csv /tmp/run1.csv
make bench-m4
```

Compare the two runs. Do files planned and file counts match exactly?
Do timings agree within your spread? If not, find out why before going
further, and write the run-to-run variation into the blog's method section.

✅ **Checkpoint:** two runs, identical counts, timings within their
min/max spread, charts regenerated identically apart from the numbers.

### 6. Ship it

```bash
make lint && make typecheck && make test
git add ingestion/benchmarks/ docs/blog/m4-iceberg/ Makefile pyproject.toml uv.lock
git commit -m "M4.8: reproducible M4 benchmark harness and charts"
gh pr create --fill        # Closes #63
```

Commit `results.csv` and the charts (they're small and the blog links
them). Never commit table data. Paste your review answers in the PR.

## Gotchas

- **Long runtime is a smell.** If the full harness takes over 15
  minutes, benchmark a subset (one or two seasons in `bench.*`) and say
  so. Readers care about the ratio, not the absolute size.
- **Laptop noise.** Plugged in, browser closed, same power mode. The M1.7
  rules apply.
- **Downloaded data isn't part of the benchmark.** Build `bench.*` from
  `raw.pbp`, not from the internet, so network speed never leaks into
  the numbers.
