# M4.10 · ADR-003: Iceberg over Delta Lake

> **Ticket:** [#65](https://github.com/Dfscashline21/sideline/issues/65) ·
> **Mode:** hand · **Time:** 90 min ·
> **Needs:** M4.2 (your catalog choice); best after M4.4 to M4.7

## Why this matters

"Why Iceberg and not Delta?" (or the reverse) is asked in nearly every
lakehouse interview. A weak answer recites feature lists. A strong
answer names **your constraints**, the options you weighed against them,
and what you gave up. An ADR (architecture decision record) is that
answer written down once, so it's consistent every time you're asked.

The ticket also asks for the **catalog choice**: you made it in M4.2;
now you justify it properly.

## What you'll produce

`docs/adr/003-iceberg-over-delta.md`, one to two pages.

## Steps

### 1. Check the ADR format (10 min)

Read ADR-001 (M2.8) if it exists, and `docs/adr/README.md`. Use the same
template so ADRs read as a set. If you have no template yet, use:

```markdown
# ADR-003: Iceberg over Delta Lake as the table format

- Status: Accepted
- Date: YYYY-MM-DD
- Deciders: <you>

## Context
## Decision
## Options considered
## Consequences
## Revisit when
```

### 2. Write the context first (20 min)

Context is **your** situation, not the industry's. Facts that shape this
decision in Sideline:

- several engines must read and write the same tables: PyIceberg and
  DuckDB now, Spark in M7, a cloud warehouse (Snowflake or BigQuery) in M10
- object storage is MinIO locally, S3 in the cloud
- no Databricks in the stack
- partitioning must change as leagues join (M4.4 showed you why)
- stat corrections need history (M4.6)

### 3. Research the options against those constraints (30 min)

For each criterion, find what each format offers **as of today**. Cite
docs, not blog posts. Both formats move fast, and claims from two years
ago are often stale.

| Criterion | Iceberg | Delta Lake | Matters here because |
|---|---|---|---|
| Engine support in *your* stack (PyIceberg, DuckDB, Spark, your warehouse) | | | M7, M10 |
| Partition evolution without rewrite | | | M4.4 |
| Hidden partitioning | | | M4.3 |
| Schema evolution by column ID | | | M4.5 |
| Catalog story (REST spec, open implementations) | | | M4.2 |
| Time travel and snapshot expiry | | | M4.6, M4.7 |
| Row-level deletes (copy-on-write / merge-on-read) | | | M4.6 |

Add **Apache Hudi** as a third option for completeness, even if you
dismiss it in a line. Interviewers like seeing you considered it.

<details>
<summary>Hint · Being fair to Delta</summary>

A one-sided ADR is a red flag. Write down where Delta is genuinely
stronger or simpler (for example, if you were on Databricks, or
single-engine Spark), and say why that doesn't apply to Sideline. Also
mention that the formats are converging (interoperability projects let
one table be read as the other), and what that means for how risky this
decision is.

</details>

### 4. Write the catalog section (20 min)

Same shape, smaller: the catalog options you saw in M4.2 (Iceberg REST
fixture, Lakekeeper, Polaris; plus Glue or a JDBC catalog, which you
didn't try), what you chose, why, and what changes in M10 (a managed or
cloud catalog?). Include one consequence you discovered by actually
running it, such as the endpoint split between containers and host.

### 5. Consequences and "revisit when" (10 min)

Consequences include the **costs**: compaction and snapshot expiry are
now your job (M4.7), PyIceberg lacks some maintenance procedures, and
so on. "Revisit when" names a concrete trigger, for example "if the
warehouse chosen in M10 can't read Iceberg natively".

### 6. Ship it

```bash

git add docs/adr/003-iceberg-over-delta.md
git commit -m "M4.10: ADR-003 Iceberg over Delta Lake, including catalog choice"
gh pr create --fill        # Closes #65
```

## Gotchas

- **Evidence from your own work beats citations.** "Partition evolution
  in M4.4 left 2002 to 2025 untouched" is stronger than a docs link. Use both.
- **Date-stamp claims** about tool support. They'll be out of date by the
  time someone reads the ADR, and the date tells them how much to trust it.
