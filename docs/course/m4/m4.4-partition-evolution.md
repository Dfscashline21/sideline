# M4.4 · Partition evolution: league, then bucket(team_id)

> **Ticket:** [#59](https://github.com/Dfscashline21/sideline/issues/59) ·
> **Mode:** hand · **Time:** 2 to 3 hours ·
> **Needs:** M4.3 (`raw.pbp` loaded, baseline recorded)

## Why this matters

In a Hive-style table, changing the partitioning means rewriting every
file and every query. At petabyte scale that's a project, not a
change. Iceberg makes partitioning **versioned metadata**: you add a new
spec, new writes use it, old files keep the spec they were written with,
and the planner handles both. Interviewers ask about this because it's
the feature that makes a table design reversible.

You'll also see the trade-off nobody mentions in the marketing: a finer
partition spec prunes better and writes **more, smaller files**.

## What you'll produce

- `ingestion/sideline_ingestion/lakehouse/evolve_partitions.py`: evolves
  `raw.pbp` from `month(game_date)` to `month(game_date), league`, then to
  `month(game_date), league, bucket(16, team_id)`, without rewriting old data.
- Proof that old and new specs coexist (files per spec ID).
- Before/after timings in `docs/notes/m4.md`.

### 2. Design the new spec on paper (20 min)

Answer in your notes before writing code:

- **Why `league` as identity?** How many distinct values will it ever
  have? What do queries filter on?
- **Why `bucket(team_id)` and not identity?** What happens to file
  counts with identity on 30 NBA teams + 12 WNBA teams + ~360 college teams
  per month?
- **How many buckets?** With N buckets, roughly how many files does one
  month of one league produce? Pick N and say why. Examples here use 16.
- **What about events with no `team_id`** (period ends, some timeouts)?

<details>
<summary>Hint 1 · Thinking about bucket counts</summary>

`bucket(N, team_id)` hashes each team into one of N buckets. One month
of NBA play-by-play is roughly 55 to 70k rows. With 16 buckets, that's
16 files of ~4k rows each, **per month**, plus one for NULL team IDs.
That's tiny for Parquet, where files of 100+ MB are normal. Keep this in
mind for step 5 and for M4.7.

</details>

<details>
<summary>Solution (open only after you have your own)</summary>

```python
"""Evolve raw.pbp's partition spec: add league, then bucket(16, team_id)."""

from pyiceberg.table import Table
from pyiceberg.transforms import BucketTransform

from sideline_ingestion.lakehouse.catalog import get_catalog
from sideline_ingestion.lakehouse.load_pbp import TABLE, load_season

BUCKETS = 16
LATEST_SEASON = 2026


def partition_names(table: Table) -> set[str]:
    return {field.name for field in table.spec().fields}


def evolve(table: Table) -> None:
    # Two commits on purpose: each creates a new spec version.
    if "league" not in partition_names(table):
        with table.update_spec() as update:
            update.add_identity("league")
    if "team_id_bucket" not in partition_names(table):
        with table.update_spec() as update:
            update.add_field("team_id", BucketTransform(BUCKETS), "team_id_bucket")


def main() -> None:
    table = get_catalog().load_table(TABLE)
    evolve(table)
    # Only the latest season is rewritten, under the new spec.
    # Every older file keeps the spec it was written with.
    rows = load_season(table, LATEST_SEASON)
    print(f"specs={sorted(table.specs())} rewrote season={LATEST_SEASON} rows={rows}")
    files = table.inspect.files()
    print(files.group_by("spec_id").aggregate([([], "count_all")]).to_pylist())


if __name__ == "__main__":
    main()
```

</details>

<details>
<summary>Hint 3 · What a test run showed (your numbers will differ)</summary>

On three seasons with a local catalog: under the old spec, the team
query planned 8 of a season's 9 files. Under the new spec, it planned 7
of **118** files. Pruning got much sharper, but the season went from 9
files to 118, and wall-clock time barely moved because each file is so
small that opening it costs more than reading it. The player query
gains nothing from team buckets (a player's events are spread across
his team's bucket *and* the opponents', because `team_id` is the acting
team), and pays the cost of more files.

That's the honest result to write up. It sets up M4.7.

## Gotchas

- **`DROP` isn't free either.** `remove_field` on a partition field
  doesn't rewrite data either; old files keep it. Evolution only moves
  forwards in metadata.
- **Bucket hashing is fixed by the spec.** Iceberg defines the hash
  (Murmur3), so every engine puts team 7 in the same bucket. DuckDB
  exposes it as `iceberg_bucket(16, 7)`; try it.
- **NULL team IDs** go in a NULL bucket. Check how many rows land there.
- **Measure under the same conditions as M4.3.** Same harness, threads
  and warm-up, or your before/after comparison is noise.
