# M4.2 · Add an Iceberg REST catalog to Compose

> **Ticket:** [#57](https://github.com/Dfscashline21/sideline/issues/57) ·
> **Mode:** agent: the agent drafts, you review it like a junior's PR ·
> **Time:** 2 to 3 hours · **Needs:** M0.3 (Compose stack), M4.1 session 2

## Why this matters

The catalog is the one piece of a lakehouse that must be strongly
consistent: it holds the pointer to each table's current metadata file
and swaps it atomically on every commit. Every engine you add later
(PyIceberg now, Spark in M7, a warehouse in M10) talks to the same
catalog, so this choice outlives the module. ADR-003 (M4.10) asks you
to justify it.

As an agent ticket, the skill is the same as M1.2: **specify clearly,
review hard, explain every line.** Compose wiring for a catalog is full
of subtle networking and credential details. That's exactly where an
agent's plausible-looking YAML goes wrong.

## What you'll produce

- A catalog service (plus any init job it needs) in `compose.yaml`,
  storing table data in MinIO bucket `sideline-lake`.
- `ingestion/sideline_ingestion/lakehouse/catalog.py`: a typed helper that
  returns the catalog (`load_catalog("sideline")`).
- An end-to-end smoke test: create a table, write rows, read them back.

## Steps

### 1. Choose the catalog (you decide, the agent doesn't)

| Option | Image | Backed by | Good | Watch out |
|---|---|---|---|---|
| **Iceberg REST fixture** | `apache/iceberg-rest-fixture:1.10.1` | In-memory SQLite by default | One container, minimal config | It's the Iceberg project's **test fixture**: by default the catalog is lost on restart unless you point it at a real database |
| **Lakekeeper** | `quay.io/lakekeeper/catalog:v0.15.1` | Postgres (you already run it) | Production-grade, small (Rust), warehouses and auth built in | One-time bootstrap and warehouse creation via its management API |
| **Apache Polaris** | `apache/polaris:1.9.0` | In-memory or a database | Apache project, the most "enterprise" option, Snowflake-originated | JVM service, heavier config, realm and principal setup |

Write two or three sentences on your choice in the PR description. You'll
expand them in ADR-003. The examples in later labs assume the catalog
answers at `http://localhost:8181`, is named `sideline` in PyIceberg, and
stores data under `s3://sideline-lake/`. Adjust if yours differs.

Check that the tag you pick still exists before you prompt:

```bash
curl -s "https://hub.docker.com/v2/repositories/apache/iceberg-rest-fixture/tags?page_size=5" | python3 -m json.tool | grep '"name"'
```

### 2. Add dependencies

```bash
uv add 'pyiceberg[pyarrow,pyiceberg-core]'
```

`pyiceberg-core` provides the Rust implementations of partition
transforms. Without it, writing to a `month()`- or `bucket()`-partitioned
table fails with `NotInstalledError`.

### 3. Write the spec, then prompt

Your spec should include at minimum:

- the catalog choice and pinned image tag
- data in a new bucket `sideline-lake`, created by the existing
  `minio-init` job (extend it, don't add a second init job)
- the catalog healthchecked, so `make up` (which uses `--wait`) only
  returns when it's ready
- any catalog bootstrap (warehouse creation) done by a one-shot init job,
  idempotent on re-run
- credentials from `.env`, with new variables added to `.env.example`
- PyIceberg configured via environment variables, not a file in your home
  directory, so it works the same on the host, in the dev container and
  in CI. PyIceberg reads `PYICEBERG_CATALOG__<NAME>__<PROPERTY>` variables,
  e.g. `PYICEBERG_CATALOG__SIDELINE__URI`.
- a typed `catalog.py` helper and a smoke test

Starting prompt:

> Add an Iceberg REST catalog to this repo's `compose.yaml` using
> *(your choice and tag)*. Table data goes to MinIO (service `minio`,
> already running) in a bucket `sideline-lake`; extend the existing
> `minio-init` service to create it. Requirements: *(paste your spec)*.
> Read `AGENTS.md` first. Explain every environment variable you set and
> which process (catalog, host Python, dev container) reads it. Don't
> change unrelated services.

### 4. Review it like a pull request

Answer each question in writing before running anything:

| Review question | What a good answer looks like |
|---|---|
| Which S3 endpoint does the **catalog** use, and which does **your host Python** use? | Inside Compose it's `http://minio:9000`; from the host it's `http://localhost:9000`. If a single URL is used everywhere, one side will fail |
| Who writes the Parquet files: the catalog or the client? | The **client** (PyIceberg) writes data files; the catalog only commits metadata. So the client needs S3 credentials too, either its own or credentials the catalog vends |
| Path-style S3 access? | MinIO needs path-style (`s3.path-style-access` / `URL_STYLE 'path'`), not virtual-host style |
| What survives `make down` then `make up`? | Catalog state must survive. If it's in-memory, every table "disappears" on restart while its files stay in MinIO |
| Is the init job idempotent? | Re-running `make up` doesn't fail because the warehouse or bucket already exists |
| Secrets? | Only in `.env`; `.env.example` has placeholders; nothing hard-coded in `compose.yaml` |
| Are ports bound sensibly? | Consider `127.0.0.1:8181:8181` (M0 study guide, known limitation 2) |
| Does `catalog.py` pass mypy? | Typed return value (`Catalog`), no `Any` leaking |

Ask the agent to explain anything you can't. Then explain it back.

<details>
<summary>Hint · Things agents commonly get wrong here</summary>

- Using `localhost` for the catalog's own S3 endpoint. Inside a container,
  `localhost` is the container itself.
- Forgetting the region. Many S3 clients insist on one even for MinIO;
  `us-east-1` is the usual dummy value.
- Healthchecks using `curl` in an image that doesn't ship `curl`.
- Pinning `latest`.
- Configuring PyIceberg via `~/.pyiceberg.yaml`, which CI and the dev
  container won't have.

</details>

### 5. Smoke test end to end

Write (or have the agent write, then review) a pytest integration test
marked so it only runs when the stack is up. For example, skip if the
catalog URL doesn't answer. It should:

1. create namespace `smoke` if missing
2. create a small table with a known schema
3. append three rows
4. read them back and assert the values
5. drop the table

Then prove a second engine can see the same table. DuckDB 1.5 can
attach a REST catalog:

```sql
install iceberg; load iceberg;
create secret minio (type s3, key_id '<user>', secret '<password>',
                     endpoint 'localhost:9000', url_style 'path', use_ssl false, region 'us-east-1');
attach '<warehouse name>' as lake (type iceberg, endpoint 'http://localhost:8181/<catalog path>',
                                   authorization_type 'none');
show all tables;
```

The exact `endpoint` path and warehouse name depend on your catalog.
Lakekeeper serves its REST API under `/catalog`. Check your catalog's docs
and the [DuckDB catalog docs](https://duckdb.org/docs/stable/core_extensions/iceberg/catalogs).

✅ **Checkpoint:** a table written by PyIceberg is listed and readable in
DuckDB, and both survive `make down && make up`.

### 6. Ship it

```bash
make lint && make typecheck && make test
git add compose.yaml .env.example pyproject.toml uv.lock ingestion/
git commit -m "M4.2: Iceberg REST catalog backed by MinIO"
gh pr create --fill        # Closes #57
```

Put your review answers from step 4 in the PR description.

## Gotchas

- **Restart test.** Do `make down && make up` and read the table again.
  This catches the in-memory-catalog trap immediately.
- **Two buckets, two jobs.** `sideline-raw` is raw JSON (M2);
  `sideline-lake` is Iceberg. Keep them separate so lifecycle rules in M10
  can differ.
- **DuckDB write support.** DuckDB 1.4+ can also write to REST catalogs.
  These labs use PyIceberg for writes and DuckDB for reads, so if writes
  from one tool fail, you can tell which side is misconfigured.
