## Why this matters

The NBA corrects stats after games: a rebound credited to the wrong
player, an assist added on review. At work, the equivalent is a late
adjustment to an invoice, a refund or a restated metric. Two questions
always follow: **"what did the report say on Monday?"** and **"what
changed, and when?"**

In a mutable table, Monday's answer is gone. In Iceberg, every commit is
a snapshot you can still read, so you can show both versions side by side.
That's useful for audits, debugging ("the dashboard was right yesterday")
and reproducible ML training sets (M12).

## What you'll produce

- `ingestion/sideline_ingestion/lakehouse/correct_play.py`: credits one
  rebound to a different player as a single, labelled commit.
- The play read **before** and **after** the correction, by snapshot ID
  **and** by timestamp, in Python and DuckDB.
- A short write-up in `docs/notes/m4.md`.

<summary>Solution (open only after you have your own)</summary>

```python
"""Credit one rebound to a different player as a single labelled commit."""

import argparse

import pyarrow as pa
import pyarrow.compute as pc

from sideline_ingestion.lakehouse.catalog import get_catalog
from sideline_ingestion.lakehouse.load_pbp import TABLE


def correct(play_id: int, new_athlete_id: int, reason: str) -> None:
    table = get_catalog().load_table(TABLE)
    play_filter = f"play_id = {play_id}"
    current = table.scan(row_filter=play_filter).to_arrow()
    if current.num_rows != 1:
        raise ValueError(f"expected exactly one row for play {play_id}, found {current.num_rows}")
    column = current.schema.get_field_index("athlete_id_1")
    fixed = current.set_column(column, "athlete_id_1", pa.array([new_athlete_id], type=pa.int32()))
    old_athlete = pc.min(current["athlete_id_1"]).as_py()
    table.overwrite(
        fixed,
        overwrite_filter=play_filter,
        snapshot_properties={
            "sideline.change": "stat-correction",
            "sideline.play_id": str(play_id),
            "sideline.athlete_from": str(old_athlete),
            "sideline.athlete_to": str(new_athlete_id),
            "sideline.reason": reason,
        },
    )
    print(f"play {play_id}: athlete {old_athlete} -> {new_athlete_id}")


def main() -> None:
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("--play-id", type=int, required=True)
    parser.add_argument("--athlete-id", type=int, required=True)
    parser.add_argument("--reason", required=True)
    args = parser.parse_args()
    correct(args.play_id, args.athlete_id, args.reason)


if __name__ == "__main__":
    main()
```

The `num_rows != 1` guard matters: a filter that matched zero rows would
"correct" nothing and still commit, and one that matched many would
rewrite them all to the same player.

</details>

<details>
<summary>Hint 3 · Why so much for one row?</summary>

PyIceberg's `overwrite` is **copy-on-write**: the whole data file that
held the play (a month of games) is rewritten without it, and the
corrected row lands in a new one-row file. Reads stay simple and fast;
writes are expensive.

The alternative is **merge-on-read**: write a small *delete file* saying
"row N of file F is gone" and append the new row. Writes are cheap; reads
must merge deletes until compaction. DuckDB 1.5's `UPDATE` on an attached
Iceberg catalog works this way. Try it on a scratch copy of the table as
a stretch, and compare the files each approach produces.

</details>

## Gotchas

- **One `overwrite` makes two snapshots** in PyIceberg: first one that
  removes rows (operation `delete` if whole files went, `overwrite` if a
  file was rewritten), then an `append`. The snapshot "just before the append" already has the row
  deleted. That's why you record the snapshot ID **before** committing.
- **Time travel only reaches snapshots you keep.** Expiring snapshots
  (M4.7) deletes your ability to read Monday. Retention is a policy
  decision: write down what yours should be.
- **Timestamps are UTC milliseconds** in metadata. Convert carefully when
  someone says "Monday 9am".
