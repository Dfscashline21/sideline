## Why this matters

"How does a lakehouse query skip files?" is the Iceberg interview
question, and the module's closed-book check. The answer has two
layers, and most candidates only know one:

1. **Iceberg metadata** prunes whole files before anything is opened, using
   partition values and per-file column stats stored in manifests.
2. **Parquet footers** prune row groups *inside* each file that survives,
   using per-row-group min/max stats.

Learn both on real files, where you can see the numbers, and the drawing
in M4.11 becomes a description of things you've actually looked at.

## Session 1 · Parquet from the inside (60 min)

**Read:** [Parquet file format concepts](https://parquet.apache.org/docs/concepts/)
and [file format](https://parquet.apache.org/docs/file-format/). Focus on
row groups, column chunks, pages, and the footer.

The mental model:

```
file.parquet
├── row group 0   (~100k+ rows)
│   ├── column chunk: game_date   ── pages ── (encoded, compressed)
│   ├── column chunk: type_text   ── pages
│   └── ...
├── row group 1
│   └── ...
└── footer: schema + per row group, per column: min, max, null count, sizes, encodings
```

A reader opens the **footer first**, decides which row groups and
columns it needs, and only then reads bytes. That's why Parquet is fast
for "a few columns, some rows" and slow for "one row, all columns".

### Exercise 1.1: look at a real footer

DuckDB reads only the footer of a remote file, so this is quick:

```sql
select row_group_id, row_group_num_rows, path_in_schema, type,
       stats_min, stats_max, encodings, compression,
       total_compressed_size, total_uncompressed_size
from parquet_metadata('https://github.com/sportsdataverse/sportsdataverse-data/releases/download/espn_nba_pbp/play_by_play_2024.parquet')
where path_in_schema in ('game_date', 'type_text', 'game_id')
order by row_group_id, path_in_schema;
```

Before running it, predict: how many row groups does a 614k-row file
have? Will each row group's `game_date` min/max overlap the others?

<details>
<summary>What to notice</summary>

- About five row groups of roughly 120k rows each.
- `type_text` compresses about 2:1 (`total_compressed_size` vs
  uncompressed), helped by **dictionary encoding**: there are only ~140
  distinct event types, so each value is stored once in a dictionary
  and the column holds small integer references. Look for
  `RLE_DICTIONARY` in `encodings`.
- Whether `game_date` ranges overlap depends on how the writer sorted
  the rows. If they overlap heavily, a filter on `game_date` can't skip
  any row group. **Sort order decides how useful min/max stats are.**

</details>

### Exercise 1.2: stats in action

## Session 2 · Why a table format at all? (45 min)

**Read:** [Iceberg spec overview](https://iceberg.apache.org/spec/#overview)
(stop at "Specification") and the first half of
[Iceberg's "Hidden partitioning"](https://iceberg.apache.org/docs/latest/partitioning/).

A folder of Parquet files isn't a table. Write down, in one line each,
what goes wrong with "just a folder" when:

1. Two writers add files at the same time.
2. A reader lists the folder while a writer is halfway through.
3. You rename a column.
4. You want yesterday's version of the data.
5. A query filters on `game_date`, but the folders are named `year=2024/month=01`.

Iceberg fixes each of these with one idea: **the table is whatever the
current metadata file says it is**, and you change the table by writing
a new metadata file and atomically swapping a pointer in the catalog.

## Session 3 · The metadata tree, on real files (90 min)

**Read:** the [spec's "Overview" diagram](https://iceberg.apache.org/spec/#overview)
and the sections on snapshots, manifest lists and manifests.

```
catalog  ──►  current metadata file (v3.metadata.json)
                ├── schemas (with column IDs), partition specs, sort orders
                ├── snapshots: [s1, s2, s3]  ← current-snapshot-id = s3
                └── s3 ──► manifest list (snap-s3.avro)
                             ├── manifest A (lists data files + partition values + column stats)
                             │     ├── data file 00001.parquet
                             │     └── data file 00002.parquet
                             └── manifest B
                                   └── data file 00003.parquet
```

Write a short script yourself that:

1. Creates a `SqlCatalog` backed by SQLite with a local `file://`
   warehouse folder.
2. Creates a table partitioned by `month(game_date)` with three columns
   (`game_id`, `game_date`, `points`).
3. Appends a small Arrow table spanning two months, then appends again.

<details>
<summary>Hint · Skeleton</summary>

```python
from pyiceberg.catalog.sql import SqlCatalog
from pyiceberg.partitioning import PartitionField, PartitionSpec
from pyiceberg.schema import Schema
from pyiceberg.transforms import MonthTransform
from pyiceberg.types import DateType, IntegerType, NestedField

catalog = SqlCatalog(
    "study",
    uri="sqlite:////tmp/iceberg-study/catalog.db",
    warehouse="file:///tmp/iceberg-study/warehouse",
)
catalog.create_namespace_if_not_exists("demo")
schema = Schema(
    NestedField(1, "game_id", IntegerType()),
    NestedField(2, "game_date", DateType()),
    NestedField(3, "points", IntegerType()),
)
spec = PartitionSpec(
    PartitionField(source_id=___, field_id=1000, transform=MonthTransform(), name="game_date_month")
)
table = catalog.create_table("demo.games", schema=schema, partition_spec=spec)
# table.append(pyarrow_table)  ×2
```

</details>

Then go and **look**:

```bash
find /tmp/iceberg-study/warehouse -type f | sort
```

Decode the file names: `NNNNN-<uuid>.metadata.json` are metadata files
(one per commit), `snap-<snapshot id>-….avro` are manifest lists, and
`<uuid>-m0.avro` are manifests. Data files live under
`data/game_date_month=2024-01/`. That folder name is a convenience for
humans; readers never rely on it.

Open the newest `*.metadata.json` in an editor. Find: `current-snapshot-id`,
the `snapshots` list, each snapshot's `manifest-list`, the `schemas`
(note the field `id`s), and `partition-specs`. Then in DuckDB:

```sql

select manifest_path, status, content, file_path, record_count
from iceberg_metadata('/tmp/iceberg-study/warehouse/demo/games/metadata/<newest>.metadata.json');
```

### Exercise 3.2: trace file skipping

For `where game_date = date '2024-01-15'`, write the reader's steps:

1. Catalog → which metadata file?
2. Metadata → which snapshot → which manifest list?
3. Manifest list → it stores a **partition summary per manifest**
   (lower/upper partition values). Which manifests can it skip?
4. Manifest → per data file: partition value plus column lower/upper
   bounds. Which files can it skip?
5. Each surviving Parquet file → footer stats per row group.

<details>
<summary>Check your answer</summary>

Pruning happens at three levels: manifests (via partition summaries in
the manifest list), data files (via partition values and column bounds
in the manifest), and row groups (via Parquet footer stats). Only after
all three does any data get read. A filter on a column that isn't the
partition column can still skip files through **column bounds**, if
the data is sorted or clustered so that bounds are narrow.

</details>

## Session 4 · Hidden partitioning (45 min)

In Hive-style tables, you partition by a **column you must also filter
on**: add a `game_month` string column, and every query must say
`where game_month = '2024-01'`. Query by `game_date` and it scans everything.

Iceberg stores the **transform** (`month(game_date)`) in the partition
spec. Writers compute the partition value; readers apply the same
transform to your `game_date` predicate. Users never see or type the
partition column. It's *hidden*.
