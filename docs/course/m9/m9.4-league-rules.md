# M9.4 · League-aware rule checks

> **Ticket:** [#122](https://github.com/Dfscashline21/sideline/issues/122) ·
> **Mode:** hand · **Time:** 3 hours ·
> **Needs:** M9.1, staged play-by-play for all four leagues (M5, M6, M7)

## Why this matters

Generic checks ("not null", "unique") catch generic bugs. The bugs that
actually reach a dashboard are usually **domain** bugs: a men's college
game parsed as quarters, a clock that reads 12:00 in a 10-minute period,
a shot at 60 feet wide on a 50-foot court. Writing checks that know the
domain, and that **differ by league without four copies of the code**,
is what separates a data engineer from someone who installed a test
library.

## What you'll produce

- `quality/rules/league_rules.csv`: one row per league with its game
  structure. Rules as **data**, not code.
- Checks for three rules, each a query that returns violating rows
  (zero rows = pass):
  1. A finished game has at least its league's regulation periods.
  2. No event shows more time left than its period lasts.
  3. Every field-goal attempt with coordinates is on the court.
- A test per league that **plants a bad record** and proves the check
  fails on it (the acceptance criterion).

## Steps

### 1. Decide where checks live (15 min)

Two reasonable options. Pick one and note why in the PR:

- **dbt tests** (singular tests in `transform/tests/`, or a generic test
  with arguments). Fits naturally if staging is in dbt, runs in
  `dbt build`, results land in dbt's artifacts.
- **Plain SQL files** in `quality/checks/`, run by a small Python runner
  that writes to `ops.check_results` (see the
  [module overview](README.md#where-things-go)).

Either way, a check is "a query that returns bad rows". That's the
pattern for the whole module.

### 2. Encode the rules as data (20 min)

Measure the league structure in **your** staged data before writing it
down. For example, for each league: the maximum period number per game
(how often?), and the maximum clock value per period.

<summary>Hint · What the data says</summary>

On the 2024-25 ESPN play-by-play: NBA quarters start at 720 s, WNBA and
women's college at 600 s, men's college halves at 1,200 s, and overtime
periods at 300 s in all four leagues. Confirm this against your own
staging tables; don't copy it blindly.

</details>

Write `quality/rules/league_rules.csv`:

```csv
league,regulation_periods,period_seconds,ot_seconds
nba,4,720,300
...
```

If you use dbt, make it a seed (`dbt seed`) so checks can join to it.

✅ **Checkpoint:** four rows, every number confirmed by a query you can
show.

### 3. Rule 1: enough periods (30 min)

</details>

Run it on real data **before** planting anything. You'll get hits.
For each, decide: bad data, or a legitimate exception?

<details>
<summary>Hint 2 · What you'll probably find</summary>

On 2024-25 data: three NBA "games" with one period (the 2025 All-Star

</details>

### 4. Rule 2: clock within the period (30 min)

The period length depends on the league **and** on whether it's
regulation or overtime. That's a `CASE` against the joined rule row.

Watch for the clock column: if your staging didn't already normalise
`start_quarter_seconds_remaining` and `start_period_seconds_remaining`
(men's college) into one column, do it now, in staging, not in the check.

### 5. Rule 3: shots on the court (30 min)

A basketball court is 50 × 94 feet. Look at the coordinate columns
first:

```sql
select min(coordinate_x_raw), max(coordinate_x_raw),
       min(coordinate_y_raw), max(coordinate_y_raw)
from <your staged pbp>
where shooting_play and type_text not ilike '%free throw%';
```

Then decide on bounds and **document the tolerance**. Real data has a
few thousand NBA corner shots per season recorded at `y = -1` or `-2`
(just behind the baseline in this frame), and values down to `-5`. A strict `y >= 0` rule fails on
real, correct data and gets ignored, which is how alert fatigue starts.

<details>
<summary>Hint · Two real problems this rule finds</summary>

1. Sentinel values: a handful of college shots have
   `coordinate_x_raw = -214748340`. That's not a location; it's a
   placeholder that should have been NULL. Fix staging, keep the check.
2. Free throws: depending on the source they may carry a fixed
   coordinate or none at all. Exclude them; they aren't field-goal
   attempts.

</details>

<details>
<summary>Solution for rules 1 to 3 (open only after you have your own)</summary>

Assumes a staged view with one normalised clock column, `period_clock`
(seconds remaining at the event, within its period). Tested against the
2024-25 play-by-play of all four leagues.

```sql
-- Check:    league-aware structural rules on play-by-play
-- Pattern:  rules as data (league_rules) + checks that return violating rows
with league_rules(league, regulation_periods, period_seconds, ot_seconds) as (
    -- in the repo this is quality/rules/league_rules.csv (a dbt seed)
    values ('nba', 4, 720, 300), ('wnba', 4, 600, 300),
           ('ncaa_m', 2, 1200, 300), ('ncaa_w', 4, 600, 300)
),
pbp as (
    select league, game_id, period_number, period_clock,
           shooting_play, type_text, coordinate_x_raw, coordinate_y_raw
    from stg_pbp_all                      -- your staged, all-league view
),
periods as (   -- rule 1: a finished game has at least the regulation number of periods
    select p.league, p.game_id, 'too_few_periods' as rule, max(period_number)::varchar as observed
    from pbp p join league_rules r using (league)
    group by p.league, p.game_id, r.regulation_periods
    having max(period_number) < r.regulation_periods
),
clock as (     -- rule 2: no event has more time left than its period lasts
    select p.league, p.game_id, 'clock_exceeds_period', max(period_clock)::varchar
    from pbp p join league_rules r using (league)
    group by p.league, p.game_id, p.period_number, r.regulation_periods, r.period_seconds, r.ot_seconds
    having max(period_clock) > case when p.period_number <= r.regulation_periods
                                    then r.period_seconds else r.ot_seconds end
),
court as (     -- rule 3: field-goal attempts with coordinates are on the court
    select league, game_id, 'shot_off_court', coordinate_x_raw || ',' || coordinate_y_raw
    from pbp
    where shooting_play and type_text not ilike '%free throw%'
      and coordinate_x_raw is not null
      -- 50 x 94 ft court; y >= -5 tolerates corner shots logged just behind the baseline
      and not (coordinate_x_raw between 0 and 50 and coordinate_y_raw between -5 and 94)
)
select * from periods
union all select * from clock
union all select * from court;
```

On real 2024-25 data this returns 3 NBA rows (All-Star games), 1 + 10
men's college rows (truncated game, sentinel coordinates) and 1 + 4
women's college rows. That's the baseline to explain before you plant
anything.

Rule 1 only makes sense for **finished** games. In production, join to
your game status (from `dim_game` or the schedule) so a game in
progress isn't flagged at half-time.

</details>

### 6. Plant a bad record per league (45 min)

This is the acceptance criterion. Write a test (pytest, or a dbt unit
test) that, for **each** league:

1. builds a tiny table of known-good events (a few rows is enough),
2. inserts one bad record that breaks a rule *specific to that league*,
3. runs the check and asserts it returns exactly that record.

Good planted records are league-specific on purpose:

| League | Planted record | Rule it should trip |
|---|---|---|
| nba | Event in period 1 with 750 s left | clock (NBA quarters are 720 s) |
| wnba | Event in period 2 with 700 s left | clock (WNBA quarters are 600 s; 700 would pass in the NBA) |
| ncaa_m | Finished game whose last event is in period 1 | periods (needs 2 halves) |
| ncaa_w | Shot at `x = 62` | court |

Also plant one record that **should pass** but would fail a naive rule,
such as a men's college event in period 2 with 1,150 s left. That proves
the check is league-aware, not just strict.

✅ **Checkpoint:** four failing cases detected, the passing case passes,
and the test runs in CI.

### 7. Record results

Make the runner (or a dbt `on-run-end` hook) write one row per check per
run into `ops.check_results` with `league`, `check_name`, `status` and the
violation count as `observed`. M9.8 and M9.10 depend on this.

### 8. Ship it

PR with the CSV, checks, tests and a short section in the PR body

each. `Closes #122`.

## Gotchas

- **Exceptions in the check vs upstream.** Hard-coding "except game
  401752955" into a check rots fast. Prefer fixing scope upstream
  (exclude exhibitions in staging) or an exceptions seed with a reason
  and an expiry date.
- **In-progress games.** Rules about completeness need a "finished" flag.
- **Severity.** Not every rule should block the pipeline. A truncated
  college game might warn; a men's game parsed as quarters should fail.
  Store severity with each check.
