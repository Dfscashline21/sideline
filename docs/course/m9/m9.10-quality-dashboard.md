# M9.10 · Quality dashboard

> **Ticket:** [#128](https://github.com/Dfscashline21/sideline/issues/128) ·
> **Mode:** agent: the agent drafts, you review it like a junior's PR ·
> **Time:** 2 to 3 hours · **Needs:** `ops.check_results` (M9.4/M9.5),
> `ops.freshness_daily` and the first SLO panel (M9.6), one incident (M9.9)

## Why this matters

Checks that only live in logs are invisible to everyone but you. A
quality dashboard makes data health something a stakeholder can look at
before asking "is this number right?". It's also the epic's portfolio
artifact: a reviewer clicking from the README should see, in ten seconds,
that this project *measures* its own reliability.

The dashboard is boilerplate, so an agent drafts it. **What it shows**
and **whether it tells the truth** are your job.

## What you'll produce

- A dashboard with three sections: **check results**, **SLO
  attainment**, **open incidents**.
- A link to it from the README (the acceptance criterion), plus a
  screenshot in the README so it's visible even when the stack isn't running.

## Steps

### 1. Design it on paper first (30 min)

Before prompting, sketch the page and decide the questions each panel
answers. A design that works:

| Section | Question it answers | Panel |
|---|---|---|
| Check results | Is anything failing **right now**? | Latest status per check per league (red/amber/green), failing ones first |
| | Is a check flaky? | Pass/fail history per check over 30 days |
| SLO attainment | Are we meeting freshness? | Attainment per league over the window, error budget remaining (from M9.6) |
| | When did we miss? | Daily met/missed strip per league |
| Open incidents | What's being worked on? | Incidents in `docs/incidents/` whose status isn't `resolved`, with links |

Decide where it lives. The course default is Streamlit in
`serving/dashboard/`, alongside where M11's public dashboard will go.
Keep the quality page separate from the public one: it's an internal view.

✅ **Checkpoint:** a sketch (paper photo or ASCII) in the PR description.

### 2. Prompt the agent

> Read `AGENTS.md`. Build a quality dashboard page in
> `serving/dashboard/` with Streamlit, reading from Postgres (connection
> settings from `.env`): *(paste your panel table from step 1)*.
>
> Data sources: `ops.check_results` (columns: …), `ops.freshness_daily`
> and the attainment view from M9.6 (columns: …), and incident Markdown
> files in `docs/incidents/` whose `**Status:**` line isn't `resolved`.
>
> Keep queries in one module so they can be tested without Streamlit.
> Read-only database access. No new styling frameworks. Add a
> `make quality-dashboard` target. Pin dependencies.

Paste the **actual** column names from your tables in place of the
dots; agents invent columns otherwise.

### 3. Review it like a pull request

| Review question | What a good answer looks like |
|---|---|
| Does "latest status" really use the **latest** run per check and league? | A window or `DISTINCT ON` by `checked_at`, not `MAX(status)` |
| Does attainment match your M9.6 numbers exactly? | Compare one league by hand |
| Are days with no games excluded the same way as in M9.6? | Uses the M9.6 view, doesn't recompute it differently |
| What does the page show with **zero** rows (fresh clone)? | A clear "no data yet" message, not a stack trace |
| Is the database user read-only? | Yes, or a documented reason why not |
| Are incident statuses parsed robustly? | Tolerates spacing; unknown status counts as open |
| Are the queries testable without Streamlit? | Plain functions with a unit test or two |

<details>
<summary>Hint · The bug to look for first</summary>

"Latest status per check" is the classic place for a wrong aggregate.
`max(status)` returns `'pass'` over `'fail'` alphabetically, so a check that
failed in the latest run but passed earlier shows green. This is exactly
the "top 1 per group" pattern from M1.6: rank by `checked_at` within
`(check_name, league)` and keep rank 1.

</details>

### 4. Verify it against reality

- Re-run one M9.8 failure in miniature (e.g. plant a bad record) and
  watch the check go red on the dashboard, then green after the fix.
- Compare SLO attainment on the page with your own query.
- Change an incident's status to `resolved` and confirm it disappears.

✅ **Checkpoint:** every number on the page traced to a query you ran
yourself.

### 5. Link it from the README

The README's architecture or numbers section (M0.6) gets:

- a link to the dashboard (local URL, and the hosted one once M11 is
  live),
- a screenshot committed under `docs/img/`, since the local URL only
  works when the stack is up,
- one sentence on what it shows.

## Gotchas

- **Dashboards that lie by omission.** If a check *didn't run*, there's
  no fail row, so it looks fine. Show "last run" time per check and flag
  anything stale. A missing heartbeat is a failure.
- **Too many panels.** If everything is red or amber, nothing is. Show
  failing items first and keep history behind a click.
- **Screenshots go stale.** Retake the README screenshot when the
  layout changes; note the date under it.
