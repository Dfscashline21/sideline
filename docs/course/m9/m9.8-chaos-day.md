# M9.8 · Chaos day

> **Ticket:** [#126](https://github.com/Dfscashline21/sideline/issues/126) ·
> **Mode:** hand · **Time:** half a day ·
> **Needs:** M9.2 to M9.6 (checks and SLO in place), M6.6 alerting

## Why this matters

Every check you've written has passed on data you chose. Chaos day asks
the only question that matters: **when the real failure happens, does
anything notice?** You break three realistic things on purpose and
record, minute by minute, what caught each one. Where nothing does, you
add the missing check. Teams that run these exercises find their gaps
on a quiet weekday instead of during the playoffs.

It's also where your M9.9 postmortem and your best interview story come from.

## What you'll produce

- `docs/notes/m9-chaos-day.md`: for each failure, your prediction, what
  actually happened, a timeline, and what caught it.
- Any new or fixed checks, so that **each failure is caught by a check
  or alert** (the acceptance criterion).

## The three failures

| # | Failure | Real-world version |
|---|---|---|
| 1 | **Renamed API field** | `nba_api` returns `POINTS` instead of `PTS` after an upstream change |
| 2 | **Double-loaded day** | A retry or manual re-run lands the same day twice |
| 3 | **Week-late stat correction** | The league changes a stat for a game seven days ago (a rebound reassigned, a scoring change) |

## Steps

### 1. Make it safe (30 min)

You'll damage data on purpose, so first make the damage undoable.

- Stop the stack (`make down`) and back up the data volumes. Compose
  names them `sideline_minio-data` and `sideline_postgres-data`
  (project name + volume name):

  ```bash
  mkdir -p .data/backup
  for v in minio-data postgres-data; do
    docker run --rm -v sideline_$v:/data -v "$PWD/.data/backup":/backup alpine \
      tar czf /backup/$v.tgz -C /data .
  done
  ```

- Pick the **date range** you'll break (one game day, one league) and
  write it down. Everything outside it must stay untouched.
- Write how you'll restore (the reverse `tar xzf`, then a rebuild of the
  affected days). Test the restore on Postgres **before** starting.

✅ **Checkpoint:** you've restored a backup once and the pipeline still
runs. Without this, stop: chaos day without a way back is just an outage.

### 2. Predict before you break (30 min)

For each failure, write down **before** doing anything:

- Which check or alert do you expect to catch it?
- Where in the pipeline (ingestion, staging, marts, SLO)?
- How long after the break until someone is notified?
- What would a consumer see in the meantime?

<details>
<summary>Hint · Prompts for your predictions</summary>

1. Renamed field: does your extractor's Pydantic validation (M2.5) fail
   the run? Does the M9.2 **contract** catch it? (Careful: the CI job
   only runs when *you* change code. Nothing in CI sees tomorrow's API
   response.)
2. Double load: is the raw zone idempotent (M2.7)? If not, which
   downstream check notices: a uniqueness test on `(game_id, team_id)`,
   M9.5's volume check, or neither?
3. Late correction: your incremental `fact_play` has a 3-day lookback
   (M5.6). A change to a game 7 days old falls outside it. What notices
   that gold no longer matches the source?

</details>

### 3. Failure 1: renamed field (45 min)

Simulate the upstream change **at the boundary**, not by editing your
extractor's logic: for example, a test double for the API client that
renames `PTS` to `POINTS` in the response, enabled by an environment
variable for one run. Then run the daily pipeline for your chosen day.

Record the timeline (clock times): break → first symptom → first alert
→ diagnosis → fix → recovery.

If nothing failed loudly, the gap is that the contract is only checked
in CI. Close it: run the source contract against **each day's landed
data** (a Dagster asset check that runs `datacontract test` on that
day's raw files, or the equivalent validation in your ingestion step),
and make a failure alert.

### 4. Failure 2: double-loaded day (45 min)

Land the same day twice in the way that's realistic for **your**
pipeline: two raw objects with different run IDs, or a staging model
that unions both. Run the downstream build.

Expected catchers: a uniqueness test on the grain, and M9.5's volume
check (a double load is about 2 × the median event count, far beyond any
real game). If both fire, good: note which fired first and which gave
the clearer message.

Then ask the follow-up: **why was a double load possible at all?**
Ingestion idempotency (M2.7) should make it impossible. If it wasn't,
fix that too, and record both fixes.

### 5. Failure 3: week-late stat correction (60 min)

This is the one most pipelines miss. Change one stat in the **source**
for a game 7 days back (in your stubbed or landed source data: move a
rebound from one player to a teammate, or add 1 point). Run the normal
daily pipeline, which only reprocesses recent days.

Now gold disagrees with the source, and no row is invalid. Uniqueness,
ranges, volume and freshness all pass.

<details>
<summary>Hint 1 · Nudge</summary>

You need a check that compares gold with a **fresh** read of the source
for a window longer than the incremental lookback.

</details>

<details>
<summary>Hint 2 · Approach</summary>

A **reconciliation check**: once a day, re-pull (or re-read) the box
scores for the last 14 days and compare per-game totals (points,
rebounds per team) with gold. Any difference means a correction landed
that the incremental model missed. The fix it triggers is a targeted
re-run of the affected games (`--start/--end` from M2.4, then a
`--full-refresh` or partition rebuild of the affected rows).

Also look at consistency checks that *might* catch it by luck: player
points summing to the team score fails only if the correction touched one
side.

</details>

Build the reconciliation check, run it, confirm it fires, then repair
gold with your backfill path and confirm it passes again.

### 6. Restore and verify

Restore the backups (or rebuild the broken days), run the full checks,
and confirm everything is green with the same row counts as before
chaos day. Record the counts.

### 7. Write it up

`docs/notes/m9-chaos-day.md`, one section per failure:

```markdown
## Failure 2: double-loaded day
- Prediction: volume check fires during the 06:00 run
- What happened: uniqueness test failed at 06:12, volume check at 06:13; no alert for 40 min because ...
- Timeline: 09:00 break · 09:05 run starts · 09:12 first failure · ...
- Caught by: ... · Gap found: ... · Fix: PR #...
```

End with a table: failure, predicted catcher, actual catcher, time to
detect. Where prediction and reality differ is the interesting part.

### 8. Ship it

Notes plus every new check in a PR. `Closes #126`. Pick the failure with
the most surprising timeline for M9.9.

## Gotchas

- **Breaking the wrong data.** Restrict every action to the chosen date
  range and league; double-check commands that delete or rewrite.
- **Alerts going nowhere.** A check that "fails" in a log nobody reads
  didn't catch anything. The acceptance criterion is *caught by a check
  or alert*: make sure a failure reaches you.
- **Stubbing too deep.** Simulate failures where they'd really happen
  (the API response, the raw zone), not by editing the code under test.
