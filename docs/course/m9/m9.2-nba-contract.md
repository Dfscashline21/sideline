# M9.2 · NBA source contract by hand

> **Ticket:** [#120](https://github.com/Dfscashline21/sideline/issues/120) ·
> **Mode:** hand · **Time:** 3 to 4 hours ·
> **Needs:** M9.1 session 2, the M2 NBA extractor and its Pydantic models (M2.5)

## Why this matters

`nba_api` wraps an undocumented website API. It has changed field names
and response shapes before, and it will again. Right now that knowledge
lives in your Pydantic models and your head. A contract makes it
**explicit, reviewable and enforced**: the fields you depend on, their
types and ranges, who owns the source, and what service level you
expect. CI then stops anyone (including you, at midnight) from quietly
loosening those expectations.

This is also the most common shape of a "data contracts" interview
question: *"Walk me through a contract you wrote and how you enforced it."*

## What you'll produce

- `quality/contracts/nba/nba_api_team_game_log.odcs.yaml`: an ODCS
  contract for one NBA source entity, written by hand.
- A tiny fixture, `quality/contracts/fixtures/nba_team_game_log.json`,
  that the contract is tested against.
- A CI job that **lints** every contract, **tests** it against its
  fixture, and **fails on breaking changes** compared with `main`.
- Proof: a PR with a breaking change, failing.

## Steps

### 1. Pick the entity (15 min)

One contract per source entity. Start with the one your marts depend on
most. The examples use team game logs (nba_api's `LeagueGameLog`
endpoint: one row per team per game), but use whichever entity your M2
extractor actually lands.

Decide *what shape* the contract describes. `nba_api` responses are
nested (`resultSets[].headers` + `rowSet` arrays), but your M2.5 Pydantic
models validate **one flat record per row**. Contract the flat record:
that's the thing your code relies on, and it's checkable.

Write the decision in a comment at the top of the file.

### 2. List the fields you actually use (30 min)

Not every field the API returns: the ones **something downstream
reads**. Search your code for them:

```bash
grep -rn "GAME_ID\|TEAM_ID\|PTS" ingestion/ transform/models/staging/
```

For each field, write down: name, logical type, required or not, and any
range or allowed values. Pay attention to:

- **`GAME_ID` is a string** (`"0022400061"`). It has leading zeros.
  Store it as an integer and you silently corrupt every join.
- `WL` has two allowed values. Can it be NULL (a game in progress)?
- Points, rebounds, minutes: what's a *defensible* range? Derive it from
  data, not instinct. (M1's practice data has seasons of real values.)

✅ **Checkpoint:** a table of 10 to 20 fields with types and rules,
and for every range a one-line note of where the number came from.

### 3. Write the contract (60 min)

Start from the ODCS docs' examples, not a blank file. The parts you need:

| Section | ODCS key | What to put |
|---|---|---|
| Header | `apiVersion`, `kind`, `id`, `version`, `status`, `name` | `kind: DataContract`, `version: 1.0.0` |
| Ownership | `team` | You, with a role (owner). Who is the *upstream*? Document it in `description` |
| Where the data is | `servers` | A `local` server pointing at the fixture (CI) and an `s3` server for MinIO |
| Schema | `schema[].properties[]` | Your fields from step 2 |
| Quality | `quality` (on schema or property) | Uniqueness of `(GAME_ID, TEAM_ID)`, no NULL keys |
| Service level | `slaProperties` | Freshness and frequency you expect from the source |

<details>
<summary>Hint 1 · Nudge: types and ranges</summary>

In ODCS, the logical type goes in `logicalType` (`string`, `integer`,
`number`, `date`, `boolean`, …), and constraints such as `minimum`,
`maximum` or `pattern` go in `logicalTypeOptions`. `physicalType` is
what the storage calls it. `required: true` means "must not be NULL".

</details>

<details>
<summary>Solution (open only after you have your own)</summary>

A compact version. Your field list, ranges and SLA values should come
from your own steps 2 and 4.

```yaml
# Source contract: what Sideline EXPECTS from nba_api's LeagueGameLog
# (team mode), one flat record per team per game, as validated by
# ingestion/sideline_ingestion/nba/models.py. We don't own the API;
# this contract documents our dependency and fails CI if we loosen it.
apiVersion: v3.1.0
kind: DataContract
id: nba-api-team-game-log
name: NBA team game log (nba_api LeagueGameLog)
version: 1.0.0
status: active
domain: sideline
description:
  purpose: Team box score totals per NBA game, the source of fact_team_game.
  limitations: Unofficial API (stats.nba.com). No upstream SLA; values below are our expectation.
team:
  name: sideline-ingestion
  members:
    - username: Dfscashline21
      role: owner
servers:
  - server: ci-fixture
    type: local
    path: ./quality/contracts/fixtures/nba_team_game_log.json
    format: json
schema:
  - name: team_game_log
    physicalName: nba_team_game_log
    properties:
      - name: GAME_ID
        logicalType: string
        required: true
        logicalTypeOptions:
          pattern: "^00[1-6][0-9]{7}$"     # 10 chars: "00", season-type digit, 2-digit year, 5-digit game number
      - name: TEAM_ID
        logicalType: integer
        required: true
      - name: GAME_DATE
        logicalType: date
        required: true
      - name: MATCHUP
        logicalType: string
        required: true
      - name: WL
        logicalType: string
        enum: ["W", "L"]                    # NULL while a game is in progress
      - name: PTS
        logicalType: integer
        required: true
        logicalTypeOptions: {minimum: 0, maximum: 200}
      - name: FGA
        logicalType: integer
        required: true
        logicalTypeOptions: {minimum: 0, maximum: 150}
      - name: FTA
        logicalType: integer
        required: true
        logicalTypeOptions: {minimum: 0, maximum: 100}
      - name: OREB
        logicalType: integer
        required: true
        logicalTypeOptions: {minimum: 0}
      - name: TOV
        logicalType: integer
        required: true
        logicalTypeOptions: {minimum: 0}
    quality:
      - type: library
        metric: duplicateValues
        arguments:
          properties: [GAME_ID, TEAM_ID]
        mustBe: 0
        description: One row per team per game.
slaProperties:
  - property: latency
    value: 6
    unit: h
    description: Final box scores available within 6 hours of the game ending.
  - property: frequency
    value: 1
    unit: d
```

Check every key against the ODCS schema for the `apiVersion` you choose,
and run `datacontract lint` on it: the linter has the final say, not
this example. In particular, check how your `datacontract-cli` version
wants a **multi-column** uniqueness rule expressed; if the `library`
metric doesn't support it, use a `type: sql` quality rule that counts
duplicate `(GAME_ID, TEAM_ID)` pairs and `mustBe: 0`.

Is the season-type digit range right? Check it against real IDs: regular
season, playoffs, play-in and the NBA Cup final all use different digits.

</details>

### 4. Make the fixture (20 min)

Take 5 to 10 real records from a raw file in MinIO, flatten them the
same way your extractor does, and save them as
`quality/contracts/fixtures/nba_team_game_log.json`. Include at least
one game with leading-zero IDs (all of them) and both a `W` and an `L`.

A fixture is small, real and committed. It isn't "data" in the
`.gitignore` sense: it's a test input, like any unit-test fixture. Keep it
under a few KB.

### 5. Run the CLI locally (30 min)

Add the tool to the dev dependency group (pin it), then:

```bash
uv add --dev "datacontract-cli[duckdb]"
uv run datacontract lint quality/contracts/nba/nba_api_team_game_log.odcs.yaml
uv run datacontract test quality/contracts/nba/nba_api_team_game_log.odcs.yaml
```

✅ **Checkpoint:** `lint` passes, `test` passes against the fixture. Now
edit the fixture so one row has `PTS: -3`, and see `test` fail. Revert.

### 6. Detect breaking changes (30 min)

`datacontract breaking OLD NEW` compares two versions of a contract and
fails when the new one breaks a guarantee consumers rely on. In CI, OLD
is the version on `main` and NEW is the one in the PR:

```bash
git show origin/main:quality/contracts/nba/nba_api_team_game_log.odcs.yaml > /tmp/old.odcs.yaml
uv run datacontract breaking /tmp/old.odcs.yaml quality/contracts/nba/nba_api_team_game_log.odcs.yaml
echo "exit code: $?"
```

Try each change from M9.1 exercise 2.1 locally and record which ones
`breaking` flags. Do its rules match your answers? Write the
disagreements in your notes. They're good interview material.

### 7. Wire it into CI (45 min)

Add a `contracts` job to `.github/workflows/ci.yml` that, for every
`*.odcs.yaml` under `quality/contracts/`:

1. runs `datacontract lint`,
2. runs `datacontract test` (against the fixture server),
3. if the file exists on `main`, runs `datacontract breaking` against
   the `main` version.

<details>
<summary>Hint · CI details that bite</summary>

- `actions/checkout` fetches one commit by default, so `origin/main`
  doesn't exist in the runner. Use `fetch-depth: 0`, or
  `git fetch origin main --depth=1` before `git show`.
- A **new** contract has no `main` version: skip `breaking` for it
  rather than failing.
- On a push to `main` itself, comparing `main` with `main` is pointless.
  Run `breaking` only on `pull_request` events.
- Loop with `set -e` so the first failure fails the job, or collect
  failures and exit non-zero at the end so you see all of them at once.

</details>

Then make `contracts` a **required check** in branch protection,
alongside `python`.

✅ **Checkpoint:** a PR that only fixes a typo in `description` passes.

### 8. Prove a breaking change fails the build

Open a PR that removes `TOV` from the contract (or changes `GAME_ID` to
`integer`). CI must go red on the `breaking` step. Screenshot it, link it
from your notes, then close the PR without merging.

If you *intend* a breaking change, the honest process is: bump the
contract's major `version`, update consumers in the same PR, and say so
in the PR description. Decide how CI should allow that (a label? a
version-bump rule?) and write it down. You don't have to implement it.

## Gotchas

- **Version strings.** `apiVersion` is the ODCS spec version; `version`
  is *your* contract's version. Don't mix them up.
- **`datacontract-cli` and the newest ODCS.** The tool may lag the spec
  by a release. If `lint` rejects `v3.2.0`, use the latest version it
  accepts and note it.
- **Ranges are guesses until measured.** "PTS ≤ 200" is safe; "PTS ≥ 70"
  will eventually fail on a real (if rare) low-scoring game. Every bound
  needs a source.
- **Contract vs Pydantic.** Both now describe the same record. Decide
  which is the source of truth, and add a test that they agree, or
  generate one from the other. Two hand-maintained copies will drift.
