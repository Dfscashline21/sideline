# M9.3 · WNBA and college contracts

> **Ticket:** [#121](https://github.com/Dfscashline21/sideline/issues/121) ·
> **Mode:** agent: the agent drafts, you review it like a junior's PR ·
> **Time:** 2 hours · **Needs:** M9.2 merged (your NBA contract is the template)

## Why this matters

Once one contract exists, the rest are repetitive, which is exactly the
work an agent should draft. The risk is just as clear: an agent copies
the NBA contract, changes the names, and ships NBA *assumptions* for
leagues that differ. Women's college games are 40 minutes, not 48; men's
college has halves; college IDs and score ranges are different. The
skill here is **reviewing for wrong assumptions**, not checking syntax.

## What you'll produce

- One contract per remaining source entity under
  `quality/contracts/{wnba,ncaa_m,ncaa_w}/`, each with a fixture.
- All of them passing the CI job from M9.2.
- Your review notes in the PR description.

## Steps

### 1. Inventory the sources (20 min)

List every source entity your extractors land (M6.2 WNBA, M7.3 college),
with the endpoint or file it comes from. Every row on this list needs a
contract; "all sources covered" is the acceptance criterion.

| League | Entity | Source (endpoint / release) | Downstream user |
|---|---|---|---|
| wnba | team game log | ___ | `fact_team_game` |
| ncaa_m | play-by-play | ___ | `fact_play` |
| … | | | |

✅ **Checkpoint:** the list matches `ls` of your raw zone prefixes in
MinIO. Nothing in the bucket is missing from the list.

### 2. Write down the league differences first (20 min)

**Before** prompting, write the facts the agent must not get wrong.
Don't trust the agent (or this lab) for these: check them against your
own data. Measured on the 2024-25 ESPN play-by-play (see the
[module overview](README.md#facts-about-the-data-that-the-checks-depend-on)):

- Period structure and lengths per league.
- Clock column name per league (men's college differs).
- Coordinates: present for almost all WNBA/NBA shots, missing for most
  college shots, and occasionally a sentinel value.
- ID formats: look at real IDs for each league's source and write the
  pattern yourself.

### 3. Prompt the agent

> Read `AGENTS.md` and `quality/contracts/nba/nba_api_team_game_log.odcs.yaml`.
> Draft ODCS contracts for these sources, one file each, following the
> NBA contract's structure and conventions exactly: *(paste your
> inventory table)*.
>
> These league facts override anything in the NBA contract: *(paste
> step 2)*.
>
> For every range or pattern you write, add a YAML comment saying
> whether it was copied from the NBA contract or derived for this
> league, and from what. Create a fixture for each contract with 5 to 10
> rows copied from the real raw files in MinIO (bucket `sideline-raw`),
> not invented. Don't change the NBA contract or CI.

The comment-per-range instruction is the important part: it makes
copied assumptions **visible** in review.

### 4. Review it like a pull request

Go file by file. For each, answer in the PR description:

| Review question | What a good answer looks like |
|---|---|
| Is every range commented with its origin? | Yes; NBA-copied ranges for points, minutes and FGA have been re-derived for 40-minute leagues |
| Are period and clock rules right for this league? | Men's college: 2 periods of 1,200 s; others: 4 periods; overtime 300 s everywhere |
| Is the clock field named as this league's data names it? | Men's college uses the `period` field, not `quarter` |
| Are coordinates `required: true`? | They mustn't be for college: most are NULL |
| Do the fixtures come from real files? | Spot-check one row against MinIO |
| Does `GAME_ID`'s type and pattern match this league's real IDs? | Checked against 5 real IDs |
| Is the ownership and SLA section honest? | College data may land later than the NBA's; the SLA says so |
| Would the contract pass on a full real day of data, not only the fixture? | Run `datacontract test` against the S3 server for one day |

<details>
<summary>Hint · Things agents get wrong here</summary>

- Copying `maximum: 200` points straight over: harmless, but copying
  `minimum` values or minute ranges tuned for 48 minutes isn't.
- Inventing fixture rows that "look right" instead of copying real
  ones: they'll pass a contract that real data fails.
- Making every field `required: true` because the NBA one did.
- Silently "fixing" the NBA contract to match a new league. Shared
  conventions belong in a separate PR.

</details>

### 5. Test against real data, not just fixtures

Add an `s3` server (MinIO endpoint, `sideline-raw` path for one recent
day) to one college contract, and run `datacontract test` with that
server selected. Real data is where wrong assumptions show up. Fix the
contract (or record a known issue) for every failure.

✅ **Checkpoint:** every contract passes `lint` and `test` in CI, and at
least one has passed against a real day of data.

### 6. Ship it

```bash
git switch -c m9.3-league-contracts
git add quality/contracts/
git commit -m "M9.3: WNBA and college source contracts"
gh pr create --fill     # Closes #121; paste your review table in the body
```

## Gotchas

- **Fixtures are code.** Keep them tiny and real. A 2 MB fixture is a
  data dump the `check-added-large-files` hook will (rightly) block.
- **One contract per entity, not per league.** If WNBA and NBA share an
  identical shape, it's still two contracts: they can change
  independently, and they have different owners and SLAs.
- **CI time.** Ten contracts × three commands adds up. If the job gets
  slow, run `breaking` only on changed files.
