# M9.6 · Freshness SLO and measurement

> **Ticket:** [#124](https://github.com/Dfscashline21/sideline/issues/124) ·
> **Mode:** hand · **Time:** 3 hours ·
> **Needs:** M9.1 session 3, the daily pipeline from M6 writing to gold

## Why this matters

"Yesterday's box scores in gold by 6:00 AM Pacific, 99% of days" sounds
simple. Measuring it honestly isn't: what counts as "in gold", which
games were expected, what "6:00 AM Pacific" means on the night the
clocks change, and what to do on days with no games. An SLO you can't
measure precisely is a slogan. This lab turns it into a number on a
dashboard, which is the acceptance criterion.

## What you'll produce

- A precise written definition of the SLI, in `quality/slo/README.md`.
- `ops.freshness_daily`: one row per league per game day, with the
  deadline, when the data landed, and whether the SLO was met.
- An attainment view: % of game days met over a rolling window, plus
  the remaining **error budget**.
- That number visible on a dashboard. M9.10 builds the full quality
  dashboard; here you add the first panel.

## Steps

### 1. Write the SLI definition before any code (30 min)

Answer each question in `quality/slo/README.md`. These are the decisions;
the SQL just follows them.

| Question | Your answer |
|---|---|
| Which table is "gold"? | e.g. `fact_team_game` |
| What does "in gold" mean for one game? | Both team rows present? Plus player rows? |
| What's "yesterday"? | The game's date in which time zone? (ESPN and the NBA date games in Eastern time) |
| Which games were **expected**? | From the schedule, status final. Not "whatever we loaded" |
| Deadline | 06:00 in `America/Los_Angeles`, the day after the game date |
| Days with no games | Excluded from the denominator, or counted as met? |
| Postponed games | Not expected that day |
| Window | Rolling 90 days? A season? See the error-budget arithmetic in M9.1 |

<details>
<summary>Hint · Why "expected" must come from the schedule</summary>

If you only look at games you loaded, a game you **never** loaded can't
be late, so it never counts against you. The SLO then reports 100% on
the night the pipeline silently skipped a game. Expected games must come
from an independent source: the schedule.

</details>

✅ **Checkpoint:** someone else could compute the SLI from your
definition and get the same number.

### 2. Record when data lands (30 min)

You need the time each game reached gold. Two options:

- A `loaded_at` timestamp column on the gold table, set at write time.
- A load log written by the Dagster asset (asset materialisation
  timestamps are another source).

Pick one. Store it as a **timestamp with time zone** (UTC). Local times
without a zone will bite you twice a year.

### 3. Compute one row per league per game day (45 min)

<details>
<summary>Hint 1 · Approach</summary>

1. Expected games per league and day from the schedule.
2. Landed games and their latest `loaded_at` from gold.
3. `LEFT JOIN` expected to landed, so missing games show up.
4. Deadline = 06:00 local Los Angeles time on `game_day + 1`, converted
   to an absolute timestamp.
5. Met = every expected game landed **and** the last one landed before
   the deadline.

</details>

<details>
<summary>Solution (open only after you have your own)</summary>

DuckDB. `timezone('America/Los_Angeles', <timestamp>)` interprets a
plain timestamp as Los Angeles local time and returns an absolute
`timestamptz`, so daylight saving time is handled for you.

```sql
-- one row per league x game day: deadline is 06:00 Pacific on the following calendar day
with expected as (            -- games that should be in gold, from the schedule
    select league, game_date as game_day, count(*) as games_expected
    from schedule
    where status = 'final'
    group by 1, 2
),
landed as (                   -- when each game's last team row reached gold
    select league, game_date as game_day, game_id, max(loaded_at) as landed_at
    from fact_team_game
    group by 1, 2, 3
),
per_day as (
    select e.league, e.game_day, e.games_expected,
           count(l.game_id) as games_landed,
           max(l.landed_at) as last_landed_at,
           -- 06:00 local time in Los Angeles, converted to an absolute instant (handles DST)
           timezone('America/Los_Angeles', (e.game_day + interval 1 day + interval 6 hour)::timestamp) as deadline
    from expected e
    left join landed l using (league, game_day)
    group by 1, 2, 3
)
select *,
       games_landed = games_expected and last_landed_at <= deadline as met
from per_day;
```

Write the result into `ops.freshness_daily` (upsert by league and
game day, so re-running a day replaces its row instead of duplicating it).

</details>

### 4. Test the time-zone edges (30 min)

Build a tiny fixture and assert the results. Include the two
daylight-saving mornings. In 2026 the US clocks change on **8 March**
(spring forward) and **1 November** (fall back).

| Game day | Landed at (UTC) | Expected `met` | Why |
|---|---|---|---|
| 2026-03-07 | 2026-03-08 13:59 | **false** | Deadline is 06:00 PDT on 8 March = 13:00 UTC. In winter time, 13:59 UTC would have been 05:59 |
| 2026-11-01 | 2026-11-02 13:30 | true | Back on PST: deadline is 14:00 UTC |
| any | game never landed | false | Missing must count as a miss |

✅ **Checkpoint:** all three pass. If the first one says `true`, your
deadline is a fixed UTC offset, not a time zone. That's the bug this
test exists to catch.

### 5. Attainment and error budget (30 min)

From `ops.freshness_daily`, compute per league over a rolling window:

- `days_measured`, `days_met`, `attainment = days_met / days_measured`
- `budget_days = (1 − 0.99) × days_measured`: misses allowed
- `budget_remaining = budget_days − days_missed`

<details>
<summary>Hint · The arithmetic that matters</summary>

Over 90 game days the budget is 0.9 days, so a single miss puts you
below 99%. If your window is that short, say plainly that the SLO is
effectively "never miss", or lengthen the window to a full season so
the 99% means something. Write the choice in `quality/slo/README.md`.

</details>

### 6. Schedule the measurement (20 min)

Add a Dagster asset (or schedule) that runs at **06:05 Pacific** each
day: it computes yesterday's row in `ops.freshness_daily` and records a
check result (`check_name = 'freshness_slo'`) in `ops.check_results`.

Use the schedule's time zone setting (`execution_timezone` on a Dagster
schedule), not a UTC cron. The same DST trap applies.

Should a miss **page** someone at 06:05? Decide using M9.1's alerting
principles: a miss is a symptom consumers feel. But one late college
game at 06:05 might be a ticket, not a page. Write the rule down.

### 7. Put it on a dashboard

Add a first panel: attainment per league over the window, with the
error budget remaining, and a daily strip of met/missed days. Build it
wherever M9.10's quality dashboard will live, so M9.10 extends it
instead of replacing it. A Streamlit page reading the attainment view is
enough.

✅ **Checkpoint:** the panel shows a real number for at least the NBA,
from real pipeline runs.

### 8. Ship it

Definition, SQL, tests, Dagster asset and the panel in one PR.
`Closes #124`.

## Gotchas

- **Backfills distort `loaded_at`.** Re-loading last month sets
  `loaded_at` to today, so every old day looks "late". Record the first
  landing time per game, or exclude backfill runs from the SLI.
- **West-coast late games.** A 7:30 PM tip in Los Angeles ends around
  10 PM Pacific. If the daily run starts at midnight Eastern, those games
  aren't final yet. Your run schedule has to fit the deadline, not the
  other way round.
- **"99% of days" per league or overall?** Report per league. An overall
  number hides a league that's always late behind the NBA's volume.
