# M9.9 · Postmortem for one chaos failure

> **Ticket:** [#127](https://github.com/Dfscashline21/sideline/issues/127) ·
> **Mode:** hand · **Time:** 90 min ·
> **Needs:** M9.8 notes (timelines and fixes)

## Why this matters

A postmortem turns one bad day into lasting improvements. Senior
engineers are judged less on whether incidents happen than on how they
learn from them, and "tell me about an incident you led the review for"
is a standard senior interview question. **Blameless** means you look for
how the *system* allowed the failure, not who to blame. "The engineer
ran the backfill twice" is a symptom; "the backfill wasn't idempotent and
nothing stopped a second run" is a cause you can fix.

## What you'll produce

`docs/incidents/2026-MM-DD-<slug>.md` (the date of chaos day, e.g.
`2026-03-12-double-loaded-day.md`) for one chaos-day failure: summary,
impact, timeline, root cause, what went well, what didn't, action items
with owners. Saved to `docs/incidents/`, which is the acceptance criterion.

## Steps

### 1. Pick the failure (10 min)

Choose the chaos failure with the most to learn from: usually the one
where your prediction was wrong, detection was slow, or a gap was found.
A failure your checks caught in two minutes makes a dull postmortem.

### 2. Rebuild the timeline (20 min)

From your M9.8 notes, plus evidence: Dagster run logs,
`ops.check_results` timestamps, alert messages, git commits. Every entry
gets a time and a source:

```markdown
| Time (PT) | Event | Source |
|---|---|---|
| 09:00 | Raw files for 2026-03-10 landed a second time (simulated) | MinIO object timestamps |
| 09:12 | `unique_fact_team_game_grain` failed | ops.check_results |
| 09:52 | First human notified | Slack alert |
```

Mark the four key moments: **start of impact, detection, mitigation,
resolution**. The gaps between them are your headline numbers: time to
detect and time to recover.

### 3. Measure impact (15 min)

Be specific, even though nobody external was affected:

- Which tables and dashboards showed wrong data, and for how long? (Use
  your M9.7 lineage graph to find the downstream reach.)
- How many rows or games were affected?
- Was the freshness SLO missed? How much error budget did it use?

### 4. Find the root cause: five whys (20 min)

Start at the symptom and ask "why?" until you reach something you can
fix in the system. Stop when the answer is a missing safeguard, not a
person.

<details>
<summary>Hint · An example chain (yours will differ)</summary>

1. Why was `fact_team_game` doubled? Staging read two raw files for the day.
2. Why were there two? The re-run wrote a new object with a new run ID.
3. Why did staging read both? It reads every object under the day's prefix.
4. Why wasn't the re-run idempotent? Raw keys include the run ID, and
   nothing marks the "current" load for a day.
5. Why didn't a check stop it before gold? The uniqueness test runs
   after the marts build, not between staging and marts.

Two root causes: a non-idempotent landing pattern, and a check in the
wrong place. Each gets an action item.

</details>

Often there's more than one cause. List the **contributing factors**
separately (alert routed to an unread channel, runbook out of date…).

### 5. Write the document (30 min)

A structure that works:

```markdown
# Double-loaded game day (chaos exercise), 2026-03-12

**Status:** resolved · **Severity:** SEV-3 (internal data, no external consumers) · **Author:** ...

## Summary
Three sentences: what happened, impact, how it was fixed.

## Impact
Tables, rows, duration, SLO budget used.

## Timeline
(table from step 2)

## Root cause
The five whys, then the root causes in one paragraph each.

## Contributing factors

## What went well
## What went badly
## Where we got lucky

## Action items
| Action | Type | Owner | Due | Issue |
|---|---|---|---|---|
| Make raw landing idempotent per (league, day) | prevent | @you | ... | #... |
| Run uniqueness test before marts build | detect | @you | ... | #... |
```

Action item types: **prevent** (it can't happen again), **detect**
(we'd notice faster), **mitigate** (smaller impact next time). Aim for
at least one of each. Every action becomes a GitHub issue, linked.

### 6. Review it blamelessly (5 min)

Search your draft for names and for words like *forgot*, *careless*,
*should have*, *mistake*. Rewrite each sentence about the system: "the
re-run path had no guard" rather than "I forgot to check".

### 7. Ship it

```bash
git switch -c m9.9-postmortem
git add docs/incidents/
git commit -m "M9.9: postmortem for chaos-day double load"
```

PR with `Closes #127`. Add the incident to `docs/incidents/README.md` as
a one-line index entry. M9.10's dashboard will list open incidents from
this folder, so keep the **Status** line in that exact format.

## Gotchas

- **Too much narrative, too few facts.** If a timeline entry has no
  source, it's a memory, and memories are wrong.
- **Action items nobody owns.** "Improve monitoring" isn't an action.
  "Route `severity=critical` checks to the pager, by Friday, owner @you" is.
- **It's an exercise.** Say so in the summary, but write it as if it
  were real. That's the practice.

## Done when

- [ ] Timeline with sources and the four key moments; time to detect and recover stated
- [ ] Impact quantified, using lineage for downstream reach
- [ ] Root causes found with five whys; contributing factors listed
- [ ] Prevent, detect and mitigate action items, each a linked issue
- [ ] Blameless language check done; saved to `docs/incidents/`; `Closes #127`
