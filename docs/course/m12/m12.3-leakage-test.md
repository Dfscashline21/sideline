# M12.3 · Leakage test

> **Ticket:** [#154](https://github.com/Dfscashline21/sideline/issues/154) ·
> **Mode:** hand · **Time:** 3 hours ·
> **Needs:** M12.2 merged

## Why this matters

In M12.2 you were careful. Careful doesn't survive the next person
editing the model, or you in three months copying a window and getting
`LEAD` where you meant `LAG`. A leak doesn't throw an error: it makes the
model *look better*, which is exactly why nobody goes looking for it.
The only reliable defence is a **test that fails when a leak appears**,
running in CI on every change.

## What you'll produce

- `ml/tests/test_leakage.py` (or a dbt test, see step 2) that checks
  every feature in `feat_team_game`.
- Proof that it **fails on a planted leak** (the acceptance criterion):
  a second test that deliberately leaks and asserts the check catches it.

## Steps

### 1. Choose what "leak" means operationally (20 min)

Two kinds of test catch different leaks. Read both, then decide.

| Test | How it works | Catches | Misses |
|---|---|---|---|
| **Timestamp lineage** | Each feature also outputs the timestamp of the newest row it used (`*_source_ts`); assert it's `< prediction_ts` | Wrong join condition, `<=` instead of `<` | Leaks that don't go through a timestamped join, e.g. a window frame that includes the current row |
| **Truncation (counterfactual)** | Recompute features for a game using *only* data that existed at its tip-off, with that game's outcome blanked out. They must equal the features from the full pipeline | Anything: frames, `LEAD`, season-level aggregates, joins to final tables | Slower; needs the feature logic callable on an arbitrary input table |

The truncation test asks the real question ("would this value have been
the same at tip-off?") so it's the one this lab builds. Add timestamp
lineage too if you have time; it's cheap.

### 2. Make the feature logic testable (45 min)

To recompute features on a truncated dataset, the feature SQL must run
against **any input table**, not just the production one.

- If features live in dbt: dbt has unit tests (`unit_tests:` in YAML, dbt
  1.8+) that feed fixed input rows to a model. You can build the
  truncation check from those, but it's verbose.
- Simpler: keep the SQL in a file or function that takes the source table
  name, call it from dbt *and* from Python tests.

Pick one. Write down why.

### 3. Build a fixture (30 min)

A small synthetic `team_games` table: a few teams, ~30 games each,
timestamps spaced out, deterministic wins and losses. Synthetic means the
test runs in CI with no data download and you know every value.

✅ **Checkpoint:** you can compute `form_win_pct_last10` for one fixture
row by hand.

### 4. Write the truncation check (60 min)

<details>
<summary>Hint 2 · Approach</summary>

1. List every **outcome column** (only known after the game): result,
   score, stats. Keep it in one constant so new outcome columns get added
   in one place.
2. `known_at_tipoff` = rows with `game_ts < G.game_ts`, plus G's row with
   outcome columns set to `NULL`.
3. Features for G from `known_at_tipoff` must equal features for G from
   the full table.
4. Check several games: early season, mid season, last game.

</details>

<summary>Solution (open only after you have your own)</summary>

`ml/features.py` (feature logic that runs on any table; trimmed to two
features for the example):

```python
import duckdb

FEATURE_SQL = """
select league, game_id, team_id, game_ts as prediction_ts,
    avg(team_winner::int) over w10 as form_win_pct_last10,
    date_diff('day', lag(game_ts) over (partition by league, team_id order by game_ts, game_id),
              game_ts) as rest_days
from {table}
window w10 as (partition by league, team_id, season order by game_ts, game_id
               rows between {frame})
"""


def build_features(
    con: duckdb.DuckDBPyConnection,
    frame: str = "10 preceding and 1 preceding",
    table: str = "team_games",
) -> duckdb.DuckDBPyRelation:
    return con.sql(FEATURE_SQL.format(frame=frame, table=table))
```

`ml/tests/test_leakage.py`:

```python
import duckdb
import pytest

from features import build_features

OUTCOME_COLS = ["team_winner"]  # every column only known after the game


def _fixture() -> duckdb.DuckDBPyConnection:
    con = duckdb.connect()
    con.execute("""
        create table team_games as
        select 'nba' as league, 2024 as season, g as game_id, t as team_id,
               timestamp '2024-01-01 19:00' + to_days(g * 2 + t) as game_ts,
               ((g * 7 + t * 3) % 5) < 2 as team_winner
        from range(1, 31) a(g), range(1, 3) b(t)
    """)
    return con


def _features_known_at_tipoff(
    con: duckdb.DuckDBPyConnection, game_id: int, team_id: int, frame: str
) -> list[tuple[object, ...]]:
    """Rebuild one game's features from only what existed at its tip-off."""
    row = con.execute(
        "select game_ts from team_games where game_id = ? and team_id = ?", [game_id, team_id]
    ).fetchone()
    assert row is not None
    con.execute(
        "create or replace table known_at_tipoff as select * from team_games where game_ts < ?",
        [row[0]],
    )
    nulls = ", ".join(f"null as {c}" for c in OUTCOME_COLS)
    con.execute(
        f"insert into known_at_tipoff by name "
        f"select * exclude ({', '.join(OUTCOME_COLS)}), {nulls} "
        "from team_games where game_id = ? and team_id = ?",
        [game_id, team_id],
    )
    return (
        build_features(con, frame, "known_at_tipoff")
        .filter(f"game_id = {game_id} and team_id = {team_id}")
        .fetchall()
    )


def check_no_leakage(frame: str) -> None:
    con = _fixture()
    full = build_features(con, frame)
    for game_id, team_id in [(5, 1), (12, 2), (25, 1), (30, 2)]:
        expected = _features_known_at_tipoff(con, game_id, team_id, frame)
        actual = full.filter(f"game_id = {game_id} and team_id = {team_id}").fetchall()
        assert actual == expected, f"leak at game {game_id}, team {team_id}"


def test_features_use_only_pre_tipoff_data() -> None:
    check_no_leakage("10 preceding and 1 preceding")


def test_planted_leak_is_caught() -> None:
    with pytest.raises(AssertionError):
        check_no_leakage("9 preceding and current row")  # includes this game's own result
```

Both tests pass. Change `lag(` to `lead(` in the feature SQL and
`test_features_use_only_pre_tipoff_data` fails, as it should: the
"rest days" would then come from the next game, which doesn't exist yet
at tip-off.

</details>

### 5. Plant real leaks and watch them fail (30 min)

The planted-leak test proves the check works for one kind of leak. Prove
it for others by temporarily breaking your **real** feature logic, one at
a time, running the test, and reverting:

- [ ] frame includes the current row
- [ ] `LEAD` instead of `LAG` for rest days
- [ ] form computed from a season-level aggregate (the M12.1 naive join)
- [ ] injury `ASOF` join with `<=` replaced by a plain join on game date

Record each in your notes: which leak, did the test fail, with what
message. If one passed when it should have failed, your test has a
blind spot; fix the test, not the note.

✅ **Checkpoint:** every planted leak fails the test, and the clean
version passes.

The test uses a synthetic fixture, so it runs in the existing CI job with

## Gotchas

- **A forgotten outcome column.** If you add `team_score` to the table but
  not to `OUTCOME_COLS`, a feature using it passes the test. Derive the
  list from your M3 grain notes, and review it whenever the table changes.
- **Floating-point equality.** Averages computed over the same rows in a
  different order can differ in the last bits. If comparisons flap, round
  to 9 decimal places before comparing.
- **Sampling too few games.** A leak that only affects the last game of a
  season won't show up if you only test early games.
