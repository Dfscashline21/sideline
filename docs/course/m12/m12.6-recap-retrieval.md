# M12.6 · Recap embeddings and retrieval endpoint

> **Ticket:** [#157](https://github.com/Dfscashline21/sideline/issues/157) ·
> **Mode:** agent: the agent drafts, you review it like a junior's PR ·
> **Time:** 4 to 6 hours · **Needs:** M12.1 session 2, M11.3 (the API)

## Why this matters

Retrieval (finding the right documents for a question, then answering
only from them) is now a routine data-platform feature. The data
engineering part is everything around the model: where the text comes
from, how it's chunked and kept fresh, which metadata makes it filterable
("last night" means a date filter, not a vibe), and whether the answer
can be traced to its sources. The acceptance bar is exactly that: the
endpoint **answers from retrieved sources**.

## What you'll produce

- A `documents` table in Postgres with pgvector: text chunks, embeddings,
  and metadata (league, game_id, date, source, URL or source ID)
- An ingestion script that embeds new documents idempotently
- `GET /v1/ask?q=...&date=...` in the M11.3 API, returning an answer
  **and the retrieved passages it used**

## Steps

### 1. Choose the documents (hand, 30 min)

You need text. Options, with honest trade-offs:

| Source | Pros | Cons |
|---|---|---|
| **Injury report reasons** (the `nba_stats_injury_report` data from M12.2) | Real, timestamped, already in your pipeline | Short and repetitive; NBA only |
| **Recaps you generate from your own box scores and play-by-play** (a template: final score, top scorers, biggest run, lead changes from M1.8) | You own the text; covers every league; facts are checkable against your marts | It's machine-written; say so on the page |
| **Published recaps from a news site** | Rich writing | Check the site's terms before collecting anything; copyright and scraping limits apply |

Templated recaps are the recommended default: they cover all leagues,
and in M12.7 you can verify every expected answer against your own
tables. Write the choice down.

### 2. Add pgvector to the Compose Postgres

The `postgres:16-alpine` image doesn't include the pgvector extension.
The pgvector project publishes images with it, e.g.
`pgvector/pgvector:0.8.7-pg16-trixie` (check Docker Hub for the current
tag; keep the Postgres major version at 16 to match your data volume).

Then, once:

```sql
create extension if not exists vector;
```

✅ **Checkpoint:** `select extversion from pg_extension where extname = 'vector';`
returns a version.

### 3. Choose an embedding model (hand, 20 min)

A small local model is plenty here and costs nothing per call:
`sentence-transformers` with a compact model such as
`all-MiniLM-L6-v2` (384-dimensional vectors). Your vector column's
dimension must match the model's output, so read it from the model card,
not from memory.

A hosted embedding API is also fine; it adds a key to manage (Secrets
Manager in the cloud, `.env` locally) and a per-call cost.

### 4. Prompt the agent

> Implement retrieval for this repo.
>
> (1) `ml/retrieval/ingest.py`: read documents from *(your source)*, chunk
> them (*your rule: e.g. one recap = one chunk*), embed with
> sentence-transformers model *(name)*, and upsert into Postgres table
> `documents(id text primary key, league text, game_id text, doc_date
> date, source text, source_ref text, body text, embedding vector(N))`,
> where `id` is a deterministic hash of source and source_ref, so
> re-running inserts nothing new. Create an HNSW index with cosine distance.
>
> (2) In `serving/api/`, add `GET /v1/ask?q=&league=&date=` that embeds
> `q` with the same model, filters by league and date (if given)
> **before** ranking, returns the top 5 chunks by cosine distance, and an
> `answer` built only from those chunks. Every response includes the
> retrieved chunks with id, source_ref, date and distance. If nothing
> passes the filters, return an empty answer saying so, never a guess.
>
> Add it to `openapi.yaml` first. Tests with a tiny fixture table. Typed;
> lint and typecheck pass. Database URL from env vars already in `.env`.

How you build `answer` is your call: either the top passage verbatim
(no language model, fully traceable), or a language model instructed to
answer **only** from the provided passages and cite their ids. Start
without one; add it only if you can evaluate it in M12.7.

### 5. Review it

| Review question | What good looks like |
|---|---|
| Is the same model used for documents and queries? | One constant, imported in both places |
| Does the vector dimension match the model? | Read from the model, asserted at startup |
| Are filters applied before ranking? | `WHERE league = %s AND doc_date = %s ORDER BY embedding <=> %s LIMIT 5` |
| Is ingestion idempotent? | Deterministic ids, `ON CONFLICT DO NOTHING`/`DO UPDATE` |
| Does the response always include its sources? | Yes, even when the answer is empty |
| What happens with "last night"? | The endpoint takes an explicit date; the client resolves "last night". Don't let the embedding guess dates |
| Is user input in SQL parameterised? | Always |

<details>
<summary>Hint · Why the date must be a filter</summary>

Embeddings capture *meaning*, not *time*. "How did the Celtics do last
night?" is semantically close to every Celtics recap ever written. Without
a date filter, the top result might be from 2008. Metadata filters do the
precise part; vectors do the fuzzy part.

</details>

### 6. Try it

```bash
uv run python ml/retrieval/ingest.py
curl 'http://localhost:8000/v1/ask?q=who+scored+the+most&league=nba&date=2026-04-12'
```

✅ **Checkpoint:** the answer's facts appear in the returned passages, and
each passage's `source_ref` leads back to a real game.

## Gotchas

- **Changing the Postgres image on an existing volume.** Alpine and
  Debian builds can differ in text collation. If Postgres warns about a
  collation version mismatch, read the warning before ignoring it. If the
  volume holds nothing you need yet, recreating it is simplest.
- **Model downloads.** The first run downloads the embedding model. Cache
  it in the dev container (a volume), or CI and every container start
  will re-download it.
- **Re-embedding.** Changing the model or chunking means re-embedding
  everything. Store the model name with each row so mixed embeddings are
  detectable.
