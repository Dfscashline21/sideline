# M12.9 · Ready-when check (closed-book)

> **Ticket:** [#160](https://github.com/Dfscashline21/sideline/issues/160) ·
> **Mode:** hand, closed-book · **Time:** 45 min ·
> **Needs:** M12.1 to M12.8 done

## Why this matters

The M12 promise: *explain exactly how a naive join leaks future data into
training, with an example.* In an interview this comes as "how do you
build training data?" or "the model was great offline and bad in
production, why?". You need to answer from a blank whiteboard, then write
the fix.

## The rules

- No AI, no notes, no docs, no repo, no running queries until the timer stops.
- Whiteboard or paper. Talk out loud; record yourself if you can.

## Steps

### 1. Pick a scenario you haven't rehearsed

Roll a die: 1–2 → A, 3–4 → B, 5–6 → C. Don't read the others; save them
for IP.2 or IP.3 practice.

<details>
<summary>Scenario A</summary>

A feature "player's points per game this season" is joined to each game
on `(player_id, season)`. The model predicts whether the player scores
over 20 points. Explain the leak, give a one-row example, and write the
corrected SQL.

</details>

<details>
<summary>Scenario B</summary>

Injury status is joined to games on `(team_id, game_date)` from a table
of injury reports published several times a day, with timestamps in US
Eastern time. Tip-off times are in UTC. Explain every way this can leak,
and write the corrected join.

</details>

<details>
<summary>Scenario C</summary>

A teammate trains on 2015 to 2025 games with
`train_test_split(test_size=0.2)` and a `StandardScaler` fitted before
splitting. They report 74% accuracy. List every leak you can find, and
describe the split and pipeline you'd use instead.

</details>

### 2. Explain it: 10 minutes, timed

Out loud, cover:

- the **prediction time** for this problem
- which data is available at that time and which isn't
- the **concrete leaked value** for one example row
- why the model looks better offline and what happens in production

### 3. Fix it: 10 more minutes, timed

Write the corrected SQL or pipeline on the board: an as-of join with a
strictly-before timestamp condition, a frame excluding the current row,
a time-based split, or fitting on training data only, as the scenario
requires. Then describe the test that would catch this leak if someone
reintroduced it (your M12.3 truncation test).

### 4. Check it

Timer off. Compare with your M12.1 notes, M12.2 model and M12.3 test.
If you can, run your corrected SQL on the practice data.

### 5. Score yourself honestly

| Result | Meaning |
|---|---|
| Leak explained with an example, a correct fix and a test, in 20 min | **Pass.** Close the ticket. |
| Explained it, but the fix had a `<=` or frame mistake | Redo M12.1 step 3 from a blank file, retry with another scenario in 2 days |
| Couldn't produce a concrete leaked value | Reread your M12.8 post's hook, then retry |

### 6. Write the notes

Append to `docs/notes/m12.md`:

```markdown
- What I missed:

<three sentences: what was hardest and why>
```
