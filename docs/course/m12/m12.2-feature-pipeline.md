# M12.2 · Feature pipeline with as-of joins

> **Ticket:** [#153](https://github.com/Dfscashline21/sideline/issues/153) ·
> **Mode:** hand · **Time:** 6 to 8 hours ·
> **Needs:** M12.1, M5 marts (`fact_team_game`, `dim_game`, `dim_venue`), M6/M7 (all three leagues loaded)

## Why this matters

This is the table the M12.4 model trains on, and the one the M12.3 test
guards. Every column must answer: *"Could I have known this value at
tip-off?"* Four features, four different ways to get that wrong: a
rolling window that includes the current game, rest days computed from
the *next* game, travel from a venue table that changed later, and an
injury report published after tip-off.

## What you'll produce

`feat_team_game`: one row per **team per game**, for **NBA, WNBA and
college** (the acceptance criterion), keyed by `(league, game_id,
team_id)`, with `prediction_ts` (tip-off) and these features:

| Feature | Definition (write yours precisely) |
|---|---|
| `form_win_pct_last10` | Win % over the team's previous 10 games this season |
| `form_net_pts_last10` | Average point margin over the previous 10 games |
| `rest_days` | Days since the team's previous game (any season type) |
| `is_back_to_back` | `rest_days = 0`... or 1? Define it |
| `travel_km` | Distance from the previous game's venue to this one |
| `players_out` | Players listed Out on the latest injury report **before** tip-off (NBA only; see step 5) |

Build it as a dbt model (`transform/models/marts/ml/feat_team_game.sql`)
so it's tested and documented like any mart, or in `ml/features/` if you
kept ML separate. Pick one and note why.

## Steps

### 1. Write the contract first (30 min)

At the top of the model, as a comment:

- **Grain:** one row per league, game, team.
- **Prediction time:** `prediction_ts = game tip-off timestamp (UTC)`.
- **Rule:** every feature uses only rows with timestamp `< prediction_ts`.
- **Nulls:** what each feature is when there's no history (first game of a
  season, first game ever, no injury data).

✅ **Checkpoint:** you've decided `<` versus `<=` and written why.

### 2. Rolling form (90 min)

You did this in M1.4. The difference now: the frame must **exclude the
current game**, and it's per team rather than per player.

<details>
<summary>Hint 1 · Nudge</summary>

Which frame from M1.4 excludes the current row? Does it still work for
the first 9 games of a season, and what should `form_win_pct_last10` be
for game 1?

</details>

<details>
<summary>Hint 2 · Skeleton</summary>

```sql
avg(team_winner::int) over (
    partition by league, team_id, season
    order by game_ts, game_id
    rows between ___ preceding and ___ preceding
) as form_win_pct_last10
```

Add `count(*)` over the same frame as `form_games_in_window`, so the
model (and you) can tell "50% over 10 games" from "50% over 2".

</details>

### 3. Rest days (45 min)

`LAG` the previous game's timestamp per team, across seasons and season
types (a playoff game yesterday still tires you out). Compute days
between them.

Watch the trap: `LEAD` would give you days until the *next* game, which
is a future fact. It's easy to grab the wrong one when copying window
code.

✅ **Checkpoint:** a known back-to-back in your data has `rest_days = 0`
(or 1, per your definition), and a team's season opener has a large value
or `NULL`, as you decided.

### 4. Travel distance (90 min)

You need coordinates per venue. ESPN data gives venue IDs and cities but
not latitude/longitude.

1. Build a dbt **seed** `venue_coordinates.csv` (`venue_id`, `lat`,
   `lon`), by hand or from a public geocoding source, for the venues you
   actually play in. College has hundreds; NBA and WNBA have a few dozen
   each. Decide whether college gets coordinates by venue or by team's
   home city, and say so.
2. Compute great-circle distance between the previous game's venue and
   this one.

<details>
<summary>Hint · Haversine in SQL</summary>

```sql
2 * 6371 * asin(sqrt(
    pow(sin(radians(lat2 - lat1) / 2), 2)
  + cos(radians(lat1)) * cos(radians(lat2)) * pow(sin(radians(lon2 - lon1) / 2), 2)
)) as travel_km
```

Check it on one pair you know (e.g. two cities whose distance you can
look up).

</details>

Point-in-time note: a team that moves arena mid-history (relocations) is
handled because you join on the *game's* venue, not the team's current
home. Make sure you do.

### 5. Injuries (90 min)

The NBA publishes an official injury report many times a day. A public
copy with a `report_datetime` per snapshot is in sportsdataverse
(`nba_stats_injury_report` release, files `injury_report_<season>.parquet`).
Check which seasons exist before relying on it.

The point-in-time rule here is **"latest report published before tip-off"**:

<details>
<summary>Hint 1 · Approach</summary>

1. Aggregate each report snapshot to one row per team per report:
   `count(*) filter (where current_status = 'Out')`.
2. `ASOF LEFT JOIN` that onto games on `team` and
   `report_ts < prediction_ts`.

</details>

<details>
<summary>Hint 2 · The two traps in this data</summary>

- **Time zones.** ESPN's `game_date_time` is a timezone-aware timestamp.
  The injury report's `report_datetime` is a plain timestamp with no
  zone, and the same file's `game_time` column is labelled `(ET)`, so
  US Eastern is the likely zone. Confirm it against one report whose
  publication time you can check, because if you're wrong, comparing
  them is off by 4 or 5 hours: enough to let a post-tip-off report leak
  in. Convert both to UTC explicitly and write a comment.
- **IDs.** The report uses NBA Stats team and player IDs
  (`1610612747`…), not ESPN's. Map them through your M3.4 crosswalk or a
  team abbreviation mapping, and test that every game found a team.

</details>

**WNBA and college:** there's no comparable historical injury feed in
this course's sources. Don't fake it. Set `players_out = NULL` with
`injury_source_available = false` for those leagues and document it on
the M11.6 data product page. "Features for all three leagues" means
every row exists and every available feature is computed, not that every
source exists everywhere.

### 6. Assemble and sanity-check (60 min)

Join the features on `(league, game_id, team_id)` into `feat_team_game`.
Then check, for each league:

- row count equals the number of team-games in `fact_team_game`
- the share of NULLs per feature, and whether each is explained
- one game picked at random, with every feature recomputed by hand

✅ **Checkpoint:** three leagues present, row counts match, NULLs explained.

Add dbt tests: a uniqueness test on the key, `not_null` on `prediction_ts`,
`dbt_utils.accepted_range` (or a custom test) on `form_win_pct_last10` between 0 and 1.
M12.3 adds the important one.

## Gotchas

- **`LEAD` vs `LAG`.** Grep your model for `lead(` before committing.
- **Partitioning by season for rest days** makes every opener look rested
  and hides cross-season information you're allowed to use. Form resets
  per season; rest days shouldn't.
- **Seeds are data too.** If a venue coordinate is wrong, every distance
  from it is wrong. Spot-check a few.
