# M12.4 · Train a simple model

> **Ticket:** [#155](https://github.com/Dfscashline21/sideline/issues/155) ·
> **Mode:** agent: the agent drafts, you review it like a junior's PR ·
> **Time:** 3 hours · **Needs:** M12.2 features, M12.3 leakage test passing

## Why this matters

The ticket says it: *logistic regression is fine; the pipeline is the
point.* Nobody hires a data engineer for model accuracy. They hire one
whose training data is correct, whose split respects time, and whose
results can be reproduced from a commit. A simple model on clean,
leak-free features beats a fancy one on leaky features, and you already
measured why in M12.1.

## What you'll produce

- `ml/train.py`: reads `feat_team_game`, builds one row per game (home vs
  away), trains logistic regression, evaluates on a **held-out season**
- `ml/reports/<run>.json` (gitignored or small): metrics, seasons used,
  feature list, git commit
- Accuracy on the held-out season reported in `docs/notes/m12.md` (the
  acceptance criterion), next to baselines

## Steps

### 1. Decide the split and the baselines (hand, 20 min)

- **Train:** all complete seasons except the last. **Test:** the last
  complete season. Never a random split (M12 overview, gotchas).
- **Per league or pooled?** NBA, WNBA and college differ a lot (home
  advantage, schedule length). Start with one model per league, or a
  pooled model with a `league` feature. Write which and why.
- **Baselines** to beat, computed on the same test season:
  1. always pick the home team
  2. pick the team with the better win % before tip-off (M12.1)

A model that can't beat baseline 2 isn't adding anything.

### 2. Add dependencies

```bash
uv add --dev scikit-learn pandas
```

(Dev group because nothing in production imports them yet. Revisit if

### 3. Prompt the agent

> Write `ml/train.py` for this repo. Input: the `feat_team_game` table in
> the DuckDB file at env var `SIDELINE_WAREHOUSE_DB` (read-only). It has
> one row per (league, game_id, team_id) with `prediction_ts`, a
> `home_away` column, the label `team_won`, and features: *(list yours)*.
>
> Steps: (1) pivot to one row per game: home features, away features, and
> their differences; label = home team won. (2) Train scikit-learn
> `LogisticRegression` inside a `Pipeline` with `StandardScaler`, on
> seasons `< test_season`; evaluate on `test_season` only (CLI arg,
> default: latest complete season). (3) Report accuracy, log loss and
> Brier score for the model and for two baselines: always-home, and
> better pre-tip-off win %. (4) Write a JSON report with metrics, row
> counts per split, feature names, coefficients, and `git rev-parse HEAD`.
> Fix the random seed. Typed functions; `make lint` and `make typecheck`
> pass. No hyperparameter search.

### 4. Review it like a pull request

| Review question | What good looks like |
|---|---|
| Is the split by season, with test seasons never touching training? | `season < test_season` for train; scaler fitted on train only (inside the `Pipeline`) |
| Where is the scaler fitted? | Inside the pipeline on training data. Fitting it on all data leaks test-set statistics |
| How are home/away rows paired? | Join on `game_id`; assert exactly one home and one away row per game, and count the games dropped |
| Are NULL features handled the same in train and test? | One imputation rule, fitted on train |
| Are the baselines computed on exactly the same test rows? | Same games, same count printed |
| Is the run reproducible? | Seed fixed, commit hash and seasons in the report |
| Does it re-check leakage? | Ideally it refuses to run if the M12.3 test fails (or CI guarantees that) |

<details>
<summary>Hint · Things agents often get wrong here</summary>

- `train_test_split(..., shuffle=True)`: the default, and wrong for time data.
- `StandardScaler().fit(X)` on everything before splitting.
- Dropping NULL rows silently, so early-season games vanish from the test
  set and accuracy looks higher than it is.
- Reporting accuracy only. Accuracy hides whether probabilities are
  sensible; log loss and Brier score don't.

</details>

### 5. Run it and read the numbers

```bash
uv run python ml/train.py --test-season 2026
```

✅ **Checkpoint:** the model beats always-home, and is close to or above
the pre-tip-off win % baseline.

For a sense of scale: a quick reference run with just three NBA
differences (last-10 win %, last-10 point margin, rest days), trained on
2021-22 to 2024-25 and tested on 2025-26 (1,231 games), scored **0.647**
accuracy and 0.621 log loss, against 0.555 for always-home. Your numbers
will differ with your features; much higher than ~0.70 for NBA games
should make you suspicious, not happy. Rerun the M12.3 test.

## Gotchas

- **Coefficient signs are a free sanity check.** A positive coefficient on
  "away team's recent win %" for predicting a home win means something's
  wrong with your pivot.
- **COVID-affected seasons** (2019-20 bubble, 2020-21 limited crowds)
  have unusual home advantage. Note it if your training range includes them.
- **Don't tune on the test season.** If you change features after seeing
  test results, you've started fitting the test set. Hold out a second,
  newer season later if you iterate a lot.
