## Why this matters

Most ML failures in production aren't bad models. They're bad data: a
feature that quietly used information from the future during training,
so the model looked brilliant offline and fell apart live. Data engineers
own that failure, because they build the joins. "Explain leakage with an
example" is the M12 ready-when check and a frequent interview question
for data roles near ML.

### 2. Predict before you query (10 min)

### 3. Rebuild the demo yourself (60 min)

Open `.data/practice.duckdb` and build both versions for NBA regular
seasons 2022 to 2026.

<details>
<summary>Hint 1 · Nudge</summary>

You need, for each team and each game, its win % **as of just before**
that game. That's a running average (M1.4) stored per team and
timestamp, then looked up by the game's tip-off time.

</details>

<details>
<summary>Hint 2 · Approach</summary>

1. `running`: one row per team-game with the win % **after** that game
   (window over `game_date_time`, frame up to `current row`).
2. For each game, `ASOF LEFT JOIN running` on team and season with
   `running.game_date_time < game.game_date_time`. That returns the latest
   row strictly before tip-off.
3. First game of a season: no prior row, so `NULL`. Decide on a default
   (0.5 is a fair "no information").
4. Naive version: join to one row per team-season with the final win %.
5. Predict home win if home win % ≥ away win %; compare with `team_winner`.

Remember the All-Star filter from M1.3.

</details>

<details>
<summary>Solution (open only after you have your own)</summary>

```sql
with tg as (
    select game_id, season, game_date_time, team_id, team_home_away, team_winner
    from nba_team_box
    where season between 2022 and 2026 and season_type = 2
    qualify count(*) over (partition by team_id, season) >= 20      -- drop All-Star "teams"
),
running as (          -- win % AFTER each game, stamped with that game's tip-off
    select team_id, season, game_date_time,
           avg(team_winner::int) over (partition by team_id, season order by game_date_time
                                       rows between unbounded preceding and current row) as win_pct_after
    from tg
),
season_final as (     -- the leak: computed from the whole season
    select team_id, season, avg(team_winner::int) as win_pct_final from tg group by all
),
games as (
    select h.game_id, h.season, h.game_date_time, h.team_id as home_id, a.team_id as away_id,
           h.team_winner as home_won
    from tg h join tg a on a.game_id = h.game_id and a.team_home_away = 'away'
    where h.team_home_away = 'home'
),
naive as (
    select g.*, hf.win_pct_final as h_wp, af.win_pct_final as a_wp
    from games g
    join season_final hf on hf.team_id = g.home_id and hf.season = g.season
    join season_final af on af.team_id = g.away_id and af.season = g.season
),
pit as (
    select g.*, coalesce(hr.win_pct_after, 0.5) as h_wp, coalesce(ar.win_pct_after, 0.5) as a_wp
    from games g
    asof left join running hr
        on hr.team_id = g.home_id and hr.season = g.season and hr.game_date_time < g.game_date_time
    asof left join running ar
        on ar.team_id = g.away_id and ar.season = g.season and ar.game_date_time < g.game_date_time
)
select 'naive (season-final win %)' as features, count(*) as games,
       round(avg(((h_wp >= a_wp) = home_won)::int), 3) as accuracy from naive
union all
select 'point-in-time (as of tip-off)', count(*), round(avg(((h_wp >= a_wp) = home_won)::int), 3) from pit
union all
select 'always pick home', count(*), round(avg(home_won::int), 3) from games;
```

When this lab was written it returned 0.676 naive, 0.631 point-in-time
and 0.553 always-home over 6,153 games. Small differences are fine if
the source data was re-published since.

</details>

✅ **Checkpoint:** naive accuracy is clearly higher than point-in-time.
If they're equal, your "before tip-off" isn't before tip-off: check
`<` versus `<=`.

## Session 2 · Stores, embeddings, retrieval (2 hours)

### 5. Offline vs online stores (45 min)

notes:

- What does the offline store hold, and what's it used for?
- What does the online store hold, and what latency does it need?

  (Name: training/serving skew. You met it in M11.1.)

  precompute features for each scheduled game once, before tip-off? Pick
  one and say why.

### 6. Embeddings and retrieval (45 min)

sections) and the sentence-transformers quickstart. Then write, in your
own words:

- What an embedding is, in one sentence.
- Why similarity search needs an index at scale (HNSW vs IVFFlat: one
  line each).
- Why retrieval quality is measured separately from answer quality
  (recall@k: did the right document come back in the top k?).
