## Why this matters

"It seemed to work when I tried it" is how retrieval systems ship and
then quietly degrade. An evaluation set turns "seems fine" into a number
you can track: when you change the chunking, the embedding model or the
filters, the score tells you whether it got better. It's the same idea as
a test suite and a benchmark, applied to search. Interviewers increasingly
ask "how would you evaluate a RAG system?", and the answer starts here.

## What you'll produce

- `ml/retrieval/eval/questions.yaml`: **20 questions**, each with the
  expected answer and the expected source document(s)
- `ml/retrieval/eval/run_eval.py`: runs every question through retrieval
  and scores it
- `ml/retrieval/eval/history.csv`: one row per eval run, so the score is
  **recorded and tracked** (the acceptance criterion)

## Steps

### 1. Write the questions by hand (60 min)

This is the part that can't be delegated: an agent writing questions
from the same documents tends to mirror their wording, which makes
retrieval look better than it is.

For each question, record:

```yaml
- id: q01
  question: Who led the Celtics in scoring in their season opener?
  filters: { league: nba, date: 2023-10-25 }
  expected_sources: [<document id or source_ref>]
  expected_answer: "..."         # checked against your marts, not the recap
  type: lookup
```

Mix the types on purpose, roughly:

| Type | Example shape | How many |
|---|---|---|
| Direct lookup | "Final score of game X?" | 6 |
| Paraphrase | Asks for a fact using words that aren't in the document | 5 |
| Filter-dependent | Same team, different date, so only the filter gets it right | 4 |
| Cross-league | A WNBA or college question | 3 |
| **No answer** | A question whose answer isn't in any document | 2 |

✅ **Checkpoint:** every `expected_answer` was verified against your
gold tables (a SQL query you can show), and the "no answer" questions
really have no matching document.

### 2. Choose the metrics (20 min)

For retrieval (did the right document come back?):

- **Recall@k:** share of questions where an expected source is in the
  top k (use k = 5, matching the endpoint).
- **MRR (mean reciprocal rank):** average of 1 / rank of the first
  expected source (0 if absent). Rewards putting it first.

For the endpoint as a whole:

- **No-answer handling:** for the "no answer" questions, did it decline
  rather than return something confident?
- **Answer correctness** (only if `answer` uses a language model): does
  it match `expected_answer`? Check by hand for 20 questions; that's fine
  at this size.

<details>
<summary>Solution · the scoring core (compare after writing yours)</summary>

```python
from dataclasses import dataclass


@dataclass
class Result:
    question_id: str
    ranked_ids: list[str]
    expected: set[str]


def reciprocal_rank(ranked_ids: list[str], expected: set[str]) -> float:
    for rank, doc_id in enumerate(ranked_ids, start=1):
        if doc_id in expected:
            return 1.0 / rank
    return 0.0


def score(results: list[Result], k: int = 5) -> dict[str, float]:
    answerable = [
        r for r in results if r.expected
    ]  # "no answer" questions have no expected sources
    hits = [any(d in r.expected for d in r.ranked_ids[:k]) for r in answerable]
    return {
        f"recall@{k}": sum(hits) / len(answerable),
        "mrr": sum(reciprocal_rank(r.ranked_ids[:k], r.expected) for r in answerable)
        / len(answerable),
        "n_answerable": float(len(answerable)),
    }
```

No-answer questions are scored separately (did the endpoint decline?),
because "retrieved nothing relevant" is the *correct* outcome for them.

</details>

### 4. Run it, then change one thing

Run the eval and record the baseline. Then change **one** setting

run again. Record both rows in `history.csv`.

✅ **Checkpoint:** two rows in the history, and you can explain the
difference. (Removing the date filter should hurt filter-dependent
questions. If it doesn't, those questions aren't testing what you think.)

## Gotchas

- **Expected answers from the recap text.** If the recap template has a
  bug, a question checked against the recap passes anyway. Check answers
  against the marts.
- **IDs that change.** If ingestion ids aren't deterministic (M12.6), a
  re-ingest breaks every `expected_sources` entry. Another reason for
  hashed ids.
- **Twenty is small.** One question moves recall@5 by 5 points. Report
  the count alongside the score, and don't over-read small changes.
