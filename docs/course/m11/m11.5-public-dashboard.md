# M11.5 · Public dashboard

> **Ticket:** [#148](https://github.com/Dfscashline21/sideline/issues/148) ·
> **Mode:** agent: the agent drafts, you review it like a junior's PR ·
> **Time:** 4 to 6 hours · **Needs:** M5 marts; M8 for the live view

## Why this matters

The epic says it plainly: the live dashboard URL is **the first thing
recruiters click**. It has to load fast, look intentional, and show the
three things that make Sideline unusual: trends over time, comparison
*across leagues* (the crosswalk from M3.4), and a live game view (M8).

The engineering problem hiding inside it: a hosted app on the internet
can't read your laptop's MinIO or `.data/`. Getting the right data to the
right place, cheaply and safely, is the actual work.

## What you'll produce

- `serving/dashboard/`: the app (Streamlit in the examples; Evidence is a
  good static-site alternative)
- A **public URL** that loads in **under 3 seconds** (both acceptance criteria)
- A link to it at the top of the README's pitch section

## Steps

### 1. Decide how data reaches the hosted app (hand, 45 min)

This decision is yours, not the agent's. Options:

| Option | How | Trade-off |
|---|---|---|
| **Small exports shipped with the app** | A pipeline step writes compact Parquet files for the dashboard (team trends, player comparison) | Simple, fast, free. Data refreshes only when you redeploy or re-export |
| **Exports in public object storage** | Same Parquet files uploaded to a public-read bucket prefix (M10 S3); the app reads by URL with DuckDB | Refresh without redeploy. You must be sure nothing private is in that prefix |
| **The API from M11.3, hosted** | Dashboard calls your API | One source of truth; you now host and pay for the API too |
| **Live game view** | Reads the M8 output (Iceberg sink or a small "latest state" table) | Needs something reachable from the internet; a replayed game from a snapshot is acceptable for a portfolio |

Write your choice and reason in `docs/notes/m11.md`. Make the exports
**pre-aggregated**: the dashboard should never aggregate millions of rows
on page load.

✅ **Checkpoint:** the total data the dashboard loads is a few MB at
most, and you know exactly which columns are in it (no PII from M10.8).

### 2. Sketch the pages (hand, 30 min)

On paper, three views, each answering one question:

1. **Team trends**: how has a team's net rating (or win %) moved this
   season and across seasons?
2. **Player comparison across leagues**: pick two players (e.g. a college
   player and the same person in the NBA via the crosswalk); show per-game
   stats side by side.
3. **Live game view**: score, win probability over time from M8.6, the
   latest events.

For each chart, write the question it answers in one line. Charts without
a question get cut.

### 3. Prompt the agent

> Build a Streamlit dashboard in `serving/dashboard/app.py` for this
> repo. It reads these Parquet files with DuckDB: *(list files and
> columns)*. Data location comes from env var `SIDELINE_DASHBOARD_DATA`
> (a local folder or an https/s3 URL prefix).
>
> Pages: *(paste your three sketches with the question each chart
> answers)*.
>
> Requirements: cache data loads with `st.cache_data` (with a TTL);
> no aggregation over more than ~100k rows at runtime; every chart has a
> title that states the question; league selector on every page; works
> with no live data available (show "no game in progress" instead of
> crashing). Typed functions; `make lint` and `make typecheck` pass. Put
> dashboard-only dependencies in a `requirements.txt` inside
> `serving/dashboard/` for the hosting platform, and explain why it
> can't just use `uv.lock`.

### 4. Review it

| Review question | What good looks like |
|---|---|
| What runs on every page load? | Only cached reads of small files; nothing that recomputes from raw facts |
| What's in the data files? | Exactly the columns you listed; no names of private people, no secrets, no PII |
| What happens when a file or the live feed is missing? | A friendly message, not a stack trace (a public stack trace leaks paths) |
| Are cache TTLs sensible? | Matches how often the exports refresh |
| Do charts answer the stated questions? | Axis labels, units, league in the title |

### 5. Deploy and measure

Deploy to a free host (Streamlit Community Cloud deploys from a GitHub
repo; Evidence builds a static site you can host on GitHub Pages or
Netlify). Then measure load time **from a cold browser**:

- Open the URL in a private window with DevTools → Network, "Disable
  cache" ticked. Record the time until the first chart is visible, three
  times.
- Or run Lighthouse (DevTools → Lighthouse) and record its numbers.

✅ **Checkpoint:** under 3 seconds, warm app, cold browser. Record the
numbers and method in your notes.

<details>
<summary>Hint · If it's slow</summary>

- **Free hosts put idle apps to sleep.** The first visitor after a quiet
  period waits for a cold start, far longer than 3 seconds. Decide how
  you'll handle that (a scheduled ping, a paid tier, or a static site
  that has no server to wake) and say so honestly in the README.
- **Large files.** Check the network tab for the biggest download.
  Pre-aggregate further, or drop columns.
- **Too many charts on the first page.** Load the others on demand
  (separate pages or tabs).

</details>

### 6. Link it

Add the URL to the README's pitch section, the place PF.1 will polish.

## Gotchas

- **Secrets on the host.** If the app needs credentials (e.g. for a
  private bucket), use the host's secrets settings, never a committed
  file. A public dashboard should ideally need none.
- **Sleeping apps** break the "under 3 seconds" claim for the first
  visitor. Be honest in the README about what you measured.
- **`requirements.txt` drift.** The host installs from it, not from
  `uv.lock`. Generate it with `uv export` so versions match.
