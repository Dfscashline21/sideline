# M11.2 · API design (spec before code)

> **Ticket:** [#145](https://github.com/Dfscashline21/sideline/issues/145) ·
> **Mode:** hand · **Time:** 3 hours ·
> **Needs:** M11.1, M5 marts

## Why this matters

An API is a contract. Once an app depends on `/players/{id}/season-stats`,
changing a field name breaks someone's screen. Writing the **OpenAPI spec
first** forces the decisions that are expensive to change later
(resource names, pagination, caching, versioning, error shape) while
they're still cheap. Interviewers love "design an API for X" because it
shows whether you think about consumers or just about tables.

Spec-first also unlocks M11.3: you can hand the spec to an agent and judge
its implementation against something precise.

## What you'll produce

- `serving/api/openapi.yaml`: an OpenAPI 3.1 spec, committed **before**
  any implementation code (the acceptance criterion; the git history
  proves it).
- A short design note in the spec's `info.description`, or in
  `docs/notes/m11.md`, explaining your pagination, caching and versioning choices.

## Steps

### 1. List the consumer questions (20 min)

Don't start from tables. Start from what the app and dashboard will ask.
Write 5 to 8 questions, for example:

- Who is this player, and what are their stats this season?
- How did this player do across every season and league?
- What's this team's record and trend this season?
- List players in a league and season, sorted by points per game.
- What's the live state of game X? (Comes from M8; may be a later version.)

### 2. Turn questions into resources (30 min)

Nouns, plural, nested only one level. Sketch them as a table:

| Method + path | Answers question | Reads table | Returns |
|---|---|---|---|
| `GET /v1/players/{player_id}` | who is this | `dim_player` (current row) | one player |
| `GET /v1/players/{player_id}/season-stats` | stats per season | ? | list |
| `GET /v1/teams/{team_id}/games` | ? | `fact_team_game` | paginated list |
| … | | | |

Think about `player_id`: is it your `player_crosswalk` ID (one per person
across leagues), or a league's own ID? A player who goes from college to
the NBA should be one resource. That's what M3.4 was for.

✅ **Checkpoint:** every endpoint maps to one gold table or a read model
you'll build. If an endpoint needs a 4-table join at request time, design
a read model for it now (and note it as a dbt model to add).

### 3. Decide pagination (30 min)

<details>
<summary>Hint 1 · Nudge</summary>

What happens with offset pagination (`?offset=100&limit=50`) if new games
are inserted while a client is paging? And what does `OFFSET 100000`
cost the database?

</details>

<details>
<summary>Hint 2 · Approach</summary>

Two options:

- **Offset/limit**: simple and allows jumping to page N, but rows shift
  when data changes, and deep pages get slow.
- **Cursor (keyset)**: the response returns `next_cursor` (an opaque
  encoding of the last row's sort key, e.g. `game_date, game_id`); the
  next request asks for rows after it. Stable and fast at any depth, but
  no "jump to page 7".

For a game log that grows over time, a cursor is the stronger answer.
For a 30-row team list, don't paginate at all. Always set a maximum
`limit`.

</details>

### 4. Decide caching (30 min)

Your data changes when the pipeline runs (daily, plus post-game runs from
M6.5), not per request. Use that.

- **HTTP caching:** `Cache-Control: public, max-age=...` and an `ETag`
  per response, so clients and CDNs can skip refetching.
- **Server-side caching:** an in-process or Redis cache keyed by path and
  query, invalidated or expiring when new data lands.

Write down: which endpoints are cacheable, for how long, and what
invalidates them. (A finished game's box score never changes, except for
a stat correction: remember M4.6.)

### 5. Decide versioning and errors (20 min)

- **Versioning:** a path prefix (`/v1/...`) is the easiest to reason
  about and to route. Write the rule for what counts as a breaking change
  (removing or renaming a field, changing a type) versus a safe one
  (adding an optional field).
- **Errors:** one error shape everywhere, e.g. RFC 9457 "problem details"
  (`type`, `title`, `status`, `detail`). Specify the 404 for an unknown
  player and the 400 for a bad cursor.

### 6. Write the spec (60 min)

Write `serving/api/openapi.yaml` by hand. Use `components/schemas` for
`Player`, `SeasonStats`, `Page`, `Problem`, and reference them with
`$ref` so shapes are defined once.

<details>
<summary>Solution · One complete endpoint (compare after writing yours)</summary>

```yaml
  /v1/teams/{team_id}/games:
    get:
      operationId: listTeamGames
      summary: A team's games, newest first, cursor-paginated
      parameters:
        - { name: team_id, in: path, required: true, schema: { type: integer } }
        - { name: season, in: query, schema: { type: integer, example: 2026 } }
        - { name: limit, in: query, schema: { type: integer, minimum: 1, maximum: 100, default: 25 } }
        - { name: cursor, in: query, description: Opaque; copy from next_cursor, schema: { type: string } }
      responses:
        "200":
          description: One page of games
          headers:
            Cache-Control: { schema: { type: string, example: "public, max-age=300" } }
            ETag: { schema: { type: string } }
          content:
            application/json:
              schema:
                type: object
                required: [data, next_cursor]
                properties:
                  data: { type: array, items: { $ref: "#/components/schemas/TeamGame" } }
                  next_cursor: { type: [string, "null"], description: null on the last page }
        "400": { $ref: "#/components/responses/BadRequest" }
        "404": { $ref: "#/components/responses/NotFound" }
```

`type: [string, "null"]` is OpenAPI 3.1 syntax (3.0 used `nullable: true`).

</details>

### 7. Validate it

```bash
uvx --from openapi-spec-validator openapi-spec-validator serving/api/openapi.yaml
```

Then paste the spec into an online viewer (Swagger Editor or Redocly) and
read it as a consumer would. Is every field described? Is there an
example for each response?

✅ **Checkpoint:** the validator passes, and you can answer "what does a
client do to get page 2?" by reading only the spec.

## Ship it

Commit the spec **on its own**, before any implementation, so the history
shows spec-first:

```bash
git switch -c m11.2-api-spec
git add serving/api/openapi.yaml
git commit -m "M11.2: OpenAPI spec for the Sideline API (before implementation)"
```

PR with `Closes #145`.

## Gotchas

- **Leaking table names into the API.** `dim_player_scd2_current` is not
  a resource name. The API is a promise; the warehouse is an
  implementation detail you'll want to change.
- **Floats for IDs, strings for numbers.** Be explicit with types and
  formats (`integer`, `date`, `number`) so generated clients are correct.
- **Unbounded lists.** Every list endpoint needs a maximum `limit`.
