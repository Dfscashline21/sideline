# M11.4 · Load test: p95 under 200 ms

> **Ticket:** [#147](https://github.com/Dfscashline21/sideline/issues/147) ·
> **Mode:** mixed · **Time:** 3 to 4 hours ·
> **Needs:** M11.3 merged, M1.7 (measure → plan → change → measure)

## Why this matters

"It's fast on my laptop" means one user, a warm cache and no
concurrency. A load test tells you what happens when 50 people hit it at
once, and **p95** tells you what the slowest regular users experience.
This is M1.7's loop again (measure, find the bottleneck, change the work,
measure again), applied to a service instead of a query.

## Steps

### 1. Install the tool

```bash
uv add --dev locust
```

Locust is Python, so the test lives next to the code it tests. (k6 is a
popular alternative written in Go with JavaScript scripts; either is
fine for interviews.)

### 2. Design the traffic model (hand, 30 min)

Real traffic isn't one endpoint in a loop. Write down, before any code:

- **Mix:** e.g. 60% player season stats, 25% team games (first page),
  10% team games (page 2+), 5% player detail. Justify it in one line.
- **IDs:** sample real `player_id`s and `team_id`s from your serving DB.
  Hitting one ID measures your cache, not your API. Include some
  unknown IDs too (404s are traffic).
- **Users and ramp:** e.g. 50 concurrent users, ramping up over 30
  seconds, held for 3 minutes.
- **Target:** p95 < 200 ms with an error rate < 1%, measured after ramp-up.

✅ **Checkpoint:** you can explain why your mix looks like a game-night
fan app rather than a benchmark.

### 3. Write the locustfile

The task weights and the ID sampling are yours; the class structure is
boilerplate.

<details>
<summary>Hint · Skeleton</summary>

```python
import random

from locust import HttpUser, between, task

PLAYER_IDS: list[int] = []  # load a sample of real IDs on start
TEAM_IDS: list[int] = []


class Fan(HttpUser):
    wait_time = between(0.5, 2)

    @task(60)
    def season_stats(self) -> None:
        pid = random.choice(PLAYER_IDS)
        self.client.get(f"/v1/players/{pid}/season-stats", name="/v1/players/[id]/season-stats")

    @task(25)
    def team_games(self) -> None: ...
```

`name=` groups requests with different IDs into one line of the report.
Without it, you get one row per ID and no useful percentiles.

</details>

### 4. Run a baseline

Start the API the way it would run in production (no `--reload`), then
run Locust headless and save CSVs:

```bash
mkdir -p .data/loadtest
SIDELINE_SERVING_DB=.data/serving.duckdb uv run uvicorn serving.api.main:app --port 8000 &
uv run locust -f serving/api/loadtest/locustfile.py --headless \
  -u 50 -r 5 -t 3m --host http://localhost:8000 --csv .data/loadtest/baseline
```

Read `.data/loadtest/baseline_stats.csv`: the `95%` column per endpoint
and for `Aggregated`. Record p50, p95, p99, requests per second and
failures in your notes with: laptop model, workers, users, duration,
whether the cache was warm.

✅ **Checkpoint:** you have a baseline table, whatever the numbers are.
If p95 is already well under 200 ms, double your users until it isn't.
You need to see the system bend to learn anything.

### 5. Find the bottleneck (hand)

<details>
<summary>Hint 1 · Nudge</summary>

Is the slow part the database query, Python, or waiting? Compare: a
single request's time (curl with `-w '%{time_total}'`) against the
p95 under load. If one request is fast but p95 is slow, requests are
**queueing**, not computing.

</details>

<details>
<summary>Hint 2 · Usual suspects, in order of likelihood</summary>

1. **Aggregation at request time.** An endpoint that sums or ranks facts
   per call. Fix: a precomputed read model (M1.7 again).
2. **One worker.** Uvicorn runs one process by default. Try
   `--workers 4` (and check your DuckDB connection is opened per worker).
3. **Sync code blocking the event loop.** A DuckDB call inside an
   `async def` endpoint blocks every other request on that worker. Make
   the endpoint a plain `def` (FastAPI runs those in a threadpool), or
   push the call to a thread.
4. **No cache, or a cache that never hits.** Check hit rate under the
   realistic ID mix.
5. **Missing filter pushdown.** `EXPLAIN ANALYZE` the endpoint's query.
   Is it scanning the whole table for one player? Sort or partition the
   read model by the lookup key.

</details>

Change **one thing at a time** and re-run the same test. Keep a row per
run in your notes.

## Gotchas

- **Load generator on the same laptop.** Locust and the API compete for
  CPU. Note it as a limitation; if Locust's CPU warning appears, results
  are suspect.
- **Measuring the cache.** A warm cache with 5 IDs gives a great p95 that
  means nothing. Your ID sample decides what you measured.
- **Averages.** Never report only the average. One slow endpoint at 5%
  of traffic can hide inside a good mean.
