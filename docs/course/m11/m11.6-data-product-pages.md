# M11.6 · Data product pages

> **Ticket:** [#149](https://github.com/Dfscashline21/sideline/issues/149) ·
> **Mode:** mixed · **Time:** 3 hours ·
> **Needs:** M5 marts, M9.6 freshness SLOs, M3.2 grain statements

## Why this matters

A table becomes a **data product** when someone can depend on it without
asking you questions. That needs four facts written down: who owns it,
what one row means (grain), how fresh it is promised to be, and what's
known to be wrong with it. Teams that skip this get the same Slack
questions every week and, worse, silent misuse ("I summed `fact_play`
points and got double the score").

Interviewers ask "how do you make data discoverable and trustworthy?".
These pages are a concrete answer.

## What's hand, what's agent

| Part | Who | Why |
|---|---|---|
| Grain, known issues, intended uses and "do not use for" | **You** | Only the builder knows where the bodies are buried |
| Owner and freshness promise | **You** | They're commitments |
| A script that renders pages from dbt metadata and your YAML | Agent may draft | Templating |
| Column lists and lineage links | Generated | Already in dbt; never retype them |

## What you'll produce

- `docs/data-products/<table>.md`: **one page per gold table** (acceptance criterion)
- `docs/data-products/README.md`: an index
- The hand-written facts stored as metadata next to the model, so pages
  regenerate when the model changes

## Steps

### 1. List your gold tables (15 min)

Gold = everything a consumer is allowed to use: your `marts/` models plus
any read models from M11.3. Write the list. Anything not on it is
internal, and the index should say so.

```bash
ls transform/models/marts/
```

✅ **Checkpoint:** each gold table has a consumer from M11.1's step 4. If
one doesn't, ask whether it should be gold.

### 2. Write the facts by hand (90 min)

For each table, in its dbt YAML under `meta:` (so it lives with the model),
write:

| Field | Example for `fact_team_game` |
|---|---|
| `owner` | your name or a role: who answers questions and fixes it |
| `grain` | "One row per team per game. Key: (`game_id`, `team_id`)." Reuse your M3.2 statement |
| `freshness_slo` | "Updated within 2 hours of a game's final buzzer, 99% of game days" (your M9.6 SLO) |
| `known_issues` | Real ones you've hit. E.g. All-Star games appear as fake teams; NBA Cup final counts as an 83rd regular-season game; ESPN team IDs differ between leagues |
| `intended_uses` | Team trends, API team endpoints |
| `do_not_use_for` | E.g. "player-level stats: use `fact_player_game`" |

<details>
<summary>Hint · What a good "known issues" entry looks like</summary>

Specific, with impact and a workaround:

> Seasons before 2008 have no college data. Cross-league comparisons
> for players who were in college before 2008 will show NBA seasons only.

Not: "Some data may be incomplete."

Look in `docs/incidents/`, your M9 chaos-day notes, and the gotchas
tables in this course. You've already found most of them.

</details>

### 3. Let an agent draft the renderer

> Write `docs/data-products/render.py` that reads
> `transform/target/manifest.json` (after `dbt docs generate`) and, for
> each model in `models/marts/` with `meta.owner` set, writes
> `docs/data-products/<model>.md` with: description, owner, grain,
> freshness SLO, known issues, intended uses, do-not-use-for, the column
> table (name, type, description, tests), upstream models, and a link to
> the hosted dbt docs page (M5.12). Also write an `index` README listing
> every page. Fail with a clear error if a mart is missing any required
> `meta` field. Standard library only; typed; passes `make lint` and
> `make typecheck`.

Review: does it fail loudly when `owner` or `grain` is missing? (A page
with a blank grain is worse than no page.) Does it read tests and column
descriptions from the manifest rather than hard-coding them?

### 4. Add the current freshness

A promise is more useful next to reality. Either have the renderer read
the last measured freshness from your M9.6 SLO table, or link each page
to the M9.10 quality dashboard. Pick one.

### 5. Wire it into the build

Add `make data-products` (generate docs, then render). Consider a CI check
that fails if a new mart is added without `meta.owner` and `meta.grain`.
That's the "can't forget" version.

✅ **Checkpoint:** delete `meta.grain` from one model, run the target and
watch it fail. Put it back.

## Ship it

```bash
make data-products
git add docs/data-products/ transform/models/ Makefile
git commit -m "M11.6: data product pages for every gold table"
```

PR with `Closes #149`. Link the index from the README's architecture or

## Gotchas

- **Hand-typed column lists rot.** If you edit a page by hand, the next
  render overwrites it. Put human facts in `meta`, generate the rest.
- **Owners must be real.** "Data team" isn't an owner when you're the team.
  Use your name.
- **Known issues aren't failures.** Writing them down builds trust; hiding
  them destroys it the first time someone finds one.
