# M11.3 · FastAPI implementation

> **Ticket:** [#146](https://github.com/Dfscashline21/sideline/issues/146) ·
> **Mode:** agent: the agent drafts, you review it like a junior's PR ·
> **Time:** 3 to 4 hours · **Needs:** M11.2 spec merged

## Why this matters

You designed the contract in M11.2. Now an agent writes the
implementation, and your job is the one senior engineers actually do
most: **check the code against the contract**, and make sure the tests
would catch it if it drifted. "All endpoints tested" is the acceptance
bar, and the strongest version of that is a test that checks every
response *against the spec itself*.

## What you'll produce

- `serving/api/` — a FastAPI app implementing every endpoint in
  `openapi.yaml`, with the caching you designed.
- Tests for every endpoint in `serving/api/tests/`.
- `make api` to run it locally.

## Steps

### 1. Prepare the data the API reads

The API should read **gold tables or read models**, never raw facts. Decide
where it reads from:

| Option | Fits when |
|---|---|
| A DuckDB file exported from your marts, opened **read-only** | Local dev and the M11.4 load test |
| Parquet files exported per read model | You want to ship the data with a container or to object storage |
| Your M10.5 cloud warehouse | Not for an API: per-query latency and cost (M11.1) |

Add any read models your spec needs (e.g. `player_season_stats`) as dbt
models in `transform/models/marts/`, built and tested like the rest.
That's your SQL; the agent only writes Python around it.

✅ **Checkpoint:** every endpoint in the spec can be answered by a
`SELECT ... WHERE <key> = ?` on one table.

### 2. Add dependencies

```bash
uv add fastapi uvicorn
uv add --dev httpx schemathesis
```

(`httpx` powers FastAPI's `TestClient`; `schemathesis` generates requests
from your OpenAPI spec and checks responses against it.)

### 3. Prompt the agent

> Implement `serving/api/` for this repo from the OpenAPI spec at
> `serving/api/openapi.yaml`. Use FastAPI. The data is in a DuckDB file
> at the path from env var `SIDELINE_SERVING_DB`, opened read-only; use
> one cursor per request from a shared connection
> (`con.cursor()`), never string-formatted SQL, only `?` parameters.
>
> Requirements:
> - Paths, parameters, response models, status codes and the error shape
>   (`application/problem+json`) must match the spec exactly. Use Pydantic
>   models that mirror `components/schemas`.
> - Cursor pagination as described in the spec.
> - Caching: *(paste your M11.2 caching decisions: which endpoints,
>   lifetimes, `Cache-Control` and `ETag` behaviour, server-side cache)*.
> - Tests in `serving/api/tests/` with `fastapi.testclient.TestClient` and
>   a small fixture DuckDB built in the test (not the real data): happy
>   path, 404, bad cursor, last page, and cache headers for every endpoint.
> - Every function typed; `make lint`, `make typecheck`, `make test` pass.
> - No new dependencies beyond fastapi, uvicorn, httpx, schemathesis.
>
> Explain anything non-obvious in the PR description.

Load `AGENTS.md` into the session first so it follows your conventions.

### 4. Review it like a pull request

Read before running. Answer in writing:

| Review question | What good looks like |
|---|---|
| Does every route's path, method and status code match the spec? | Check them side by side, endpoint by endpoint |
| How is SQL built? | `?` parameters only. No f-strings with request input (SQL injection) |
| How are DuckDB connections handled across threads? | A shared read-only connection with a cursor per request, or a connection per worker. Never one cursor shared by concurrent requests |
| How is the cursor encoded and validated? | Opaque (e.g. base64 of the sort key), decoded with error handling: garbage returns 400, not 500 |
| What does the cache key include? | Path **and** query parameters. Missing a parameter serves one user another's page |
| When does the cache expire or get invalidated? | Matches your M11.2 decision, and the pipeline's refresh schedule |
| Is `ETag` stable for identical data? | Derived from content or data version, not from time |
| Do 404s use the problem+json shape? | Same shape as the spec, everywhere |

<details>
<summary>Hint · Things agents often get wrong here</summary>

- Using `@lru_cache` on a function that takes a request object, which never hits.
- Opening a new DuckDB connection per request (slow), or one cursor shared
  across threads (crashes under load; you'd find it in M11.4).
- Catching all exceptions and returning 200 with an empty list.
- Response models that silently drop fields the spec requires.
- Tests that hit the real `.data/` database, so CI fails (there's no data there).

</details>

### 5. Prove it matches the spec

Unit tests check behaviour you thought of. A spec-based test checks
**everything the spec promises**. Write this one yourself (it's short):

```python
# serving/api/tests/test_contract.py
import schemathesis

schema = schemathesis.openapi.from_path("serving/api/openapi.yaml")
schema.app = ...  # point it at your FastAPI app (see the schemathesis docs for your version)


@schema.parametrize()
def test_api_matches_spec(case: schemathesis.Case) -> None:
    case.call_and_validate()
```

The exact way to attach the app has changed between schemathesis major
versions. Look up "ASGI" or "FastAPI" in the docs for the version `uv`
installed, rather than trusting this snippet or an agent's memory.

✅ **Checkpoint:** run `make test`. If the contract test finds a
mismatch, decide which is wrong, the spec or the code, and fix that one.

### 6. Run it

Add a Make target in the existing style:

```make
api: ## Run the Sideline API locally on :8000
	SIDELINE_SERVING_DB=.data/serving.duckdb $(UV_RUN) uvicorn serving.api.main:app --reload
```

Open `http://localhost:8000/docs`. FastAPI generates its own spec at
`/openapi.json`. Diff it against yours: they won't be byte-identical, but
paths, parameters and schemas should match.

## Ship it

```bash
make lint && make typecheck && make test
git add serving/ transform/ Makefile pyproject.toml uv.lock
git commit -m "M11.3: FastAPI implementation with caching and contract tests"
```

Paste your review table into the PR. PR with `Closes #146`.

## Gotchas

- **`serving/api` must be importable** for `uvicorn serving.api.main:app`.
  Add `__init__.py` files, or run from inside the folder; pick one and
  note it in `AGENTS.md`.
- **The fixture database belongs to the tests.** CI has no `.data/`.
- **Read-only isn't a lock-free swap.** When the pipeline refreshes the
  serving DB, write a new file and rename it into place; don't write into
  the file the API is reading.
