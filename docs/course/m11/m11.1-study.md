# M11.1 · Study: serving patterns

> **Ticket:** [#144](https://github.com/Dfscashline21/sideline/issues/144) ·
> **Mode:** hand · **Time:** 3 to 4 hours ·
> **Needs:** M5 marts exist (you'll reason about real tables)

## Why this matters

Up to now you've built tables. Nobody gets value from a table until
something reads it. "How would you serve this?" is where a data engineer
shows they understand consumers: an analyst in a BI tool, a mobile app
and an ML model all want the *same* numbers, but with completely
different latency, freshness, shape and access needs. Picking the wrong
pattern is how teams end up with a 30-second dashboard or an app hitting
the warehouse on every page view.

## What you'll produce

`docs/notes/m11.md` with:

- one line per serving pattern, in your own words
- a decision table you can reuse
- **three Sideline use cases**, each with the pattern you'd pick and why
  (the acceptance criterion)

## Steps

### 1. Learn the six patterns (90 min)

For each one, find out: who reads it, typical latency, how fresh the data
is, and what breaks when it's overloaded.

| Pattern | What it is | Read up on |
|---|---|---|
| **BI on the warehouse** | Dashboards query the warehouse directly (Snowflake, BigQuery, DuckDB) | Your M10.5 warehouse docs; "BI query performance" |
| **Semantic layer** | Metric definitions in one place (dbt Semantic Layer / MetricFlow, Cube) that every tool queries | dbt docs: "About MetricFlow"; Cube docs intro |
| **OLAP store** | A database built for sub-second aggregations on fresh events (ClickHouse, Druid, Pinot) | ClickHouse "What is OLAP" page |
| **API over a read model** | A service answering key lookups from a precomputed table or cache | Your M11.2/M11.3 labs; "CQRS read model" |
| **Reverse ETL** | Pushing warehouse data *into* operational tools (CRM, ad platforms) | Hightouch or Census "What is reverse ETL" |
| **Feature store** | Offline store for training plus online store for low-latency inference, same definitions | Feast docs: "Concepts"; you'll revisit this in M12.1 |

✅ **Checkpoint:** for each pattern you can say one situation where it's
the *wrong* choice.

<details>
<summary>Hint · Sanity values to compare against</summary>

Orders of magnitude, not exact figures:

- BI on a warehouse: seconds; freshness = last pipeline run; ad-hoc
  aggregations; cost per query scanned.
- API on a read model: tens of milliseconds; freshness = last refresh of
  the read model; key lookups; cost = always-on compute.
- OLAP store: sub-second aggregations over data seconds old; cost =
  running and operating another cluster.
- Reverse ETL: minutes to hours; it pushes rather than serves.
- Feature store online: single-digit to tens of milliseconds per entity
  lookup; offline: batch.

</details>

### 3. Apply it to three Sideline use cases (60 min)

Write one paragraph each. Name the pattern, the table(s) it reads, the
latency and freshness it needs, and one alternative you rejected.

1. **An analyst** wants to explore which lineups perform best, slicing
   by season and league, in a BI tool.
2. **A fan-facing app** shows a player's season stats page, and must load
   fast for thousands of users during a game night.
3. **The M12 win-probability model** needs each team's recent form at
   prediction time, the same values it was trained on.

<details>
<summary>Hint 1 · Nudge</summary>

Ask of each: does the reader know the question in advance (fixed shape)
or explore (ad-hoc)? How many readers at once? Is a 5-minute-old number
acceptable?

</details>

<details>
<summary>Hint 2 · One defensible answer set</summary>

There's more than one right answer; this is one you should be able to
argue against:

1. **BI on the warehouse, through a semantic layer.** Ad-hoc, few users,
   seconds are fine, and metric definitions (e.g. "possessions",
   "TS%") must match everywhere. Rejected: an API (the questions aren't
   known in advance).
2. **API over a read model** (`player_season_stats` keyed by
   `player_id, season`), cached. Fixed shape, many users, tens of ms.
   Rejected: dashboard queries straight to the warehouse (cost and
   latency scale with traffic).
3. **Feature store pattern**: the same feature definitions computed
   offline for training and served online (or precomputed per game) for
   inference. Rejected: having the app recompute features (training and
   serving logic drift apart, called *training/serving skew*).

</details>

### 4. Close the loop with your own data

Look at your `marts/` folder. Mark each gold table with which pattern(s)
