## Why this matters

Every ingestion interview circles back to the same four questions:

1. The API failed. What does your job do?
2. Your job ran twice. What happens to the data?
3. How does tomorrow's run know where today's stopped?
4. Where does the data land, and can you replay it?

This study block gives you precise answers to all four before you write
the extractor, so the code in M2.3 and M2.4 implements ideas you already
understand.

## Session 1 · Retries and exponential backoff (60 min)

**Read:**
[AWS Architecture Blog: Exponential Backoff and Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)
and the
[AWS Builders' Library: Timeouts, retries, and backoff with jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/).

Key ideas to capture:

- **Which failures to retry.** Transient ones only: timeouts, connection
  resets, `429 Too Many Requests`, `5xx`. Never `400`, `401`, `403` or
  `404`: retrying a bad request just makes it fail more slowly.
- **Exponential backoff.** Wait `base × 2^attempt` between attempts, capped
  at a maximum, so a struggling server gets breathing room.
- **A retry budget.** A maximum number of attempts, then fail loudly.
- **Honour `Retry-After`.** If the server tells you when to come back, use it.

### Exercise 1.1

On paper: with `base = 1s`, `cap = 30s` and 6 attempts, what are the

worst-case time before the job gives up?

Waits after attempts 1 to 5 (no wait after the last): 1, 2, 4, 8, 16 s.
Total waiting: 31 s, plus up to 6 request timeouts. Notice the timeout
can dominate. That's why the timeout value matters as much as the backoff.

</details>

## Session 2 · Why jitter matters (60 min)

Backoff alone has a flaw. If 100 clients fail at the same moment (the
server restarted), they all retry after 1 s, then all after 2 s, then all
after 4 s. They stay synchronised, so every retry is another spike. This
is the **thundering herd**.

**Jitter** randomises each wait so retries spread out. The AWS article
compares three flavours. The simplest good one is **full jitter**:

```
sleep = random_between(0, min(cap, base × 2^attempt))
```

## Session 3 · Idempotency (60 min)

**Definition to learn precisely:**

> An operation is **idempotent** if performing it once or many times with
> the same input leaves the system in the same state.

Not "it doesn't crash when run twice". The *resulting state* is identical.

| Operation | Idempotent? | Why |
|---|---|---|
| `PUT s3://bucket/nba/.../0022400061.json` with the same bytes | Yes | Same key, same content, same final state |
| `INSERT INTO games VALUES (...)` | No | A second run adds a duplicate row |
| `INSERT ... ON CONFLICT (game_id) DO UPDATE` | Yes | The key decides the row |
| `PUT .../<uuid4()>.json` | No | A new random key every run means duplicates |
| `UPDATE balance SET amount = amount + 10` | No | Applies twice |
| `UPDATE balance SET amount = 110` | Yes | Same final state |

### Exercise 3.1

For each, say whether it's idempotent and how you'd make it so:

1. A job that appends today's games to a CSV file.
2. A job that writes `raw/games/{datetime.now().isoformat()}.json`.
3. A job that deletes a day's partition, then writes it again (what if
   it crashes between the delete and the write?).

<details>
<summary>Discussion</summary>

1. Not idempotent. Write one file per logical unit (per day, per game)
   with a deterministic name, or deduplicate on read.
2. Not idempotent: the timestamp makes every run's key unique. Derive the
   key from the *input* (the date range, the game ID), not from the clock.
3. Idempotent if it finishes, but not **crash-safe**: a crash in between
   leaves the partition empty. Write the new data somewhere else first,
   then swap. This "write, then commit" idea comes back in M2.4 (watermark
   written last) and M4 (Iceberg snapshots).

</details>

The pattern to remember: **deterministic keys + a commit step written last.**

## Session 4 · Incremental extraction and watermarks (45 min)

**Read:** the "incremental load" and "high watermark" sections of any
data-engineering text you have, or search "high watermark incremental
extraction". *Fundamentals of Data Engineering* (Reis and Housley),
chapter on ingestion, covers it well.

A **watermark** is the furthest point you've loaded, stored so the next
run knows where to start. For Sideline: the last game date fully landed.

Questions to answer in your notes:

1. **When** is the watermark written: before, during or after the data?
   What goes wrong in each case if the job dies halfway?
2. Where does it live? Options: a file next to the data, a database
   table, or derived by listing what's already landed. One advantage and
   one drawback for each.
3. A stat correction changes a game from 3 days ago. A watermark-only
   job never re-reads that game. What's the usual fix? (Look up "lookback
   window". You'll build one in M5.6.)
4. How do **backfills** (`--start/--end`) interact with the watermark?
   Should loading October 2023 change a watermark that says November 2024?
