# M2.2 · Design the raw zone layout

> **Ticket:** [#37](https://github.com/Dfscashline21/sideline/issues/37) ·
> **Mode:** hand · **Time:** 90 min ·
> **Needs:** M2.1 sessions 3 and 5 (idempotency, raw zone)

## Why this matters

The raw zone is the one part of the platform you can never rebuild from
something else. If a transform is wrong, you rerun it from raw. If raw is
wrong or missing, the data is gone. Its layout decides whether you can:

- replay any past run exactly as the API returned it,
- rerun a failed job without creating duplicates,
- find "everything we received on 3 November" in one prefix listing,
- add WNBA (M6) and college (M7) without redesigning anything.

"Design a storage layout for raw API data" is a common system-design
warm-up question. This lab is your answer, written down.

## What you'll produce

A **Raw zone** section in `ingestion/README.md` that documents:

- the key template, with every path segment explained
- file naming and format
- how re-runs avoid overwriting history (the acceptance criterion)
- where state (watermarks) and quarantined records live
- two worked example keys

## Steps

### 1. List what the layout must support

Before choosing anything, write the requirements as a short list. At
minimum:

- Several sources (`nba_api` now, maybe `espn` later), several leagues,
  several entities (game list, box score, play-by-play).
- Daily incremental runs **and** backfills of arbitrary date ranges.
- Re-running the same job: no duplicates.
- Re-running on a later day: keeps the earlier copy (history).
- Cheap listing: "everything ingested on day X" and "every play-by-play
  file for league Y" should each be one prefix.

### 2. Choose the segment order

The ticket suggests `source/league/entity/ingest_date`. The contract
default for these labs is `league/source/entity/ingest_date`. Either can
be right. Decide by asking which prefix you'll list most often.

<details>
<summary>Hint 1 · Nudge</summary>

S3 and MinIO list by **prefix**: you can cheaply list everything under
`a/b/`, but not "everything where the second segment is `b`". Put the
segment you filter on most often first.

Who reads the raw zone? Downstream jobs, which are organised per
league (M6 adds a WNBA pipeline, M7 college). Debugging a broken source
is organised per source.

</details>

<details>
<summary>Hint 2 · The trade-off in one table</summary>

| Order | Cheap to list | Awkward to list |
|---|---|---|
| `league/source/...` | Everything for the NBA, across sources | One source across all leagues |
| `source/league/...` | Everything from `nba_api`, across leagues | One league across sources |

Write down which you chose and why. That sentence goes in the README.

</details>

### 3. Partition by ingest date, in Hive style

Use `ingest_date=YYYY-MM-DD` as a path segment, not a bare date.

- **Ingest date, not game date.** The raw zone records *what we received
  and when*. A backfill run today of 2003 games lands under today's ingest
  date; the game date lives inside the data. That's what lets you answer
  "what did the API give us on 3 November?" during an incident.
- **`key=value` naming** (Hive style) lets DuckDB, Spark and Iceberg
  tooling read the partition as a column automatically
  (`hive_partitioning=true` in DuckDB).

### 4. Make re-runs safe: the run ID

This is the core design decision. Two requirements pull in different
directions:

- **Idempotent:** the same run, repeated (e.g. after a crash), must not
  create duplicates.
- **History:** a run on a later day must not overwrite the earlier copy.

<details>
<summary>Hint 1 · Nudge</summary>

What if part of the key came from the **request** (which dates you asked
for) and part from **when** you asked (the ingest date)?

</details>

<details>
<summary>Hint 2 · Approach</summary>

Make `run_id` deterministic from the run's input, e.g.
`run_id = <start>-<end>` of the requested game-date range:

- Same request, same day (a restart): same `ingest_date`, same `run_id`,
  so the **same keys**. Objects already written are skipped or
  overwritten with identical bytes. No duplicates.
- Same request, a later day: a new `ingest_date`, so **new keys**. The
  earlier copy is untouched. That's history.

Contrast with `run_id = uuid4()` or a timestamp: every restart writes a
fresh set of keys, which is exactly the duplicate problem M2.7 tests for.

</details>

### 5. Decide file naming and format

- One JSON file per API response, **bytes exactly as received** (no
  pretty-printing, no re-serialising: that's M2.8's ADR).
- Name files by what they contain: `game_log.json` for a list response,
  `<game_id>.json` for per-game responses. Game IDs keep their leading
  zeros.
- Compression: optional. If you gzip, say so in the extension
  (`.json.gz`) and decide now. Changing it later means every reader changes.

### 6. Place state and quarantine outside the data

Prefixes starting with `_` are a common convention for "not data":

- `_state/<league>/<source>/watermark.json`: the M2.4 watermark
- `_quarantine/<league>/<source>/<entity>/ingest_date=…/<run_id>/…`:
  M2.5's rejected records
- `.../<run_id>/_manifest/manifest.json`, or a `_manifest` entity: a
  record of what a run contains, written **last**

Why keep them out of the entity prefixes? So `list everything under
nba/nba_api/playbyplay/` returns only play-by-play files.

### 8. Encode it in one function

Even though M2.3 is where code starts, write the key builder now, so the

<details>
<summary>Solution (open only after you have your own)</summary>

```python
from datetime import date


def raw_key(
    league: str, source: str, entity: str, ingest_date: date, run_id: str, name: str
) -> str:
    return f"{league}/{source}/{entity}/ingest_date={ingest_date.isoformat()}/{run_id}/{name}.json"
```

```python
def test_raw_key() -> None:
    key = raw_key(
        "nba", "nba_api", "playbyplay", date(2024, 10, 24), "20241022-20241023", "0022400061"
    )
    assert key == "nba/nba_api/playbyplay/ingest_date=2024-10-24/20241022-20241023/0022400061.json"
```

</details>

## Gotchas

- **Leading zeros.** If any code path turns a game ID into an `int`, the
  key changes and you get "duplicates" that are really two spellings of
  one game.
- **Dates in keys.** Always ISO format (`2024-10-24`). It sorts correctly as
  text; `10/24/2024` doesn't.
- **Don't encode the run time in the key** (e.g. `run_at=14-03-22`). It
  breaks idempotency for the same reason a UUID does.
