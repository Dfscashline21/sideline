# M2.4 · Incremental loads with watermarks and `--start/--end`

> **Ticket:** [#39](https://github.com/Dfscashline21/sideline/issues/39) ·
> **Mode:** hand · **Time:** 3 to 4 hours ·
> **Needs:** M2.1 session 4, M2.3 merged

## Why this matters

A pipeline that reloads everything every day doesn't scale and hammers
the source. A pipeline that loads only "new" data needs to remember where
it stopped, which is the **watermark**. And every incremental pipeline
eventually needs a **backfill**: a bug fix, a new column, a missing week.

The interview question is: *"How does your job know what's new, and how
do you reload last March without breaking tomorrow's run?"* After this
lab you'll answer it with code you wrote.

## What you'll produce

- `ingestion/sideline_ingestion/watermark.py`: read, write and range logic.
- `ingestion/sideline_ingestion/cli.py`: no arguments = daily incremental
  run; `--start/--end` = backfill of any range.
- Tests for both modes and for the edge cases below.

## Steps

### 1. Decide the watermark's meaning, home and timing (20 min)

Write three sentences in `ingestion/README.md` under a **Watermark**
heading:

1. **Meaning.** "The last game date whose games have *all* landed." Not
   "the last date we ran", and not "the last game we saw".
2. **Home.** The contract default is a small JSON object in the raw
   bucket, `_state/nba/nba_api/watermark.json`. It lives next to the data
   it describes and needs no extra service. (The alternatives, a Postgres
   table or listing the raw zone, are fine too. Name the one you rejected
   and why.)
3. **Timing.** Written **last**, after every object for the run has
   landed. A crash before that point leaves the old watermark, so the next
   run redoes the unfinished work.

### 2. Read and write the watermark (30 min)

Two small functions over the `ObjectStore` protocol from M2.3:

```python
def read_watermark(store: ObjectStore, league: str, source: str) -> date | None: ...
def write_watermark(store: ObjectStore, league: str, source: str, last: date) -> None: ...
```

`None` means "never loaded". Test the round trip with `MemoryStore`.

### 3. Work out the range to load (60 min)

This is the core logic. Write it as a **pure function** (no I/O, no
clock) so every case is a one-line test:

```python
def resolve_range(
    start: date | None, end: date | None, watermark: date | None, today: date, first_day: date
) -> tuple[date, date]: ...
```

Rules to implement:

| Input | Range |
|---|---|
| `--start` and `--end` given | exactly that range (a backfill) |
| only one of them given | error: they go together |
| `--start` after `--end` | error |
| neither, watermark exists | day after watermark → yesterday |
| neither, no watermark | `first_day` → yesterday |

Why yesterday, not today? Today's games haven't finished, and landing a
half-played game's play-by-play then advancing the watermark past it
would skip the rest of the game for ever.

<details>
<summary>Hint · "Already up to date"</summary>

If the watermark is yesterday, the daily range is `today → yesterday`:
start is after end. Don't treat that as an error in `resolve_range`.
Return it and let the caller log "up to date, nothing to load" and exit 0.
A scheduled job that fails every time there's nothing new will be
switched off by someone, and then it won't run when there *is* something new.

</details>

<details>
<summary>Solution (open only after you have your own)</summary>

```python
def resolve_range(
    start: date | None, end: date | None, watermark: date | None, today: date, first_day: date
) -> tuple[date, date]:
    """Explicit --start/--end wins; otherwise load from the day after the watermark to yesterday."""
    if start is not None or end is not None:
        if start is None or end is None:
            raise ValueError("--start and --end must be given together")
        if start > end:
            raise ValueError("--start must not be after --end")
        return start, end
    begin = watermark + timedelta(days=1) if watermark else first_day
    return begin, today - timedelta(days=1)
```

</details>

✅ **Checkpoint:** five tests, one per table row, all passing.

### 4. Backfills must not move the watermark backwards (30 min)

Scenario: the watermark says 9 November 2024. You backfill October 2003.
If the run then writes `watermark = 2003-10-31`, tomorrow's daily run
reloads twenty-one years.

Rule: **only advance the watermark, never move it back.** Read the
current value at the end of `nba.run` and write `end` only if it's later.

Write the test first:

```python
def test_backfill_does_not_move_watermark_back() -> None:
    store = MemoryStore()
    nba.run(FakeApi(), store, date(2024, 11, 1), date(2024, 11, 9), date(2024, 11, 10))
    nba.run(FakeApi(), store, date(2024, 10, 22), date(2024, 10, 23), date(2024, 11, 10))
    assert read_watermark(store, "nba", "nba_api") == date(2024, 11, 9)
```

(`FakeApi` is a callable that returns canned bytes. Write a minimal one
now; M2.6 replaces it with recorded fixtures.)

<details>
<summary>Hint · Is a backfill of a gap safe?</summary>

What if the daily run has been broken since 1 November, the watermark is
31 October, and you backfill 10 to 15 November? With the rule above, the
watermark jumps to 15 November and 1 to 9 November is never loaded. Two
options: (a) backfills never touch the watermark at all, or (b) only
advance when the backfill **starts at or before** watermark + 1 day. Pick
one, implement it, and write down why. Both are defensible.

</details>

### 5. "Any range" means across seasons too (45 min)

`leaguegamelog` takes one `Season`. A first run from 2001 to today, or a
backfill from June to November, spans several. Split the range at each
1 October and run each piece separately:

```python
def split_by_season(start: date, end: date) -> list[tuple[date, date]]: ...
```

<details>
<summary>Solution (open only after you have your own)</summary>

```python
def split_by_season(start: date, end: date) -> list[tuple[date, date]]:
    """Cut a date range at each 1 October so every piece sits inside one NBA season."""
    pieces: list[tuple[date, date]] = []
    while start <= end:
        next_season = date(start.year if start.month < 10 else start.year + 1, 10, 1)
        piece_end = min(end, next_season - timedelta(days=1))
        pieces.append((start, piece_end))
        start = piece_end + timedelta(days=1)
    return pieces
```

Each piece gets its own `run_id` and advances the watermark when it
finishes. A crash in piece 7 of 24 leaves pieces 1 to 6 committed.

</details>

Note: `SeasonType=Regular Season` excludes playoffs. Decide whether your
extractor loops over `Regular Season` and `Playoffs` too, and write the
decision in `ingestion/README.md`.

### 6. The CLI (45 min)

`ingestion/sideline_ingestion/cli.py` with `argparse`:

- `--start` and `--end`, parsed with `type=date.fromisoformat` so bad
  dates fail at the command line, not halfway through a run
- reads the watermark, resolves the range, logs it, then runs each
  season piece
- exits 0 with an "up to date" message when there's nothing to load

<details>
<summary>Solution skeleton (open only after you have your own)</summary>

```python
def main(argv: list[str] | None = None) -> None:
    logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")
    args = parse_args(argv)
    store = S3Store("sideline-raw")
    today = date.today()
    watermark = read_watermark(store, nba.LEAGUE, nba.SOURCE)
    start, end = resolve_range(args.start, args.end, watermark, today, FIRST_DAY)
    if start > end:
        logging.info("up to date: watermark %s, nothing to load", watermark)
        return
    fetch = functools.partial(fetch_raw, requests.Session())
    for piece_start, piece_end in nba.split_by_season(start, end):
        nba.run(fetch, store, piece_start, piece_end, ingest_date=today)
```

`date.today()` is called once, in `main`, and passed down. Everything
below `main` takes dates as arguments, which is why it's all testable.

</details>

## Gotchas

- **Time zones.** NBA game dates are US Eastern. `date.today()` on a
  laptop in another time zone (or a UTC server in M10) can be a day ahead.
  Decide which "today" you mean and use it in one place.
- **Watermark ≠ ingest date.** The watermark is a *game* date. The
  ingest date in the key is the *run* date. Don't mix them up in code.
- **Stat corrections.** A watermark-only design never re-reads old games.
  That's acceptable for raw landing now. M5.6 adds a 3-day lookback
  downstream; mention it in your README as a known limitation.
