# M2.8 · ADR-001: Why we land raw data unchanged

> **Ticket:** [#43](https://github.com/Dfscashline21/sideline/issues/43) ·
> **Mode:** hand · **Time:** 90 min ·
> **Needs:** M2.2 (the decision), M2.5 (the quarantine trade-off)

## Why this matters

An **Architecture Decision Record** (ADR) is a short document that
records one significant decision: the context, what was decided, what
else was considered, and what follows from it. Teams write them so that
in a year, someone can learn *why* things are the way they are without
finding the person who decided.

ADRs are also interview gold. "Tell me about a technical decision you
made and the alternatives" is a standard senior question, and each ADR
is a prepared answer. This is the first of six in the curriculum, so
it also sets the format the others follow.

## What you'll produce

`docs/adr/001-raw-data-unchanged.md`, naming at least two alternatives
and why they lost.

## Background: the format

These labs use Michael Nygard's original format, the most widely used:

```markdown
# ADR-001: Land raw data unchanged

- Status: Accepted
- Date: YYYY-MM-DD
- Deciders: <you>

## Context
What problem forced a decision. Facts and constraints, no opinions yet.

## Decision
One or two sentences, in the active voice: "We will ..."

## Alternatives considered
Each option, with why it lost.

## Consequences
What becomes easier, what becomes harder, what we must now do.
```

Read Nygard's short post
[Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)
for the reasoning behind each section.

## Steps

### 1. Write the context (20 min)

Facts only. What's true about Sideline that forces a decision about
storing API responses? Prompts:

- The sources are unofficial, undocumented APIs that change without notice.
- Downstream models (M3, M5) don't exist yet, so you don't know every
  field you'll need.
- Bugs in parsing code are inevitable. What happens to data parsed
  wrongly if the original is gone?
- Reloading history from the API is slow and rate-limited. How long
  would refetching every game since 2002 take at a polite request rate?
  Estimate it from your M2.3 logs.

✅ **Checkpoint:** someone who has never seen Sideline understands from
the context alone why this decision needed making.

### 2. Write the decision (10 min)

One or two sentences. What exactly is "unchanged"? Bytes as received, not
re-serialised, not reformatted, not filtered. Say whether compression
counts as a change (it's lossless, so most teams say no) and whether the
M2.5 quarantine is part of the decision.

### 3. Write the alternatives (30 min)

The ticket requires at least two, each with why it lost. Candidates:

| Alternative | Its genuine strength | Why it might lose |
|---|---|---|
| Parse on ingest and store only clean, typed tables (Parquet/Postgres) | Smaller, faster to query, one less layer | A parsing bug destroys information; new fields need a refetch |
| Store parsed JSON (re-serialised, pretty-printed) | Easier to read by eye | Not what the API sent; key order and number formats change; harder to prove what you received |
| Store only the fields we use now | Minimal storage | Every new requirement means a historical refetch |
| Don't store raw at all; transform in flight | Simplest pipeline | No replay, no audit, no debugging of past runs |

Give each alternative its **best** case before saying why it lost. An ADR
that strawmans the alternatives doesn't convince anyone, including an
interviewer.

<details>
<summary>Hint · Make the losses concrete</summary>

Tie each loss to something in Sideline:

- "In M4.5 we add shot coordinates. If we'd stored only the fields we
  used in M2, that's a refetch of every game since 2002."
- "In M2.5 we found <whatever you found>. With parse-on-ingest, those
  records would have been lost or silently coerced."

Concrete beats abstract every time.

</details>

### 4. Write the consequences (20 min)

Both kinds, honestly:

- **Easier:** replay any transform from source, audit what the API sent
  on any date, add fields later without refetching.
- **Harder:** storage grows with every run (history is kept), every
  reader must parse raw JSON, schema drift is caught later (downstream)
  unless you validate at the edge (which M2.5 does).
- **Now required:** raw objects are immutable after a run completes;
  storage costs need a lifecycle policy eventually (M10.3); downstream
  models must deduplicate across ingest dates (M5).

### 5. Index and link (10 min)

- Add the ADR to `docs/adr/README.md` as a one-line entry (PF.3 builds
  the full index later).
- Link it from the **Decisions** section of the root README (M0.6).
- Link it from `ingestion/README.md`'s raw zone section.

### 6. Review it (10 min)

Read it aloud. Then ask a fresh agent session, read-only:

> Here is an ADR. Without rewriting it, list any claim that isn't
> supported by the context, and any alternative that seems strawmanned.

Fix what's real. The words stay yours.

## Gotchas

- **ADRs are immutable.** If the decision changes later, write a new ADR
  that supersedes this one and set this one's status to "Superseded by
  ADR-00N". Don't edit history. (Same principle as the raw zone.)
- **One decision per ADR.** If you find yourself deciding the bucket
  layout too, that's a separate ADR, or it belongs in `ingestion/README.md`.
- **Too long is a smell.** One page. If it's longer, the context is
  doing the job of a design doc.
