# M2.5 · Validate at the edge with Pydantic

> **Ticket:** [#40](https://github.com/Dfscashline21/sideline/issues/40) ·
> **Mode:** hand · **Time:** 3 to 4 hours ·
> **Needs:** M2.3 merged, a few real responses landed in MinIO

## Why this matters

APIs change without warning. A field gets renamed, a number arrives as a
string, an error page comes back with status `200`. If nothing checks,
bad data flows into the raw zone and on into every downstream table, and
you find out weeks later from a wrong dashboard.

**Validating at the edge** means checking, at the moment data enters your
platform, only the fields you actually rely on. Anything that fails goes
to **quarantine** with a reason: it isn't silently dropped, and it isn't
silently accepted. Interviewers like this pattern because it shows you
think about failure as data, not as exceptions.

## What you'll produce

- `ingestion/sideline_ingestion/validate.py`: Pydantic models for the
  fields you rely on, plus a validator per entity.
- A gate in the extractor: valid responses land in the raw zone
  unchanged; invalid ones land under `_quarantine/` with a reason file.
- Tests: a malformed record lands in quarantine with a reason; valid
  records are unaffected.

## Steps

### 1. List the fields you rely on (30 min)

Open one landed `game_log`, `boxscore` and `playbyplay` file each. For
each entity, write down the fields **your code or the next modules
actually use**. Be strict: this is a short list, not the whole schema.

| Entity | Fields relied on (suggestion) | Why |
|---|---|---|
| `game_log` | `GAME_ID`, `GAME_DATE`, `TEAM_ID`, `MATCHUP`, `WL`, `PTS` | Drives which games are fetched; feeds `dim_game` |
| `boxscore` | game ID, team IDs, player IDs, points, minutes | Feeds `fact_player_game` |
| `playbyplay` | `actionNumber`, `period`, `clock`, `actionType`, `teamId` | Feeds `fact_play` and M1.5-style possessions |

Field names above for the v3 endpoints come from `nba_api`'s
`expected_data` for `PlayByPlayV3` and `BoxScoreTraditionalV3`. Confirm
them, and their nesting and types, against **your** landed files.

### 2. Decide the unit of quarantine (20 min)

This decision matters more than the code. Read ADR-001's premise
(raw = bytes exactly as received) and pick one:

| Option | Raw zone contains | Problem |
|---|---|---|
| A. Response-level gate | Only responses whose relied-on fields all validate | One bad row quarantines the whole response |
| B. Land everything, flag records | Every response; bad records listed in quarantine | Invalid data **is** in the main raw zone (fails the ticket) |
| C. Split responses | Rewritten responses minus bad rows | Breaks "unchanged"; you can't replay what the API sent |

These labs use **option A**: the response is the unit you land, so it's
also the unit you quarantine. The quarantined copy keeps the bytes
unchanged, plus a reason file naming exactly which records failed.
"Valid records unaffected" then means every other response (other games,
other days) lands normally, and a fix-and-replay of the quarantined one
is a single object.

If you choose differently, write the trade-off in `ingestion/README.md`.

### 3. Model the game log (45 min)

The game log uses the v2 table format, so first turn
`{"resultSets": [{"name", "headers", "rowSet"}]}` into a list of dicts,
then validate each with a model:

```python
class GameLogRow(BaseModel):
    GAME_ID: str
    GAME_DATE: date
    TEAM_ID: int
    MATCHUP: str
    WL: str | None
    PTS: int | None
```

Add one **field validator** for a rule the type can't express: a
`GAME_ID` is exactly 10 digits.

</details>

<details>
<summary>Hint 2 · Turning `rowSet` into dicts</summary>

`dict(zip(headers, row, strict=True))`. The `strict=True` raises if a row
has a different length from the headers, which is itself a schema change
you want to catch, not hide.

</details>

<details>
<summary>Solution (open only after you have your own)</summary>

```python
"""Edge validation: model the fields we rely on."""

import json
from datetime import date
from typing import Any

from pydantic import BaseModel, ValidationError, field_validator


class GameLogRow(BaseModel):
    GAME_ID: str
    GAME_DATE: date
    TEAM_ID: int
    MATCHUP: str
    WL: str | None
    PTS: int | None

    @field_validator("GAME_ID")
    @classmethod
    def ten_digit_id(cls, value: str) -> str:
        if len(value) != 10 or not value.isdigit():
            raise ValueError("GAME_ID must be 10 digits")
        return value


def rows_from_result_set(payload: dict[str, Any], name: str) -> list[dict[str, Any]]:
    """stats.nba.com v2 format: {"resultSets": [{"name", "headers", "rowSet"}]}."""
    for result_set in payload["resultSets"]:
        if result_set["name"] == name:
            headers: list[str] = result_set["headers"]
            return [dict(zip(headers, row, strict=True)) for row in result_set["rowSet"]]
    raise KeyError(name)


def validate_game_log(body: bytes) -> list[str]:
    """Return the problems found; an empty list means valid."""
    try:
        rows = rows_from_result_set(json.loads(body), "LeagueGameLog")
    except (ValueError, KeyError, TypeError) as exc:  # not JSON, or not the expected envelope
        return [f"envelope: {type(exc).__name__}: {exc}"]
    problems: list[str] = []
    for i, row in enumerate(rows):
        try:
            GameLogRow.model_validate(row)
        except ValidationError as exc:
            for err in exc.errors(include_url=False):
                problems.append(f"row {i} {'.'.join(map(str, err['loc']))}: {err['msg']}")
    return problems
```

`json.JSONDecodeError` is a subclass of `ValueError`, and `zip(...,
strict=True)` raises `ValueError` too, so one `except` covers "not JSON"
and "rows don't match headers".

</details>

### 4. Model play-by-play and box score (45 min)

Same idea: a model for one action (or one player line), and a
`validate_playbyplay(body) -> list[str]` that finds the list inside the
envelope and validates each item. Keep the models to the fields from
step 1.

Watch the types in your real files. In v3 responses some numbers arrive
as strings (scores in particular), and `teamId` is `0` or missing for
events like period starts. Decide whether Pydantic should **coerce**
(its default "lax" mode turns `"12"` into `12`) or reject. Lax is usually
right at the edge, because you're checking meaning, not formatting.

✅ **Checkpoint:** every file you've landed so far validates with zero
problems. If one doesn't, either the model is wrong or you've found real
bad data. Find out which.

### 5. The gate (45 min)

One function used for every write in the extractor:

```python
def land(
    store: ObjectStore, key: str, body: bytes, validate: Callable[[bytes], list[str]]
) -> bool: ...
```

- No problems: `store.put(key, body)`, return `True`.
- Problems: write the **unchanged** bytes to `_quarantine/<key>`, write a
  reason file next to it, return `False`.

<details>
<summary>Solution (open only after you have your own)</summary>

```python
def land(store: ObjectStore, key: str, body: bytes, validate: Callable[[bytes], list[str]]) -> bool:
    """Write body unchanged to key if valid, else to _quarantine/<key> with a reason file."""
    problems = validate(body)
    if not problems:
        store.put(key, body)
        return True
    store.put(f"_quarantine/{key}", body)
    reason = {"key": key, "problems": problems}
    store.put(
        f"_quarantine/{key.removesuffix('.json')}.reason.json",
        json.dumps(reason, indent=2).encode(),
    )
    return False
```

Prefixing the whole raw key with `_quarantine/` keeps the quarantine
layout identical to the raw layout, so replaying a fixed object is a
copy to the key without the prefix.

</details>

Then wire it into `nba.run`:

- A quarantined **game log** means you can't trust its game IDs. Stop
  the run with a clear error and don't advance the watermark.
- A quarantined **game** response: count it, log it at `WARNING`, carry
  on with the other games. Decide whether the watermark advances. (These
  labs say yes, because the quarantine holds the bytes and the reason, and
  the run summary reports the count. Note that M9 will alert on it.)

### 6. Test both criteria (30 min)

```python
def test_malformed_goes_to_quarantine_with_reason() -> None:
    s = MemoryStore()
    assert not land(s, "nba/x/game_log.json", BAD, validate_game_log)
    assert s.get("_quarantine/nba/x/game_log.json") == BAD
    reason = json.loads(s.get("_quarantine/nba/x/game_log.reason.json"))
    assert "row 0 GAME_DATE" in reason["problems"][0]
    assert s.list_keys("nba/") == []
```

Write the others:

- a valid response lands unchanged and nothing appears in quarantine
- an HTML error page with status 200 is an envelope problem
- in a full `nba.run` with a fake API, one game's malformed play-by-play
  is quarantined while the other games land normally (**valid records
  unaffected**)

## Gotchas

- **Don't validate everything.** A model with 40 fields fails the first
  time the API adds or renames one you never used. Pydantic ignores extra
  fields by default; keep it that way here.
- **Validation must never change what you store.** Validate a parsed copy;
  store the original bytes. `model_dump_json()` output is not the raw data.
- **A quarantine nobody reads is a bin.** Put the quarantined count in
  the run log now. M9 turns it into an alert.
