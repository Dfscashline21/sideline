# M2.7 · Kill-and-restart idempotency test

> **Ticket:** [#42](https://github.com/Dfscashline21/sideline/issues/42) ·
> **Mode:** hand · **Time:** 3 to 4 hours ·
> **Needs:** M2.4 (watermark), M2.6 (fake fetch, MemoryStore, MinIO test setup)

## Why this matters

This is the M2 epic's "ready when": *kill the job mid-run, restart it,
and end with exactly the right data and no duplicates.* Every pipeline
claims to be idempotent. Few can **prove** it. A test that kills the job
at an arbitrary point and compares the result with a clean run turns the
claim into evidence, and it's a strong thing to describe in an interview.

## What you'll produce

- Extractor changes so a restart resumes cleanly: skip what already
  landed, write a manifest last.
- An automated pytest that crashes a run partway, restarts it, and
  asserts the output is **identical** to a clean run.
- A script that does the same with a real `kill -9` against MinIO.

## Steps

### 1. Predict before you test (20 min)

On paper, walk through your current `nba.run` being killed after it has
landed the game log and 3 of 8 game objects. Then it restarts. For each
question, write your prediction:

1. Which keys exist after the crash?
2. Has the watermark moved?
3. Does the restart refetch the 3 landed objects? Does it matter?
4. Will the restarted run's keys equal a clean run's keys? Its bytes?
5. Is anything a reader could see *during* the crash misleading?

Keep the page. You'll check it against the test.

### 2. Write the test first (60 min)

Simulating a kill in-process is fast and deterministic: make the fake
fetch raise after N calls.

<details>
<summary>Hint 1 · Nudge</summary>

You need three stores: one clean run, and one that crashes and is then
restarted. Then compare the clean store with the restarted one. With
`MemoryStore`, "identical output" is literally `a.objects == b.objects`:
same keys, same bytes, nothing extra.

</details>

✅ **Checkpoint:** you know which assertion fails (if any) and why.

### 3. Make the restart resume, not repeat (45 min)

Before fetching a game object, check whether its key already exists and
skip it if so. This is safe because of one property from the M2 overview:
**an S3 `PUT` is atomic**. A key either holds a complete object or doesn't
exist, so "exists" means "fully landed".

Count skipped objects in the run summary.

<details>
<summary>Hint · Why not skip the game log too?</summary>

You could. But the game log decides *which* games belong to the run, and
refetching it is one cheap call. The trade-off: if the API's bytes for the
game log change between attempts (a late score correction, a timestamp
field), the restarted run's game log differs from a clean run's. Decide
which you prefer and make the test's comparison match the decision.
These labs refetch it.

</details>

### 4. A manifest, written last (45 min)

Readers need a way to tell "run finished" from "run in progress or
crashed". Write `.../<run_id>/manifest.json` (or a `_manifest` entity, per
your M2.2 layout) **after** every object and **before** the watermark.

Watch for a subtle trap: if the manifest records what *this attempt* did
(objects written, objects skipped), a restarted run's manifest differs
from a clean run's, and your "identical output" assertion fails. Record
what the *run contains* instead.

<details>
<summary>Solution (core of `nba.run`, open only after you have your own)</summary>

```python
    game_log = fetch(f"{BASE}/leaguegamelog", game_log_params(start, end))
    store.put(key("game_log", "game_log"), game_log)
    ids = game_ids(game_log)

    counts = {"games": len(ids), "objects_written": 1, "objects_skipped": 0}
    landed = [key("game_log", "game_log")]
    for game_id in ids:
        for entity, endpoint in (("boxscore", "boxscoretraditionalv3"), ("playbyplay", "playbyplayv3")):
            k = key(entity, game_id)
            landed.append(k)
            if store.exists(k):  # landed before a crash: don't fetch again
                counts["objects_skipped"] += 1
                continue
            store.put(k, fetch(f"{BASE}/{endpoint}", {"GameID": game_id}))
            counts["objects_written"] += 1

    # Commit point: manifest, then watermark, only after every object landed.
    # The manifest lists what the run contains, not what this attempt did,
    # so a restarted run produces a byte-identical manifest.
    manifest = {"run_id": run_id, "games": len(ids), "objects": sorted(landed)}
    store.put(key("_manifest", "manifest"), json.dumps(manifest, indent=2).encode())
    current = read_watermark(store, LEAGUE, SOURCE)
    if current is None or end > current:
        write_watermark(store, LEAGUE, SOURCE, end)
    log.info("run %s complete: %s", run_id, counts)
    return counts
```

(The M2.5 gate wraps each `store.put` in your version.) With this, the
test's final assertions are:

```python
assert crashed.objects == clean.objects  # same keys, same bytes, no extras
assert restarted_api.calls == 1 + 2  # game log + the two objects not landed before the crash
```

where the fake game log holds two games, so four game objects in total.

</details>

### 5. Crash at every point, not just one (30 min)

One crash point proves little. Parametrise the test over **every**
possible crash point, from "before the first call" to "after the last
fetch":

```python
@pytest.mark.parametrize("crash_after", range(0, 5))
def test_restart_after_any_crash(crash_after: int) -> None: ...
```

Also crash *between* the manifest and the watermark (make the store raise
on the watermark write). The restart must still converge to the clean
result.

✅ **Checkpoint:** every crash point passes. This parametrised test is the
"automated test" acceptance criterion.

### 6. The real thing: `kill -9` against MinIO (45 min)

An in-process exception isn't a real kill: `finally` blocks run, buffers
flush. Write `ingestion/scripts/kill_restart.sh` (or `.py`) that:

1. Runs a clean backfill of a short range into one prefix (use the
   `prefix` option you gave `S3Store` in M2.6, e.g. via an environment
   variable).
2. Starts the same backfill into a second prefix in the background,
   sleeps a few seconds, and sends `kill -9` to it.
3. Restarts it to completion.
4. Lists both prefixes, strips the prefix, and compares the key lists
   and each object's checksum (MinIO returns an `ETag`; for single-part
   uploads it's the MD5 of the content).
5. Prints `IDENTICAL` or the differences, and exits non-zero on any.

Run it against the live API (or the ESPN fallback) with `make up`
running. A clean run of a 2-day range fetches about 30 to 40 objects, so a
3 to 5 second sleep usually lands the kill mid-run. Check the log to
confirm it was.

✅ **Checkpoint:** `IDENTICAL`, with the log proving the kill happened
mid-run, and the restart log showing skipped objects.

## Gotchas

- **ETag isn't always MD5.** Multipart uploads produce a different ETag
  format. Your objects are small single `PUT`s, but if you ever compare
  large files, hash the downloaded bytes instead.
- **The clock is an input.** The ingest date is part of every key. A
  crash before midnight and a restart after it produce keys under two
  dates. Pass `ingest_date` explicitly on restart (a `--ingest-date`
  option), or accept the split and note it.
- **"No duplicate rows"** in the criteria: in the raw zone a row lives
  inside an object, so no duplicate *keys* means no duplicate rows *within
  a run*. Duplicates *across* runs (the same game ingested on two days) are
  history by design. M5 deduplicates them downstream.
