# M3.2 · Write grain statements for every table

> **Ticket:** [#47](https://github.com/Dfscashline21/sideline/issues/47) ·
> **Mode:** hand · **Time:** 2 hours ·
> **Needs:** M3.1 sessions 1 and 2

## Why this matters

Most reporting bugs are grain bugs: a join that silently turns one row
into three, a "per game" table that's really per game per team, a sum
that double-counts. A one-sentence grain statement per table is the
cheapest defence there is. It's also exactly what M9 will test: every
grain statement becomes a uniqueness check.

## What you'll produce

A **Grains** section in `docs/design/data-model.md`: one sentence per
table for `fact_play`, `fact_shot`, `fact_player_game`,
`fact_team_game` and every dimension, each with the column(s) that make
a row unique, and a record of the ambiguities you found and fixed.

## What a good grain statement looks like

Pattern: **"One row per ⟨thing⟩ ⟨qualifier⟩, as ⟨recorded by / of⟩ ⟨source or time⟩."**
Then the **key**: the columns that are unique together.

| Weak | Strong |
|---|---|
| "Player stats" | "One row per player per game in which the player was on the roster, including did-not-play rows. Key: `(game_sk, player_sk)`." |
| "Games" | "One row per scheduled game in any league, including postponed and cancelled games. Key: `game_sk`." |

The strong versions answer the questions a reader would otherwise have
to guess: are DNPs in? Are cancelled games in? Is it per league or all
leagues?

## Steps

### 1. List every table

From the [module overview](README.md#the-model-youre-designing): four
facts and the dimensions (`dim_player`, `dim_team`, `dim_season`,
`dim_game`, `dim_date`, `dim_venue`). Add any you think are missing,
and say why.

### 2. Draft one sentence each, fast (30 min)

Don't polish. Get a sentence and a key down for every table.

### 3. Attack each grain for ambiguity (45 min)

For every statement, ask these questions and tighten the sentence until
each has a clear answer:

| Question | Example it catches |
|---|---|
| **Which events are in, and which are out?** | Are free throws in `fact_shot`? Are substitutions in `fact_play`? |
| **What about rows with nothing in them?** | DNP rows in `fact_player_game`. Postponed games in `dim_game` |
| **Across all leagues, or one table per league?** | Is `fact_play` one table with a `league` column? |
| **Which version of the truth?** | When a stat is corrected the next day, is it one row updated, or two rows? |
| **Is the key really unique?** | Check it against real data (step 4) |
| **For SCD dimensions: per entity, or per entity per version?** | `dim_player` is one row per player **per version** |

### 4. Check keys against real data (30 min)

You have real play-by-play and box scores in `.data/practice.duckdb`
from M1. Test whether your proposed keys are actually unique. For
example:

```sql
select count(*) as n_rows,
       count(distinct (game_id, game_play_number)) as n_keys
from nba_pbp;
```

Equal counts mean the key is unique in this data. Try the obvious
alternatives too. In the ESPN play-by-play, `(game_id, sequence_number)`
looks like a natural event key, but it isn't quite unique, while
`(game_id, game_play_number)` is. Your M2 `nba_api` source will have its
own event number; find out whether that one is unique the same way.

✅ **Checkpoint:** every fact grain's key has been tested against data,
or explicitly marked "untested: source not loaded yet".

### 5. Write it up

Add the section to `docs/design/data-model.md`. Include a short
**Ambiguities resolved** list: what was unclear in your first draft and
how you settled it. That list is the evidence for the ticket's second
criterion.

<summary>Solution: one reasonable set (compare after writing your own)</summary>

```markdown
## Grains

| Table | Grain | Key |
|---|---|---|
| fact_play | One row per play-by-play event in any league, as recorded by the source, including non-scoring events (fouls, substitutions, timeouts); stat corrections replace the row. | (league, source_game_id, event_number) → play_sk |
| fact_shot | One row per field-goal attempt (free throws excluded), with shot location where the source provides it. | play_sk (a shot is a play) |
| fact_player_game | One row per player per game for every player on the game roster, including did-not-play rows with null stats. | (game_sk, player_sk) |
| fact_team_game | One row per team per game: two rows per completed game. | (game_sk, team_sk) |
| dim_player | One row per player per version of their tracked attributes (SCD2); the current version has is_current = true. | player_sk; (player_id, valid_from) unique |
| dim_team | One row per team per version (SCD2: name, city, conference changes). | team_sk; (team_id, valid_from) unique |
| dim_season | One row per league season (NBA 2026-27 and WNBA 2026 are different rows). | season_sk; (league, season_label) unique |
| dim_game | One row per scheduled game in any league, including postponed and cancelled games. | game_sk; (league, source_game_id) unique |
| dim_date | One row per calendar date, 2000-01-01 to 2035-12-31. | date_sk (yyyymmdd) |
| dim_venue | One row per venue per version (SCD2: names change with sponsors). | venue_sk |

### Ambiguities resolved
- fact_shot: free throws excluded (shot charts, FG%); FT trips stay in fact_play.
- fact_player_game: DNP rows kept so "games missed" is countable; stats null, not 0.
- dim_player: grain is per version, not per player.
- fact_play: (game_id, sequence_number) was not unique in ESPN data; use the event number column.
```

Notice `fact_shot` reuses `play_sk`: a shot is a subset of plays, which
keeps the two tables consistent.

</details>

## Gotchas

- **"Per game" without "per what".** Box scores have two teams. Always
  name every entity in the grain.
- **Zeros vs nulls.** A DNP player has *no* points, not zero points.
  Averages treat them differently.
- **Grain creep.** If you find yourself adding a column to the key
  "just to make it unique", stop. Either the grain sentence is wrong,
  or the data has duplicates that need fixing upstream.
