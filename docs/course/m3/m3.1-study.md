## Session 1 · The four-step design process (90 min)

**Read:** Toolkit chapter 1 and the start of chapter 3.

Kimball designs every star schema in four steps:

1. **Choose the business process** (e.g. "a play happens in a game").
2. **Declare the grain** (what exactly is one row?).
3. **Identify the dimensions** (who, what, where, when, how).
4. **Identify the facts** (the numbers measured at that grain).

The order matters. Grain comes **before** dimensions and facts, because
the grain decides which dimensions and facts are even possible.

### Exercise 1.1

Apply the four steps to a process you know from work, on paper. Then
apply them to "a player plays in a basketball game". What's the grain?
Which dimensions? Which facts?

<details>
<summary>Check your answer</summary>

- Process: a player's participation in a game.
- Grain: **one row per player per game** (`fact_player_game`).
- Dimensions: player, team, opponent team, game, date, season.
- Facts: minutes, points, rebounds, assists, shot attempts and makes.

If you wrote "one row per player per game per team", ask yourself:
can a player play for two teams in one game? No, so `team` is an
attribute of the row, not part of the grain.

</details>

## Session 2 · Fact table types (60 min)

**Read:** Toolkit chapter 2 (fact table techniques).

| Type | Grain | Sideline example |
|---|---|---|
| **Transaction** | One event | `fact_play`, `fact_shot` |
| **Periodic snapshot** | State at regular intervals | Standings at the end of each day |
| **Accumulating snapshot** | One row per process instance, updated as milestones happen | A game: scheduled → tipped off → final → stats corrected |
| **Factless fact** | An event with no measures | Player appeared on the active roster for a game |

Also learn **additive**, **semi-additive** and **non-additive** facts.
Points are additive (sum across anything). A team's win count at a date
is semi-additive (sum across teams, not across dates). Shooting % is
non-additive: never average percentages, store makes and attempts.

## Session 3 · Slowly changing dimensions (90 min)

**Read:** the SCD section of chapter 5 and the Kimball Group summary of
types 0 to 7.

| Type | What happens on change | Keeps history? |
|---|---|---|
| 0 | Nothing: the original value never changes | No change at all |
| 1 | Overwrite the old value | No |
| 2 | Close the current row, add a new row | Yes, full |
| 3 | Keep "current" and "previous" columns | One step only |
| 6 | Type 2 rows **plus** a Type 1 "current" column on every row (1 + 2 + 3 = 6) | Yes, and easy "as of today" reporting |

### Exercise 3.1: the trade

A player is traded on 30 December. On paper, draw `dim_player` after
the trade under Type 1, Type 2 and Type 6. Then answer, for each type:
*"How many points did the Raptors' players score in November?"*

<details>
<summary>Explanation</summary>

- **Type 1:** one row, team = Knicks. November's Raptors points get
  credited to the Knicks. **Wrong answer.**
- **Type 2:** two rows (Raptors until 30 Dec, Knicks from 30 Dec). The
  fact rows point at the version valid on the game date. **Right answer.**
- **Type 6:** the same two rows, but each also has
  `current_team = Knicks`. You can group by historical team (correct
  history) *or* current team ("how have the players now on the Knicks
  done this season?") without a second join.

This is the M3.3 ticket in miniature.

</details>

## Session 4 · Data Vault and OBT (60 min)

**Data Vault** splits everything into:

- **Hubs:** unique business keys (one row per player ever seen)
- **Links:** relationships between hubs (player-team, player-game)
- **Satellites:** descriptive attributes with load timestamps (all history, by default)

It's built for **many sources that change often** and for **auditability**:
every row records where and when it came from, and nothing is ever
updated in place. The cost is many joins before anyone can query it,
so teams usually build Kimball-style marts on top of a vault.

**One Big Table (OBT)** pre-joins facts and dimensions into one wide
table. Columnar warehouses compress repeated values well, so it's fast
and simple for a single use case. It's painful when a dimension
attribute changes (rewrite history?) and when many use cases need
different grains.

### Exercise 4.1

Write a paragraph answering: **when does Data Vault beat Kimball?**
Think about: number of sources, how often source schemas change, audit
or regulatory requirements, team size, and who queries the result.

<details>
<summary>What a strong answer covers</summary>

Data Vault wins when you integrate **many** sources (dozens) whose
schemas change often, when you need a full audit trail of every load
(finance, healthcare, regulated industries), and when several teams load
in parallel and can't coordinate one conformed model up front. Kimball
wins when the number of sources is manageable, the consumers are
analysts and BI tools that need simple star joins, and the team is small.
Sideline has a handful of sources, one engineer, and analytical
consumers: Kimball. You'll write this up properly in M3.8.

</details>
