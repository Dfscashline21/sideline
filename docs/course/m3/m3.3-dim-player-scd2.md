# M3.3 · Design dim_player as SCD Type 2

> **Ticket:** [#48](https://github.com/Dfscashline21/sideline/issues/48) ·
> **Mode:** hand · **Time:** 2 to 3 hours ·
> **Needs:** M3.1 session 3, M3.2 (`dim_player` grain)

## Why this matters

"Players get traded" is the classic SCD2 interview prompt, and it's
real here: dozens of NBA players change teams every season. If
`dim_player` just overwrites the team, every historical "points by team"
query quietly moves a traded player's old points to his new team.
This design is what M5.5 builds as a dbt snapshot and what M7.6 and
M12 join against "as of" a game date, so the column decisions you
make now carry through the rest of the course.

## What you'll produce

A `dim_player` section in `docs/design/data-model.md` with:

- every column, its type, and whether it's tracked as Type 1 or Type 2
- `valid_from`, `valid_to` and `is_current` defined precisely
- a worked example of a mid-season trade, row by row
- the as-of join condition that facts will use

## Steps

### 1. List the columns and classify them (30 min)

Start from what sources give you about a player: name, team, position,
jersey number, height, weight, birth date, college, draft year.

For each, decide:

| Choice | Meaning | Ask yourself |
|---|---|---|
| **Type 2** | A change creates a new row; history kept | Would a historical report be *wrong* if this were overwritten? |
| **Type 1** | Overwrite in place on every row | Is a change a *correction* rather than a real-world change? |
| **Type 0** | Never changes | Is it fixed at birth or at draft? |

<details>
<summary>Hint · Nudge: the tricky ones</summary>

- A name **spelling correction** ("Jokic" → "Jokić") is Type 1: the
  player didn't change. A **legal name change** might be Type 2.
- Height and weight change slowly and are re-measured. Does anyone
  report "points by player height at the time"? If not, Type 1 is fine
  and avoids a new row every time a source re-rounds a number.
- Birth date and draft year never change: Type 0. If a source "changes"
  one, that's a data-quality incident (M9), not a new version.

</details>

### 2. Define the history columns precisely (30 min)

Write exact definitions, not just names. Decide:

1. **Is `valid_to` inclusive or exclusive?** Pick **half-open**
   intervals: a row is valid for `valid_from <= d < valid_to`. Then one
   row's `valid_to` equals the next row's `valid_from`, with no gaps and
   no overlaps.
2. **What's `valid_to` on the current row?** `NULL`, or a far-future
   sentinel like `9999-12-31`? A sentinel makes the as-of join a simple
   range check with no `OR valid_to IS NULL`. dbt snapshots use `NULL`
   by default, and since dbt 1.9 the `dbt_valid_to_current` config can
   set a sentinel instead. You'll meet that in M5.5.
3. **Date or timestamp?** Games happen on dates. If a trade and a game
   fall on the same day, which version does that game get?
4. **Effective date or detected date?** A snapshot run notices the
   trade when it next runs, maybe a day late. Which date goes in
   `valid_from`: when the change happened, or when you saw it?

Course default (used by M5 and later): half-open dates, current row has
`valid_to = 9999-12-31` and `is_current = true`.

### 3. Write the as-of join (20 min)

Facts store the **durable** player key (`player_id`, the same across
versions). To get the attributes "as they were" on a game date:

```sql
from fact_player_game f
join dim_player p
  on  p.player_id   = f.player_id
  and f.game_date  >= p.valid_from
  and f.game_date   < p.valid_to
```

Alternatively, look up the right `player_sk` once at load time and store
it on the fact row. Write down which you choose and the trade-off.

<details>
<summary>Hint · The trade-off</summary>

- **Store `player_sk` on the fact (Kimball's default):** fast, simple
  joins. But the lookup happens at load time, so a late-arriving
  dimension change means re-keying old facts.
- **Store `player_id` and join as-of at query time:** always correct
  even when history is fixed later, but every query pays for a range
  join. M7.6 measures exactly that cost in Spark.

</details>

### 4. Work the trade example (45 min)

The real case: **OG Anunoby** played for the Toronto Raptors until
29 December 2023, was traded to the New York Knicks, and played his
first Knicks game on 1 January 2024. Check it in your M1 data:

```sql
select team_short_display_name, min(game_date), max(game_date), count(*)
from nba_player_box
where athlete_display_name = 'OG Anunoby' and season = 2024 and season_type = 2
group by 1 order by 2;
```

Now, on paper, fill in:

1. `dim_player` rows for him **before** the trade (one row).
2. `dim_player` rows **after** the trade (what changed on the old row?
   what's on the new row?).
3. Two `fact_player_game` rows: one from November 2023 and one from
   January 2024. Which `dim_player` row does each join to?
4. The query "total points by team for players while on that team" for
   the Raptors in 2023-24. Show it returns his Raptors points, not his
   Knicks points.

<details>
<summary>Solution: the worked example</summary>

`dim_player` after the trade (the trade was completed on 30 December 2023):

| player_sk | player_id | display_name | team | position | valid_from | valid_to | is_current |
|---|---|---|---|---|---|---|---|
| 101 | 3934719 | OG Anunoby | TOR | F | 2021-10-19 | 2023-12-30 | false |
| 245 | 3934719 | OG Anunoby | NYK | F | 2023-12-30 | 9999-12-31 | true |

- Before the trade only row 101 existed, with `valid_to = 9999-12-31`
  and `is_current = true`. The trade **closed** it (set `valid_to` and
  `is_current = false`) and **inserted** row 245. Nothing else on row
  101 changed.
- A game on 2023-11-20 satisfies `2021-10-19 <= d < 2023-12-30`, so it
  joins to row 101 (Raptors). A game on 2024-01-01 joins to row 245.
- Exactly one row matches any date, because the intervals are half-open
  and touch without overlapping.

(3934719 is his ESPN `athlete_id`. The first `valid_from` is simply
where the M1 practice data starts, the 2021-22 opening night. Use your
source's ID and the date your history actually starts. The surrogate
keys 101 and 245 are made up.)

</details>

### 5. Write the design section

In `docs/design/data-model.md`, add a `dim_player` section with the
column table (name, type, SCD type, description), the history-column
definitions, the as-of join, and the worked example.

## Gotchas

- **The fact row already knows the team.** A box score says which team
  the player played for in *that* game, so `fact_player_game` should
  carry `team_sk` directly. `dim_player`'s team is for questions like
  "which players were on the Raptors on 1 December?". Say this in your
  design. It's a common interview follow-up, and M3.7's critique may
  raise it.
- **Two changes in one day** (traded, then waived) create a zero-length
  row with half-open dates. Decide whether to keep it.
- **Overlapping rows** are the classic SCD2 bug: two rows valid on the
  same date, so the as-of join doubles facts. M9 will add a test for it;
  write the rule down now ("for each `player_id`, intervals never overlap").
