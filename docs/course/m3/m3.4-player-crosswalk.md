# M3.4 · Design the cross-league player identity crosswalk

> **Ticket:** [#49](https://github.com/Dfscashline21/sideline/issues/49) ·
> **Mode:** hand · **Time:** 2 to 3 hours ·
> **Needs:** M3.2, M3.3 (`player_id` is the durable key)

## Why this matters

Sideline's best questions cross leagues: "how did this NBA rookie shoot
in college?", "which conferences produce the most efficient pros?". Each
source gives the same human a different ID. Joining them is **entity
resolution**, a problem every company has: customers across CRM and
billing, products across suppliers, patients across hospitals.

This ticket is **design only**. M7.3 builds it once college data
arrives. A design with explicit rules and a plan for doubt is what
separates a senior answer from "join on name".

## What you'll produce

`docs/design/player-crosswalk.md` with:

- the sources and the ID each one uses
- the matching keys and rules, in priority order
- a plan for ambiguous matches (same name, different person)
- the `player_crosswalk` table design

## Steps

### 1. Inventory the sources and their IDs (30 min)

| Source | Leagues | Player ID | Other identifying fields? |
|---|---|---|---|
| `nba_api` (stats.nba.com), from M2 | NBA | `PERSON_ID` | name, birth date, school, draft year/round/pick, height |
| ESPN via sportsdataverse (M1 data) | NBA, WNBA, college | `athlete_id` | name, team, jersey, position |
| WNBA's own stats site (if you use it in M6) | WNBA | its own person ID | ? |
| A college source (M7.3) | NCAA men's and women's | ? | ? |

Fill in the question marks as far as you can now. Look at what
`nba_api`'s player-info endpoint returns (you used it in M2).

Then check one surprising fact in your M1 data:

```sql
select 'nba' as src, athlete_id, min(season), max(season)
from nba_player_box where athlete_display_name = 'Paolo Banchero' group by all
union all
select 'ncaa', athlete_id, min(season), max(season)
from ncaa_player_box where athlete_display_name = 'Paolo Banchero' group by all;
```

✅ **Checkpoint:** you've seen that ESPN uses the **same** `athlete_id`
for a player in college and the NBA. So within ESPN, the college-to-pro
link is free. The hard links are **between sources**: ESPN ↔ `nba_api`,
ESPN ↔ any other college source.

### 2. See why names aren't enough (20 min)

```sql
select athlete_display_name, count(distinct athlete_id) as people,
       list(distinct team_short_display_name) as teams
from ncaa_player_box
where season = 2025
group by 1
having count(distinct athlete_id) > 1
order by people desc
limit 10;
```

In the 2024-25 men's college data, 313 display names belong to more
than one `athlete_id`. Five different "Caleb Williams". Now think about
the opposite problem: the **same** person written differently:
"Jabari Smith Jr." vs "Jabari Smith", "Nikola Jokic" vs "Nikola Jokić",
"OG Anunoby" vs "O.G. Anunoby".

### 3. Design the matching rules (60 min)

Design rules in **tiers**, from most to least certain. Each tier says
what must match and what confidence that gives.

<details>
<summary>Hint 1 · Nudge</summary>

Which attributes almost never collide between two different people, and
are present in both sources? Birth date alone collides constantly.
Name plus birth date almost never does.

</details>

<details>
<summary>Hint 2 · Approach</summary>

1. **Normalise** names first: lowercase, strip accents, drop
   punctuation and suffixes (`jr`, `sr`, `ii`, `iii`), collapse spaces.
   Keep the original too; normalising is lossy.
2. **Tier 1, deterministic:** a published ID mapping, or normalised
   name + birth date.
3. **Tier 2, strong:** normalised name + college + draft year (for
   college-to-pro), or name + team + season (within a league).
4. **Tier 3, candidate only:** fuzzy name match (edit distance, nickname
   list: "Nic" / "Nicolas") plus one corroborating field. **Never
   auto-accepted.**
5. Anything else: no match. A missing link is better than a wrong one.

</details>

### 4. Plan for ambiguous matches (30 min)

This is the second acceptance criterion. Answer each:

- Two candidates tie in the same tier (two "Jalen Jacksons" with no
  birth date). What happens?
- A match is accepted, and months later turns out to be wrong. How do you
  undo it without breaking every fact that used it?
- Who reviews tier-3 candidates, where do they record the decision, and
  how is it reapplied on the next run?

<details>
<summary>Hint · The key ideas</summary>

- **Ambiguity never auto-resolves.** Ties go to a review queue table,
  never "pick the first".
- **Manual decisions are data.** Store them in a small, version-controlled
  overrides file (a dbt seed in M5), e.g. `force_match` and
  `never_match` pairs. The pipeline applies overrides before rules,
  so a human decision survives every re-run.
- **Facts reference the Sideline person ID, never a source ID.**
  Fixing a wrong match then means changing crosswalk rows, not facts.

</details>

### 5. Design the table

<details>
<summary>Solution: one reasonable design (compare after writing yours)</summary>

`player_crosswalk`: one row per (source, source player ID).

| Column | Meaning |
|---|---|
| `player_id` | Sideline's durable person ID (the key `dim_player` versions share) |
| `source` | `nba_api`, `espn`, `wnba_stats`, … |
| `source_player_id` | The ID in that source |
| `match_method` | `override`, `id_map`, `name_dob`, `name_college_draft`, `new_person` |
| `match_confidence` | `high` / `medium` (tier 3 is never written here) |
| `matched_at` | When this link was made |
| `reviewed_by` | Null unless a human decided |

Rules, applied in order on every run:

1. Apply `crosswalk_overrides` (`force_match`, `never_match`).
2. Keep existing links; never silently re-point a source ID.
3. Tier 1: name (normalised) + birth date → `high`.
4. Tier 2: name + college + draft year, or name + team + season → `medium`,
   only if exactly one candidate.
5. Tier 3 candidates → `crosswalk_review_queue`, not the crosswalk.
6. Unmatched source IDs get a **new** `player_id` (`new_person`). If a
   later override merges two people, keep the surviving ID and record the
   retired one in a `player_id_merges` table so old references still resolve.

Tests to add in M9: each `(source, source_player_id)` maps to exactly
one `player_id`; no `player_id` has two IDs from the same source unless
an override says so.

</details>

## Gotchas

- **WNBA and NBA players never share a `player_id`.** They're different
  people. But a women's college player and a WNBA player often should.
  Make sure your rules allow the second and can't produce the first.
- **ESPN's shared college/pro ID is a gift, not a guarantee.** Write a
  check for it (M9) rather than assuming it forever.
- **Don't design the matcher's code.** That's M7.3. Here you only fix the
  rules and the table so M7.3 can be checked against them.
