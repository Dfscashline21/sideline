# M7.12 · Ready-when check (closed-book)

> **Ticket:** [#105](https://github.com/Dfscashline21/sideline/issues/105) ·
> **Mode:** hand, closed-book · **Time:** 45 min ·
> **Needs:** M7.6 to M7.11 done

## Why this matters

The M7 promise: *shown a slow job's Spark UI, name the bottleneck and two
fixes in 5 minutes.* That's a common senior interview format: they share
a screenshot or describe the metrics and watch how you reason. If you
need the docs open, the module hasn't stuck yet.

## The rules

- **No AI, no notes, no docs** until the timer stops.
- Talk out loud as you would to an interviewer. Record it if you can.
- For each case: **5 minutes** to name the bottleneck, the evidence for
  it, and **two** fixes with a trade-off each.

## Steps

### 1. Prepare a job you haven't seen (before the check, 20 min)

You need at least one **real** UI you haven't diagnosed before. Two ways:

- Ask a friend, or a fresh agent session, to write a PySpark job against
  your Iceberg tables containing **one** hidden performance problem
  (skew, an exploding join, a missing broadcast, far too many shuffle
  partitions, a UDF on a hot path, a cache that spills…). You must not
  read the code. Run it, leave the UI open at http://localhost:4040.
- Or have someone else run one of your M7 experiments with a setting
  changed, without telling you which.

### 2. Diagnose the real job (5 min, timed)

Start the timer. Use only the Spark UI: Jobs, Stages, SQL, Executors,
Environment. Say out loud:

1. Which stage takes the most time?
2. What does the task distribution look like (max vs median)?
3. What does the SQL plan show at that point (join type, exchanges)?
4. **Bottleneck:** one sentence.
5. **Two fixes,** each with a trade-off.

Then read the code and check yourself.

### 3. Three sealed written cases (5 min each)

Open one at a time, timer running. These describe what you'd see in the
UI. Answers are in the second block of each; open them only after you've
said yours out loud.

<details>
<summary>Case A</summary>

A daily job joins 2 billion play events to a 40 MB team dimension.
Stage 3 takes 22 minutes; the other stages take under a minute. The SQL
tab shows `SortMergeJoin` with an `Exchange` under **both** sides.
Shuffle write for stage 2 is 180 GB. Task times in stage 3 are even:
median 40 s, max 55 s.

</details>

<details>
<summary>Case A · answer</summary>

**Bottleneck:** shuffling and sorting the huge fact side for a join with
a small dimension. 40 MB is above the default 10 MB broadcast threshold,
so Spark chose sort-merge. Even task times rule out skew.

**Fixes:** (1) broadcast the dimension, with a `broadcast()` hint or by
raising `spark.sql.autoBroadcastJoinThreshold`; trade-off: driver and
every executor must hold it, risky if it grows. (2) Select only needed
dim columns so it's smaller and qualifies for broadcast; trade-off: none
really, but it needs maintaining as queries change.

</details>

<details>
<summary>Case B</summary>

An aggregation by `player_id` has 200 tasks in its final stage. 199
finish in 2 to 4 seconds; one runs for 9 minutes and shows a
**Shuffle Read Size** of 6 GB versus a median of 30 MB. Spill (disk) is
non-zero only for that task.

</details>

<details>
<summary>Case B · answer</summary>

**Bottleneck:** key skew: one `player_id` value (often a NULL or sentinel
like `-1`/`0`) holds a huge share of the rows, so one task does almost
all the work and spills.

**Fixes:** (1) find the hot key; if it's a sentinel, filter or handle
those rows separately; trade-off: needs a data-model change.
(2) Two-stage salted aggregation (aggregate by `(player_id, salt)`, then
by `player_id`); trade-off: extra stage and code complexity. For a join,
AQE skew join could also split it, but it only applies to joins, not to
this aggregation.

</details>

<details>
<summary>Case C</summary>

A job on 50 MB of input takes 4 minutes. The Stages tab shows 6 stages,
each with **200 tasks**, most taking 20 to 50 ms, with scheduler delay
and task deserialization time similar to the compute time. The Executors
tab shows almost no memory pressure. AQE is disabled in the Environment
tab.

</details>

<details>
<summary>Case C · answer</summary>

**Bottleneck:** overhead, not data. 200 shuffle partitions (the default)
for 50 MB means thousands of tiny tasks whose scheduling cost exceeds
their work.

**Fixes:** (1) enable AQE (`spark.sql.adaptive.enabled`) so it coalesces
small partitions; trade-off: plans change at runtime, which can surprise
people reading the static `explain()`. (2) Lower
`spark.sql.shuffle.partitions` for this job; trade-off: a fixed number
won't suit days when data is 100x bigger. (Bonus: at 50 MB, ask whether
this should be a DuckDB job. Your M7.9 chart answers that.)

</details>
