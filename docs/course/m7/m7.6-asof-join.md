## Why this matters

Joining facts to a slowly changing dimension **as of the event date** is
one of the most common joins in warehousing, and one of the most
commonly done wrong (joining to the *current* row instead). It's also
the perfect case to compare join strategies: one side is huge (every
play), the other is small (players × versions). Which strategy Spark
picks, and why, is a classic interview question.

## What you'll produce

- `spark/sideline_spark/asof_join.py`: every `fact_play` event joined
  to the `dim_player` row valid on its game date.
- Spark UI screenshots of **both** plans (broadcast and sort-merge).
- A timing comparison in `docs/notes/m7.md`.

## The dimension, as built in M3/M5

`dim_player` has a surrogate key `player_sk`, a durable `player_id`, and
SCD2 columns using **half-open** date intervals:

```
valid_from <= game_date < valid_to          -- the row valid on game_date
is_current = true  ⇔  valid_to = date '9999-12-31'
```

<details>
<summary>Hint 3 · What to say</summary>

Broadcast ships the small dim once to each executor and never moves the
big fact table. Sort-merge shuffles **and sorts** both sides by
`player_id`. Sort-merge wins (or is the only option) when neither side
fits in executor memory: a broadcast that's too big makes the driver
collect it and every executor hold it, which ends in out-of-memory
errors. Also mention the range condition: in both strategies it's
evaluated *after* matching on `player_id`, so a player with many
versions costs more comparisons.

</details>

<details>
<summary>Solution (open only after you have your own)</summary>

```python
from pyspark.sql import DataFrame, SparkSession


def asof_player_join(spark: SparkSession, broadcast_dim: bool | None = None) -> DataFrame:
    """Attach the dim_player version valid on each play's game_date.

    Half-open SCD2 intervals: valid_from <= game_date < valid_to.
    broadcast_dim: True forces a broadcast hint, False disables broadcast,
    None leaves the choice to Spark.
    """
    f = spark.table("lake.marts.fact_play")
    d = spark.table("lake.marts.dim_player").select(
        "player_id", "player_sk", "valid_from", "valid_to"
    )
    if broadcast_dim is False:
        spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "-1")
        spark.conf.set("spark.sql.adaptive.autoBroadcastJoinThreshold", "-1")
    if broadcast_dim is True:
        from pyspark.sql.functions import broadcast

        d = broadcast(d)
    cond = (f.player_id == d.player_id) & (f.game_date >= d.valid_from) & (f.game_date < d.valid_to)
    return f.join(d, cond, "left").select(f["*"], d.player_sk)
```

Selecting only the four dim columns you need keeps the broadcast small.
A wide dim with 40 columns can push it past the threshold and silently
change the plan.

</details>

## Gotchas

- **`BETWEEN` double-counts boundary days** with half-open intervals: a
  play on the exact `valid_to` date matches two versions.
- **Config leaks between runs.** `spark.conf.set` persists for the
  session. Unset it, or use a fresh session per experiment.
- **First run is slower** (JIT warm-up, file listing, jar loading).
  Discard it.
- **Broadcast is decided on estimated size.** Iceberg reports table size
  from metadata; a big dim with a selective filter may still not
  broadcast until AQE sees the real size.
