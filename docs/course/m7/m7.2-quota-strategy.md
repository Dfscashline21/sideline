# M7.2 · Design the college quota strategy

> **Ticket:** [#95](https://github.com/Dfscashline21/sideline/issues/95) ·
> **Mode:** hand · **Time:** 2 to 3 hours ·
> **Needs:** your NBA extractor (M2.3 to M2.5), a free
> [CollegeBasketballData.com](https://collegebasketballdata.com) API key

## Why this matters

Most real APIs are budgeted: rate limits, monthly quotas, per-call
pricing. A pipeline that ignores the budget works fine in testing and
then fails on the 23rd of the month, or runs up a bill. The senior move
is to **design the budget first**: decide what each call is worth, get
everything cheap from somewhere else, and make the code refuse to
overspend.

## What you'll produce

- `docs/design/college-quota.md`: the monthly call budget, which data
  comes from which source, and why.
- `ingestion/sideline_ingestion/quota.py`: a guard that **refuses** to make
  a call that would exceed the budget, with tests.

## Steps

### 1. Inventory both sources (45 min)

**ESPN season files** (free, unlimited, same pattern as M1). List the
releases that exist for each college league:

```bash
gh api --paginate 'repos/sportsdataverse/sportsdataverse-data/releases?per_page=100' \
  --jq '.[].tag_name' | grep -E 'espn_(mens|womens)_college_basketball' | sort
```

**CollegeBasketballData.com API** (1,000 calls a month on the free key).
Install the client and list what it can do:

```bash
uv add cbbd
uv run python -c "import cbbd; print([n for n in dir(cbbd) if n.endswith('Api')])"
```

Each `...Api` class has `get_...` methods (games, plays, substitutions,
lineups, draft picks, ratings, lines, recruiting, transfer portal…).
Every method call is one API call against your quota.

Build a table:

| Data you need | ESPN file? | API endpoint? | Calls per season if from API |
|---|---|---|---|
| Schedule and results | | | |
| Team and player box scores | | | |
| Play-by-play | | | |
| Draft picks (college → pro links for M7.4) | | | |
| Lineups | | | |
| Ratings (e.g. adjusted efficiency) | | | |

✅ **Checkpoint:** you've found that the heavy, per-game data is
available as files, and that a few useful things only exist in the API.

### 2. Do the arithmetic (30 min)

Count calls the way the API counts them: **per request**, not per row.
For each candidate API dataset, estimate:

- calls for a one-off **backfill** (all historical seasons)
- calls for a **normal month** of daily runs
- calls for **tournament week** (M7.10 will replay it)
- calls for **retries**: a failed call usually still counts

<details>
<summary>Hint 1 · Nudge: per-game endpoints are the trap</summary>

Anything you fetch **per game** costs thousands of calls a season: Division
I men's alone has about 6,000 games. Anything fetched **per season** or
**per year** costs one call, or one per team at most. Which of your API
datasets are per-season?

</details>

<details>
<summary>Hint 2 · Approach: a budget with headroom</summary>

A sensible split of 1,000 calls:

| Bucket | Share | Why |
|---|---|---|
| Scheduled runs | ~60% | Predictable daily/weekly calls |
| Backfill | ~20% | Spread over several months if needed |
| Retries and reruns | ~10% | Failures happen; don't let them exhaust the month |
| Reserve | ~10% | Manual debugging, tournament surprises |

The exact split is your decision; documenting the reasoning is the
deliverable.

</details>

### 3. Write the design doc (30 min)

`docs/design/college-quota.md`, short:

1. **Sources:** what comes from ESPN files and what from the API, and why.
2. **Budget:** calls per month by bucket, with the arithmetic shown.
3. **Guard behaviour:** what happens when a call would exceed the budget
   (refuse, log, alert?), and when the month resets (calendar month, UTC?).
4. **What we'd do with a paid tier:** one paragraph. Interviewers like
   "what would change with more budget?"

### 4. Design the guard before coding it (20 min)

Questions to answer in writing first:

- **Where is the counter stored?** It must survive restarts and be shared
  by every run. In memory won't do. A small Postgres table (Compose already
  runs Postgres) or a JSON object in MinIO are both reasonable.
- **When do you count?** Before the call (reserve) or after (record)? If
  two runs check at the same time with 1 call left, what happens?
- **What's the unit of refusal?** A single call, or a whole planned run
  ("this backfill needs 120 calls and only 80 remain, so don't start")?

### 5. Write the guard (45 min)

Interface suggestion (yours may differ):

```python
class QuotaExceeded(Exception): ...


class CallBudget:
    def __init__(self, store: BudgetStore, monthly_limit: int, reserve: int) -> None: ...
    def remaining(self, now: datetime) -> int: ...
    def reserve(self, calls: int, now: datetime) -> None:
        """Atomically reserve `calls` or raise QuotaExceeded."""
```

<details>
<summary>Hint 3 · Skeleton: an atomic reservation in Postgres</summary>

The race in step 4 disappears if the check and the increment happen in
**one statement**:

```sql
insert into api_quota (provider, month, used) values (:provider, :month, 0)
on conflict (provider, month) do nothing;

update api_quota
set used = used + :calls
where provider = :provider and month = :month
  and used + :calls <= :limit
returning used;
```

No row returned means the reservation would exceed the limit: raise
`QuotaExceeded`. The month key (`'2027-03'`) makes the reset automatic.

</details>

Take the time as a parameter (`now`) instead of calling
`datetime.now()` inside. That makes month rollover testable.

### 6. Test it (30 min)

Tests in `ingestion/tests/test_quota.py`. At minimum:

- reserving within the limit succeeds and `remaining` drops
- reserving past the limit raises `QuotaExceeded` and **doesn't** change
  the counter
- a new month starts at zero
- the reserve bucket is respected (scheduled runs can't spend it)

Use an in-memory fake `BudgetStore` for unit tests; one integration test
against the Compose Postgres proves the SQL.

✅ **Checkpoint:** a test that calls `reserve` in a loop stops exactly at
the limit.

## Gotchas

- **Never put the API key in code or the repo.** `.env` locally
  (`CBBD_API_KEY=`), add it to `.env.example` with an empty value.
- **The client may make more than one HTTP call per method** (pagination).
  Check what one method call actually sends before trusting your
  arithmetic: log requests while testing.
- **Failed calls count.** A retry loop with backoff (M2.3) can burn
  quota fast. Retries must go through the guard too.
