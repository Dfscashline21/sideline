## Why this matters

"What happens when Spark runs this job?" and "Why is this stage slow?"
are the core of every Spark interview. The answers all come back to one
idea: **data has to move between machines, and moving it is expensive.**
This lab builds that mental model with small experiments where you
watch it happen in the Spark UI.

- `docs/notes/m7-spark-cheatsheet.md`: one page, in your own words.
- The ability to explain, out loud with no notes, **what a shuffle is and
  why it's expensive** (the acceptance criterion).

## Session 1 · Driver, executors, jobs, stages, tasks (60 min)

**Read:** [Spark cluster mode overview](https://spark.apache.org/docs/latest/cluster-overview.html)
and the "Jobs", "Stages" and "SQL / DataFrame" sections of the
[Web UI guide](https://spark.apache.org/docs/latest/web-ui.html).

The vocabulary, from biggest to smallest:

| Term | What it is |
|---|---|
| **Driver** | Your Python process. Builds the plan, schedules work, collects results |
| **Executor** | A worker process that runs tasks. In `local[4]` mode there's one executor with 4 cores |
| **Job** | Triggered by an **action** (`count`, `write`, `collect`). Transformations alone do nothing |
| **Stage** | A chunk of a job with no data movement inside it. Stages are cut at shuffles |
| **Task** | One stage applied to one partition. One task runs on one core |

### Exercise 1.1: laziness

```python

df2 = df.filter("x = 3")
```

## Session 2 · Narrow vs wide, and the shuffle (90 min)

**Read:** the "Shuffle operations" section of the
[RDD programming guide](https://spark.apache.org/docs/latest/rdd-programming-guide.html#shuffle-operations).
It's old API, but the explanation is still the best one.

- A **narrow** transformation (`filter`, `withColumn`, `select`) computes
  each output partition from **one** input partition. No data moves.
- A **wide** transformation (`groupBy`, `join`, `orderBy`, `distinct`)
  needs rows with the same key **together**, wherever they started. Every
  task writes its rows into buckets by key (**shuffle write**), then
  every task of the next stage fetches its bucket from all of them
  (**shuffle read**). That's the shuffle.

### Exercise 2.1: see the stage boundary

```python
games = (
    spark.range(20_000_000)
    .withColumn("team", F.col("id") % 30)
    .withColumn("pts", (F.rand() * 140).cast("int"))
)
games.groupBy("team").agg(F.avg("pts")).collect()
```

In the SQL tab, open the query's diagram. Find the `Exchange` node.
In the Stages tab, find **Shuffle Write** on the first stage and
**Shuffle Read** on the second. Note the sizes.

### Exercise 2.2: why is it expensive?

Write down, in your own words, the four costs a shuffle adds. Then check
yourself:

<details>
<summary>The four costs</summary>

1. **Serialization:** rows are turned into bytes to be written.
2. **Disk:** shuffle files are written to local disk, even in memory-heavy jobs.
3. **Network:** on a real cluster, every reduce task fetches from every map
   task (N × M connections).
4. **A barrier:** the next stage can't start until the whole previous stage
   finishes, so one slow task holds everyone up (that's what makes
   **skew** so damaging, M7.7).

</details>

### Exercise 2.3: shuffle partitions

```python
spark.conf.get("spark.sql.shuffle.partitions")  # default "200"
spark.conf.set("spark.sql.adaptive.enabled", "false")
games.groupBy("team").agg(F.avg("pts")).collect()
```

How many tasks ran after the shuffle? How many of them had any data
(only 30 teams exist)? Now set `spark.sql.adaptive.enabled` back to
`true` and rerun. What changed in the task count? You've just seen AQE
coalesce partitions. Session 4 explains it.

## Session 3 · Join strategies (75 min)

**Read:** "Join Strategy Hints" in the
[SQL performance tuning guide](https://spark.apache.org/docs/latest/sql-performance-tuning.html).

| Strategy | How it works | When Spark picks it |
|---|---|---|
| **Broadcast hash join** | Small side copied to every executor; big side never shuffles | Small side below `spark.sql.autoBroadcastJoinThreshold` (default **10 MB**), or a `broadcast()` hint |
| **Shuffle hash join** | Both sides shuffled by key; hash table built per partition | Rarely by default; with a `shuffle_hash` hint |
| **Sort-merge join** | Both sides shuffled **and sorted** by key, then merged | The default for two large sides |
| **Broadcast nested loop join** | Every row against every row of a broadcast side | Non-equi joins with no equality key. Dangerous at scale |

### Exercise 3.1

```python
players = (
    spark.range(5_000)
    .withColumnRenamed("id", "player_id")
    .withColumn("name", F.concat(F.lit("p"), "player_id"))
)
events = spark.range(20_000_000).withColumn("player_id", F.col("id") % 5_000)

events.join(players, "player_id").explain()
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "-1")
events.join(players, "player_id").explain()
```

Which join appears in each plan? Count the `Exchange` nodes in each.
Time both with `.write.format("noop").mode("overwrite").save()` (runs
the whole job without writing anything). Reset the threshold afterwards
with `spark.conf.unset(...)`.

million rows?

## Session 4 · Adaptive Query Execution (60 min)

**Read:** the "Adaptive Query Execution" section of the tuning guide.

AQE re-plans **between stages**, using real sizes measured at runtime.
It's on by default (`spark.sql.adaptive.enabled = true`). Three features:

1. **Coalescing partitions:** merges small post-shuffle partitions
   (you saw it in exercise 2.3).
2. **Switching join strategy:** turns a sort-merge join into a broadcast
   join if a side turns out small after filtering.
3. **Skew join handling:** splits a huge partition into smaller ones.
   A partition counts as skewed when it's larger than **both**
   `skewedPartitionFactor` (default 5) × the median partition size **and**
   `skewedPartitionThresholdInBytes` (default 256 MB).

That 256 MB default matters: on laptop-sized data AQE will often **not**
consider anything skewed. You'll lower it on purpose in M7.7.
