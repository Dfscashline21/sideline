# M7.9 · DuckDB vs Spark crossover benchmark

> **Ticket:** [#102](https://github.com/Dfscashline21/sideline/issues/102) ·
> **Mode:** mixed: core logic by hand, boilerplate by agent ·
> **Time:** 4 hours · **Needs:** M7.5, M1.7 (how to measure properly)

## Why this matters

"Why did you use Spark?" is a question you must be able to answer with
evidence. On one machine, DuckDB is usually faster than Spark for small
and medium data: no JVM start-up, no task scheduling, no shuffle files.
Spark's strengths (spilling, distribution, fault tolerance) only pay off
past some size. Finding **your machine's** crossover point, with a chart,
turns "it depends" into a real answer.

## What you'll produce

- `spark/bench/`: a harness that runs the same query on DuckDB and Spark
  at increasing data sizes and writes results to a CSV.
- A crossover chart (time vs data size, one line per engine) in
  `docs/notes/m7-img/` and a write-up in `docs/notes/m7.md`.

## Steps

### 1. Pick a fair workload (30 min)

Choose **one** query representative of Sideline work that both engines
run from the **same files**. A good one has a join and an aggregation,
for example player-season totals joined to `dim_player`, grouped by
league and season.

Write down:

- **Input format:** Parquet files on local disk (not the Iceberg catalog,
  so catalog overhead doesn't muddy the comparison; mention it as a
  follow-up).
- **Output:** a small result collected to the driver, or written to
  Parquet. Same for both engines.
- **Machine:** CPU, cores, RAM, and the memory each engine may use.

### 2. Build the data-size ladder (45 min)

Generate datasets at roughly doubling sizes from real play-by-play,
e.g. 1M, 2M, 4M, … up to well past what fits comfortably in RAM. Grow
the data by replicating real rows with a distinguishing column (e.g.
`copy_id`) so value distributions stay realistic.

<details>
<summary>Hint · Where's the interesting part of the ladder?</summary>

Your RAM size is the landmark. Note the on-disk Parquet size **and** the
in-memory size (much bigger, because Parquet is compressed). Make sure the
ladder has several points past the size where the in-memory data no
longer fits. That's where engines start spilling to disk, and where
behaviour changes.

Disk space check before you start: the largest rung can be tens of GB.

</details>

### 3. Decide what you're timing (30 min)

Write the rules **before** you see any numbers:

- Spark session start-up (the JVM, a few seconds) is **excluded** from
  query time but **reported separately**: for a 1-second query it
  matters, and an honest chart says so.
- One warm-up run per engine per size, then the median of 3 to 5 runs.
- Same parallelism: DuckDB `SET threads = N`, Spark `local[N]`, same N.
- Memory limits: DuckDB `SET memory_limit = 'XGB'`, Spark
  `spark.driver.memory` (in local mode the driver runs everything).
  Give both the same budget.
- Spark `spark.sql.shuffle.partitions`: pick one value and keep it
  fixed, or let AQE coalesce. Say which.

### 4. Write the harness (60 min, agent may draft)

Prompt the agent with your decisions from steps 1 to 3:

> Write `spark/bench/crossover.py`: for each dataset path in a list, run
> query file `X.sql` on DuckDB and Spark under these rules: *(paste)*.
> Append one row per run to `spark/bench/results.csv` with engine, rows,
> bytes on disk, run number, seconds, and whether it was a warm-up. Typed,
> no new dependencies except what's in the `spark` group. Kill a run that
> exceeds a timeout and record it as a timeout, not a crash.

Review checklist:

- [ ] Both engines read the **same** files and return the **same** result
      (the harness checks row counts or a checksum of the result)
- [ ] Spark start-up time is measured but not included in query time
- [ ] Warm-up runs are recorded but flagged
- [ ] DuckDB connection and Spark session are created **once** per size,
      not per run (or that choice is deliberate and documented)
- [ ] Timeouts and out-of-memory errors are recorded as results, not lost

### 5. Run it and chart it (60 min)

Run the ladder. Close other heavy apps, plug in power. Plot median time
vs rows (or GB) for both engines, **log scale on both axes**, timeouts
marked. A plotting library in the `spark` group is fine (an agent can
write the plotting script).

✅ **Checkpoint:** a chart with two lines and a visible answer to "where
do they cross?"

### 6. Interpret honestly (30 min)

Write in `docs/notes/m7.md`:

1. Where's the crossover on your machine, in rows and GB? Or, if Spark
   never wins locally (a perfectly possible result), the largest size
   tested and why you think it didn't.
2. What changed at the crossover: did DuckDB start spilling? Did Spark's
   fixed overheads stop mattering?
3. What would move the crossover: more RAM, more cores, a real cluster,
   a different query shape (very wide shuffles)?
4. What you'd recommend for Sideline's real data volumes, and why.

<details>
<summary>Hint · Things worth checking in the results</summary>

- DuckDB's line often bends upwards once data exceeds its memory limit
  (it spills to a temp directory). Check the size where that happens.
- Spark's line is often flat at small sizes: fixed overhead dominates.
  The flat part tells you its minimum cost per query.
- If either engine failed outright at some size, that's a data point.
  Record the error.

</details>

### 7. Ship it

Harness, results CSV (small, so it's fine to commit), chart, write-up.
PR with `Closes #102`.

## Gotchas

- **Don't compare a warm engine with a cold one.** The OS file cache
  favours whichever engine runs second. Alternate the order, or run
  each engine's ladder after a fresh read of the files.
- **Laptop thermal throttling** shows up as later runs getting slower.
  Watch for a drifting median.
- **Generated data that's too uniform** (e.g. `range()` ids) hides
  real-world costs like skew and string handling. Use real rows.
