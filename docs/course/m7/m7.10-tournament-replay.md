# M7.10 · March Madness tournament-week replay

> **Ticket:** [#103](https://github.com/Dfscashline21/sideline/issues/103) ·
> **Mode:** hand · **Time:** 4 hours ·
> **Needs:** M7.3 and M7.4 (college data through staging), M6 (Dagster
> partitioned pipeline), M7.2 (quota)

## Why this matters

Sports data has extreme peaks. The NCAA tournament's first round is 32
men's games over two days (Thursday and Friday), and the women's first
round runs alongside it; on a normal Tuesday in March there's a handful.
A pipeline sized for the average day can fall behind exactly when people
care most. **Load testing with a realistic replay** before the real
event is standard practice, and "how did you know it would keep up?" is
a strong interview story.

## What you'll produce

- A replay script that feeds a real past tournament week through the
  **full** pipeline (ingest → dbt build → quality checks → publish) on the
  original game schedule, sped up.
- A freshness target, written down **before** the replay.
- A results table proving every game met the target, in `docs/notes/m7.md`.

## Steps

### 1. Define the freshness target (20 min)

Freshness = time from a game's **final buzzer** to its data being
**queryable in the marts**. Decide a target and write it down first,
e.g. "every game's box score and play-by-play are in `marts` within
30 minutes of the final". Base it on what a user would expect, not on
what you think the pipeline can do.

Also decide what you'll measure for "final buzzer" (the schedule's end
time? the last play's wallclock?) and for "queryable" (a dbt run
completing? a row visible via Spark/DuckDB?).

### 2. Pick the week and its games (30 min)

Use a completed tournament, e.g. 2025. In the ESPN schedule files,
`season_type = 3` includes the NIT, CBI and College Basketball Crown, so
filter on the headline:

```sql
select game_id, game_date_time, notes_headline
from read_parquet('https://github.com/sportsdataverse/sportsdataverse-data/releases/download/espn_mens_college_basketball_schedules/mbb_schedule_2025.parquet')
where notes_headline like 'Men''s Basketball Championship%'
order by game_date_time;
```

The 2025 men's first round was 20 to 21 March. Include women's games
from the matching release and decide whether to include the NIT (it
loads the pipeline too).

✅ **Checkpoint:** a list of the week's games with start times. Plot
games per hour: the peak hour is what your pipeline must handle.

### 3. Design the replay (45 min)

The pipeline must believe it's tournament week. Options, from simplest:

1. **Clock-driven replay:** a script walks the schedule at speed-up
   factor k (e.g. 1 real minute = 30 replay minutes). When a game
   "ends", it makes that game's raw files available (copies them into
   the landing area, or tells your extractor's source stub to serve them).
2. **Partition replay:** launch the Dagster partitions for each game day
   with the original timestamps injected, as your M6.5 post-game sensor
   would have.

<details>
<summary>Hint · Things the design must answer</summary>

- **Speed-up and the target.** If you replay 30x faster, a 30-minute
  freshness target becomes 1 real minute. Scale the target, or replay
  in real time for the peak hours only.
- **Quota.** A replay must not spend real API calls. Serve data from
  files or a recorded fixture (M7.2's guard should refuse anyway; check it).
- **Isolation.** Replay into a separate namespace or a branch of the
  tables, so you don't overwrite production marts with re-ingested data.
- **Timestamps.** Record "available at" and "queryable at" per game, in
  replay time.

</details>

### 4. Instrument freshness (30 min)

For every game, capture:

| Column | Source |
|---|---|
| `game_id` | schedule |
| `final_at` (replay time) | when the replay released the game |
| `ingested_at` | extractor log / raw object timestamp |
| `marts_at` | when a query first sees the game in `marts` |
| `freshness_min` | `marts_at − final_at` |

A small polling script that checks for each released game in the marts
every few (replay) minutes is enough.

### 5. Run it (60 min)

Run the whole week. Watch the Dagster UI during the peak: are runs
queuing? Is one step (often dbt build, or a Spark job if you put one in
the path) the bottleneck?

✅ **Checkpoint:** every game has a `freshness_min`.

### 6. Prove it, or fix it (45 min)

Report: max and 95th-percentile freshness, the number of games over
target, and freshness by hour against games per hour.

If any game missed the target: find the bottleneck, change one thing
(concurrency limits, partition-level runs instead of full rebuilds,
`dbt build --select` for only affected models), and replay the peak day
again. The ticket is done when **all** games meet the target.

<details>
<summary>Hint · Common bottlenecks</summary>

- **Full `dbt build` on every game.** Rebuilding every model for each
  game is wasted work. Build only the affected partitions/models (M5.6's
  incremental models should make this cheap).
- **Runs queued behind each other.** Dagster concurrency limits that
  are sensible for daily runs serialise a burst. Check run queue settings.
- **A non-incremental mart** (e.g. a full-table lineup rebuild) that grows
  with the season.

</details>

### 7. Ship it

Replay script, the freshness table (as a small CSV or a notes table),
and the write-up: target, results, bottleneck found, change made. PR
with `Closes #103`.

## Gotchas

- **Time zones.** Schedule times are UTC; tournament sites span US time
  zones. Keep everything in UTC.
- **Overtime and delays** make games end later than planned. Use actual
  end times from the data, not start + 2 hours.
- **The replay itself can be the bottleneck.** If your polling script
  hammers the catalog, it slows the pipeline it's measuring.
