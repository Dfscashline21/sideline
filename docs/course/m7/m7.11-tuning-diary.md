## Why this matters

This post is the M7 portfolio artifact. A hiring manager won't run your
Spark jobs, but they will read 5 minutes of "here was the problem, here's
the evidence, here's what I changed, here's the result". A **diary**
format (dated entries, before and after) shows how you think, which
is worth more than a polished tutorial anyone could copy.

## What you'll produce

- `docs/blog/spark-tuning-diary.md`, also published somewhere public
  (your site, dev.to, Hashnode, Medium, or GitHub Pages).
- A link to it from the README's "Decisions" or "Numbers" section.

## Steps

### 1. Gather the evidence (30 min)

Make an inventory in `docs/notes/m7.md` of what you already have:

| Lab | Before screenshot | After screenshot | Numbers |
|---|---|---|---|
| M7.6 as-of join | sort-merge plan | broadcast plan | medians |
| M7.7 skew | skewed task metrics | after salting, after AQE | stage times |
| M7.8 lineups | job DAG / SQL tab | | rows, run time |
| M7.9 crossover | | | chart |

If something's missing, re-run that experiment now. You can't
screenshot a session that has ended (unless you turned on the event log
and run the history server).

### 2. Pick the story (20 min)

Three to four entries, not everything. Pick the ones where:

- the **before** screenshot shows a visible problem (one long task, a
  huge shuffle, an extra `Exchange`)
- you can explain **why** the fix works, not only that it did
- there's a number that changed

A good arc: start with the crossover ("when should we even use Spark?"),
then the as-of join, then skew, ending on the lesson that fixing the data
(no sentinel keys) beat tuning the engine.

### 3. Outline each entry (30 min)

Same shape every time, so readers can skim:

```markdown
## Day 3: the job with one slow task

**Symptom.** One task of 32 took ~6x longer than the median.
**Evidence.** [screenshot: Stages tab summary metrics, max vs median]
**Diagnosis.** 7.8% of events had no player and were mapped to key -1...
**Fix.** ...
**Result.** Stage time from __ s to __ s. [after screenshot]
**What I'd tell my past self.** One sentence.
```

### 4. Prepare the screenshots (45 min)

- **Crop** to the part that matters, and **annotate** it: an arrow or box
  around the max task, the `Exchange` node, the `skew=true` label.
- Width ~1200 px, PNG, under ~300 KB each.
- Alt text that states the finding ("Stage 4: max task 38 s vs median
  4 s"), not "screenshot".
- Remove anything private: hostnames, paths with your username,
  internal URLs.

### 5. Write it (2 hours)

Rules that make technical posts readable:

- **Lead with the result.** First paragraph: what you tuned and the
  biggest number that moved.
- **One idea per entry.** If an entry needs two screenshots to explain,
  it might be two entries.
- **Explain the mechanism in plain words.** "Spark sends every row with
  the same key to the same task" beats "hash partitioning".
- **Be honest about the setup.** Laptop, `local[N]`, data size. Local
  results don't transfer directly to a cluster, and saying so builds
  credibility.
- **End with what you'd do on a real cluster** and what you'd measure next.

Aim for 1,200 to 2,000 words.

### 6. Get one review (async)

Ask one person (a colleague, a friend in data, a community Slack) to
read it and tell you the one part they didn't understand. Fix that part.
An agent may proofread **after** you've written it: spelling and
clarity only, no rewriting.

### 7. Publish and link

1. Commit `docs/blog/spark-tuning-diary.md` and images to the repo.
2. Publish to your chosen platform; set the canonical URL to one place.
3. Link it from the README.

PR with `Closes #104`.

## Gotchas

- **Screenshots of a moving target.** If you re-ran an experiment with
  different settings, make sure before and after use the same data and
  the same `local[N]`.
- **Big images in git.** Keep them small; the repo has a large-file
  pre-commit hook for a reason.
- **Over-claiming.** "10x faster" on a laptop toy example invites a
  hard follow-up question. State exactly what was measured.
