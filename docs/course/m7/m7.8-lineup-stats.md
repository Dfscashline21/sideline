# M7.8 · 5-player lineup stats

> **Ticket:** [#101](https://github.com/Dfscashline21/sideline/issues/101) ·
> **Mode:** hand · **Time:** 4 to 5 hours ·
> **Needs:** M7.5 (Spark + Iceberg with SQL extensions), M1.5
> (sessionization), play-by-play and player box scores for at least the NBA

## Why this matters

Lineup analysis ("how does this five-player unit do together?") is a real
basketball question and a great data-engineering one. Rebuilding who is
on court from substitution events is **stateful sessionization**, and
naively generating combinations is a self-join that **explodes**:
choosing 5 of 13 rostered players gives 1,287 combinations per team per
game. You'll practise controlling that blow-up, then writing the result
idempotently with `MERGE INTO`.

## What you'll produce

- `spark/sideline_spark/lineups.py`: for each game, the stints when each
  five-player unit was on court, and per-lineup totals (seconds played,
  points for and against, possessions if you have them from M1.5).
- An Iceberg table, e.g. `lake.marts.lineup_stats`, written with
  `MERGE INTO` so re-running a game doesn't duplicate rows.
- A paragraph explaining the table's partitioning.

## Steps

### 1. Understand how substitutions are recorded (30 min)

The two data sources differ, and code written for one breaks on the other:

| League data | Substitution rows | Columns |
|---|---|---|
| NBA (ESPN) | **One row** per swap: `"X enters the game for Y"` | `athlete_id_1` = entering, `athlete_id_2` = leaving |
| College (ESPN, men's and women's) | **Two rows** per swap: `"Subbing in for <team>-<name>"` and `"Subbing out for …"` | One player per row in `athlete_id_1`; direction is in `text` |

Look at a few of each yourself. Also look at what happens at the start of
each period: do substitutions get logged, or does the lineup silently
change? (Starters come from the player box score: `starter = true`.)

✅ **Checkpoint:** you can state, for one NBA and one college game, how
you'll know the five players on court at any moment.

### 2. The naive approach, and why not (20 min)

Think through, don't run: "for each game, self-join the team's players
five times with `p1 < p2 < p3 < p4 < p5`, then check which combinations
were on court." How many rows per team-game? Per season? That's the
explosion the ticket is about. Write the numbers in your notes.

The better approach builds lineups **from events**, so only lineups that
actually happened ever exist.

### 3. Track the on-court set (90 min)

<details>
<summary>Hint 1 · Nudge</summary>

Each substitution changes the set of five. Between two substitutions
(or period boundaries), the set is constant: that's a **stint**. You
need, for each team, the set after every substitution event.

</details>

<details>
<summary>Hint 2 · Approach</summary>

Two workable designs:

1. **Window-based (pure DataFrame):** represent each event as a delta
   (+player / −player), then compute a running set with an ordered
   window: `collect_list` of deltas over
   `rowsBetween(Window.unboundedPreceding, Window.currentRow)`, reduced to
   the current set with `aggregate` or a small UDF. Simple; the running
   list gets long, but games are small.
2. **Grouped map:** `groupBy("game_id", "team_id").applyInPandas(fn, schema)`
   where `fn` walks one game's events in order with a Python set. Easy to
   read and test; Python per group is slower but games are independent.

Either way, sort the five IDs and join them into a `lineup_key` string
(`"123-456-789-1011-1213"`) so the same five always make the same key.
Validate: every stint must have exactly 5 players. Count and inspect
those that don't.

</details>

<details>
<summary>Hint 3 · Skeleton (grouped map)</summary>

```python
def stints_for_game(pdf: pd.DataFrame) -> pd.DataFrame:
    pdf = pdf.sort_values("event_seq")
    on_court: set[int] = set(starters_for(pdf))  # from the box score
    rows = []
    start_sec = 0.0
    for ev in pdf.itertuples():
        if is_period_start(ev):
            ...  # reset / re-read lineup
        if is_sub(ev):
            rows.append(close_stint(on_court, start_sec, ev.game_seconds))
            apply_sub(on_court, ev)  # NBA: in+out; college: in OR out
            start_sec = ev.game_seconds
    ...
    return pd.DataFrame(rows)
```

</details>

Then aggregate stints to lineup totals: seconds on court, points scored
by the team and by the opponent during each stint (from the score
columns at stint start and end).

✅ **Checkpoint:** for 3 games, total lineup seconds per team equals game
length (48 min plus overtime for the NBA; 40 for men's college, 4 × 10
for women's). Points for the team across all its stints equals its final score.

### 4. Choose the partitioning (30 min)

Write down the queries this table serves, then pick partitions:

- "Best lineups for team X this season": filters on league, season, team
- "All lineups including player Y": can't use partitions well (5 player
  columns); think about whether that matters
- Daily pipeline writes: one game day at a time

<details>
<summary>Hint · Things to weigh</summary>

- `league` and `season` are low-cardinality and in almost every filter:
  good partition columns.
- Partitioning by `team_id` or `game_id` creates many small files per
  season. Iceberg can use `bucket(team_id, N)` if you need it (you met
  partition transforms in M4.4).
- A `MERGE INTO` only rewrites files in partitions it touches. Partition
  so a daily merge touches a small part of the table.

</details>

### 5. Write with `MERGE INTO` (45 min)

Create the table once, then merge each run's results. The key that
identifies a row is (league, season, team, lineup), or per game if you
store per-game rows. Decide which. Requires the Iceberg SQL extensions
from M7.5.

```sql
MERGE INTO lake.marts.lineup_stats t
USING lineup_updates s
ON  t.league = s.league AND t.season = s.season
AND t.team_id = s.team_id AND t.lineup_key = s.lineup_key
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *
```

Careful: if your table holds **season totals** and you merge **one
game's** stats, `UPDATE SET *` overwrites the season total with one
game. Either store per-game rows and aggregate in a view, or recompute
the affected season totals before merging. Pick one and say why.

Run the same game twice. Row count must not change. Then:

```sql
SELECT snapshot_id, operation FROM lake.marts.lineup_stats.snapshots;
```

The second merge creates a new `overwrite` snapshot even though the data
is identical. That's normal; note what it means for table maintenance.

✅ **Checkpoint:** re-running is idempotent, totals still reconcile.

## Gotchas

- **Lineups that aren't five players.** Missing substitutions in the
  source are common. Count them, keep them out of totals, report the rate.
- **Simultaneous events.** Fouls, free throws and substitutions can share
  a clock time; order by the event sequence column, never the clock.
- **College `text` parsing.** "Subbing in for" vs "Subbing out for" is the
  only direction signal. Test it on both men's and women's games.
