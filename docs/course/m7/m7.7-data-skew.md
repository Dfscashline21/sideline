## Why this matters

Skew is the most common reason a Spark job that "should" take minutes
takes hours: 199 tasks finish in seconds and one runs forever, because
one key holds a huge share of the rows. "How do you detect and fix
skew?" is asked in nearly every Spark interview. A good answer names
**where you saw it** (the task-time distribution in the Stages tab) and
**two fixes with trade-offs** (salting, AQE skew join).

## What you'll produce

- `spark/sideline_spark/skew.py`: a join that suffers from skew, plus
  two fixed versions (salting, AQE).
- Screenshots: the skewed stage, and the same stage after each fix.
- Before/after stage times in `docs/notes/m7.md`.

## Where the skew comes from in Sideline

Measured on NBA play-by-play (2024 to 2026 seasons, ~1.9M events):

| Key | Rows | Why |
|---|---|---|
| Median player (`athlete_id_1`) | ~1,200 events | |
| Busiest player | ~11,500 events | Stars touch the ball more: ~9x the median |
| `athlete_id_1` IS NULL | ~147,000 events (7.8%) | Team events: timeouts, team rebounds, period ends |

The NULLs are the nastiest. If a pipeline replaces NULL with a sentinel
like `-1` or `0` "so the join works", every team event lands on **one
key**, about 13x the biggest star. College data adds data-rich programs:
schools whose games have fuller play-by-play than others.

## Steps

### 1. Build a join that skews (45 min)

Join play-by-play events to a per-player table on player ID, where team
events carry a sentinel ID (do it deliberately in this experiment):

```python
from pyspark.sql import functions as F

events = spark.table("lake.raw.pbp").withColumn(  # or your fact_play; all leagues
    "player_key", F.coalesce("athlete_id_1", F.lit(-1))
)
```

Small data won't show skew on a laptop: everything fits in a few MB.
Make it big enough to see by unioning all leagues and seasons you have,
and if needed multiplying it (`crossJoin(spark.range(k))` with a column
that keeps rows distinct). Aim for a fact side of **tens of millions of rows**.

Use a sort-merge join so both sides shuffle by key (disable broadcast:
`spark.sql.autoBroadcastJoinThreshold = -1`). Turn **AQE off** for the
baseline so you see the raw problem:

```python
spark.conf.set("spark.sql.adaptive.enabled", "false")
spark.conf.set("spark.sql.shuffle.partitions", "32")
```

Run with the `noop` writer, median of 3.

### 2. See it in the UI (30 min)

Stages tab → the join's stage → **Summary Metrics for Completed Tasks**.
Compare **Max** with **Median** for *Duration* and *Shuffle Read Size*.
Skew looks like a max many times the median, and an **Event Timeline**
where one bar keeps going after the rest have finished.

✅ **Checkpoint:** screenshot of the summary metrics and timeline
showing one task far larger than the median. Save as
`docs/notes/m7-img/m7.7-skewed.png`.

Confirm the cause with data, not just the UI:

```python
events.groupBy("player_key").count().orderBy(F.desc("count")).show(5)
```

### 3. Fix 1: salting (60 min)

Spread the hot key across N partitions by adding a random **salt** on
the big side and replicating the small side N times.

<details>
<summary>Hint 1 · Approach</summary>

- Big side: `salt = floor(rand() * N)`.
- Small side: cross join with `range(N)` so every key exists with every salt.
- Join on `(player_key, salt)`.

The hot key's rows now go to N different partitions. The cost: the
small side is N times bigger.

</details>

<details>
<summary>Hint 2 · Skeleton</summary>

```python
N = 16
big = events.withColumn("salt", (F.rand(seed=42) * N).cast("int"))
small = players.crossJoin(spark.range(N).select(F.col("id").cast("int").alias("salt")))
fixed = big.join(small, ["player_key", "salt"])
```

Refinement worth trying: salt **only the hot keys** (e.g. the sentinel
and the top 10 players) and leave the rest unsalted, so the small side
grows much less.

</details>

Measure (median of 3, AQE still off) and screenshot the same stage.
Check the output row count matches the unsalted join.

### 4. Fix 2: AQE skew join (45 min)

Turn AQE back on with skew handling, and remove the salt:

```python
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
```

Run it. It probably **won't** help yet. A partition only counts as
skewed when it's bigger than **both** 5 × the median partition and
`spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes` (default
**256 MB**). Laptop partitions are rarely that big. Lower the threshold
and the target size for the split pieces:

```python
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes", "8MB")
spark.conf.set("spark.sql.adaptive.advisoryPartitionSizeInBytes", "8MB")
```

In the SQL tab, the join node should now read **`SortMergeJoin(skew=true)`**,
with `AQEShuffleRead` nodes above the exchanges. That label is your
proof AQE split the partition.

For reference, a synthetic test while writing this lab (30M rows, 80%
on one key, `local[4]`): ~6 s with skew unhandled, ~2.7 s once AQE
split the partition with the lowered threshold, ~4.3 s with 16-way
salting. Your numbers will differ; the direction should not.

Plus a paragraph: which fix would you ship, and why?

<details>
<summary>Hint 3 · Trade-offs to mention</summary>

- **AQE**: no code change, works only for joins (and only some join
  types), needs thresholds tuned to your data sizes.
- **Salting**: works anywhere, including aggregations; costs code
  complexity and replicates the small side.
- **The real fix for the sentinel**: don't create it. Team events
  shouldn't join to a player table at all. In an **inner** join, NULL
  keys can't match, and Spark filters them out before the shuffle (look
  for `isnotnull` in the plan). In a **left** join they're kept, and all
  NULLs hash to the same partition, so the skew comes back. Split team
  events off before the join. Fixing the data model beats tuning the
  engine.

</details>

## Gotchas

- **Unset configs between experiments**, or start a new session. A
  leftover `adaptive.enabled = false` makes the AQE run look useless.
- **`rand()` without a seed** gives different salts on recomputation; if
  a stage retries, rows can move. Use a seed, or derive salt from a
  column (`hash(event_id) % N`).
- **Local mode hides network cost.** On a real cluster skew is worse:
  the hot task also waits on fetching its oversized shuffle block.
