# M5.4 · Remaining staging models and schema YAML

> **Ticket:** [#71](https://github.com/Dfscashline21/sideline/issues/71) ·
> **Mode:** agent: the agent drafts following your M5.3 pattern; you review ·
> **Time:** 2 hours · **Needs:** M5.3 merged (the pattern and `CONVENTIONS.md`)

## Why this matters

This is the realistic agent workflow: a human sets the pattern, an agent
copies it at scale, the human reviews. It only works if the pattern is
explicit (M5.3) and the review is systematic. Copying is exactly where
small mistakes multiply: one wrong dedup key, copied ten times.

## What you'll produce

- A staging model for **every** source table declared in `_sources.yml`.
- Every model documented in YAML (model and column descriptions, tests).

## Steps

### 1. List what's missing (by hand, 10 min)

```bash
cd transform
uv run dbt ls --resource-type source
uv run dbt ls --resource-type model --select staging
```

Write the list of sources without a staging model. That list *is* the
agent's task, and your checklist for the review.

### 2. Prompt the agent

> Write staging models for these sources in `transform/models/staging/`:
> *(list)*. Follow `transform/CONVENTIONS.md` and copy the structure of
> `stg_nba__games`, `stg_nba__play_by_play` and `stg_nba__players` exactly
> (source → renamed → deduped CTEs, explicit column lists, dedup on the
> key keeping the latest `_loaded_at`). For each model add YAML: model
> description, a description for every column, `unique` + `not_null` on the
> key, and `relationships` tests to parent staging models where a foreign
> key exists. Before writing each model, query the source to confirm the
> key is unique after dedup, and tell me the key and the evidence. Don't
> change my three existing models.

The last instruction matters: an agent "tidying up" your hand-written
models would make M5.3's hand work an agent's.

### 3. Review checklist

Go model by model. Tick every row before approving:

| Check | How |
|---|---|
| Key is right | Re-run `count(*)` vs `count(distinct key)` on the source yourself for 2 models |
| Dedup keeps the latest load | Read the `qualify`; same ordering as M5.3? |
| Names follow `CONVENTIONS.md` | Booleans `is_`, timestamps `_at`, ids `_id` |
| No logic snuck in | No joins, no `case` business rules, no aggregates |
| Casts are explicit | Every column in `renamed` has a cast or a reason not to |
| Descriptions say something | "The game id" for `game_id` is useless; "ESPN game id, unique per game, shared across leagues' id spaces" is useful |
| Tests ran | `dbt build -s staging` output, not the agent's word for it |

<details>
<summary>Hint · Mistakes agents commonly make here</summary>

- Inventing a key that *looks* unique (`player_id`) on a table whose real
  grain is player-per-game.
- Writing descriptions copied from column names.
- "Improving" the pattern in one model (a different CTE name, a
  `distinct` instead of `qualify`) so the models drift apart.
- Adding `relationships` tests to tables in a different league, which fail
  for legitimate reasons.

</details>

### 4. Prove coverage (by hand)

Write a tiny check you can rerun forever. A singular test
`tests/assert_every_source_has_staging.sql` can't easily inspect the
graph, so do it in the shell instead:

```bash
uv run dbt ls --resource-type source --output name | sort > /tmp/sources.txt
uv run dbt ls --select staging --output name | sort > /tmp/staging.txt
# compare by eye or with a short script; every source table should map to a stg_ model
```

Or turn it into a Make target. M5.10's test count benefits from every
model having its key tests.

✅ **Checkpoint:** every source has a staging model; `dbt build -s staging`
is green; you changed at least one thing in the agent's draft (and can
say why).

### 5. Ship it

PR `m5.4-staging-rest`, `Closes #71`. Paste the review table with ticks
and the one-line key/evidence for each model.

## Gotchas

- **`dbt docs` won't nag you about missing descriptions.** Missing docs
  are silent. A package like `dbt_meta_testing` or a CI check can enforce
  them; for now, review by eye.
- **One YAML file per folder or per model?** Either works; pick one, put
  it in `CONVENTIONS.md`, and make the agent follow it.
