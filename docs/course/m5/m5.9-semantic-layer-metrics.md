# M5.9 · Metrics in the semantic layer

> **Ticket:** [#76](https://github.com/Dfscashline21/sideline/issues/76) ·
> **Mode:** hand · **Time:** 3 to 4 hours ·
> **Needs:** M5.7 (facts), M5.8 (`dim_date`), M1.5 and M1.6 (possessions, TS%)

## Why this matters

Ask three analysts for "true shooting %" and you'll get three numbers:
one averages per-game percentages, one forgets free throws, one includes
the playoffs. A **semantic layer** defines each metric **once**, in code,
and every dashboard, API and notebook asks it for the number instead of
re-deriving it. That's the modern answer to "why do our reports
disagree?", which is a common interview question.

## What you'll produce

Four metrics defined once with MetricFlow, the dbt semantic layer engine:

- points per game
- true shooting %
- offensive rating (points per 100 possessions)
- pace (possessions per 48 minutes)

Queryable with `mf query`, and checked against a known source for 3 players.

## Setup

```bash
uv add --group dbt "dbt-metricflow[duckdb]"   # needs Python < 3.15 (see module README)
cd transform && uv run mf --version
```

MetricFlow needs a **time spine** model, a table with one row per day.
Your `dim_date` (M5.8) can be it. Declare it in YAML:

```yaml
models:
  - name: dim_date
    time_spine:
      standard_granularity_column: date_day
    columns:
      - name: date_day
        granularity: day
```

## Steps

### 1. Learn the three building blocks (30 min)

Read [About MetricFlow](https://docs.getdbt.com/docs/build/about-metricflow)
and [Semantic models](https://docs.getdbt.com/docs/build/semantic-models).

| Block | What it is | Example |
|---|---|---|
| **Semantic model** | A fact table described for MetricFlow: entities (keys), dimensions, measures | `player_games` on `fact_player_game` |
| **Measure** | An aggregation of a column | `sum(points)`, `count(player_game_id)` |
| **Metric** | What people query. Built from measures or other metrics | `points_per_game = total_points / games` |

Metric types you'll need: `simple` (one measure), `ratio` (metric ÷
metric), `derived` (an expression over metrics).

### 2. Describe `fact_player_game` as a semantic model

<details>
<summary>Hint 1 · Skeleton</summary>

```yaml
semantic_models:
  - name: player_games
    model: ref('fact_player_game')
    defaults: {agg_time_dimension: game_date}
    entities:
      - {name: player_game, type: primary, expr: player_game_id}
      - {name: player, type: foreign, expr: player_id}
    dimensions:
      - {name: game_date, type: time, type_params: {time_granularity: day}}
      - {name: player_name, type: categorical}
    measures:
      - {name: points, agg: sum}
      - {name: games, agg: count, expr: player_game_id}
      - {name: fga, agg: sum}
      - {name: fta, agg: sum}
```

`fact_player_game` needs a single-column key (`player_game_id`) for the
primary entity. Add one if it doesn't have it.

</details>

### 3. Define points per game and TS%

**Ratio of sums, not average of ratios.** TS% for a season is
`sum(points) / (2 × (sum(FGA) + 0.44 × sum(FTA)))`, not the mean of each
game's TS%. A 1-for-1 game would otherwise count as much as a 12-for-20 one.

<details>
<summary>Hint 2 · Approach</summary>

Simple metrics for the totals; a `ratio` for points per game; a `derived`
metric for TS%. A ratio's numerator and denominator must be **metrics**,
not measures (that's a parse error in current dbt).

</details>

<details>
<summary>Solution · the two player metrics (after you have your own)</summary>

```yaml
metrics:
  - {name: total_points, label: Points, type: simple, type_params: {measure: points}}
  - {name: total_games,  label: Games,  type: simple, type_params: {measure: games}}
  - {name: total_fga,    label: FGA,    type: simple, type_params: {measure: fga}}
  - {name: total_fta,    label: FTA,    type: simple, type_params: {measure: fta}}

  - name: points_per_game
    label: Points per game
    type: ratio
    type_params: {numerator: total_points, denominator: total_games}

  - name: true_shooting_pct
    label: True shooting %
    type: derived
    type_params:
      expr: total_points / (2 * (total_fga + 0.44 * total_fta))
      metrics: [total_points, total_fga, total_fta]
```

This exact YAML was run with MetricFlow 0.15 on ESPN data for
1 to 10 January 2024; `mf validate-configs` passed and `mf query` returned
per-player values.

</details>

```bash
uv run dbt parse
uv run mf validate-configs
uv run mf query --metrics points_per_game,true_shooting_pct \
  --group-by player_game__player_name --order -points_per_game --limit 5
```

Note the dimension name: MetricFlow addresses dimensions through an
entity, `player_game__player_name`. Plain `player_name` won't resolve.

✅ **Checkpoint:** `mf query` returns your top scorers with plausible TS%
(roughly 0.55 to 0.70 for stars).

### 4. Possessions, offensive rating and pace

These are **team** metrics. You need possessions per team-game. Reuse
M1.5's box-score estimate:

```
possessions = FGA − ORB + TOV + 0.44 × FTA
```

Add a semantic model on a team-game grain (your `fact_player_game`
aggregated to team per game, or an intermediate `int_team_game` model)
with measures for points, FGA, ORB, TOV, FTA and minutes played. Then:

- `possessions`: derived from the four measures
- `offensive_rating` = 100 × points ÷ possessions
- `pace` = 48 × possessions ÷ (team minutes ÷ 5)

Why divide minutes by 5? Team minutes sum all five players on the floor;
a regulation game has 240 team minutes. Overtime is why pace isn't simply
"possessions per game".

### 5. Check against a known source (3 players)

Pick 3 players and one team, one full season. Compare your values with
[Basketball-Reference](https://www.basketball-reference.com/) (player
pages: per-game and advanced tables; team page: ORtg and Pace).

Record in `docs/notes/m5.md`:

| Player / team | Metric | Mine | Reference | Diff | Why |
|---|---|---|---|---|---|

Expect PPG to match exactly and TS% to within rounding. Team ORtg and pace
will differ slightly: Basketball-Reference's possession formula averages
both teams and adds an offensive-rebound-percentage term. M1.5 showed the
simple formula's systematic bias. Explain the difference; don't fudge it.

✅ **Checkpoint:** 3 players' PPG and TS% match; team metrics differ by a
small, explained amount.

## Gotchas

- **Average of ratios.** The classic metrics bug. The semantic layer
  prevents it only if you define the metric as a ratio of sums.
- **Playoffs.** Reference sites split regular season and playoffs. Add a
  `season_type` dimension and filter: `--where "{{ Dimension('player_game__season_type') }} = 'regular'"`.
- **Python 3.15.** `dbt-metricflow` won't install. Pin 3.12.
