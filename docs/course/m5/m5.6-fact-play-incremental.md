# M5.6 · `fact_play` incremental with a 3-day lookback

> **Ticket:** [#73](https://github.com/Dfscashline21/sideline/issues/73) ·
> **Mode:** hand · **Time:** 3 to 4 hours ·
> **Needs:** M5.1 (strategy failure modes), M5.4, M3.2 grain for `fact_play`

## Why this matters

`fact_play` is the biggest table in Sideline, one row per play-by-play
event, so rebuilding it daily gets slow. Incremental fixes that, and
introduces the module's central risk: **stat corrections**. The league
regularly re-scores plays after a game (an assist credited, a shot
changed from 2 to 3). Corrections arrive days later. An incremental model
that only looks at "new" games never sees them.

The **lookback window** is the fix: every run reprocesses the last N days,
not just the newest. This lab builds it and proves both properties the
ticket asks for.

## What you'll produce

`models/marts/fact_play.sql`, incremental, that:

- is **idempotent**: re-running a day changes nothing
- picks up a **correction that arrives 2 days late**

## Steps

### 1. State the grain and key (15 min)

From M3.2: one row per play-by-play event. The key is the staging
`play_id` (or `(game_id, event_number)`). Write it at the top of the model
as a comment, and add `unique` + `not_null` tests now, before writing
logic. They're your safety net for everything that follows.

### 2. Choose the strategy (30 min)

From your M5.1 table, three candidates on dbt-duckdb:

| Strategy | Re-run a day | Correction to an existing play | Play deleted upstream |
|---|---|---|---|
| `append` | ? | ? | ? |
| `delete+insert` | ? | ? | ? |
| `merge` | ? | ? | ? |
| `microbatch` | ? | ? | ? |

Fill it in. Then pick one and write two sentences why: they become the
start of ADR-004 (M5.13). (The labs' examples use `delete+insert`, which
was tested; `merge` and `microbatch` with `lookback` also passed the same
checks in testing.)

### 3. Write the incremental filter

<details>
<summary>Hint 1 · Nudge</summary>

`where game_date > (select max(game_date) from {{ this }})` only loads
*new* days. Which days must you reload to catch a 2-day-late correction?

</details>

<details>
<summary>Hint 2 · Approach</summary>

Look back from the newest date already in the target:
`where game_date >= (select max(game_date) - interval 3 day from {{ this }})`.
Combined with `unique_key`, rows in that window are replaced, so a
corrected row overwrites the old one, and new rows are added.

Why anchor on `max(game_date)` in the target and not `current_date`?
Think about the off-season, and about running a backfill for 2019.

</details>

<details>
<summary>Solution (after you have your own)</summary>

```sql
-- Grain: one row per play-by-play event. Key: play_id.
{{ config(
    materialized='incremental',
    incremental_strategy='delete+insert',
    unique_key='play_id',
) }}

{% set lookback_days = var('fact_play_lookback_days', 3) %}

select
    play_id,
    game_id,
    event_number,
    period,
    team_id,
    primary_player_id,
    event_type,
    points_scored,
    game_date,
    _loaded_at
from {{ ref('stg_nba__play_by_play') }}
{% if is_incremental() %}
where game_date >= (
    select max(game_date) - interval {{ lookback_days }} day from {{ this }}
)
{% endif %}
```

Making the lookback a `var` means a one-off deeper reprocess is
`dbt build -s fact_play --vars '{fact_play_lookback_days: 30}'` with no code change.

</details>

### 4. Prove idempotency

```bash
uv run dbt build -s fact_play --full-refresh
# record: count(*), count(distinct play_id), sum(points_scored)
uv run dbt build -s fact_play
uv run dbt build -s fact_play
# record the same three numbers
```

✅ **Checkpoint:** all three numbers identical across runs. Write it as a
singular test or a script you can rerun, not a one-off query.

### 5. Prove a 2-day-late correction lands

Simulate a correction in a **dev copy** of the raw data (never the real
raw zone):

1. Pick a play from 2 days before the latest date in `fact_play`.
2. Insert a corrected copy of it into the raw source with a newer
   `_loaded_at` and a changed value (e.g. `score_value` 2 → 3).
3. `dbt build -s +fact_play` (staging dedup keeps the newest load; the
   lookback reprocesses that day).
4. Query the play in `fact_play`.

Then repeat with a correction **5 days** late.

✅ **Checkpoint:** the 2-day-late correction appears; the 5-day-late one
doesn't. That second result isn't a failure. It's the documented limit of
your window, and it goes in ADR-004 together with what you'd do about it.

In testing with ESPN 2023-24 data (games 1 to 10 January 2024, so the
window started at 7 January), a correction to a 8 January play was
picked up and one to a 4 January play wasn't, under both
`delete+insert` and `merge`.

### 6. Catch silent failure with a test

The epic's ready-when question asks how you'd *catch* an incremental model
going wrong. Add at least one test that would fail if the incremental logic
broke:

- the `unique` test on `play_id` (catches duplicates from a bad strategy)
- a reconciliation test: row count per `game_date` in `fact_play` equals
  the count in `stg_nba__play_by_play` for the last 30 days

<details>
<summary>Hint · Reconciliation test shape</summary>

A singular test returns the rows that are wrong. Full-outer-join two
per-day counts and return days where they differ. Limiting it to recent
days keeps it cheap.

</details>

### 7. Ship it

PR `m5.6-fact-play`, `Closes #73`. Paste the idempotency numbers and both
correction results.

## Gotchas

- **Lookback anchored on `current_date`.** During the off-season it
  reprocesses nothing useful; during a 2019 backfill it misses everything.
- **Staging must dedup to the latest load.** If staging keeps the old copy,
  the lookback reprocesses the *old* value. M5.3's dedup rule is half of
  this lab.
- **`--full-refresh` in production.** It works, but on a big table it's a
  long outage of correct data. Know how long it takes before you need it.
- **Microbatch needs `event_time` on the upstream model too**, and a
  bounded range, or dbt schedules a batch for every day since `begin`.
