# M5.12 · Host dbt docs on GitHub Pages

> **Ticket:** [#79](https://github.com/Dfscashline21/sideline/issues/79) ·
> **Mode:** agent: the agent drafts the workflow, you review ·
> **Time:** 90 min · **Needs:** M5.9 (models worth documenting), M5.11 (CI pattern)

## Why this matters

The epic's portfolio artifact is a **hosted docs site with lineage**. A
recruiter or hiring manager can click from `fact_play` back to the raw
source and see every test and description on the way, without cloning
anything. It's the cheapest way to show the depth of the model.

## What you'll produce

- A workflow that builds dbt docs on every merge to `main` and publishes
  them to GitHub Pages.
- The docs URL linked from the README.

## Background: the static docs option

`dbt docs generate` normally writes `index.html` plus `manifest.json`
and `catalog.json`, which `dbt docs serve` loads at runtime. With
`--static` (tested with dbt 1.12), dbt also writes
`target/static_index.html`: **one self-contained file** with the data
embedded. That's ideal for Pages: no extra files to upload, nothing to
fetch at runtime.

`dbt docs generate` builds `catalog.json` by querying the warehouse, so it
needs built models (column types and row counts come from the database).
In CI, that means `dbt build` first.

## Steps

### 1. Decide what the public sees (by hand, 15 min)

The docs include compiled SQL and column descriptions. Check:

- no internal hostnames, credentials or private notes in descriptions
- `docs: show: false` on anything you don't want public (e.g. CI-only models)

### 2. Prompt the agent

> Add a GitHub Actions workflow `.github/workflows/dbt-docs.yml` for this
> repo: on push to `main` (and manually via `workflow_dispatch`), set up uv,
> `uv sync --group dbt`, then in `transform/`: `dbt deps`, `dbt build`
> (target `ci`), `dbt docs generate --static`. Publish
> `transform/target/static_index.html` as `index.html` to GitHub Pages
> using the official `actions/configure-pages`, `actions/upload-pages-artifact`
> and `actions/deploy-pages` actions, each pinned to an exact version. Use
> the minimum permissions (`pages: write`, `id-token: write`,
> `contents: read`). Explain each permission.

### 3. Review checklist

- [ ] Actions pinned to exact versions that exist (check each tag on GitHub)
- [ ] Permissions minimal, at job level, and explained
- [ ] Triggers only on `main` (and manual), not on every PR
- [ ] `concurrency` set so two quick merges don't race to deploy
- [ ] The published file is `static_index.html` renamed to `index.html`

### 4. Turn on Pages and deploy (by hand)

Repository **Settings → Pages → Source: GitHub Actions**. Merge the
workflow, watch the run, open the URL it prints
(`https://<owner>.github.io/sideline/`).

✅ **Checkpoint:** the site loads, the lineage graph (bottom-right
button) shows sources → staging → marts, and `fact_play` shows its tests.

### 5. Link it from the README

Under the "Decisions" or "Architecture" section from M0.6, add the docs
link with one line on what's there. Also add the URL to the repo's
"About" box (`gh repo edit --homepage <url>`).

### 6. Ship it

PR `m5.12-dbt-docs`, `Closes #79`.

## Gotchas

- **Empty catalog.** If `dbt build` didn't run before `docs generate`,
  the site loads but columns show no types. Check one model page.
- **Pages caching.** A fresh deploy can take a minute or two to appear.
- **Public repo, public docs.** Anything in a description is published.
