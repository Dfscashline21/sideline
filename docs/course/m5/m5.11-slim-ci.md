# M5.11 · Slim CI with `state:modified+`

> **Ticket:** [#78](https://github.com/Dfscashline21/sideline/issues/78) ·
> **Mode:** agent: the agent drafts the workflow, you review ·
> **Time:** 2 to 3 hours · **Needs:** M5.4 (a real project), M0.5 (CI)

## Why this matters

Building the whole dbt project on every PR is slow, and it only gets
slower. "Slim CI" builds **only what the PR changed, plus everything
downstream of it**, and borrows everything else from production. It's a
standard senior-level dbt question: "How do you keep CI fast as the
project grows?"

## What you'll produce

A CI job where a PR touching one model builds **only that model's
subtree**, shown in the job log.

## How it works

1. `main` builds produce a `manifest.json`: a snapshot of the project.
2. A PR job downloads that manifest as the **state**.
3. `dbt build --select state:modified+ --state <dir>` selects models whose
   definition changed, plus (`+`) their children.
4. `--defer` makes unselected parents resolve to the *production* (state)
   versions instead of failing because they don't exist in the CI database.

This selection was tested with dbt 1.12: after adding a comment to one
staging model, `dbt ls -s state:modified+ --state <prod manifest>` listed
that model and its three downstream models, and nothing else.

## Steps

### 1. Decide where state and prod data come from (by hand, 30 min)

Two questions the agent can't answer for you:

| Question | Options |
|---|---|
| Where does the `main` manifest live? | GitHub Actions artifact from the last `main` run (simplest), or an object-store bucket |
| What does `--defer` point at? | Locally there's no shared prod warehouse. Options: build parents with `dbt build --empty` (schema only, no rows) in CI, or download a small prod DuckDB file |

For Sideline today, a reasonable choice: artifact for the manifest;
`--empty` for unmodified parents; real rows only for the modified subtree,
from a small CI fixture dataset. Write down your choice.

### 2. Prompt the agent

> Add a `dbt` job to `.github/workflows/ci.yml` for this repo. On push to
> `main`: `dbt deps`, `dbt build`, then upload `transform/target/manifest.json`
> as an artifact named `dbt-manifest`. On pull requests: download the latest
> `dbt-manifest` artifact from `main` (use the GitHub API or
> `dawidd6/action-download-artifact`, pinned to an exact version), then run
> `dbt build --select state:modified+ --state ./prod-state --defer`. If no
> artifact exists yet, fall back to a full build. Use the `ci` target from
> `transform/profiles.yml`. Explain how the PR job gets data for models it
> doesn't build. *(paste your step-1 decisions)*

### 3. Review checklist

- [ ] Every action pinned to an exact version (M0's lesson: no floating `v4`)
- [ ] The artifact comes from `main`, not from another PR branch
- [ ] Fallback works on the very first run, when there's no artifact
- [ ] No secrets needed (local DuckDB); if any are, they come from
      `secrets.*`, never the YAML
- [ ] The job prints the selected nodes (`dbt ls -s state:modified+ ...`)
      before building, so the log *shows* what's slim about it
- [ ] Unit tests on modified models still run (they need parents: see M5.10)

### 4. Prove it (by hand)

1. Merge the workflow, and let `main` produce the first manifest.
2. Open a PR that changes **one** staging model (add a column).
3. Read the job log.

✅ **Checkpoint:** the log lists that model and its downstream models
only, and the build runs only those. Screenshot or paste the relevant log
lines into the PR description: they're the acceptance evidence.

Then open a second PR that changes only a Markdown file. What does the
dbt job select? (It should select nothing and finish fast.)

### 5. Ship it

PR `m5.11-slim-ci`, `Closes #78`, with the log evidence.

## Gotchas

- **Artifacts expire** (90 days by default). A repo with no `main` merges
  for three months falls back to full builds. Note it; it's fine here.
- **What counts as "modified"** includes config and macro changes. Edit a
  macro used everywhere and slim CI builds everything. That's correct.
- **`state:modified` vs `state:modified+`.** Without `+`, a broken child
  of your change isn't tested. Always the `+` in CI.
- **Seeds and snapshots** are selected too if modified; a snapshot in CI
  against an empty database is harmless but meaningless.
