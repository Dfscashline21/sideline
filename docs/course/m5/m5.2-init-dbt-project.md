# M5.2 · Initialize the dbt project with sources and freshness

> **Ticket:** [#69](https://github.com/Dfscashline21/sideline/issues/69) ·
> **Mode:** agent: the agent drafts, you review every line ·
> **Time:** 2 hours · **Needs:** M2 raw zone, M4 Iceberg tables, the
> [module overview](README.md) (versions and the Python 3.12 pin)

## Why this matters

Scaffolding is where agents shine, and also where they quietly bake in
bad defaults: absolute paths in `profiles.yml`, secrets committed, sources
pointing at the wrong schema, freshness that never fails. Your job is to
specify precisely and review hard, as you did in M1.2.

**Sources** are dbt's contract with the outside world: every model reads
raw data only through `{{ source(...) }}`, so lineage starts at a named,
documented, freshness-checked input instead of a hard-coded path.

## What you'll produce

- `transform/` dbt project (`sideline`), `dbt build` running clean.
- Sources for the NBA raw data with **freshness checks** configured.
- Make targets `dbt-build` and `dbt-freshness`.

## Steps

### 1. Pin Python and add dependencies (by hand, 10 min)

```bash
git switch -c m5.2-dbt-init
echo "3.12" > .python-version
uv add --group dbt "dbt-core~=1.12" "dbt-duckdb~=1.11"
uv sync --all-groups
uv run dbt --version
```

Why a separate `dbt` dependency group? Think about the dev container and
CI: does every job need dbt?

✅ **Checkpoint:** `dbt --version` shows core 1.12.x and the duckdb plugin.

### 2. Decide how dbt reads raw data (by hand, 20 min)

dbt-duckdb runs SQL inside DuckDB, so "reading Iceberg/raw" means
DuckDB reading it. Two options:

| Option | How | Pros | Cons |
|---|---|---|---|
| Iceberg tables from M4 | DuckDB `iceberg` extension, attached to your REST catalog | Typed, partitioned, time travel | More moving parts in `profiles.yml` |
| Raw JSON in MinIO from M2 | `httpfs` + `read_json` over `s3://sideline-raw/...` | Simplest, closest to source | You do the typing and dedup in staging |

Write down which you chose and why. Many teams do both: Iceberg for the
big event tables (play-by-play), raw JSON for small reference feeds.

### 3. Write the spec, then prompt the agent

Your spec should cover:

- project name `sideline`, profile `sideline`, targets `dev` and `ci`
- DuckDB database file under `.data/` (gitignored), path relative to the
  repo, never absolute
- MinIO credentials read from environment variables (`.env`), via
  dbt's `env_var()`; nothing secret in YAML
- folder layout from the [module overview](README.md#what-you-build-and-where),
  with `+materialized: view` for staging and `table` for marts
- `packages.yml` with `dbt_utils` and `metaplane/dbt_expectations`
- one source block per league/feed in `models/staging/_sources.yml`, with
  `loaded_at_field` and `freshness` thresholds
- **one** trivial model (`select 1`) so `dbt build` has something to run;
  real staging models are M5.3, by hand

Prompt:

> Set up a dbt Core 1.12 project in `transform/` for this repo using
> dbt-duckdb 1.11. Follow AGENTS.md. Requirements: *(paste spec)*.
> For reading *(Iceberg / raw JSON in MinIO)*, configure DuckDB extensions
> and S3 settings in `profiles.yml` using `env_var()`. Explain every
> setting in `profiles.yml` and `dbt_project.yml` that isn't obvious. Do
> not write staging models.

### 4. Review it

| Question | Good answer |
|---|---|
| Where does `profiles.yml` live, and how does dbt find it? | In `transform/`, found via `--profiles-dir` or `DBT_PROFILES_DIR` set by the Make target. Not `~/.dbt/` (CI can't see that) |
| Any literal password or key? | No. `env_var('MINIO_ROOT_USER')` and so on |
| What's `loaded_at_field`? | A timestamp column of *when the row landed*, which your extractor must write. If M2 didn't, add an ingestion timestamp now |
| Are freshness thresholds sensible for a league that doesn't play every day? | The NBA has off-days and an All-Star break; a 24-hour `error_after` will page you for nothing. See step 5 |
| Does the DuckDB file name clash with a schema name? | A file `raw.duckdb` becomes catalog `raw`; a schema also named `raw` then errors as "ambiguous". Pick distinct names |

### 5. Get freshness right (by hand, 20 min)

Freshness syntax that was tested with dbt 1.12 (the `config:` block is
the current form):

```yaml
sources:
  - name: nba_raw
    schema: raw
    config:
      loaded_at_field: _loaded_at
      freshness:
        warn_after: {count: 24, period: hour}
        error_after: {count: 48, period: hour}
    tables:
      - name: pbp
      - name: player_box
```

Run `uv run dbt source freshness`. Then make one table deliberately stale
(point a test source at a table whose newest `_loaded_at` is old) and
watch it fail.

✅ **Checkpoint:** you've seen `PASS`, and you've seen `ERROR STALE`.

Season-aware thresholds come later (M6 adds a league calendar; M9 adds
SLOs). For now, write a comment in `_sources.yml` noting the off-season
problem.

### 6. Make targets and ship it

```make
dbt-build: ## Build and test all dbt models
	cd transform && $(UV_RUN) dbt build --profiles-dir .

dbt-freshness: ## Check raw source freshness
	cd transform && $(UV_RUN) dbt source freshness --profiles-dir .
```

```bash
make dbt-build && make dbt-freshness
git add transform/ Makefile pyproject.toml uv.lock .python-version
git status          # no .duckdb, no target/, no logs/
```

Add `transform/target/`, `transform/logs/` and `transform/dbt_packages/`
to `.gitignore` if the M0.1 entries don't already cover them. PR with
`Closes #69`, and paste your review answers in the description.

## Gotchas

- **dbt v2 banner.** The 1.12 CLI announces that v2 exists. The labs are
  tested on v1 with dbt-duckdb. Don't switch mid-module.
- **`dbt deps` first.** `packages.yml` does nothing until `dbt deps`
  installs them. Add it to the Make target or CI will fail on day one.
- **Credentials in `target/`.** Compiled SQL can contain resolved values.
  Keep `target/` ignored.
