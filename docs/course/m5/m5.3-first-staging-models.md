# M5.3 · First staging models by hand

> **Ticket:** [#70](https://github.com/Dfscashline21/sideline/issues/70) ·
> **Mode:** hand · **Time:** 3 hours ·
> **Needs:** M5.2 merged; M3.2 grain statements

## Why this matters

Staging is the one layer that touches raw data, so it's where you set the
pattern every later model copies, including the ones an agent writes in
M5.4. Get the pattern right here and M5.4 is a review exercise; get it
wrong and you'll be fixing 20 copies.

A staging model does exactly three things, and nothing else:

1. **Rename** columns to your conventions.
2. **Cast** to the right types.
3. **Dedupe** so every row is unique on its key.

No joins, no business logic, no aggregates. Those belong in marts.

## What you'll produce

- `stg_nba__games`, `stg_nba__play_by_play`, `stg_nba__players` in
  `transform/models/staging/nba/`, each with tests.
- `transform/CONVENTIONS.md` documenting your naming rules (the ticket's
  "consistent naming conventions documented").

## Steps

### 1. Write the conventions first (30 min)

Decide before you write SQL, so all three models agree. Cover at least:

| Topic | Decide |
|---|---|
| Model names | e.g. `stg_<league>__<entity>`, plural entity, double underscore |
| Keys | `<entity>_id` (`game_id`, `player_id`); surrogate keys later in marts |
| Booleans | `is_` / `has_` prefix (`is_home`, `is_starter`) |
| Timestamps / dates | `_at` for timestamps (`tipoff_at`), `_date` for dates |
| Units | in the name when ambiguous (`minutes_played`, `clock_seconds_remaining`) |
| Metadata columns | `_loaded_at`, `_source_file`: leading underscore, kept through staging |
| Case | snake_case everywhere |

Write them in `transform/CONVENTIONS.md`. Link it from `AGENTS.md`, because
the agent in M5.4 must follow it.

### 2. Profile the raw data (30 min)

For each source, before writing the model:

```sql
-- in `uv run dbt show --inline "..."` or a DuckDB shell
select count(*), count(distinct <candidate_key>) from <raw table>;
```

If those two numbers differ, you have duplicates. Find out why: a re-run
of the extractor? The same game in two daily files? A correction?
**The reason decides the dedup rule.**

✅ **Checkpoint:** for each of the three sources you can state its key,
whether it has duplicates, and why.

### 3. Write `stg_nba__games`

Start with the simplest. Structure every staging model the same way:

```sql
with source as (
    select * from {{ source('nba_raw', 'games') }}
),
renamed as (
    select
        -- ids
        ...
        -- dates and times
        ...
        -- attributes
        ...
        -- metadata
        _loaded_at
    from source
),
deduped as (
    select * from renamed
    ___   -- keep one row per key
)
select * from deduped
```

<details>
<summary>Hint 1 · Nudge: which duplicate to keep?</summary>

If the same game was loaded twice, which copy is right? The one loaded
**most recently**, because it reflects any correction.

</details>

<details>
<summary>Hint 2 · Approach</summary>

The M1 pattern: `qualify row_number() over (partition by <key> order by _loaded_at desc) = 1`.
Add a second tiebreaker column if two loads can share a timestamp.

</details>

### 4. Write `stg_nba__play_by_play` and `stg_nba__players`

Play-by-play is the big one. Decide:

- What's the key? An event ID from the source, or `(game_id, event_number)`?
  Check uniqueness both ways.
- Cast the clock: a string like `"7:42"` should become
  `clock_seconds_remaining` (an integer or decimal).
- Keep raw event-type text, but normalise case and whitespace.

Players: if the source has one row per player per *roster load*, staging
still dedupes to **one row per player per load**, not to one row per
player. History is M5.5's job; don't collapse it here.

<details>
<summary>Solution · stg_nba__play_by_play skeleton (after you have your own)</summary>

```sql
with source as (
    select * from {{ source('nba_raw', 'pbp') }}
),
renamed as (
    select
        cast(id as bigint)                 as play_id,
        cast(game_id as bigint)            as game_id,
        cast(game_play_number as integer)  as event_number,
        cast(period_number as integer)     as period,
        cast(team_id as bigint)            as team_id,
        cast(athlete_id_1 as bigint)       as primary_player_id,
        lower(trim(type_text))             as event_type,
        cast(score_value as integer)       as points_scored,
        cast(shooting_play as boolean)     as is_shot,
        cast(game_date as date)            as game_date,
        cast(start_game_seconds_remaining as integer) as game_seconds_remaining,
        _loaded_at
    from source
),
deduped as (
    select * from renamed
    qualify row_number() over (partition by play_id order by _loaded_at desc) = 1
)
select * from deduped
```

Column names here are from the ESPN feed used in M1. If M2 lands
`nba_api` play-by-play, the source columns differ but the shape is the same.

</details>

### 5. Tests and docs for all three

In `models/staging/nba/_stg_nba.yml`, for each model:

- `unique` and `not_null` on the key
- `not_null` on columns that must exist (game date, team)
- `accepted_values` where there's a closed set (e.g. home/away)
- `relationships` from play-by-play `game_id` to `stg_nba__games.game_id`
- a one-line `description` on the model and on every key column

And **one unit test** proving your dedup keeps the latest load. This is
the exact shape that was tested with dbt 1.12:

```yaml
unit_tests:
  - name: pbp_dedup_keeps_latest_load
    model: stg_nba__play_by_play
    given:
      - input: source('nba_raw', 'pbp')
        rows:
          - {id: 1, type_text: "jump shot",  _loaded_at: 2024-01-01 00:00:00}
          - {id: 1, type_text: "Layup Shot", _loaded_at: 2024-01-02 00:00:00}
    expect:
      rows:
        - {play_id: 1, event_type: "layup shot"}
```

Columns you don't list in `given` are filled with NULL; columns you don't
list in `expect` aren't checked.

✅ **Checkpoint:** `make dbt-build` passes with all tests green, and
`dbt build -s stg_nba__play_by_play` runs the unit test before building.

PR `m5.3-staging-by-hand` with `Closes #70`. In the description, state
each model's key and dedup rule in one line.

## Gotchas

- **Dedup before or after renaming?** After: then the `qualify` uses your
  clean names, and the logic reads the same in every model.
- **`select *` in staging.** Fine in the first CTE; never in `renamed`.
  An explicit column list is what makes the model a contract.
- **Silent type coercion.** DuckDB will happily cast `"7:42"` to NULL in
  some paths. Add `not_null` on every cast column you depend on.
