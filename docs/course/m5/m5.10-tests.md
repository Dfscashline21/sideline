# M5.10 · 50+ tests including unit tests

> **Ticket:** [#77](https://github.com/Dfscashline21/sideline/issues/77) ·
> **Mode:** mixed: tricky-logic tests by hand, boilerplate tests by agent ·
> **Time:** 3 hours, plus the tests you've added in every earlier lab ·
> **Needs:** M5.3 to M5.9

## Why this matters

"50 tests" is easy to hit with 50 `not_null`s, and nearly worthless if
that's all they are. The point is **coverage of the ways this project
actually breaks**: duplicates from incremental runs (M5.6), wrong
validity dates (M5.5), grain changes from joins (M5.7), and edge-case
logic (M5.8 season labels). The epic's ready-when question is really
"which test would have caught it?"

## What you'll produce

- 50+ passing tests across generic, singular, unit and `dbt_expectations`.
- At least **3 unit tests on tricky logic**, written by you.
- `docs/notes/m5-test-map.md`: what each important test protects against.

## The four kinds

| Kind | Where | Checks | Example |
|---|---|---|---|
| Generic | YAML `data_tests:` | a property of a column/model | `unique`, `not_null`, `relationships`, `accepted_values` |
| Singular | `tests/*.sql` | a query that returns bad rows | no overlapping SCD2 versions (M5.5) |
| Unit | YAML `unit_tests:` | a model's **logic** on fixed inputs | dedup keeps the latest load (M5.3) |
| Package | `dbt_expectations` | richer column checks | values between bounds, row-count comparisons |

### 2. Build the test map first (by hand, 45 min)

List the failure modes, then map each to a test. Start from this, and
add your own:

| Failure mode | Where it would happen | Test that catches it |
|---|---|---|
| Duplicate rows after an incremental run | `fact_play`, `fact_shot` | `unique` on key |
| Late correction missed | `fact_play` | reconciliation vs staging, last 30 days (M5.6) |
| Grain blown up by a join | `fact_player_game` | `unique_combination_of_columns` (M5.7) |
| Overlapping SCD2 versions | `dim_player` | singular no-overlap test (M5.5) |
| Wrong season label | `dim_season` | ? |
| Points don't add up to the team score | facts | ? |
| Impossible values (negative points, FG% > 1) | facts | ? |
| Fact row with no matching dim | facts | ? |

Every row should end with a test you can name. That map is the deliverable
that makes the number 50 mean something.

### 3. Write three unit tests on tricky logic (by hand)

Candidates (pick at least 3, each must test a real edge case):

1. **Dedup** keeps the latest `_loaded_at`, and breaks ties deterministically.
2. **Season label**: a cross-year NBA season → `"2023-24"`; a single-year
   WNBA season → `"2024"`; the October-ending 2019-20 bubble season.
3. **Clock parsing**: `"7:42"` → 462 seconds; `"0:00.4"` → 0.4 (sub-minute
   clocks show tenths); bad input → NULL, not an error.
4. **Free throws excluded** from `fact_shot`.
5. **As-of join**: a game on the exact trade date gets the *new* team's
   version (half-open ranges).

<details>
<summary>Hint · Unit-test shape (tested with dbt 1.12)</summary>

```yaml
unit_tests:
  - name: season_label_cross_year_and_single_year
    model: dim_season
    given:
      - input: ref('stg_nba__games')
        rows:
          - {season: 2024, game_date: 2023-10-24}
          - {season: 2024, game_date: 2024-06-17}
    expect:
      rows:
        - {season_year: 2024, season_label: "2023-24"}
```

Only list the input columns the model uses; the rest are NULL. Only list
output columns you want to check. If `dim_season` unions several leagues,
give each `ref()` an input (an empty `rows: []` is allowed).

</details>

✅ **Checkpoint:** run each unit test, then break the logic it protects
(swap `desc` to `asc`, change `<` to `<=`) and watch it fail. A test you've
never seen fail hasn't proved anything.

### 4. Agent: fill the generic-test gaps

> In `transform/models/`, find every model column that is a primary or
> foreign key, or used in a metric, and has no `not_null`/`unique`/
> `relationships` test. Add the missing tests and any missing column
> descriptions. List what you added per model. Don't modify SQL, unit
> tests or singular tests.

Review: every `relationships` test points at the right parent;
`accepted_values` lists are real (check them with a `select distinct`);
nothing was added to silence a failure (e.g. a `where` config that

### 5. Add `dbt_expectations` where it earns its place

Two or three good uses, not twenty:

- `expect_column_values_to_be_between` on `points` (0 to a sane max) and
  TS% inputs
- `expect_table_row_count_to_equal_other_table` between staging and fact
  for a reconciliation

### 6. Severity and noise

Not every failure should block a build. Set `severity: warn` on checks
that flag "suspicious" rather than "wrong" (e.g. a player scoring 70). Note
in the test map which are `warn` and why. That's a preview of M9's alert
fatigue discussion.

```bash
uv run dbt build          # everything green

```

## Gotchas

- **Unit tests need their parents to exist.** dbt reads the input
  models' column types from the warehouse. Running `dbt test` on a unit
  test whose parent changed but wasn't rebuilt fails with a compilation
  error. `dbt build` handles the order; in CI, `dbt build --empty` on the
  parents is a cheap way to create them.
- **Tests on views run the view's whole query.** Fine for staging today;
  watch the runtime as data grows.
- **`relationships` across leagues** fail legitimately once WNBA rows exist
  but parents don't. Scope them with a `where` config, and say why.
- **Counting** both `dbt ls --resource-type test` and `unit_test`. The
  ticket says 50+ tests *including* unit tests.
