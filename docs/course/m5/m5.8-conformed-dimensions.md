# M5.8 · Conformed dimensions: date, game, team, season, venue

> **Ticket:** [#75](https://github.com/Dfscashline21/sideline/issues/75) ·
> **Mode:** mixed: core logic by hand, boilerplate by agent ·
> **Time:** 3 to 4 hours · **Needs:** M3.5 (dim designs), M5.4

## Why this matters

A **conformed** dimension means the same thing in every fact and every
league. `dim_season` built now for the NBA has to work unchanged when the
WNBA arrives in M6 and college in M7. Otherwise "points per game by
season" means three different things in three places. Interviewers ask
about conformed dimensions because they're what separates a set of tables
from a model.

The hard case is in the acceptance criteria: **NBA seasons cross calendar
years.** The WNBA's don't.

## What you'll produce

`dim_date`, `dim_game`, `dim_team`, `dim_season`, `dim_venue` in
`models/marts/`, all built and tested, ready for more leagues.

## Who writes what

| Part | Who | Why |
|---|---|---|
| `dim_season` logic (labels, start/end dates, cross-year rule) | **you** | The tricky, interview-relevant bit |
| `dim_date` spine and its attributes (game day, days into season) | **you** | Small, and it teaches the spine pattern |
| League-awareness: keys that include `league` | **you** | Wrong here, wrong everywhere |
| `dim_team`, `dim_venue`, `dim_game` column lists, renames, YAML docs and tests | agent | Mechanical once the pattern exists |

## Steps

### 1. Agree the keys (by hand, 20 min)

ESPN reuses team IDs across leagues (M1: NBA 14 is the Heat, WNBA 14 is
the Storm). Every conformed dim's natural key therefore includes `league`.
Write down, for each dim: natural key, surrogate key, and grain.

✅ **Checkpoint:** `dim_team`'s natural key is `(league, team_id)`, not
`team_id`. If yours isn't, revisit M3.5 before going on.

### 2. Build `dim_season` (by hand)

One row per league-season. Columns at minimum: `season_sk`, `league`,
`season_year` (the year it ends, as in the source data), `season_label`
(`"2023-24"` for the NBA, `"2024"` for the WNBA), `start_date`,
`end_date`, `regular_season_end_date`.

<details>
<summary>Hint 1 · Nudge</summary>

Where do the dates come from? You have every game. The first and last
game dates per league-season *are* the season's dates. No hard-coded
calendar needed.

</details>

<details>
<summary>Hint 2 · Approach</summary>

Aggregate `stg_nba__games` (later, the union of all leagues) by
`league, season`: `min(game_date)` and `max(game_date)`, and the max over
regular-season games only. The label is cross-year when the start and end
dates are in different calendar years.

</details>

<details>
<summary>Solution · season label (after you have your own)</summary>

```sql
case
    when year(start_date) <> year(end_date)
        then year(start_date) || '-' || right(cast(year(end_date) as varchar), 2)
    else cast(year(end_date) as varchar)
end as season_label
```

Deriving the rule from the data, rather than `if league = 'nba'`, means
college (also cross-year) works in M7 with no change. A hard-coded
league check would have needed editing.

</details>

Test it: a singular test that 2024 NBA → `"2023-24"`, and a test that
`start_date < end_date` for every row.

### 3. Build `dim_date` (by hand)

A date spine from the first season to the end of next season, one row per
day. Use `dbt_utils.date_spine` or DuckDB's `range()`/`generate_series`.
Add attributes: day of week, is weekend, and **per league**: `season_sk`
the date falls in, is it a game day.

Careful: a single date can belong to an NBA season *and* a WNBA season.
So either `dim_date` stays league-free (calendar only) and the
league-specific attributes go in a bridge `dim_date_league`, or you
accept one row per date per league. Choose, and write down why.

### 4. Agent: `dim_team`, `dim_venue`, `dim_game`

Prompt:

> Build `dim_team`, `dim_venue` and `dim_game` in `transform/models/marts/`
> following `CONVENTIONS.md` and the pattern of `dim_season`
> (league-aware natural keys, `dbt_utils.generate_surrogate_key` for
> surrogate keys, left joins). Grains: *(paste from M3.5)*. Add YAML docs
> for every column, `unique`/`not_null` on surrogate and natural keys, and
> `relationships` from `dim_game` to `dim_team`, `dim_season`, `dim_venue`.
> Don't change `dim_season` or `dim_date`.

Review checklist:

- [ ] Every natural key includes `league`
- [ ] `dim_team` handles relocations/renames (one `team_id`, changing
      names), as M3.5 decided: SCD1 overwrite or SCD2 history?
- [ ] `dim_venue`: neutral-site games (the NBA plays games abroad;
      college tournaments are all neutral). Does `dim_game` have
      `is_neutral_site`?
- [ ] All-Star "teams" (M1: `Team LeBron`, `EAST`…) are either excluded
      or flagged, not mixed in as franchises
- [ ] Tests ran green in *your* terminal

### 5. Ready for WNBA and college

Prove "ready" without building M6: add a **fake** second league to a
staging model in a dev branch (a few hand-written rows via a seed file),
rebuild the dims, and check:

- no key collisions (the M1 team-ID clash)
- `dim_season` labels the single-year league correctly with no code change

Then delete the fake rows.

✅ **Checkpoint:** all five dims build, all tests pass, and the fake
league produced correct seasons with no edits to the dim SQL.

### 6. Ship it

PR `m5.8-conformed-dims`, `Closes #75`. Mark which parts were agent-drafted.

## Gotchas

- **Season year conventions differ.** ESPN's `season = 2024` means 2023-24;
  some sources label it 2023. Pick one (the year the season ends, matching
  the source) and document it in `CONVENTIONS.md`.
- **The NBA Cup final** (M1) is a regular-season game that doesn't count
  in standings. If `dim_game` has `counts_in_standings`, this is why.
- **Bubble season.** 2019-20 ended in October 2020. Your derived end date
  will say so. That's correct; don't "fix" it.
