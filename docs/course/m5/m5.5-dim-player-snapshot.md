# M5.5 · `dim_player` snapshot (SCD2)

> **Ticket:** [#72](https://github.com/Dfscashline21/sideline/issues/72) ·
> **Mode:** hand · **Time:** 3 hours ·
> **Needs:** M3.3 (your SCD2 design for `dim_player`), M5.4

## Why this matters

"Which team was this player on when he scored those 40?" is the question
SCD Type 2 answers. Get validity dates wrong and every as-of join in M7
and every point-in-time feature in M12 is wrong too. Not visibly wrong:
quietly attributing points to the wrong team for a few days around each
trade.

dbt snapshots are the standard tool, and they have one trap that this lab
is built around.

## What you'll produce

- `snapshots/snp_player_roster.yml`: a snapshot of the roster feed.
- `models/marts/dim_player.sql`: the SCD2 dimension built on it.
- Proof that a trade produces a new row with **correct validity dates**.

## Background: the trap

dbt has two snapshot strategies. Both were run against a simulated trade
while writing this lab:

| Strategy | Detects change by | `dbt_valid_from` becomes |
|---|---|---|
| `check` | comparing listed columns to the last snapshot | **the time you ran `dbt snapshot`** |
| `timestamp` | an `updated_at` column getting newer | **the value of `updated_at`** |

With `check`, a trade on 17 January that you snapshot on 20 January
says the player joined on the 20th. That fails the acceptance criterion.
With `timestamp`, validity follows whatever date your `updated_at` column
holds. So the real question becomes: **which column holds the true
effective date of a roster change?**

## Steps

### 1. Find the roster feed (30 min)

Check what M2 lands. Options, best first:

1. A roster endpoint with a transaction/effective date (e.g. `nba_api`'s
   team roster endpoints, loaded daily).
2. A roster endpoint without an effective date: then the best you have
   is the **load time**, meaning "we first saw it on this day".
3. No roster feed: derive "team as of game date" from player box scores.
   That's history from events, not a snapshot (see the stretch section).

If M2 has no roster feed, add one to the extractor as a small M2
follow-up before continuing. Note the choice in your notes.

✅ **Checkpoint:** you can name the column you'll use as `updated_at`,
and say what it *means*: effective date, or first seen.

### 2. Write the snapshot

Current dbt configures snapshots in YAML:

```yaml
snapshots:
  - name: snp_player_roster
    relation: ref('stg_nba__rosters')
    config:
      unique_key: ___
      strategy: ___
      updated_at: ___
      dbt_valid_to_current: "cast('9999-12-31' as timestamp)"
```

<details>
<summary>Hint 1 · Nudge</summary>

What makes a row in the roster feed unique *at a point in time*: a
player, or a player-team pair? What happens to the snapshot if a player
is on two teams in one feed (a trade mid-load)?

</details>

<details>
<summary>Hint 2 · Approach</summary>

`unique_key: player_id`, `strategy: timestamp`, `updated_at:` your
effective-date column (or `_loaded_at` if that's all you have).
`dbt_valid_to_current` makes current rows end on 9999-12-31 instead of
NULL, which keeps as-of joins simple. M3 settled on **half-open** ranges:
`valid_from <= d and d < valid_to`. Don't use `between`: it includes both
ends, so on the trade date a player matches two versions.

</details>

### 3. Simulate a trade, then verify

You can't wait for a real trade, so fake one in a dev copy of the source.
Pascal Siakam is a good real-world example: he played for Toronto until
15 January 2024 and debuted for Indiana on 19 January (the trade was
17 January).

1. Snapshot once with the player on team A, effective date X.
2. Change the source row: team B, effective date Y (later).
3. Snapshot again.
4. Query the snapshot for that player.

✅ **Checkpoint:** two rows. Row 1: team A, valid X → Y. Row 2: team B,
valid Y → 9999-12-31. If row 2's `dbt_valid_from` is *today*, you're
using `check` or the wrong `updated_at`.

<details>
<summary>Solution (after you have your own)</summary>

```yaml
snapshots:
  - name: snp_player_roster
    relation: ref('stg_nba__rosters')
    config:
      unique_key: player_id
      strategy: timestamp
      updated_at: effective_at        # or _loaded_at if the feed has no effective date
      dbt_valid_to_current: "cast('9999-12-31' as timestamp)"
```

Tested with dbt-duckdb 1.11: changing `team_id` from 10 to 20 with
`updated_at` moving from 2024-01-01 06:00 to 2024-01-05 06:00 produced
`(10, 2024-01-01 06:00 → 2024-01-05 06:00)` and
`(20, 2024-01-05 06:00 → 9999-12-31)`. The same change under `check`
stamped both boundaries with the run time.

</details>

### 4. Build `dim_player` on the snapshot

The snapshot is raw history; the dimension is what facts join to. In
`models/marts/dim_player.sql`:

- `player_sk`: a surrogate key per *version*
  (`dbt_utils.generate_surrogate_key(['player_id', 'dbt_valid_from'])`)
- `player_id`: the durable natural key, the same across all versions
- attributes from your M3.3 design (name, position, team, …)
- `valid_from` and `valid_to` (renamed from `dbt_valid_from` /
  `dbt_valid_to`), half-open, current row ending 9999-12-31
- `is_current` (`valid_to = '9999-12-31'`)

These names are the ones M3 settled on. Every as-of join in M5.7, M7 and
M12 depends on them, so don't improvise here.

Tests:

- `unique` on the surrogate key
- a singular test that **no player has overlapping versions**:

```sql
-- tests/assert_dim_player_no_overlaps.sql
select a.player_id
from {{ ref('dim_player') }} a
join {{ ref('dim_player') }} b
  on a.player_id = b.player_id
 and a.player_sk <> b.player_sk
 and a.valid_from < b.valid_to
 and b.valid_from < a.valid_to
```

- exactly one `is_current` row per player (write it yourself)

PR `m5.5-dim-player`, `Closes #72`. Include the before/after query output
from step 3 in the description.

## Gotchas

- **Snapshots aren't rebuildable.** `--full-refresh` doesn't recreate
  history; the snapshot table *is* the history. Never drop it casually,
  and make sure M10 backs it up.
- **Snapshots only see what exists when they run.** Two changes between
  runs record as one. Run the snapshot at least as often as the feed changes.
- **Hard deletes.** A player waived off every roster disappears from the
  feed. Look up `hard_deletes` in the snapshot docs and decide: ignore,
  invalidate, or add a new "deleted" row.

## Stretch: history from events

Snapshots start recording the day you turn them on. To get 2002-to-now
player-team history, derive it from box scores: each player's games
ordered by date, islands of consecutive games for the same `team_id`
(the M1.3 pattern), `valid_from` = first game of the island. Compare it
with your snapshot for the dates both cover.
