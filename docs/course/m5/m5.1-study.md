## Why this matters

dbt is easy to start and easy to get subtly wrong. The epic's ready-when
question, "when does an incremental model silently produce wrong numbers?",
is a favourite senior interview question because every answer is a real
production incident: a duplicate, a missed late row, a deleted partition.
This lab gives you the vocabulary, and the failure mode behind each option.

- A table: **each incremental strategy → its failure mode**, which you can
  explain out loud. That's the acceptance criterion.

## Session 2 · Incremental models and strategies (90 min)

**Read:** [Incremental models](https://docs.getdbt.com/docs/build/incremental-models-overview),
[Incremental strategies](https://docs.getdbt.com/docs/build/incremental-strategy),
and the [dbt-duckdb README](https://github.com/duckdb/dbt-duckdb) section on
incremental strategies.

The core of an incremental model:

```sql
{{ config(materialized='incremental', unique_key='play_id') }}
select ...
from {{ ref('stg_nba__pbp') }}
{% if is_incremental() %}
where game_date >= (select max(game_date) from {{ this }})   -- only "new" rows
{% endif %}
```

On the first run (or with `--full-refresh`) the `if` block is skipped and
the whole table is built.

Now the strategies. For each, write **how it works** and **how it fails
silently**. Try for 10 minutes per row before opening the hint.

| Strategy | How it works | Silent failure mode |
|---|---|---|
| `append` | | |
| `delete+insert` | | |
| `merge` | | |
| `insert_overwrite` | | |
| `microbatch` | | |

<details>
<summary>Hint · Failure modes (compare after writing yours)</summary>

- **append**: inserts whatever the `is_incremental()` filter returns.
  Re-run a day, or have overlapping filters, and you get **duplicates**.
  Corrections to old rows never land.
- **delete+insert**: deletes target rows matching `unique_key` in the new
  batch, then inserts. If `unique_key` isn't actually unique in the batch,
  you insert duplicates. If a row disappears upstream (a deleted event),
  it stays in the target forever.
- **merge**: updates matches, inserts the rest. Same unique-key trap, and
  in most warehouses a duplicate key in the source makes the merge
  **error** or pick an arbitrary row. Rows deleted upstream aren't deleted.
- **insert_overwrite**: replaces whole partitions. Safe for late data
  *inside* the partitions you select. If your filter misses a partition
  that changed, the change is lost; if it selects a partition but the
  query returns only part of its rows, you **wipe** the rest.
  (dbt-duckdb doesn't support it. Sneakily, the *first* run succeeds,
  because a first run is a plain full build; the error only appears on
  the second, incremental run. Know it for BigQuery/Spark interviews.)
- **microbatch**: dbt splits the run into time batches by `event_time` and
  replaces each batch. Rows whose `event_time` is wrong or NULL land in the
  wrong batch or nowhere. A `lookback` that is too short misses late data.

The common thread: **the filter decides what you look at; the strategy
decides what happens to what you look at.** Anything outside the filter
is invisible. That's the lookback window's job in M5.6.

</details>

**Try it:** build a 3-row incremental model with `append`, run it twice
without changing the source. Count the rows. Switch to `delete+insert`
with a `unique_key`, `--full-refresh`, run twice. Count again.

✅ **Checkpoint:** you've *seen* append duplicate rows, not just read that
it does.

## Session 3 · Snapshots (45 min)

**Read:** [Snapshots](https://docs.getdbt.com/docs/build/snapshots).
Modern dbt (1.9+) configures snapshots in YAML:

```yaml
snapshots:
  - name: snp_player_roster
    relation: source('nba_raw', 'roster')
    config:
      unique_key: athlete_id
      strategy: timestamp          # or: check
      updated_at: effective_at     # timestamp strategy only
      dbt_valid_to_current: "cast('9999-12-31' as timestamp)"
```

Answer in your notes:

1. `timestamp` vs `check`: what does each compare to detect a change?
2. What do `dbt_valid_from` and `dbt_valid_to` contain under each? (One of
   them uses the time **you ran dbt**. That matters a lot in M5.5.)
3. A snapshot only sees the source **when it runs**. If the roster changes
   twice between runs, what's recorded?
4. Why can't you rebuild a snapshot's history with `--full-refresh`?

## Session 4 · Tests, unit tests and state (60 min)

**Read:** [Data tests](https://docs.getdbt.com/docs/build/data-tests),
[Unit tests](https://docs.getdbt.com/docs/build/unit-tests),
[Node selection: state](https://docs.getdbt.com/reference/node-selection/methods#state).

- **Data tests** (generic like `unique`, `not_null`; singular `.sql` files)
  check the *data* after it's built.
- **Unit tests** feed fixed input rows to one model and assert the output.
  They check the *logic*, before any real data exists.

Which kind catches a duplicated row from a bad incremental run? Which
catches a wrong `CASE` expression on an edge case the real data doesn't
contain yet?

**State selection:** dbt compares your project to a saved `manifest.json`
(the "state") and selects what changed. `state:modified+` is
"changed models plus everything downstream". Why the `+`? What is
`--defer` for? (M5.11 builds this.)
