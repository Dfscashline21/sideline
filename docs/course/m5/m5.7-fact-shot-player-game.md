# M5.7 · `fact_shot` and `fact_player_game`

> **Ticket:** [#74](https://github.com/Dfscashline21/sideline/issues/74) ·
> **Mode:** hand · **Time:** 3 hours ·
> **Needs:** M5.6 (the fact pattern), M5.5 and M5.8 (dims to join), M3.2 grains

## Why this matters

A fact table is only as trustworthy as its **grain**: the precise
statement of what one row means. Most wrong dashboard numbers trace back
to a join that silently changed the grain (one row per player per game
becomes several, and points double). The acceptance criterion is just
"grain tests pass", and that small test protects every downstream number.

## What you'll produce

- `fact_shot`: one row per field-goal attempt.
- `fact_player_game`: one row per player per game.
- Unique-key tests proving each grain.

- `fact_team_game`: one row per team per game (step 3b). The ticket
  doesn't name it, but M6, M9, M11 and M12 all build on it, so add it here.

## Steps

### 1. Write both grain statements (15 min)

Copy them from M3.2 into the model files as the first comment. If M3.2
didn't define one for `fact_shot`, write it now, precisely:

> One row per **field-goal attempt** (made or missed) in an NBA game.
> Free throws are **not** shots. Key: `play_id`.

Then answer: is a blocked shot a field-goal attempt? (Yes, in the box
score.) Is a shot that's waved off for a foul before release? Decide and
write it down.

### 2. Build `fact_shot`

Source: `fact_play` (or staging play-by-play) filtered to field-goal
attempts. Columns: keys (`play_id`, `game_id`, `player_id`, `team_id`),
foreign keys to dims, `shot_value` (2 or 3), `is_made`, `shot_type`,
coordinates if M4.5 added them, `game_seconds_remaining`.

<details>
<summary>Hint 1 · Nudge: the free-throw trap</summary>

In the ESPN feed, `shooting_play` is true for free throws as well. If you
filter on it alone, your "shots" include every free throw. How do you tell
them apart?

</details>

<details>
<summary>Hint 2 · Approach</summary>

Exclude events whose type is a free throw (`event_type like 'free throw%'`).
Then reconcile: per team per game, your shot count should equal
field-goal attempts in the box score. In M1 testing, play-by-play FGA
matched box-score FGA to within a fraction of a shot per team-game.

</details>

Make it incremental the same way as `fact_play` (same lookback var), since
it inherits its corrections.

### 3. Build `fact_player_game`

Source: staging player box scores. Decide (in the header):

- **DNP rows.** Keep them with an `is_dnp` flag (so "games on roster" is
  answerable), or drop them (so averages are simpler)? M1.4's lesson:
  averages silently skip NULLs.
- **Surrogate keys.** Join to `dim_player` **as of the game date**
  (`game_date >= valid_from and game_date < valid_to`) to get the
  `player_sk` that was valid that day. This is the payoff of M5.5.

<details>
<summary>Hint · The as-of join</summary>

```sql
left join {{ ref('dim_player') }} p
  on p.player_id = b.player_id
 and b.game_date >= p.valid_from
 and b.game_date <  p.valid_to
```

`left join` plus a `not_null` test on `player_sk` catches games with no
valid player version, rather than dropping them silently with an inner join.

</details>

### 3b. Build `fact_team_game` (later modules depend on it)

Grain: **one row per team per game**, key `(league, game_id, team_id)`.
Source: the staging team box score, joined to `dim_team`, `dim_game` and
`dim_season`. Carry `team_score`, `opponent_score`, `team_winner`,
`home_away` and the box-score totals (FGA, FTA, offensive rebounds,
turnovers).

Two checks to write as tests:

- every `game_id` has exactly **two** rows (one per team);
- each game's `team_score` equals the sum of its players' `points` in
  `fact_player_game`. Investigate any mismatch before you suppress it.

### 4. Grain tests

For each fact, in YAML:

```yaml
models:
  - name: fact_player_game
    data_tests:
      - dbt_utils.unique_combination_of_columns:
          arguments:
            combination_of_columns: [game_id, player_id]
```

And for `fact_shot`, `unique` + `not_null` on `play_id`.

Then try to break them on purpose: temporarily join `dim_player` without
the date condition. The grain test should fail for traded players.

✅ **Checkpoint:** grain tests pass on the real model and fail on the
deliberately broken join. That proves they work.

### 5. Reconcile against the box score

Write a singular test: per team per game, `count(*)` of `fact_shot` equals
the box-score FGA, and `sum(points)` in `fact_player_game` equals the team
score. Allow a small, documented tolerance only if you find a real source
discrepancy, and write down which games.

### 6. Ship it

PR `m5.7-facts`, `Closes #74`.

## Gotchas

- **`dbt_utils` test syntax.** Newer dbt versions want generic-test
  arguments nested under `arguments:` (as above). The older flat form
  still parses but warns. Check what your version prints.
- **Inner joins hide problems.** Use left joins to dims plus `not_null`
  tests on the resulting keys.
- **One player, two rows in one game?** It happens in raw data after a
  re-load. Staging should have deduped it. If the grain test fails,
  look upstream first.
