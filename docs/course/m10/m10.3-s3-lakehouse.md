# M10.3 · S3 lakehouse and catalog

> **Ticket:** [#133](https://github.com/Dfscashline21/sideline/issues/133) ·
> **Mode:** agent: the agent drafts, you review it like a junior's PR ·
> **Time:** 3 to 4 hours · **Needs:** M10.2 merged, M4 (your local Iceberg
> tables and catalog), M5 (marts to publish)

## Why this matters

Locally, your lakehouse is MinIO plus a REST catalog in Compose. In the
cloud it becomes S3 plus a managed or self-hosted catalog, and the
decisions that were free locally now carry cost, security and operational
weight: encryption, lifecycle rules, who can read which prefix, and which
catalog every engine (Spark, DuckDB, Dagster, Snowflake) can talk to.

## What you'll produce

- `infra/terraform/modules/lake/`: buckets with encryption, public access
  blocked, versioning where it matters, lifecycle rules.
- `infra/terraform/modules/catalog/`: the cloud Iceberg catalog.
- An ADR choosing **Glue Data Catalog vs a self-hosted REST catalog**.
- Proof that **Iceberg tables are readable in the cloud**.

## Steps

### 1. Decide the catalog (hand, 45 min) and write the ADR

This is your decision, not the agent's. Compare:

| | AWS Glue Data Catalog | Self-hosted REST catalog (same one as M4.2, on ECS) |
|---|---|---|
| Ops | Managed; nothing to run | A service plus its database to run, patch and pay for hourly |
| Engines | Spark, PyIceberg, Athena, Snowflake (`CATALOG_API_TYPE = AWS_GLUE`) via Glue's Iceberg REST endpoint `https://glue.<region>.amazonaws.com/iceberg` with SigV4 | Anything speaking Iceberg REST |
| Parity with local dev | Different from local (Compose uses a REST catalog) | Same as local |
| Auth | IAM | Whatever the catalog supports (OAuth, tokens) |
| Cost | Pay per object stored and request beyond the free tier (look it up) | Always-on compute plus database |

Glue speaks the Iceberg REST protocol, so the "REST vs Glue" gap is
smaller than it looks: your code can use a REST client in both places
and change only the URI and auth.

Write `docs/adr/NNN-cloud-catalog.md` (next free number) with context,
options, decision and consequences. Link it from ADR-003 (M4.10), which
already mentioned the catalog.

### 2. Design the buckets (hand, 30 min)

Decide and write down in `infra/README.md`:

- **Names**: global, so include env and account,
  e.g. `sideline-lake-dev-<account-id>`, `sideline-raw-dev-<account-id>`.
- **Prefixes**: `raw/<league>/...` (your M2.2 layout) and Iceberg
  warehouse locations per namespace.
- **Encryption**: SSE-S3 (default on all new buckets, no extra cost) or
  SSE-KMS (key-level access control and audit, but per-request KMS charges
  and a key policy to maintain; bucket keys reduce the request cost)?
- **Lifecycle** for each prefix (see Gotchas before choosing).

### 3. Prompt the agent

> Write Terraform modules `infra/terraform/modules/lake` and
> `infra/terraform/modules/catalog` for this repo, plus the calls from
> `infra/terraform/envs/dev/main.tf`. Read `infra/README.md` and
> `AGENTS.md` first. Requirements: *(paste your bucket design and ADR
> decision)*. Use separate resources for bucket configuration
> (`aws_s3_bucket_server_side_encryption_configuration`,
> `aws_s3_bucket_public_access_block`, `aws_s3_bucket_versioning`,
> `aws_s3_bucket_lifecycle_configuration`), not deprecated inline blocks.
> Tag resources with `league` where a resource belongs to one league.
> Output bucket names and ARNs and the catalog identifier. Don't create
> IAM policies with `*` actions or resources. Explain each lifecycle rule
> in a comment.

### 4. Review it like a PR

| Review question | Good answer |
|---|---|
| Is public access blocked on every bucket? | All four `block_*`/`ignore_*`/`restrict_*` flags true |
| What happens to Iceberg data files under lifecycle rules? | **No** expiration rule touches Iceberg `data/` or `metadata/` prefixes |
| Does any rule transition small objects to Infrequent Access? | No, or with a size filter and a reason |
| Is `force_destroy` set? Where? | Only on dev buckets, and you know what it does |
| What's encrypted and with what key? | Matches your step 2 decision |
| Could you explain every argument to an interviewer? | Yes, or you ask the agent and write it down |

Then `terraform plan` for dev and read the plan line by line before applying.

### 5. Get tables into the cloud catalog

Iceberg metadata stores **absolute file paths**. Your local tables point
at `s3://sideline-lake/...` on MinIO; in AWS the bucket has a different
name, so you **can't just copy the files** and register them: the copied
metadata would still point at the old bucket. (Iceberg's Spark procedures
include a table-path rewrite for migrations like this, but it's an
advanced route.) The simple, reliable route is to *re-produce* the
tables in the cloud:

1. Point your M4 loader (or a one-off PyIceberg/Spark job) at the cloud
   catalog and target bucket.
2. Re-run it for at least `raw.pbp` (or a few seasons of it) and one mart.

<details>
<summary>Hint · PyIceberg against Glue</summary>

PyIceberg has a native Glue catalog type, or you can use its REST catalog
type pointed at Glue's Iceberg endpoint with SigV4 signing. Check the
PyIceberg configuration docs for the exact property names in your
installed version. The Spark equivalent from the AWS docs:

```python
.config("spark.sql.catalog.glue", "org.apache.iceberg.spark.SparkCatalog")
.config("spark.sql.catalog.glue.type", "rest")
.config("spark.sql.catalog.glue.uri", "https://glue.us-east-1.amazonaws.com/iceberg")
.config("spark.sql.catalog.glue.warehouse", "<account-id>")
.config("spark.sql.catalog.glue.rest.sigv4-enabled", "true")
.config("spark.sql.catalog.glue.rest.signing-name", "glue")
```

</details>

### 6. Prove "readable in the cloud"

Read the table from a **different engine** than the one that wrote it.
Any two of these:

- Athena: `select season, count(*) from <db>.pbp group by 1` (Athena reads
  Glue Iceberg tables directly; it bills per data scanned, so filter)
- PyIceberg from your laptop: `catalog.load_table("raw.pbp").scan(...)`
- DuckDB's `iceberg` extension against the catalog

✅ **Checkpoint:** row counts per season match your local table for the
seasons you loaded. Record both in the PR description.

## Gotchas

- **Never let S3 lifecycle rules expire Iceberg files.** Iceberg decides
  which files are live from its metadata. If S3 deletes a data file a
  snapshot still references, the table breaks. Clean up with Iceberg's own
  maintenance (expire snapshots, remove orphan files: M4.7).
- **Infrequent Access isn't cheaper for small files.** IA has a minimum
  billable object size and a minimum storage duration. Thousands of small
  raw JSON files can cost *more* in IA. Check the S3 pricing page for the
  current minimums.
- **Abort incomplete multipart uploads.** Add a lifecycle rule for it
  (e.g. after 7 days). Failed large uploads otherwise sit there, billed and invisible.
- **Versioned buckets don't empty with `rm`.** Old versions and delete
  markers remain. M10.12 will hit this unless dev uses `force_destroy` or
  you empty all versions first.
