# M10.10 · Cut cost 30% with one documented change

> **Ticket:** [#140](https://github.com/Dfscashline21/sideline/issues/140) ·
> **Mode:** hand · **Time:** 2 hours of work, spread over about two weeks
> of measuring · **Needs:** M10.9 (tags active, report working), M10.4 running

## Why this matters

"Tell me about a time you reduced cost" is a top-five senior interview
question, and the strong answer has the same shape as M1.7's query
speed-up: **measure, find the biggest line, change one thing, measure
again, explain the trade-off.** One change, so the cause is clear.
A list of ten tweaks with a combined number proves nothing.

## What you'll produce

`docs/cost/m10.10-cost-cut.md` with a before/after cost comparison
showing at least a 30% reduction, the one change, and its trade-off.

## Steps

### 1. Establish the baseline (a week of normal running)

Run the platform normally (daily Dagster runs, the usual schedule) for
a full week, so weekdays and weekends are both included. Then pull
**daily** cost by service:

```bash
aws ce get-cost-and-usage \
  --time-period Start=YYYY-MM-DD,End=YYYY-MM-DD \
  --granularity DAILY --metrics UnblendedCost \
  --group-by Type=DIMENSION,Key=SERVICE \
  --filter '{"Tags": {"Key": "project", "Values": ["sideline"]}}'
```

Make a table: service, cost over the week, % of total. Then break the
top one or two down by **usage type** (`Key=USAGE_TYPE`). "EC2-Other" in
particular hides NAT gateway hours, NAT data processing and public IPv4
charges.

✅ **Checkpoint:** you know the top three line items and roughly what
drives each (hours running, GB processed, requests, storage).

### 2. Pick the one change (hand)

Rank candidates by **expected saving ÷ effort ÷ risk**. Estimate each
saving from the baseline table, not from a blog post.

<details>
<summary>Hint 1 · Nudge: where small platforms usually overspend</summary>

On a hobby-scale platform the bill is dominated by things that bill **per
hour whether or not they're used**, not by data volume. Which of your
resources run 24/7 but do work for a few minutes a day?

</details>

<details>
<summary>Hint 2 · Candidate changes</summary>

| Change | Saves | Trade-off |
|---|---|---|
| Remove the NAT gateway: S3 gateway endpoint plus public subnets for tasks, or interface endpoints only where needed | NAT hourly + per-GB processing | Tasks get public IPs (charged per IPv4, and more exposed), or interface endpoints cost hourly too: compare |
| Scale Dagster webserver/daemon to 0 outside the run window (scheduled scaling) | Fargate hours | No UI or sensors while scaled down; schedules must be triggered externally (e.g. EventBridge) |
| Fargate on ARM (Graviton) and/or Fargate Spot for run tasks | Per-vCPU/GB-hour price | Image must be built for ARM; Spot tasks can be interrupted, so runs need retries |
| Replace always-on RDS with a smaller/stoppable instance, or Postgres in a task | RDS hours | Durability and run history |
| CloudWatch log retention from "never expire" to 7 days in dev | Log storage | Less history for debugging |
| Iceberg snapshot expiry + orphan file cleanup | S3 storage | Less time travel |

Check current prices on the AWS pricing pages for your region before you
estimate. A 30% cut usually needs the **biggest** line item, not the
easiest one.

</details>

Write the hypothesis before changing anything: *"X is N% of the weekly
bill because of Y; changing Z should remove about M% of total cost."*

### 3. Make the change in Terraform

One PR, one change, applied through your M10.7 pipeline so the change is
recorded. Verify the platform still works: a daily run succeeds and its
outputs land where they should.

### 4. Measure the after (another full week)

Same length, same workload, same query as step 1. Don't compare a
partial week with a full one, and wait at least a day after the change
before starting the window, because cost data lags.

Compute:

```
reduction = (before_total − after_total) / before_total
```

If the workload changed between the two weeks (a backfill, extra
seasons), normalise by a unit: cost per daily run, or per 1,000 games
ingested. That's the FinOps "unit economics" idea from M10.1.

✅ **Checkpoint:** reduction ≥ 30% on a like-for-like basis. If you got
less, the write-up still counts as progress: explain why your estimate
was off, then try the next-biggest lever as a separate change.

### 5. Write it up

`docs/cost/m10.10-cost-cut.md`:

```markdown
# Cutting Sideline's AWS cost by NN%

## Baseline (dates)
Table: top services and usage types, weekly cost, % of total.

## Hypothesis
One sentence.

## Change
What, why this one, PR link.

## After (dates)
Same table. Reduction: NN% (unit-normalised if the workload changed).

## Trade-off
What got worse (exposure, latency, availability, history) and why it's acceptable here.

## What I'd do next
The next lever and its estimated saving.
```

Add the before/after number to the README's Numbers section (M0.6).

## Gotchas

- **Measuring the wrong window.** Daily granularity plus a full week on
  each side. Monthly totals mix before and after.
- **Credits.** Use unblended cost before credits, or the "after" can be $0
  for the wrong reason.
- **Removing NAT can break things silently.** Tasks in private subnets
  without a route to ECR, Secrets Manager or the internet hang at
  startup. Test a run before measuring.
- **Security trade-offs belong in the write-up.** Moving tasks to public
  subnets saves money and widens the attack surface. Say how security
  groups compensate, and update the M10.11 diagram.
