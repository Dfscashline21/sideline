# M10.6 · IAM least-privilege review

> **Ticket:** [#136](https://github.com/Dfscashline21/sideline/issues/136) ·
> **Mode:** hand · **Time:** 3 hours ·
> **Needs:** M10.3, M10.4, M10.5, M10.7 (every role and policy exists), M10.1 session 1

## Why this matters

Agents drafted most of your Terraform, and agents (like people in a
hurry) love `"Action": "s3:*"` and `"Resource": "*"`: they make errors go
away. Least privilege is the security habit interviewers probe hardest
because it's where real breaches start: a leaked CI credential with
admin rights, or a task role that can read every bucket in the account.
This lab is a line-by-line review, plus a check that stops wildcards
creeping back.

## What you'll produce

- Every IAM policy reviewed, with each `*` removed or justified in writing.
- `infra/scripts/check_iam_wildcards.py`: fails if a new wildcard appears
  without a recorded reason, run in CI.
- `docs/notes/m10-iam-review.md`: the inventory and what you changed.

## Steps

### 1. Inventory every policy (45 min)

List every role and what it's for. Get them from Terraform, not from
memory:

```bash
cd infra/terraform/envs/dev
terraform state list | grep -E 'aws_iam_(role|policy|role_policy)|aws_s3_bucket_policy'
```

Make a table in your notes:

| Role / policy | Who uses it | Trust (who can assume) | What it must do | Wildcards found |
|---|---|---|---|---|
| `sideline-dagster-exec-dev` | ECS agent | `ecs-tasks.amazonaws.com` | pull image, write logs, read 2 secrets | |
| `sideline-dagster-task-dev` | your code | `ecs-tasks.amazonaws.com` | read/write lake, read catalog | |
| `sideline-deploy-dev` | GitHub Actions | OIDC, `main` branch only | terraform apply dev | |
| `sideline-snowflake-dev` | Snowflake | Snowflake IAM user + external ID | read marts | |

✅ **Checkpoint:** every role in `terraform state list` is in the table, and
you can say who assumes it.

### 2. Review trust policies first (30 min)

Trust policies decide **who can become** the role, so they matter more
than permissions. For each, check:

- Is the principal exactly one service, account, or federated identity?
- For GitHub OIDC: is `token.actions.githubusercontent.com:sub` pinned
  to your repository **and** a branch or environment, not `repo:owner/*`?
  Is `:aud` checked?
- For Snowflake: is `sts:ExternalId` required?

A role whose trust policy is too broad is a finding even if its
permissions are tight.

### 3. Review permissions line by line (60 min)

For every `Allow` statement, ask four questions:

1. **Action**: is each action needed? Replace `s3:*` with the actual verbs.
2. **Resource**: is it the narrowest ARN? Bucket ARN for `ListBucket`,
   `bucket/prefix/*` for objects, specific secret ARNs, specific Glue
   database and table ARNs.
3. **Condition**: could a condition narrow it further (`s3:prefix` on
   `ListBucket`, `aws:SourceVpce`, a tag condition)?
4. **Is `*` truly required?** Some actions don't support resource-level
   permissions at all, so `Resource: "*"` is the only option. Find out
   per action in the [Service Authorization Reference](https://docs.aws.amazon.com/service-authorization/latest/reference/reference_policies_actions-resources-contextkeys.html):
   if the "Resource types" column is empty for an action, it needs `*`.

When `*` stays, give the statement a `Sid` and write the reason in a
comment right above it in the Terraform.

<details>
<summary>Hint · Tools that help (they don't replace reading)</summary>

- `aws accessanalyzer validate-policy --policy-type IDENTITY_POLICY
  --policy-document file://p.json` flags overly broad statements and
  syntax problems.
- CloudTrail shows which actions a role *actually* called in the last
  days. Anything granted but never called is a candidate to remove.
- IAM Access Analyzer can also generate a policy from CloudTrail activity
  (check whether it costs anything in your account before enabling paid
  analyzers).

</details>

### 4. Apply the fixes and prove nothing broke (30 min)

Apply to dev, then run the things that use each role: a Dagster daily
run, a CI deploy, a Snowflake query. An `AccessDenied` now means you
removed something needed. CloudTrail's event shows exactly which action
and resource, so add back only that.

✅ **Checkpoint:** all three still work after the tightening.

### 5. Write the guard (hand, 45 min)

Reviews decay; the next agent-written policy will bring `*` back. Write
`infra/scripts/check_iam_wildcards.py` that reads Terraform JSON output
and exits 1 when an `Allow` statement uses a wildcard that isn't in an
allow-list with a reason.

<details>
<summary>Hint 1 · Nudge: where are the policies in Terraform's JSON?</summary>

`terraform show -json` (after apply) prints the state. Resources sit
under `values.root_module.resources` and, for modules, recursively under
`child_modules`. IAM policies appear as JSON *strings* in attributes like
`policy` (on `aws_iam_policy`, `aws_iam_role_policy`,
`aws_s3_bucket_policy`) and `assume_role_policy` (on `aws_iam_role`).

</details>

<details>
<summary>Hint 2 · Approach: what counts as a wildcard?</summary>

Don't flag every `*`: `arn:aws:s3:::sideline-lake-dev/marts/*` is how you
scope to a prefix, so that's least privilege done right. Flag:

- any `*` in an **action** (`s3:*`, `glue:Get*`)
- a **resource** that is exactly `"*"`

Key the allow-list on the resource address plus the statement `Sid`, so
each exception has its own reason.

Also: `Statement`, `Action` and `Resource` can each be a single value
*or* a list in IAM JSON. Normalise them first.

</details>

<details>
<summary>Solution (open only after you have your own)</summary>

```python
"""Fail if an IAM policy in Terraform JSON uses a wildcard without a recorded reason."""

import json
import sys
from pathlib import Path
from typing import Any

POLICY_ATTRS = ("policy", "assume_role_policy")

# "<terraform address>|<statement Sid>" -> why the wildcard is needed.
ALLOWED: dict[str, str] = {
    "module.orchestrator.aws_iam_role_policy.execution|EcrAuth": (
        "ecr:GetAuthorizationToken has no resource-level permissions, so Resource must be *"
    ),
}


def as_list(value: Any) -> list[Any]:
    return [value] if isinstance(value, str | dict) else list(value or [])


def resources(module: dict[str, Any]) -> list[dict[str, Any]]:
    found = list(module.get("resources", []))
    for child in module.get("child_modules", []):
        found += resources(child)
    return found


def is_wildcard(field: str, value: str) -> bool:
    # Any * in an action is too broad (s3:*, s3:Get*). For resources, flag only the
    # bare "*": a path wildcard like arn:aws:s3:::bucket/marts/* is how prefixes are scoped.
    return "*" in value if field == "Action" else value == "*"


def findings(tf_json: dict[str, Any]) -> list[str]:
    # `terraform show -json` (state) uses "values"; a saved plan uses "planned_values".
    root = (tf_json.get("values") or tf_json["planned_values"])["root_module"]
    problems = []
    for res in resources(root):
        for attr in POLICY_ATTRS:
            raw = res.get("values", {}).get(attr)
            if not raw:
                continue
            for stmt in as_list(json.loads(raw)["Statement"]):
                if stmt.get("Effect") != "Allow":
                    continue
                key = f"{res['address']}|{stmt.get('Sid', '')}"
                for field in ("Action", "Resource"):
                    for value in as_list(stmt.get(field)):
                        if is_wildcard(field, value) and key not in ALLOWED:
                            problems.append(f"{key}: {field} {value!r}")
    return problems


def main() -> None:
    problems = findings(json.loads(Path(sys.argv[1]).read_text()))
    for problem in problems:
        print("WILDCARD", problem)
    sys.exit(1 if problems else 0)


if __name__ == "__main__":
    main()
```

Run it with `terraform show -json > /tmp/state.json && uv run python
infra/scripts/check_iam_wildcards.py /tmp/state.json`. Run it against
**state**, not a plan: in a plan, a policy that references an ARN not
created yet is *unknown* and simply missing from the JSON, so the
check would silently pass.

</details>

Add a unit test with a tiny hand-written JSON fixture (one allowed
wildcard, one forbidden) so the checker itself is tested. Then wire it
into the deploy workflow from M10.7 after `apply`.

## Gotchas

- **`ListBucket` vs `GetObject`.** Different resource ARNs (bucket vs
  objects). Tightening one often breaks the other.
- **KMS.** If buckets use SSE-KMS, readers also need `kms:Decrypt` on the
  key, and the **key policy** must allow it. The error looks like an S3 problem.
- **AWS managed policies** (`AmazonECSTaskExecutionRolePolicy` and so on)
  are convenient but broad. Reading them counts as part of the review.
- **Deny statements** with `*` are fine and often good (e.g. deny
  non-TLS access). The checker ignores them deliberately.
