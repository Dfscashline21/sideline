# M10.9 · Budget alarm and cost-per-league report

> **Ticket:** [#139](https://github.com/Dfscashline21/sideline/issues/139) ·
> **Mode:** mixed · **Time:** 3 hours, plus waiting a day for tag activation ·
> **Needs:** M10.2 (`default_tags`), ideally M10.3 and M10.4 running so there's spend to report

## Why this matters

"How much does this platform cost, and who's it for?" is a question
every data team gets from finance eventually. Answering it needs two
things you'll build here: an **alarm** so a mistake costs $20 rather than
$2,000, and **attribution** so costs land on the league (the "product")
that caused them. Splitting shared costs fairly is the interesting part,
and it's yours to design.

## What you'll produce

- `infra/terraform/modules/cost/`: an AWS Budget, an SNS topic with email
  subscription, and activated cost allocation tags. This replaces the
  hand-made budget from the [module overview](README.md).
- An alarm that **fires in a test**.
- `infra/scripts/cost_report.py`: writes `docs/cost/YYYY-MM.md` with
  monthly cost per league, including your allocation of shared costs.

## Mixed mode: who writes what

| You write (core) | Agent may draft (boilerplate) |
|---|---|
| The tagging rules: which resources get which `league` value | The `cost` Terraform module from your spec |
| The allocation rule for shared costs, and its code | The boto3 call that fetches costs |
| The test that proves the alarm fires | Markdown rendering of the report |

## Steps

### 1. Tag everything, then activate the tags (30 min, then wait)

`default_tags` (M10.2) already sets `project`, `env`, `managed`. Add
`league` to resources that belong to one league. Then decide what
`league` means for shared resources: leave it untagged, or tag it
`shared` explicitly? (Explicit is easier to report on.)

Tags don't appear in Cost Explorer until they're **activated** as cost
allocation tags, and activation only works once the tag key exists on at
least one resource. Activate them with the
`aws_ce_cost_allocation_tag` resource (`tag_key`, `status = "Active"`).
Activation can take up to a day to show, and **attribution only covers
spend after activation**, which is why M10.10 needs this done early.

✅ **Checkpoint:** in Billing → Cost allocation tags, `league`, `env` and
`project` show as Active.

### 2. The budget and its notifications (agent drafts, you review)

Spec for the agent:

- `aws_budgets_budget`: `budget_type = "COST"`, `time_unit = "MONTHLY"`,
  a `limit_amount` you choose, optional `cost_filter` on `project = sideline`.
- `notification` blocks at 50% and 80% `ACTUAL` and 100% `FORECASTED`,
  sent to an SNS topic and your email.
- An SNS topic whose **topic policy allows `budgets.amazonaws.com`** to
  publish, and an email subscription.

Review checklist:

- [ ] `threshold_type = "PERCENTAGE"` and thresholds as you specified
- [ ] SNS topic policy scoped to the budgets service principal, with an
      `aws:SourceAccount` condition
- [ ] Email subscription confirmed (AWS sends a confirmation email: click it)
- [ ] Budget limit is a variable, smaller in dev

### 3. Make the alarm fire in a test (hand, 30 min)

AWS Budgets has no "send a test notification" button, and you don't want
to *spend* money to test it. Design a test that exercises as much of the
real path as possible. Options, from weakest to strongest:

1. `aws sns publish --topic-arn <arn> --message test`: proves the topic
   and your email work, not the budget.
2. A **CloudWatch billing alarm** on `EstimatedCharges` (namespace
   `AWS/Billing`, only in `us-east-1`, needs "Receive CloudWatch billing
   alerts" enabled in Billing preferences) sending to the same topic, then
   force it: `aws cloudwatch set-alarm-state --alarm-name <name>
   --state-value ALARM --state-reason "test"`. That runs the alarm's
   actions for real.
3. A temporary budget with a tiny limit (e.g. $0.01 actual) that your
   existing spend already exceeds. Budgets are evaluated a few times a
   day, so expect a delay.

Do at least option 2. Record what you ran and the email you got (a
screenshot in the PR is fine).

✅ **Checkpoint:** an alarm email arrives from a forced state change.

### 4. Design the allocation rule (hand, 30 min)

Your bill has **direct** costs (tagged `league = nba`) and **shared** ones
(ECS cluster, NAT, RDS for Dagster, catalog). Write in your notes how
shared costs are split, and why:

| Rule | Fair when | Weakness |
|---|---|---|
| Equal split | Leagues are similar sizes | WNBA's short season pays the same as NBA's |
| By rows ingested | Cost is driven by data volume | Ignores compute-heavy transforms |
| By pipeline run time | Cost is driven by compute | Needs run durations per league (Dagster has them) |

There's no single right answer; a defensible, documented one is the goal.

### 5. Write the allocation code (hand, 30 min)

Write a pure function: direct costs per league + shared total + weights →
cost per league, where **the results always add up to the bill**.

<details>
<summary>Hint · Money and rounding</summary>

Use `Decimal`, not `float`. Rounding each share to cents can leave the
total off by a cent or two; decide which league absorbs the difference,
and test that the sum equals the bill exactly.

</details>

<details>
<summary>Solution (open only after you have your own)</summary>

```python
from decimal import ROUND_HALF_UP, Decimal


def allocate(
    direct: dict[str, Decimal], shared: Decimal, weights: dict[str, float]
) -> dict[str, Decimal]:
    """Each league's direct cost plus a share of the shared cost, proportional to its weight."""
    total_weight = sum(weights.values())
    if total_weight <= 0:
        raise ValueError("weights must sum to a positive number")
    cent = Decimal("0.01")
    result = {
        league: direct.get(league, Decimal(0))
        + (shared * Decimal(str(w / total_weight))).quantize(cent, ROUND_HALF_UP)
        for league, w in weights.items()
    }
    # Rounding can leave a cent or two over or under; give it to the biggest share
    # so the report always adds up to the bill.
    drift = sum(direct.values(), Decimal(0)) + shared - sum(result.values(), Decimal(0))
    result[max(weights, key=lambda k: weights[k])] += drift
    return result


def test_allocation_adds_up() -> None:
    direct = {"nba": Decimal("4.10"), "wnba": Decimal("1.00")}
    out = allocate(direct, Decimal("10.00"), {"nba": 1, "wnba": 1, "ncaa_m": 1})
    assert sum(out.values()) == Decimal("15.10")
    assert out["ncaa_m"] == Decimal("3.33")
```

</details>

### 6. Fetch costs and write the report (agent may draft)

The fetch is boilerplate: Cost Explorer's `get_cost_and_usage` with
`Granularity="MONTHLY"`, `Metrics=["UnblendedCost"]` and
`GroupBy=[{"Type": "TAG", "Key": "league"}]`. Untagged spend comes back
under an empty tag value (`league$`): that's your shared bucket. Add
`boto3` as a dev dependency (`uv add --dev boto3`).

Review the draft for: which cost metric it uses (unblended vs amortized,
and can you explain the difference?), how it maps the empty tag to
"shared", and that it calls your `allocate()` instead of re-implementing it.

Output `docs/cost/YYYY-MM.md` with a table: league, direct, shared share,
total, plus the rule you used and the date range.

✅ **Checkpoint:** the report's total equals the Cost Explorer total for
the same period and filter.

## Gotchas

- **Cost Explorer API requests are billed per request** (check the
  current price). Run the report monthly, not in a loop.
- **Cost data lags.** Today's spend can take up to a day to appear. Don't
  panic over a report that's lower than you expected for today.
- **Credits hide real cost.** If your account has promotional credits,
  "net" cost can be zero. Report unblended cost before credits so the
  numbers mean something.
- **Some costs can't be tagged** (certain data transfer, some per-request
  charges). They land in "shared"; say so in the report.
