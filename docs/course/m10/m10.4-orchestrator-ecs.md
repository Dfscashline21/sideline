# M10.4 · Dagster on ECS

> **Ticket:** [#134](https://github.com/Dfscashline21/sideline/issues/134) ·
> **Mode:** agent: the agent drafts, you review it like a junior's PR ·
> **Time:** 4 to 6 hours · **Needs:** M6 (your Dagster project), M10.2,
> M10.3 (cloud buckets and catalog)

## Why this matters

Running an orchestrator locally hides everything that makes it hard in
production: where its own state lives, how jobs get credentials, how
secrets reach code without being baked into images, and what it costs
to leave running. This lab turns your M6 Dagster project into a cloud
service and makes you account for each of those.

## What you'll produce

- `infra/terraform/modules/orchestrator/`: ECS cluster, Dagster services,
  run storage database, IAM roles, log groups.
- A container image for your Dagster code, pushed to ECR.
- Secrets (e.g. API keys, DB password) in **AWS Secrets Manager**, never
  in the image, the repo, or plain task-definition environment variables.
- **Daily runs succeeding in the cloud**: at least two consecutive
  scheduled days, visible in the Dagster UI and in CloudWatch Logs.

## How Dagster runs on ECS

Dagster's ECS deployment has these parts:

| Part | Role |
|---|---|
| Webserver | The UI and GraphQL API |
| `dagster-daemon` | Runs schedules and sensors, submits queued runs |
| Code location (your image) | Your assets and jobs, served over gRPC |
| Run storage | **Postgres**: run history, event logs, schedules' state |
| `EcsRunLauncher` (`dagster_aws.ecs`) | Launches **each run as its own ECS task** |

`EcsRunLauncher` can inject secrets from Secrets Manager: by default it
loads secrets tagged `dagster` as environment variables (`secrets_tag`
changes the tag), or you list them under `secrets` as `name`/`valueFrom`
pairs. Read the [Dagster ECS deployment docs](https://dagster.io/docs/deployment/oss/deployment-options/aws)
before prompting; you need to understand the moving parts to review the draft.

## Steps

### 1. Decide the shape (hand, 45 min)

Write your answers in `infra/README.md` before involving the agent:

1. **Run storage**: RDS Postgres (managed, bills hourly) or Postgres in
   its own ECS task with no persistent volume (cheap, but you lose run
   history whenever it's replaced)? For a portfolio, either is defensible
   if you say why.
2. **Networking**: tasks in private subnets with a NAT gateway (clean, but
   NAT is often the biggest line item), or public subnets with public IPs
   and tight security groups (cheaper, more exposed)? Add the **S3
   gateway endpoint** either way.
3. **UI access**: how do you reach the webserver? ALB with auth, SSM
   port-forwarding, or no UI in the cloud at all (check runs in CloudWatch)?
4. **Two IAM roles per task**, and what each needs:
   - *Execution role*: what ECS itself needs to start the task (pull from
     ECR, write logs, read the secrets referenced in the task definition).
   - *Task role*: what **your code** needs (S3 prefixes, Glue catalog,
     secrets fetched at runtime).

✅ **Checkpoint:** you can explain why the execution role and the task role
are different, and list every permission each needs.

### 2. Build and push the image (30 min)

Your M6 project likely already has a Dockerfile or can reuse
`infra/Dockerfile.dev`'s uv pattern. The image must contain your code and
`dagster.yaml`, and **no secrets**.

```bash
aws ecr create-repository --repository-name sideline-dagster   # or in Terraform
docker build --platform linux/arm64 -t sideline-dagster .      # match the Fargate CPU architecture you choose
```

Building on an Apple Silicon Mac produces ARM images by default. Either
run Fargate tasks on ARM (Graviton, also typically cheaper) or build
with `--platform linux/amd64`. A mismatch fails with `exec format error`.

### 3. Prompt the agent

> Write `infra/terraform/modules/orchestrator` for this repo. Read
> `AGENTS.md`, `infra/README.md` (my decisions for run storage,
> networking, UI access and IAM) and `orchestration/` first. It runs
> Dagster OSS on ECS Fargate: a webserver service, a daemon service, and
> my code location; `EcsRunLauncher` launches each run as its own task.
> Run storage: *(your choice)*. Secrets come from Secrets Manager via the
> task definition `secrets` block. Never put secret values in Terraform
> variables, state or environment blocks. Create one CloudWatch log group
> with a retention period. Separate execution and task roles, scoped to the
> specific ARNs from the `lake` and `catalog` module outputs; no `*`
> resources. Also write the `dagster.yaml` run launcher and storage sections.

### 4. Review it like a PR

| Review question | Good answer |
|---|---|
| Where do secret *values* come from? | Created out-of-band (console/CLI) or generated, never in a `.tf` file. Terraform references the secret ARN |
| Will the RDS password end up in state? | If Terraform generates it, yes; state is encrypted and private. Know that it's there |
| Does the execution role have `secretsmanager:GetSecretValue` on only the needed ARNs? | Yes |
| Does the task role allow `iam:PassRole`? | Only if the daemon launches runs with a role; scoped to that role's ARN |
| Log retention set? | Yes, short in dev (CloudWatch Logs bills for storage) |
| Desired counts | Webserver and daemon at 1; scaling to 0 is your nightly off switch |

### 5. Deploy and run

```bash
terraform -chdir=infra/terraform/envs/dev apply
aws ecs list-services --cluster sideline-dev
aws logs tail /sideline/dev/dagster --follow
```

Materialize one partition manually first. Then let the daily schedule
run, for at least **two consecutive days**.

✅ **Checkpoint:** two scheduled runs succeeded; their outputs exist in the
cloud lake; each run was its own ECS task (check the ECS console's stopped
tasks, or the run's tags in the Dagster UI).

### 6. Record the running cost

Note the hourly resources you've created (services, RDS, NAT, ALB) in
`docs/cost/` as the baseline for M10.10. Then scale down or destroy when
you're not testing.

## Gotchas

- **Runs inherit the launcher task's config.** By default a run task copies
  most settings from the task that launched it. If runs need more
  memory, set `run_resources` or per-job `ecs/memory` tags, not the
  daemon's size.
- **Private subnet, no NAT, no endpoints = hangs.** Tasks can't pull from
  ECR or reach Secrets Manager. You'll see tasks stuck in `PENDING` or
  `ResourceInitializationError`. Either a NAT or VPC interface endpoints
  (ECR, Logs, Secrets Manager: each has an hourly charge) are needed.
- **Time zones.** Dagster schedules default to UTC unless you set
  `execution_timezone`. NBA "game day" is US Eastern.
- **Secrets Manager deletion window.** A deleted secret is kept for 7 to 30
  days and its name can't be reused meanwhile. Set
  `recovery_window_in_days = 0` in dev so M10.12's rebuild doesn't fail on
  a name clash.
