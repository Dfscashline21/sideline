# M10.8 · PII masking for the analyst role

> **Ticket:** [#138](https://github.com/Dfscashline21/sideline/issues/138) ·
> **Mode:** hand · **Time:** 3 hours ·
> **Needs:** M8.8 (fantasy league Postgres DB), M10.1 session 1. Runs
> locally on the Compose Postgres, so no cloud cost.

## Why this matters

Sports stats aren't personal data, but your fantasy league's users are:
emails and birthdates. Every data platform with real users needs a
story for "analysts can study behaviour without seeing who people are".
Interviewers check two things: that you know **where** masking is enforced
(in the database, not in the BI tool), and that you can **prove** it
works, with a test that fails if someone removes it.

## What you'll produce

- Synthetic fantasy users: fake emails and birthdates, never real ones.
- An `analyst` role that sees masked values only and **cannot** read the raw table.
- `quality/tests/test_pii_masking.py` (or wherever your tests live): fails
  if the masking is removed or the analyst gets raw access.

## Steps

### 1. Generate synthetic users (30 min)

Add users to the fantasy league schema from M8.8 (example here:
`fantasy.users(user_id, display_name, email, birthdate)`). Rules:

- Emails on a **reserved domain**: `example.com`, `example.org` and
  `example.net` are reserved for documentation (RFC 2606), so you can never
  email or leak a real person.
- Deterministic: same seed, same users, so tests are stable.
- Enough variety to make masking bugs visible (different first letters,
  birthdates across decades).

A few lines of SQL (`generate_series`) or a small Python script with
`random.Random(42)` both work. No new dependencies needed.

✅ **Checkpoint:** `select count(*), count(distinct email) from fantasy.users`
are equal.

### 2. Decide what "masked" means (hand, 20 min)

For each column, pick a treatment and write the reason in your notes:

| Column | Options | Question to ask |
|---|---|---|
| `email` | redact entirely · partial (`u***@example.com`) · keyed hash | Do analysts need to *join* or *count distinct* users by email? |
| `birthdate` | drop · year · decade · age band | What analysis needs age, and how precise? |
| `display_name` | keep · drop | Is a self-chosen username personal data? (Often yes) |

<details>
<summary>Hint · Hashing isn't anonymising</summary>

A plain `sha256(email)` can be reversed by hashing a list of likely
emails and comparing. If analysts need a stable join key, hash with a
secret **salt** the analyst can't read. It's still pseudonymous, not
anonymous (whoever holds the salt can re-identify), which is usually
what regulations call it too.

</details>

### 3. Enforce it in the database (60 min)

Design the grants so the analyst *can't* bypass the mask:

- The raw table lives in a schema the analyst has **no** `USAGE` on.
- A view in an `analytics` schema exposes masked columns only.
- The analyst gets `USAGE` on `analytics` and `SELECT` on the view, nothing else.

Postgres views run with the **view owner's** privileges by default, so
the analyst can read through the view without any grant on the base table.

<details>
<summary>Hint 1 · Where does the salt live?</summary>

Not in a custom setting (`current_setting('sideline.pii_salt')`): any
role can `SHOW` it. Put it in a one-row table in the restricted schema
and `cross join` it inside the view. The view can read it because the
owner can; the analyst can't.

</details>

<details>
<summary>Hint 2 · Skeleton</summary>

```sql
create view analytics.users_masked as
select u.user_id,
       ___ as email_masked,
       encode(sha256(convert_to(s.salt || lower(u.email), 'UTF8')), 'hex') as email_key,
       ___ as birth_decade
from fantasy.users u cross join fantasy.pii_salt s;

create role analyst login password '...';   -- local only; cloud passwords come from Secrets Manager
grant usage on schema analytics to analyst;
grant select on analytics.users_masked to analyst;
```

</details>

<details>
<summary>Solution (open only after you have your own)</summary>

```sql
create table fantasy.pii_salt (salt text not null);
insert into fantasy.pii_salt values ('dev-only-salt');   -- real salt from a secret in the cloud

create schema analytics;
create view analytics.users_masked as
select u.user_id,
       u.display_name,
       left(u.email, 1) || '***@' || split_part(u.email, '@', 2) as email_masked,
       encode(sha256(convert_to(s.salt || lower(u.email), 'UTF8')), 'hex') as email_key,
       extract(year from u.birthdate)::int / 10 * 10 as birth_decade
from fantasy.users u
cross join fantasy.pii_salt s;

create role analyst login password 'analyst';
grant usage on schema analytics to analyst;
grant select on analytics.users_masked to analyst;
-- No grants on schema fantasy: the analyst can't see users or the salt.
```

Tested on Postgres 16: as `analyst`, the view returns `u***@example.com`
and decades, while `select * from fantasy.users` and
`select * from fantasy.pii_salt` both fail with *permission denied for
schema fantasy*.

</details>

Put the DDL in a migration or setup script that runs with the M8.8
database setup, so a fresh `make up` recreates it.

### 4. Write the test that proves it (hand, 45 min)

The acceptance criterion is precise: **the test must fail if masking is
removed.** Write the test, then break the masking on purpose and watch it fail.

What to assert, connecting **as `analyst`**:

1. No value in any column of `analytics.users_masked` equals a raw email
   or raw birthdate. (Compare against the known synthetic values, fetched
   with an admin connection in a fixture.)
2. No value even *looks* like a full email: a regex such as
   `^[^*@]+@` should match nothing.
3. Selecting from `fantasy.users` raises a permission error.

<details>
<summary>Hint · Test structure</summary>

Two connection fixtures (admin and analyst) built from `.env` values;
`pytest.raises` with the driver's permission-error class for check 3.
You need a Postgres driver as a dev dependency (`uv add --dev
"psycopg[binary]"`). Mark the test so it's skipped when Postgres isn't
reachable, and decide how CI gets a database: a `services: postgres`
block in the workflow job is the usual way.

</details>

### 5. Prove the test bites (15 min)

Do each of these on a scratch branch, run the test, confirm it **fails**,
then revert:

- Change the view to `select u.email ...`.
- `grant usage on schema fantasy to analyst; grant select on fantasy.users to analyst;`
- Recreate the view `with (security_invoker = true)` (Postgres 15+). What
  happens, and why?

✅ **Checkpoint:** three deliberate breakages, three red test runs, noted in
the PR description.

### 6. Stretch: the same in the warehouse

If you created your Snowflake trial on Enterprise edition (M10.5),
recreate the mask as a **masking policy** that shows raw values only to
an admin role, attach it to the column, and run the same test against
Snowflake. Dynamic data masking requires Enterprise edition or higher.

## Gotchas

- **Masking in the BI tool isn't masking.** Anyone with a SQL client and
  the analyst's credentials bypasses it. Enforce it in the database.
- **Aggregates leak too.** A `count(*)` grouped by birth decade and
  postcode for a tiny league can single someone out. Note it as a known
  limit; k-anonymity is a deeper topic.
- **Logs and errors.** A failed load that logs a whole row can write raw
  emails to CloudWatch. Check what your M8.8 pipeline logs.
