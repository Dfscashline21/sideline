# M10.12 · Ready-when check: tear down and rebuild (closed-book)

> **Ticket:** [#142](https://github.com/Dfscashline21/sideline/issues/142) ·
> **Mode:** hand, closed-book · **Time:** 1 hour timed, plus 30 min prep ·
> **Needs:** M10.2 to M10.11 merged

## Why this matters

The M10 promise: *tear down and rebuild the whole platform from code in
under an hour.* If you can do that, your infrastructure really is code:
nothing depends on a console click you forgot, a secret only your laptop
has, or a resource someone created by hand. It's also your disaster
recovery drill. Most teams claim they could rebuild from Terraform; few
have actually timed it.

## The rules

- **No AI, no notes, no labs.** Only the repo: `infra/README.md`, the
  Makefile, the code. If you need something the repo doesn't say, that's
  a finding: write it down and fix the repo afterwards.
- The **state bucket stays** (it's bootstrap, not platform). Decide
  beforehand whether "whole platform" includes the lake buckets. Your
  M10.2 stateful/stateless decision applies here, so write the answer in
  your notes before starting.
- Use **dev**. Never time this on prod.

## Before the clock starts (notes allowed)

Teardown is where the surprises are. Check these first:

| Trap | Why it bites | Fix before the run |
|---|---|---|
| Non-empty or versioned S3 buckets | `destroy` fails on a bucket with objects or old versions | `force_destroy = true` on dev buckets, or a documented empty-bucket step |
| Secrets Manager recovery window | A deleted secret's name is reserved for 7 to 30 days, so the rebuild fails with "already scheduled for deletion" | `recovery_window_in_days = 0` in dev (M10.4) |
| ECR repository with images | `destroy` fails unless the repository is emptied | `force_delete = true` in dev |
| KMS keys | Scheduled for deletion over 7 to 30 days, not deleted at once | Accept it (new key on rebuild) or keep keys outside the destroy scope |
| Snowflake external volume / catalog integration | Lives in Snowflake, not Terraform; trusts a role ARN | If the role keeps its name, the trust still works; check the external ID logic from M10.5 |
| Manual steps | Email subscription confirmation, GitHub environment settings | List them in `infra/README.md` as known manual steps |
| Data in the lake | Rebuilding infra doesn't rebuild data | Either keep the lake outside the destroy scope, or include a backfill in the rebuild |

Run a **dry-run destroy plan** first:

```bash
terraform -chdir=infra/terraform/envs/dev plan -destroy
```

Read it. Anything listed that you didn't expect to lose is a design
problem to fix *before* the timed run.

## The timed run (closed-book from here)

1. Start the stopwatch.
2. **Tear down** using only what the repo documents (e.g. `make cloud-down`
   or `terraform destroy` per root, in the right order).
3. Confirm it's gone: no ECS services, no RDS instance, no NAT gateway
   (`aws ec2 describe-nat-gateways --filter Name=state,Values=available`).
4. **Rebuild** from code: `terraform apply` per root, in order.
5. **Deploy the code**: push the Dagster image (via the M10.7 pipeline or
   the documented manual path).
6. **Prove it works**, with the bar decided in advance:
   - a Dagster run for one partition succeeds in the cloud
   - its output is readable from the cloud catalog (M10.3's check)
   - the warehouse can query a mart (M10.5's check)
   - the budget and alarm exist (`aws budgets describe-budgets`)
7. Stop the clock.

✅ **Checkpoint:** under 60:00, all four checks green.

## If it fails or runs long

That's a successful check: it found something. In order:

1. Write down exactly where you got stuck and what the repo was missing.
2. After the clock, fix the repo (Terraform, Makefile, `infra/README.md`) in a PR.
3. Redo the timed run. The ticket isn't done until a clean run passes.

Common culprits worth recognising:

| Symptom | Likely cause |
|---|---|
| `BucketNotEmpty` on destroy | Versioned bucket without `force_destroy` |
| `InvalidRequestException ... scheduled for deletion` on apply | Secrets Manager recovery window |
| `DependencyViolation` deleting a VPC or subnet | Something created outside Terraform (an ENI, a manual security group) still attached |
| Rebuild works but runs fail with `AccessDenied` | A permission that was added by hand in the console, never codified |
| Snowflake queries fail after rebuild | Trust policy or external ID changed |

## Clean up

Leave dev either running (if you're continuing) or torn down, and note
which in your notes. Don't leave the hourly resources up by accident.
