## Why this matters

Cloud interviews for data engineers rarely ask you to recite services.
They ask *"Why can't this Lambda read that bucket?"* or *"How do you stop
two people applying Terraform at once?"* or *"Your AWS bill doubled; where
do you look?"* All three are answered by the four topics here. IAM policy
evaluation in particular is the acceptance criterion because it's the
root of most "access denied" debugging you'll ever do.

## Session 1 · IAM: identities, policies, evaluation (90 min)

**Read:**
[Policies and permissions](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies.html),
then [Policy evaluation logic](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic.html)
(the flowchart is the important part).

Vocabulary to pin down first:

| Term | Meaning |
|---|---|
| Principal | Who's asking: a user, a role session, a service, another account |
| Action | What they want: `s3:GetObject`, `glue:GetTable` |
| Resource | What on: `arn:aws:s3:::sideline-lake/raw/*` |
| Condition | When: only from this VPC endpoint, only with this tag, only via TLS |
| Identity-based policy | Attached to the principal |
| Resource-based policy | Attached to the resource (bucket policy, KMS key policy, role trust policy) |
| Permissions boundary | A ceiling on what an identity policy can grant |
| SCP / RCP | Organization-wide ceilings (if you use AWS Organizations) |

### Exercise 1.1: evaluate by hand

For each request, write **allowed** or **denied** and *which rule decided
it*. Then check with the flowchart.

Role `dagster-task` has this identity policy:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::sideline-lake/*" },
    { "Effect": "Deny", "Action": "s3:*",
      "Resource": "arn:aws:s3:::sideline-lake/pii/*" }
  ]
}
```

1. `s3:GetObject` on `sideline-lake/marts/fact_play/data/x.parquet`
2. `s3:PutObject` on `sideline-lake/pii/users.parquet`
3. `s3:ListBucket` on `sideline-lake`
4. `s3:GetObject` on `sideline-raw/nba/x.json`
5. Same as 1, but the bucket policy on `sideline-lake` has an explicit
   `Deny` for every principal except role `snowflake-reader`.

<details>
<summary>Answers</summary>

1. **Allowed**: matching `Allow`, no `Deny` applies.
2. **Denied**: explicit `Deny` always wins, even though an `Allow` matches.
3. **Denied**: implicit deny. No statement allows `ListBucket`, and note
   that `ListBucket` applies to the *bucket* ARN (`sideline-lake`), not
   objects (`sideline-lake/*`). This is the most common real bug.
4. **Denied**: implicit deny; wrong bucket.
5. **Denied**: the resource policy's explicit `Deny` wins. Within one
   account, an `Allow` in *either* the identity or resource policy is
   enough, but a `Deny` in *any* policy ends the evaluation.

</details>

## Session 2 · VPC networking for data platforms (75 min)

**Read:** [How Amazon VPC works](https://docs.aws.amazon.com/vpc/latest/userguide/how-it-works.html),
[Gateway endpoints](https://docs.aws.amazon.com/vpc/latest/privatelink/gateway-endpoints.html),
[NAT gateways](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-nat-gateway.html).

Draw this on paper: one VPC, two availability zones, a public and a
private subnet in each. Then place:

- the Dagster ECS tasks
- the RDS Postgres for Dagster's run storage
- an Internet Gateway, a NAT gateway, an S3 gateway endpoint

### Exercise 2.1: how does the packet get there?

Trace each flow and name every hop:

1. A Dagster task in a private subnet calls `stats.nba.com`.
2. The same task writes a Parquet file to S3.
3. You, at home, open the Dagster UI.

<details>
<summary>Hints</summary>

1. Private subnet → route table → NAT gateway (in a public subnet) →
   Internet Gateway → internet. The NAT costs money per hour and per GB.
2. With an **S3 gateway endpoint**, the route table sends S3 traffic
   straight to S3, skipping the NAT. Gateway endpoints for S3 don't have an
   hourly charge, and they keep data off the NAT's per-GB meter. Remember
   this for M10.10.
3. You shouldn't reach it directly at all. Options: no public UI (use
   `aws ecs execute-command` or a port-forward through SSM), an ALB with
   authentication, or a VPN. Each has a cost and a security trade-off.

</details>

### Exercise 2.2: security groups vs NACLs

## Session 3 · Terraform state and locking (60 min)

**Read:** [State](https://developer.hashicorp.com/terraform/language/state),
[S3 backend](https://developer.hashicorp.com/terraform/language/backend/s3).

Answer in your notes:

1. What is in a state file, and why does it often contain secrets? (Look
   at what an RDS resource stores.)
2. What breaks if you and CI each keep your own local state?
3. What does the lock protect against? The S3 backend can now lock with a
   lock file in the bucket itself (`use_lockfile = true`); the older
   DynamoDB-table locking is **deprecated**. Why is one fewer moving part
   good here?
4. The state bucket can't be created by the configuration that stores
   its state in it. How do you break that chicken-and-egg problem? (You'll
   do it in M10.2.)
5. What's the difference between `terraform plan` showing "No changes"
   and your infrastructure being correct? (Think: drift from console clicks.)

## Session 4 · FinOps basics (60 min)

**Read:** [AWS cost allocation tags](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/cost-alloc-tags.html),
[AWS Budgets](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html),
the [FinOps Framework overview](https://www.finops.org/framework/).

Key ideas to get into your own words:

- **Showback vs chargeback**: report who spent what vs actually bill them.
- **Allocation**: how do you split a shared cost (the ECS cluster runs all
  leagues' jobs) across leagues? By job runtime? By rows? Equally?
- **Tags are not retroactive.** Activating a cost allocation tag only
  attributes spend *after* activation.
- **Unit economics**: cost per league per month is nice; cost per 1,000
  games ingested is better, because it survives growth.
