# M10.7 · CI/CD deploy across environments

> **Ticket:** [#137](https://github.com/Dfscashline21/sideline/issues/137) ·
> **Mode:** agent: the agent drafts, you review it like a junior's PR ·
> **Time:** 3 to 4 hours · **Needs:** M10.2, M10.4, M0.5 (your CI workflow)

## Why this matters

Until now, "deploy" meant you running `terraform apply` from your laptop
with your credentials. That doesn't scale past one person and leaves no
audit trail. The standard pattern is: **every merge to `main` deploys to
dev automatically; a tagged release deploys to prod**, using short-lived
credentials CI gets from AWS via OIDC. No access keys stored anywhere.

## What you'll produce

- An IAM OIDC provider for GitHub and one deploy role **per environment**,
  each trusting only the matching branch or environment.
- `.github/workflows/deploy.yml`: on push to `main` → plan + apply dev,
  build and push the Dagster image, roll the ECS services. On tag `v*` →
  the same for prod, behind a GitHub environment with required approval.
- A PR-time `terraform plan` so reviewers see infra changes before merge.
- Proof the pipeline works end to end: one merge reaching dev, one tag reaching prod.

## How OIDC to AWS works (read first)

1. The workflow requests a token: needs `permissions: id-token: write`.
2. GitHub issues a signed JWT with claims like `sub` (which repo, branch
   or environment) and `aud` (`sts.amazonaws.com`).
3. `aws-actions/configure-aws-credentials` calls
   `AssumeRoleWithWebIdentity`. AWS checks the token against the OIDC
   provider `https://token.actions.githubusercontent.com` and evaluates
   the role's trust policy conditions on `aud` and `sub`.
4. CI gets temporary credentials for that role only.

Example `sub` values from GitHub's docs:

```
repo:<owner>/<repo>:ref:refs/heads/main        # a job on the main branch
repo:<owner>/<repo>:environment:prod           # a job that declares `environment: prod`
```

Read [GitHub's OIDC-in-AWS guide](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)
before prompting.

## Steps

### 1. Design the trust (hand, 30 min)

Write down, per role:

| Role | Assumed by | `sub` condition | Can do |
|---|---|---|---|
| `sideline-plan` (read-only) | PR workflows | `repo:<owner>/sideline:pull_request` | `terraform plan` (read state, read resources) |
| `sideline-deploy-dev` | push to `main` | dev environment or `main` ref | apply dev |
| `sideline-deploy-prod` | tag release | `environment:prod` | apply prod |

Decide: does the prod job declare `environment: prod` (so GitHub can
require an approval and the `sub` becomes `environment:prod`)? That's the
recommended setup, because a tag alone can be pushed by anyone with write access.

<details>
<summary>Hint · Why PR plans need their own, weaker role</summary>

A pull request can come from any branch and run modified workflow code.
If the PR job could assume the dev deploy role, a malicious or careless
PR could `apply` anything. Give PRs a role that can only read: enough to
run `plan`, never `apply`. (Plans still need to read state from the state
bucket; reading the lock file is fine too.)

</details>

### 2. Prompt the agent

> Write `infra/terraform/modules/ci` (GitHub OIDC provider and the three
> roles below) and `.github/workflows/deploy.yml` for this repo. Read
> `AGENTS.md`, `infra/README.md` and the existing `.github/workflows/ci.yml`
> first. Trust design: *(paste your table)*. Workflow: PRs run `terraform
> plan` for dev with the plan role and post the result to the job summary;
> push to `main` applies dev, builds the Dagster image, pushes to ECR and
> forces a new ECS deployment; tags matching `v*` do the same for prod in
> a job with `environment: prod`. Use `permissions: id-token: write,
> contents: read` only where needed. Pin every action to an exact release
> tag (no moving major tags): check each action's releases page. Use
> `concurrency` so two deploys to the same environment can't overlap.
> No long-lived AWS keys anywhere.

### 3. Review it like a PR

| Review question | Good answer |
|---|---|
| Does every trust policy check **both** `aud` and `sub`? | Yes, `StringEquals` on both |
| Any `StringLike` with `repo:<owner>/sideline:*`? | No: that lets any branch, PR or environment assume the role |
| Is `id-token: write` granted only on jobs that need AWS? | Yes, set at job level, not workflow level |
| Are actions pinned to exact versions? | e.g. `aws-actions/configure-aws-credentials@v6.3.0`, `hashicorp/setup-terraform@v4.0.1`, `aws-actions/amazon-ecr-login@v2.1.7` (current when written) |
| Does `concurrency` include the environment name? | Yes, `group: deploy-dev` / `deploy-prod`, `cancel-in-progress: false` |
| What does the prod job deploy? | The **same image digest** that passed dev, not a fresh rebuild. Or explain why rebuilding is acceptable |
| Does a failed `apply` stop the image rollout? | Yes, by step ordering |

<details>
<summary>Hint · "Build once, deploy many"</summary>

If prod rebuilds the image from the tag, you're deploying an artifact
that never ran in dev (base images and dependencies can change between
builds). Better: tag the dev image with the commit SHA, and have the
prod job look up that SHA's image and roll it out. Whether you implement
it or not, write down the trade-off.

</details>

### 4. Configure GitHub

- Settings → Environments → create `dev` and `prod`. On `prod`, add
  yourself as a **required reviewer** and restrict deployments to tags
  matching `v*`.
- Your role ARNs aren't secrets, but storing them as environment
  variables (`vars.AWS_DEPLOY_ROLE_ARN`) keeps the workflow generic.

### 5. Prove it end to end

1. Open a PR that changes something harmless in dev Terraform (a tag
   value). Check: the plan appears in the job summary, and the PR job
   *cannot* apply (try it in a throwaway branch if you want proof:
   expect `AccessDenied`).
2. Merge. Check: dev applies, the image is pushed, ECS rolls, the next
   Dagster run uses the new image.
3. `git tag v0.1.0 && git push origin v0.1.0`. Approve the prod
   deployment in the Actions UI. Check: prod applies.

✅ **Checkpoint:** three green runs (PR plan, dev deploy, prod deploy), with
links in the PR description of the follow-up build-log entry.

## Gotchas

- **`sub` changes when a job declares `environment:`.** The claim becomes
  `repo:<owner>/<repo>:environment:<name>` instead of the `ref:` form. A
  trust policy expecting `ref:refs/heads/main` then fails with "Not
  authorized to perform sts:AssumeRoleWithWebIdentity".
- **Newer subject-claim format.** GitHub's docs note that repositories
  created after 15 July 2026, or that opt in to immutable subject claims,
  get owner and repo IDs in `sub` (`repo:octo-org@123456/octo-repo@456789:...`).
  If AssumeRole fails and your trust policy looks right, print the token's
  claims in a debug step and compare.
- **Branch protection on `main` (M0.5)** still applies: deploy happens
  only after CI passes and the PR merges.
- **Tag pushes by anyone with write access.** The prod environment's
  required reviewer is what actually gates prod.
