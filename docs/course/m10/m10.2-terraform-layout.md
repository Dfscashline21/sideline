# M10.2 · Terraform layout and remote state

> **Ticket:** [#132](https://github.com/Dfscashline21/sideline/issues/132) ·
> **Mode:** mixed · **Time:** 3 to 4 hours ·
> **Needs:** M10.1, an AWS account with a hand-made budget alarm, Terraform
> and the AWS CLI installed

## Why this matters

Every later M10 lab adds resources to this layout, and the final check
(M10.12) destroys and rebuilds everything from it in under an hour. The
choices you make now decide whether that's easy: how modules are split,
how dev and prod differ, and where state lives. "Walk me through your
Terraform repo structure" is a standard platform-engineering interview
question.

## What you'll produce

- `infra/terraform/bootstrap/`: the state bucket, applied once with local state.
- `infra/terraform/modules/`: at least one real module (start with `lake`, filled in by M10.3).
- `infra/terraform/envs/dev/` and `envs/prod/`: each with its own S3 backend key.
- `terraform plan` clean for **dev and prod**.

## Mixed mode: who writes what

| You write (core) | Agent may draft (boilerplate) |
|---|---|
| The module boundaries: which resources live in which module, and why | `versions.tf`, `providers.tf`, `variables.tf` / `outputs.tf` scaffolding |
| What differs between dev and prod, and how it's passed in | Makefile targets wrapping `init/plan/apply/destroy` |
| The bootstrap approach for the state bucket | README command reference |
| Tagging strategy (`project`, `env`, `league`, `owner`) | |

## Steps

### 1. Install and authenticate (20 min)

```bash
brew install hashicorp/tap/terraform awscli
terraform version          # expect 1.17.x or later
aws configure sso          # or an IAM Identity Center profile; avoid long-lived access keys
aws sts get-caller-identity --profile sideline
```

✅ **Checkpoint:** `get-caller-identity` returns your Sideline account, not
your employer's.

### 2. Design on paper first (30 min, hand)

Before any file exists, write in `infra/README.md`:

- The module list and one line on what each owns. (The module overview
  suggests `network`, `lake`, `catalog`, `orchestrator`, `ci`, `cost`.)
- What differs between dev and prod. Keep it short: names (`-dev`
  suffix), sizes (smaller tasks in dev), retention (shorter in dev),
  `force_destroy` (true in dev only?).
- **Stateful vs stateless.** Which modules hold data you can't easily
  recreate? M10.12 will tear down and rebuild. Decide now whether the lake
  buckets are inside the destroy blast radius.

<details>
<summary>Hint 1 · Nudge: one root per environment, or workspaces?</summary>

Two common layouts:

- **Directory per environment** (`envs/dev`, `envs/prod`), each calling
  the same modules with different inputs. Explicit, easy to review, and
  each environment has its own backend key.
- **Terraform workspaces**: one root, `terraform workspace select prod`.
  Less duplication, but easy to apply to the wrong environment.

For a two-environment portfolio project, directory per environment is
the more common recommendation. Whichever you pick, write down why.

</details>

<details>
<summary>Hint 2 · Approach: stateful vs stateless split</summary>

A pattern that makes M10.12 safe: within each environment, apply the
stateful pieces (lake buckets, catalog) and the stateless pieces
(network, ECS, RDS for Dagster) as **separate root modules** with separate
state keys, e.g. `envs/dev/data/` and `envs/dev/compute/`. Then "tear
down the platform" destroys `compute` without touching your Iceberg
tables. Simpler alternative: one root per env, with
`lifecycle { prevent_destroy = true }` on the lake buckets in prod.

</details>

### 3. Bootstrap the state bucket (30 min, hand)

The state bucket can't store its own state. Create it with a tiny,
separate configuration that uses **local** state:

```
infra/terraform/bootstrap/
├── main.tf        # one S3 bucket: versioning on, encryption on, public access blocked
└── versions.tf
```

Things the bucket needs, and why:

| Setting | Why |
|---|---|
| Versioning | Recover from a corrupted or accidentally overwritten state file |
| Server-side encryption | State contains secrets (e.g. RDS passwords) |
| Block all public access | Obviously |
| Globally unique name | Bucket names are global, e.g. `sideline-tfstate-<account-id>` |

Apply it once:

```bash
cd infra/terraform/bootstrap
terraform init && terraform apply
```

The bootstrap's own `terraform.tfstate` stays local and is gitignored.
Write in `infra/README.md` what to do if it's lost (hint: `terraform
import`).

✅ **Checkpoint:** `aws s3api get-bucket-versioning --bucket <name>`
returns `"Status": "Enabled"`.

### 4. Environment roots with remote state (45 min)

Each environment's backend:

```hcl
terraform {
  required_version = ">= 1.11"
  backend "s3" {
    bucket       = "sideline-tfstate-<account-id>"
    key          = "envs/dev/terraform.tfstate"    # prod: envs/prod/...
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true                            # S3-native locking; DynamoDB locking is deprecated
  }
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 6.0" }
  }
}

provider "aws" {
  region = "us-east-1"
  default_tags {
    tags = {
      project = "sideline"
      env     = "dev"
      managed = "terraform"
    }
  }
}
```

`default_tags` puts these tags on every taggable resource, which M10.9's
cost report depends on. Add `league` on resources that belong to one league.

An agent may draft the boilerplate. Give it your step 2 design and ask
for `versions.tf`, `providers.tf`, `variables.tf` and `outputs.tf` per
env plus an empty `modules/lake` with variables for `env` and
`name_prefix`. **Review checklist for its draft:**

- [ ] Backend `key` differs between dev and prod
- [ ] Provider version constrained, not unpinned
- [ ] No hard-coded account IDs or credentials
- [ ] Variables have `description` and `type`
- [ ] Nothing in `envs/` duplicates resource definitions that belong in a module

### 5. Fix the `.gitignore` (10 min)

M0.1's `.gitignore` ignores `.terraform.lock.hcl`, but HashiCorp
recommends committing it so every machine and CI uses the same provider
build. Remove that line. Decide how per-env values are committed, given
that `*.tfvars` is ignored (see the [module overview](README.md#gotchas-in-this-repo)).

### 6. Plan both environments

```bash
cd infra/terraform/envs/dev  && terraform init && terraform plan
cd ../prod                   && terraform init && terraform plan
terraform fmt -check -recursive infra/terraform
terraform -chdir=infra/terraform/envs/dev validate
```

"Plan clean" means: no errors and no warnings, and the plan shows only
what you expect. With only an empty module, that's "No changes". Apply
dev once to prove the backend works, then plan again: it must say **No
changes**. A second plan that still wants changes means something isn't
idempotent (a timestamp, an unordered list).

✅ **Checkpoint:** `aws s3 ls s3://sideline-tfstate-<account-id>/envs/`
shows `dev/` and `prod/` state files, and both plans are clean.

### 7. Make targets

Follow the Makefile style (`## help` comments):

```make
tf-plan-dev: ## Terraform plan for dev
	terraform -chdir=infra/terraform/envs/dev plan
cloud-down: ## Destroy dev compute (keeps state bucket and lake)
	terraform -chdir=infra/terraform/envs/dev destroy
```

Adjust `cloud-down` to your stateful/stateless split.

## Gotchas

- **Two terminals, one lock.** If an apply is killed, the lock file can be
  left behind. `terraform force-unlock <id>` exists. Use it only when
  you're sure nothing else is running.
- **Wrong profile.** Set `AWS_PROFILE=sideline` in your shell, or put
  `profile` in the provider for local runs only (CI uses OIDC, M10.7).
- **`default_tags` and some resources.** A few resource types don't support
  tags; Cost Explorer will show them untagged. That's expected.
