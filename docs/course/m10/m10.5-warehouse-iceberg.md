# M10.5 · Warehouse reading Iceberg

> **Ticket:** [#135](https://github.com/Dfscashline21/sideline/issues/135) ·
> **Mode:** mixed · **Time:** 3 to 4 hours ·
> **Needs:** M10.3 (gold/mart tables in the cloud catalog)

## Why this matters

The point of an open table format is that **one copy of the data serves
many engines**. Your Iceberg marts are written by dbt/Spark and read by
DuckDB. Now a commercial warehouse reads the same files, with no copy and
no load job. That's the lakehouse pitch, and "how would analysts query
your lake with their existing warehouse?" is a question you'll get.

## What you'll produce

- A warehouse trial account reading your cloud Iceberg tables in place.
- IAM role(s) in Terraform that let the warehouse read **only** the
  marts prefix and the catalog.
- Gold (mart) tables queryable from the warehouse, with row counts
  matching your source.
- Cost guards on the warehouse side.

## Steps

### 1. Choose the warehouse (hand, 20 min)

| | Snowflake | BigQuery |
|---|---|---|
| Reading Iceberg in **S3** | Supported: an **external volume** (storage) plus a **catalog integration** (metadata), including AWS Glue via its Iceberg REST endpoint | BigQuery reads S3 through BigQuery Omni / BigLake, which has region and setup constraints. Check current docs before choosing |
| Trial | Free trial credits (check current terms) | Free trial credits (check current terms) |
| Column masking (M10.8) | Masking policies need Enterprise edition or higher: pick that edition when creating the trial if you want to use it | Policy tags / data masking (check edition requirements) |

With your lake in S3, Snowflake is the shorter path, and the examples
below use it. If you choose BigQuery, the IAM thinking is identical;
follow its docs for the objects.

### 2. Understand the two Snowflake objects (30 min reading)

Read [Iceberg tables](https://docs.snowflake.com/en/user-guide/tables-iceberg),
[CREATE EXTERNAL VOLUME](https://docs.snowflake.com/en/sql-reference/sql/create-external-volume)
and [CREATE CATALOG INTEGRATION (Iceberg REST)](https://docs.snowflake.com/en/sql-reference/sql/create-catalog-integration-rest).

- **External volume**: how Snowflake reaches your S3 bucket. It assumes
  an IAM role *you* create, using an external ID.
- **Catalog integration**: how Snowflake finds table metadata. For Glue:
  `CATALOG_SOURCE = ICEBERG_REST`, `CATALOG_API_TYPE = AWS_GLUE`,
  `CATALOG_URI` = Glue's Iceberg endpoint, `CATALOG_NAME` = your AWS
  account ID, and `REST_AUTHENTICATION` with `TYPE = SIGV4` and an IAM role.

Draw the trust chain before writing anything:

```
Snowflake's AWS IAM user ──assumes (external ID)──► your role sideline-snowflake-<env>
                                                     ├─ s3:GetObject / ListBucket on lake marts prefix
                                                     └─ glue:Get* on the marts database/tables
```

<details>
<summary>Hint · Why an external ID?</summary>

Snowflake's IAM user is shared infrastructure across many customers. The
external ID in your role's trust policy stops *another* Snowflake
customer from tricking Snowflake into assuming your role (the "confused
deputy" problem). Interviewers like this one.

</details>

### 3. Create the role (agent drafts, you review)

Two-phase setup, because each side needs an identifier from the other:

1. Terraform creates the role with a **placeholder** trust policy (e.g.
   your own account root) and the read-only permission policy.
2. Create the external volume and catalog integration in Snowflake
   pointing at that role ARN.
3. `DESC EXTERNAL VOLUME <name>;` and `DESC CATALOG INTEGRATION <name>;`
   show Snowflake's IAM user ARN and the external ID. Put them in
   Terraform variables (they aren't secret, but you can keep them out of
   the repo if you like) and apply the real trust policy.

Review checklist for the agent's Terraform:

- [ ] Trust policy: principal is exactly Snowflake's IAM user ARN; `sts:ExternalId` condition present
- [ ] S3 actions limited to read (`GetObject`, `GetObjectVersion`, `ListBucket`) unless you deliberately want Snowflake to write
- [ ] `ListBucket` scoped with an `s3:prefix` condition to the marts prefix
- [ ] Glue actions read-only, on the catalog, database and table ARNs you use
- [ ] No `*` resources (M10.6 will check)

### 4. Create the Snowflake objects (hand)

Write the SQL yourself, from the docs, into
`infra/snowflake/setup.sql` (committed, with no secrets). Skeleton:

```sql
create external volume sideline_lake_dev
  storage_locations = ((
    name = 'lake-dev'
    storage_provider = 'S3'
    storage_base_url = 's3://sideline-lake-dev-<account-id>/'
    storage_aws_role_arn = 'arn:aws:iam::<account-id>:role/sideline-snowflake-dev'
  ))
  allow_writes = false;

create catalog integration sideline_glue_dev
  catalog_source = ICEBERG_REST
  table_format = ICEBERG
  rest_config = (
    catalog_uri = 'https://glue.us-east-1.amazonaws.com/iceberg'
    catalog_api_type = AWS_GLUE
    catalog_name = '<account-id>'
  )
  rest_authentication = (
    type = SIGV4
    sigv4_iam_role = 'arn:aws:iam::<account-id>:role/sideline-snowflake-dev'
    sigv4_signing_region = 'us-east-1'
  )
  enabled = true;
```

Then expose the tables: either one `CREATE ICEBERG TABLE` per mart that
references the catalog integration and external volume, or a
**catalog-linked database** that discovers the namespace automatically
(supported for Iceberg REST catalog integrations; use `ALLOWED_NAMESPACES`
to limit it to marts). Pick one and say why in the PR.

### 5. Cost guards (before the first query)

```sql
create warehouse sideline_xs
  warehouse_size = 'XSMALL' auto_suspend = 60 auto_resume = true initially_suspended = true;
```

And a **resource monitor** with a small credit quota that suspends the
warehouse at 100%. Look up the syntax in the
[resource monitor docs](https://docs.snowflake.com/en/user-guide/resource-monitors).

### 6. Prove gold tables are queryable

For each mart, compare the warehouse with your source of truth:

```sql
select season, count(*) from <db>.<schema>.fact_team_game group by 1 order by 1;
```

Run the same query in DuckDB/PyIceberg against the cloud catalog. Write
the side-by-side counts into the PR description.

✅ **Checkpoint:** counts match exactly. Then change a mart (re-run dbt to
add a day) and check whether Snowflake sees it. Iceberg tables from an
external catalog need a metadata refresh (manual or `AUTO_REFRESH` on the
catalog integration): find out which applies to your setup.

## Gotchas

- **Region.** Keep the Snowflake account in the same cloud region as the
  bucket, or you pay egress and lose speed.
- **Stale reads.** If counts don't change after new data lands, it's a
  refresh problem, not a data problem.
- **Recreating the external volume.** If you recreate it without fixing the
  external ID, the trust policy no longer matches and you redo step 3.
  Note this for M10.12.
- **Trial end date.** Put it in your calendar. Know what you lose when it
  ends (the account), and what you keep (the data, because it's yours in S3).
