# M0.7 · Agent instructions file (CLAUDE.md or AGENTS.md)

> **Ticket:** [#23](https://github.com/Dfscashline21/sideline/issues/23) ·
> **Mode:** hand · **Time:** 60 min ·
> **Needs:** M0.2 to M0.5 (so you know the toolchain you're describing)

## Why this matters

Coding agents (Claude Code, Codex, Copilot, Cursor…) read a
repo-level instruction file before every task. Without one, an agent
guesses your conventions and gets some wrong: it adds `requirements.txt`
when you use uv, writes untyped functions that fail mypy, or "helpfully"
writes the SQL you were meant to write yourself.

This file is also an interview artifact. "How do you use AI agents on a
team without lowering the bar?" is now a common question, and PF.4 asks
you to write that section of your portfolio. This file is your concrete
answer: **explicit rules, and explicit no-go zones.**

## What you'll produce

- One instruction file at the repo root covering layout, naming, tooling,
  testing rules and **where agents may not write core logic**.
- Written by you (the ticket is `mode:hand`). An agent may *read* it
  afterwards to tell you what's unclear; it may not write it.

## Steps

### 1. Pick the filename

- `AGENTS.md` is the cross-tool convention: many agents read it.
- `CLAUDE.md` is what Claude Code reads automatically.

You can have both without duplicating anything: write the rules in
`AGENTS.md`, and make `CLAUDE.md` a one-liner that imports it:

```markdown
@AGENTS.md
```

Claude Code expands `@path` imports in `CLAUDE.md`. Decide which setup you
want and note why in the PR description.

### 3. Write the file

Suggested sections. Rename or reorder them; the ticket only requires that
conventions, test requirements and no-go zones are present.

1. **Project in one paragraph.** What sideline is, so an agent has context.
2. **Layout.** What each top-level folder holds. One line each.
3. **Commands.** `make sync`, `make lint`, `make typecheck`, `make test`,
   `make up`. Tell agents to run lint, typecheck and tests before saying
   they're done.
4. **Conventions.** Python version, uv only (no pip, no
   `requirements.txt`), every function typed (mypy
   `disallow_untyped_defs`), ruff's line length, how to name files and
   tests, secrets only via `.env`.
5. **Testing rules.** Where tests live, naming (`test_*.py`), what needs
   a test (every new module), coverage target (M2 sets 80%).
6. **Agent boundaries.** The no-go list. Be specific: folders, file
   patterns or ticket types. Say what an agent *should* do instead
   (review, explain, write tests for your code, check answers).
7. **Git workflow.** Branch per ticket, `Closes #N` in PRs, never push to
   `main`, never commit `.env` or data files.

<details>
<summary>Hint 1 · Nudge: rules an agent can actually follow</summary>

Vague: "Write clean code." An agent can't check that.

Checkable: "Every function has type annotations; `make typecheck` must
pass." "Never add a dependency with pip; use `uv add`."

For each rule, ask: could an agent tell whether it obeyed?

</details>

<details>
<summary>Hint 2 · Approach: wording the boundaries</summary>

Boundaries work best as a short list of paths plus the reason. The reason
matters: agents generalise from it to cases you didn't list. For example
(adapt to your own decisions):

```markdown
## Where agents must not write core logic

These are interview-tested skills; the human writes them by hand.
Agents may review, explain, write tests for, or check answers to them.

- `sql/`: every practice problem and solution.
- `docs/adr/`: decisions are written by the human.
- ...
```

When a folder is *partly* hand (for example the first NBA extractor is
hand, the WNBA one later is agent), name the files, or say "the first
implementation of a pattern is hand; later copies of it may be agent".

</details>

<details>
<summary>Hint 3 · Test it on an agent</summary>

After you've written it yourself, open a fresh agent session and ask:

> Read AGENTS.md. Without changing anything, list every rule you find
> ambiguous or that you couldn't verify you'd followed.

Fix what it flags. This is the only agent involvement allowed here.

</details>

### 4. Commit and PR

```bash
git switch -c m0.7-agent-instructions
git add AGENTS.md CLAUDE.md          # whichever you created
git commit -m "M0.7: agent instructions with conventions and no-go zones"
git push -u origin m0.7-agent-instructions
gh pr create --fill                  # body: Closes #23
```

Link the file from the README's "Run locally" or "Decisions" section if
you think a reader would want it.

## Gotchas

- **Too long gets ignored.** Agents give less weight to a 600-line file.
  Aim for one screen or two. Link to the study guide for the long-form
  explanations.
- **Stale commands are worse than none.** If you rename a Make target
  later, update this file in the same PR.
- **Don't paste secrets** or real `.env` values as "examples".

   What do you review first?
