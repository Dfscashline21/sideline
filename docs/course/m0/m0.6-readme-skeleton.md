# M0.6 · README skeleton and CI badge

> **Ticket:** [#22](https://github.com/Dfscashline21/sideline/issues/22) ·
> **Mode:** hand · **Time:** 60 to 90 min ·
> **Needs:** M0.5 done (CI exists and is green on `main`)

## Why this matters

The README is the first thing a hiring manager opens, and most of them
read it for under a minute. Right now `README.md` is a **build log**: a
long, honest record of each ticket. That's valuable, but it's the wrong
front page. A front page answers, in order:

1. What is this? (**pitch**)
2. How is it put together? (**architecture**)
3. Is it real? (**numbers**)
4. Can this person make and defend decisions? (**decisions**)
5. Can I run it? (**run locally**)
6. Where is it going? (**next steps**)

You're writing the **skeleton** now and filling it in over 24 weeks. Empty
sections are fine; *missing* sections aren't, because they're the
commitment you'll grow into.

The CI badge is a small thing that says something big: "this repo is
tested on every change, and it's passing right now."

## What you'll produce

- `README.md` with exactly six top-level sections: pitch, architecture,
  numbers, decisions, run locally, next steps.
- A CI badge at the top that renders green.
- The current build log moved somewhere it isn't lost.

## Steps

### 1. Branch

```bash
git switch main && git pull
git switch -c m0.6-readme-skeleton
```

### 2. Move the build log out of the way

The build log is worth keeping; it's where your "how and why" write-ups
live. Move it rather than delete it:

1. Create `docs/build-log.md`.
2. Cut everything from `## Build log` to the end of `README.md` and paste
   it into the new file. Promote headings so the file starts with `# Build log`.
3. Search for links that pointed at the README's build log and fix them:

   ```bash
   grep -rn "build log\|README.md" docs/ --include=*.md
   ```

   The M0 study guide says "The root README.md has the per-ticket build
   log". Update that line to point at `build-log.md`.

✅ **Checkpoint:** `docs/build-log.md` renders on GitHub (push the branch
and look), and no README content was lost (`git diff --stat` shows lines
moved, not vanished).

### 3. Write the six headings

Decide the order and the exact heading text yourself. Use `##` for the
six sections so they show up in GitHub's auto-generated table of
contents (the list icon at the top of the file view).

For each section, write **one line** saying what will go there and when.
That turns the skeleton into a plan. For example, a line under
architecture might say what diagram arrives in which module.

<details>
<summary>Hint 1 · Nudge: what goes in each section?</summary>

Ask of each section: "What would convince a sceptical senior engineer in
ten seconds?"

- **Pitch:** two or three sentences. What data, which leagues, what it
  produces, for whom. No buzzword lists.
- **Architecture:** today it's a placeholder. Say what the diagram will
  show (sources, raw zone, lakehouse, transforms, serving) and that it
  arrives as the modules land. PF.2 is the final diagram.
- **Numbers:** the hardest one to leave empty, so make it a table with
  blank values: rows ingested, tables, tests, data-quality checks, p95 API
  latency, monthly cloud cost. You'll fill them in as you measure.
- **Decisions:** a link to `docs/adr/` and a one-line list of ADRs as
  they're written (ADR-001 arrives in M2.8).
- **Run locally:** the commands that actually work today. You already
  have these in the current README's "Getting started".
- **Next steps:** what's in progress and what's next, a few bullets.

</details>

### 4. Add the CI badge

GitHub generates a badge for every workflow. Its URL follows this
pattern:

```
https://github.com/<owner>/<repo>/actions/workflows/<workflow-file>/badge.svg
```

Put it directly under the `# sideline` title, wrapped in a link to the
workflow's runs page so clicking it shows the history.

Work out the owner, repo and workflow file name yourself: look at
`.github/workflows/` and `gh repo view`.

<details>
<summary>Hint · Markdown for a linked image</summary>

`[![alt text](image-url)](link-url)`: an image inside a link. Alt text
"CI" is enough.

You can also copy a ready-made snippet from GitHub: Actions tab → CI
workflow → "…" menu → **Create status badge**.

</details>

<details>
<summary>Hint · Badge for main only</summary>

By default the badge shows the latest run on **any** branch, so a broken
feature branch can turn your front-page badge red. Add `?branch=main` to
the image URL so it only reflects `main`.

</details>

✅ **Checkpoint:** push the branch, open the README on GitHub (on your
branch), and see the badge render. It will be green because `main` is green.

### 5. Keep "Run locally" honest

Every command in this section must work on a fresh clone. Run each one
yourself, in order, now. You'll re-run them timed in M0.8. If any
fails, fix the README, not your memory.

### 6. Lint, commit, PR

```bash
uv run pre-commit run --all-files     # trailing whitespace, EOF newline
git add README.md docs/
git commit -m "M0.6: README skeleton with six sections and CI badge"
git push -u origin m0.6-readme-skeleton
gh pr create --fill
```

In the PR body, write `Closes #22`. Wait for CI, then merge.

✅ **Checkpoint:** on `main`, the README shows the badge green and the
six sections appear in GitHub's table-of-contents menu.

## Gotchas

- **Relative links break when files move.** After moving the build log,
  links like `ingestion/README.md` must become `../ingestion/README.md`
  inside `docs/build-log.md`. Click a few after pushing.
- **Badge caching.** GitHub's image proxy caches badges for a few
  minutes. If it shows a stale status, wait or hard-refresh.
- **Pre-commit's `end-of-file-fixer`** will rewrite a file that doesn't
  end in exactly one newline, which blocks the commit. Re-`git add` and
  commit again; that's the hook working.
