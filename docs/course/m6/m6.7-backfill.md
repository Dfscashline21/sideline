# M6.7 · Backfill NBA 2015-2025 with concurrency 4

> **Ticket:** [#89](https://github.com/Dfscashline21/sideline/issues/89) ·
> **Mode:** hand · **Time:** 4 to 6 hours of work, plus however long the
> backfill runs · **Needs:** M6.4, M6.5; M6.6 strongly recommended

## Why this matters

"Backfill a month while daily runs continue" is this module's ready-when
check, and one of the most common senior interview scenarios. A
backfill is where every shortcut gets found out:

- appends that create duplicates on a rerun
- shared resources (a database file, an API rate limit) that were fine
  with one run at a time
- daily runs stuck in a queue behind 4,000 backfill runs

## What you'll produce

- NBA partitions from the 2015 season to 2025 materialised through the
  full graph, **4 runs at a time**.
- Daily runs keep working **during** the backfill.
- Evidence: **no duplicates** afterwards, and daily-run timings before vs
  during, written up in `docs/notes/m6.md`.

## Steps

### 1. Size the job (20 min)

Before launching anything, estimate:

- **Partitions:** every date from October 2014 to the end of the 2025
  playoffs, for `nba` only. That's thousands of daily partitions, and
  most summer dates have no games.
- **Time per partition:** materialise one game-day partition and one
  off-day partition, and time both.
- **Source limits:** M2's `nba_api` is rate-limited. Four concurrent
  ingests of 11 seasons will hit 429s. Decide whether the backfill
  ingests from `nba_api` or from the sportsdataverse season files
  (completed seasons, one download per season), and write why.

✅ **Checkpoint:** a rough estimate: total partitions × time per partition ÷ 4.
If it's days, reconsider the partition range or the source before starting.

### 2. Find the shared resources (30 min)

List everything two concurrent runs share, and what happens when four
runs hit it at once:

| Resource | What happens with 4 concurrent runs? | Plan |
|---|---|---|
| Source API | 429s, possibly a temporary ban | |
| DuckDB file used by dbt | **One writer at a time**: the other runs fail with a lock error | |
| Raw zone (MinIO) | Fine: different keys per partition | |
| Serving table (publish) | Fine *if* each publish only touches its own partition, in a transaction | |

<details>
<summary>Hint 1 · Nudge: the DuckDB problem</summary>

You don't need everything to run 4-wide. You need **runs** to overlap
while the one step that can't be shared runs one at a time. Which Dagster
feature limits concurrency for a single *step* across all runs?

</details>

<details>
<summary>Hint 2 · Approach: two levels of concurrency</summary>

Dagster has two separate knobs:

- **Run-level** (`concurrency.runs` in `dagster.yaml`): how many runs are
  in progress. Limit *backfill* runs with a tag limit on
  `dagster/backfill` (every backfill run carries that tag) and keep total
  `max_concurrent_runs` higher, so daily runs always have room.
- **Step-level pools**: give an asset `pool="duckdb_writer"`, then set
  that pool's limit to 1:
  `dagster instance concurrency set duckdb_writer 1`.
  Runs proceed in parallel; only the dbt step queues for the slot. Do
  the same for the source API (`pool="nba_api"`, limit 1 or 2).

</details>

### 3. Configure concurrency (30 min)

In `.dagster/dagster.yaml` (your `DAGSTER_HOME` from M6.4):

```yaml
concurrency:
  runs:
    max_concurrent_runs: ___          # room for 4 backfill runs + daily runs
    tag_concurrency_limits:
      - key: "dagster/backfill"
        limit: 4
```

Then add `pool=` to the assets that need it and set the pool limits.

To keep daily runs ahead of backfill runs in the queue, give the
sensor's run requests a higher priority tag: `"dagster/priority": "10"`.
Runs with higher priority are dequeued first.

✅ **Checkpoint:** `dagster instance concurrency get` lists your pools,
and the Dagster UI's run queue settings show the tag limit.

### 4. Prove idempotency on a small range first (45 min)

Don't find duplicates after 4,000 partitions. Backfill **one week**
of 2019 twice, then run the duplicate checks:

```sql
-- grain checks, one per fact (adapt to your grain)
select league, game_id, team_id, count(*) from fact_team_game
group by all having count(*) > 1;

select league, game_id, game_play_number, count(*) from fact_play
group by all having count(*) > 1;

-- and the serving table
select league, game_id, team_id, count(*) from serving.team_game
group by all having count(*) > 1;
```

All empty after the second run, and row counts unchanged between the
first and second run. If anything doubled, fix it now: it's an append
somewhere that should be a merge or a partition overwrite.

### 5. Launch the backfill (15 min, then wait)

From the UI: select the asset graph (or the job) → **Materialize** →
choose partitions: `league = nba`, dates in your range → launch as a
backfill. Watch the backfill page: 4 runs in progress, the rest queued.

### 6. Prove daily runs are unaffected (during the backfill)

While it runs:

1. Let the M6.5 sensor trigger real daily runs (or trigger a WNBA or
   recent NBA partition manually with the same tags the sensor uses).
2. Record each daily run's **queue wait** (created → started) and
   **duration**. Compare with the same numbers from a day without a backfill.
3. Confirm a daily run and a backfill run for the **same partition**
   can't corrupt each other. What happens if both publish the same date?

✅ **Checkpoint:** daily runs start within one sensor interval and
finish in a similar time to normal. If not, find out why: queue limits,
pool contention, or laptop CPU.

<details>
<summary>Solution (open only after you've designed your own): one working configuration</summary>

```yaml
# .dagster/dagster.yaml
concurrency:
  runs:
    max_concurrent_runs: 6           # 4 backfill + 2 spare for daily runs
    tag_concurrency_limits:
      - key: "dagster/backfill"
        limit: 4
  pools:
    default_limit: 4
```

```bash
dagster instance concurrency set duckdb_writer 1   # dbt + publish write steps
dagster instance concurrency set nba_api 1         # if ingesting from nba_api
```

```python
@dbt_assets(..., partitions_def=league_date_partitions, pool="duckdb_writer")
def sideline_dbt(...): ...

dg.RunRequest(run_key=..., partition_key=..., tags={"dagster/priority": "10"})
```

Why it's safe: each run touches only its own partition (raw keys per
date, dbt filtered by `run_date`/`league` vars, publish deletes and
inserts that partition in one transaction). Writes to the shared DuckDB
file are serialised by the pool. Daily runs have reserved run slots and
higher queue priority.

</details>

### 7. Verify the result

After the backfill:

- the duplicate queries from step 4 return nothing
- games per season look right (about 1,230 regular-season games per NBA
  season, fewer in 2020 and 2021; investigate any other gap)
- the backfill page shows no failed partitions, or every failure was
  retried and explained

Write `docs/notes/m6.md` → "Backfill": range, partitions, wall time,

## Gotchas

- **The laptop is the bottleneck.** Four runs at once on a laptop that
  also runs Docker can be slower than two. Measure; don't assume.
- **Retries of a failed run** can create a second run for the same
  partition. That's only safe because each partition's writes are idempotent.
- **Don't pause daily runs "to be safe".** The ticket's point is that
  you don't have to.
- **Off-day partitions** materialise fast with 0 rows. Don't alert on
  them (M6.6), and don't count them as failures.
