# M6.6 · Alerting and runbook

> **Ticket:** [#88](https://github.com/Dfscashline21/sideline/issues/88) ·
> **Mode:** mixed: you write the alert rules, an agent may draft the plumbing ·
> **Time:** 3 to 4 hours · **Needs:** M6.4, M6.5

## Why this matters

"How do you know your pipeline is broken before your users do?" Weak
answers stop at "we get a Slack message when a job fails". Strong ones
cover two failure modes:

- **Failure:** something ran and broke. Easy to detect.
- **Lateness:** nothing ran, or it ran and produced nothing. Silent, and
  it's what causes real incidents: a sensor stopped, a daemon died, an
  upstream file never arrived.

And every alert needs a **runbook**: what it means, how to check, how to
fix. An alert without one is noise at 2 a.m. M9 builds a fuller
observability story; this is the orchestration layer of it.

## What you'll produce

- An alert on **run failure** and an alert on **lateness**, delivered
  somewhere you'll see them.
- `docs/runbooks/` with **one page per alert**.
- A **test alert received**, with a screenshot in the PR.

## Steps

### 1. Pick a channel (15 min)

Anything with an incoming webhook works: a Slack incoming webhook, a
Discord channel webhook, or [ntfy.sh](https://ntfy.sh) (push to your
phone, no account needed for a public topic, so use an unguessable
topic name). Put the URL in `.env` as `ALERT_WEBHOOK_URL`, add a
placeholder to `.env.example`, never commit the real one.

### 2. Write the alert list (45 min, by hand)

Before code, write `docs/runbooks/README.md` with a table of every alert:

| Alert | Fires when | Severity | Who acts | Runbook |
|---|---|---|---|---|
| `run-failed` | A `daily_league_job` run fails | High | Whoever is on call (you) | `run-failed.md` |
| `partition-late` | A game-day partition isn't published by its deadline | High | | `partition-late.md` |
| `check-failed` | A blocking check failed, so publish was skipped | Medium | | `check-failed.md` |
| … | | | | |

Rules for a good list:

- **Every alert must be actionable.** If the response is "wait and see",
  it's a dashboard metric, not an alert.
- **Lateness is game-day aware.** No WNBA games yesterday means no WNBA
  partition is late. An alert that fires every off day will be muted
  within a week.
- **One incident, one alert.** A failed backfill of 300 partitions must
  not send 300 messages.

✅ **Checkpoint:** you can say, for each alert, what the first command in
its runbook is.

### 3. Failure alert (45 min)

Dagster's `run_failure_sensor` runs a function whenever a monitored job
fails. Inside, post to the webhook with: job name, partition key, the
failing step, a link to the run in the UI, and the runbook link.

<details>
<summary>Hint · Skeleton</summary>

```python
@dg.run_failure_sensor(monitored_jobs=[daily_league_job])
def alert_on_run_failure(context: dg.RunFailureSensorContext) -> None:
    run = context.dagster_run
    partition = run.tags.get("dagster/partition")
    is_backfill = "dagster/backfill" in run.tags
    # your routing rule: e.g. backfill failures → one summary message, not one each
    post_alert(...)  # agent can draft this helper
```

</details>

Decide the backfill rule yourself: per-run messages during a backfill
are the classic alert storm. Options: suppress and rely on the backfill
page, or send at most one message per backfill ID.

### 4. Lateness alert (60 min, by hand: the core logic)

Write a sensor (every 15 minutes is plenty) that, for each league and for
yesterday's game date:

1. asks your `fetch_games` from M6.5 whether there were games
2. if yes, and it's past the deadline (pick one, e.g. 09:00 league-local
   next morning), checks whether the publish asset's partition for that
   date and league has materialised
3. if not, posts **once**: use a cursor or run-key style key such as
   `late|wnba|2025-07-15` so later evaluations don't repeat it

<details>
<summary>Hint 1 · How do I check whether a partition materialised?</summary>

The sensor context has the Dagster instance.
`context.instance.get_materialized_partitions(asset_key)` returns the set
of partition keys that have been materialised. For a multi-partition the
keys look like `2025-07-15|wnba`. Check the exact signature in your
installed Dagster version; this area of the API evolves.

</details>

<details>
<summary>Hint 2 · Why not Dagster's built-in freshness checks?</summary>

Dagster has `build_time_partition_freshness_checks` and
`build_last_update_freshness_checks`. They're worth trying, and they may
be enough for unpartitioned dims. For Sideline's date × league
partitions, check what they consider "expected": a rule based on the
clock alone doesn't know there were no WNBA games yesterday. Test it on an
off day before relying on it, and write what you found in the runbook
README.

</details>

### 5. Runbooks (45 min)

One page per alert in `docs/runbooks/<alert>.md`. Template:

```markdown
# <alert name>

**Fires when:** ...
**Impact:** who sees stale or wrong data, and how soon
**Severity:** ...

## First 5 minutes
1. Open the run / partition in Dagster: <how to find it>
2. ...

## Common causes and fixes
| Cause | How to confirm | Fix |
|---|---|---|

## Rerun safely
The exact command or UI action to rematerialise the partition, and why
it's safe (M6.4's idempotent publish).

## Escalate / give up when
...
```

The agent may generate the skeletons; you write "how to confirm" and
"fix", because you're the one who knows how this pipeline breaks.

### 6. Prove it (30 min)

1. **Test alert received:** make a run fail on purpose (raise in the
   ingest asset behind an env flag, or point it at a bad URL) and
   capture the message. Screenshot for the PR.
2. **Lateness:** with a fake clock past the deadline and no
   materialisation, unit-test that the lateness logic returns one alert,
   and that a second evaluation returns none.
3. **Off day:** same test with no games → no alert.

✅ **Checkpoint:** one real alert received, three tests passing, and a
runbook page for every alert in the list.

## Gotchas

- **Sensors only run if the daemon runs.** `dagster dev` starts one; a
  deployment must too (M10). If the daemon dies, *no* sensor alerts,
  including lateness. That's why mature setups add an external
  heartbeat. Note it in the runbook README as a known gap.
- **Secrets in messages.** Don't include connection strings or full
  exception payloads that might contain credentials in a chat message.
- **Links rot.** `localhost:3000` links only work on your laptop. Build
  the UI base URL from config so M10's deployment can change it.
