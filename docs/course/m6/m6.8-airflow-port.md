# M6.8 · Port one league to Airflow 3 and compare

> **Ticket:** [#90](https://github.com/Dfscashline21/sideline/issues/90) ·
> **Mode:** agent: the agent ports the WNBA pipeline, **you write the comparison** ·
> **Time:** 4 to 5 hours · **Needs:** M6.4 (the Dagster version to port)

## Why this matters

Most companies still run Airflow. "We use Dagster" is a weaker interview
answer than "I built it in Dagster, ported it to Airflow 3, and here's
what each made easy and hard". This ticket buys you that sentence, and
gives ADR-005 (M6.9) real evidence instead of blog-post opinions.

The comparison is the deliverable. The port is the experiment.

## What you'll produce

- `orchestration/airflow/`: the WNBA pipeline (ingest → dbt build →
  checks → publish) as an Airflow 3 DAG that **runs end to end**.
- `docs/notes/m6-airflow-comparison.md`: your comparison notes, which
  feed ADR-005.

## Steps

### 1. Write the comparison template first (20 min, by hand)

Decide what you're measuring *before* you see the port, so the results
don't shape the questions. A starting table:

| Dimension | Dagster (M6.4) | Airflow 3 | Evidence |
|---|---|---|---|
| Lines of orchestration code | | | `wc -l` |
| How partitions (date × league) are expressed | | | |
| How the dbt integration works | | | |
| Blocking a publish on failed checks | | | |
| Backfilling a date range | | | Command and behaviour |
| Local dev loop (edit → run one partition) | | | Time it |
| Testing (unit-test a sensor / DAG) | | | |
| Seeing lineage and "what's stale?" | | | Screenshot |
| Setup and operational weight | | | Services it needs |

### 2. Run Airflow locally (30 min)

Keep Airflow out of the main lockfile: it has a large dependency tree. A
separate environment is fine and realistic:

```bash
cd orchestration/airflow
uv venv --python 3.12 && source .venv/bin/activate
uv pip install "apache-airflow==3.4.*"
export AIRFLOW_HOME=$PWD/.airflow       # gitignore it
airflow standalone                      # UI on http://localhost:8080; prints the admin password
```

Version 3.4.0 was current when this lab was written. Use the newest
3.x and record the version in your notes. For production-like setups,
Airflow's docs recommend installing with their constraints file; note
whether you did.

✅ **Checkpoint:** the UI loads and the example DAGs are listed (or hidden,
if you turned off examples).

### 3. Prompt the agent

> Port the WNBA part of our Dagster pipeline (`orchestration/sideline_orchestration/`)
> to an Airflow 3 DAG in `orchestration/airflow/dags/wnba_daily.py`.
>
> - Use the Airflow 3 task SDK (`from airflow.sdk import dag, task`).
> - One DAG run per WNBA game date. Reuse the same Python functions the
>   Dagster assets call (extractor, publish); don't reimplement them.
> - dbt: run `dbt build` with the same `--vars` the Dagster version
>   passes (`run_date`, `league`). Plain `BashOperator`/subprocess is fine;
>   tell me about Cosmos (astronomer-cosmos) as an alternative, but don't
>   use it unless I agree.
> - Quality gate: publish must not run if the checks fail.
> - Must support `airflow backfill create` over a date range.
> - Add a test that the DAG imports without errors and has the expected tasks.
>
> Explain any Airflow 3 concept you use that differs from Airflow 2.

### 4. Review it

| Review question | What a good answer looks like |
|---|---|
| Does it call the same functions as Dagster, or copy them? | Imports from `ingestion/` and the publish module |
| How does a run know its date? | From the run's logical date / data interval, not `datetime.now()` |
| Is the date the league-local game date? | Same timezone rule as M6.4, explicitly |
| What stops publish after a failed check? | A failed task upstream (default trigger rule `all_success`), or an explicit short-circuit |
| Is it idempotent per date? | Same partition-scoped writes as Dagster |
| Does `catchup` default make sense? | Set explicitly, with a comment |
| Any Airflow 2-only imports (`airflow.decorators`, `airflow.datasets`)? | Replaced by `airflow.sdk` equivalents |

### 5. Run it end to end

1. Trigger one date with WNBA games from the UI or CLI and watch it
   finish green.
2. Break a check and confirm publish is skipped.
3. Backfill a week:

   ```bash
   airflow backfill create --dag-id wnba_daily \
     --from-date 2025-07-01 --to-date 2025-07-07 --max-active-runs 2
   ```

   Airflow 3 runs backfills through the scheduler; check them in the UI.
   `--dry-run` shows what it would create first.

✅ **Checkpoint:** one green end-to-end run, one blocked publish, one
completed backfill. Screenshots for the PR.

### 6. Write the comparison (60 min, by hand)

Fill your step-1 table with evidence. Then three short paragraphs:

1. What Dagster made easier, with a concrete example from this project.
2. What Airflow made easier, with a concrete example.
3. What surprised you.

Be fair: the Airflow version was written by an agent in an afternoon;
the Dagster one by you over a week. Say how that biases the comparison.

### 7. Ship it

```bash
git switch -c m6.8-airflow-port
git add orchestration/airflow/ docs/notes/m6-airflow-comparison.md .gitignore
git commit -m "M6.8: WNBA pipeline on Airflow 3 and comparison notes"
gh pr create --fill     # Closes #90; review answers in the description
```

Don't commit `.airflow/` (it holds a SQLite database and generated
passwords) or the separate `.venv`.

## Gotchas

- **Logical date vs run date.** An Airflow daily run for 15 July runs
  *after* 15 July ends, and its logical date is the 15th. Using "now"
  inside a task is the classic Airflow bug, and it breaks backfills.
- **Two environments, one codebase.** If the Airflow venv can't import
  `ingestion/`, add the repo root to `PYTHONPATH` in your notes, rather
  than copying code into the DAG folder.
- **Port parity.** Only WNBA. Resist porting NBA "while you're there".
