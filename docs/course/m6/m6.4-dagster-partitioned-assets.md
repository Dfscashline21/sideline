# M6.4 · Dagster: daily partitioned assets per league

> **Ticket:** [#86](https://github.com/Dfscashline21/sideline/issues/86) ·
> **Mode:** hand · **Time:** 6 to 8 hours (the core of M6) ·
> **Needs:** M6.1, M6.2, M6.3; M5's dbt project builds cleanly

## Why this matters

This is where Sideline stops being a set of scripts and becomes a
platform. Interviewers ask candidates to "design the orchestration for a
daily pipeline". The answer they want has exactly the shape of this
ticket: partitioned units of data, an explicit dependency graph,
**quality gates that stop bad data being published**, and reruns that
are safe.

## What you'll produce

In `orchestration/sideline_orchestration/`:

- a **date × league** partitions definition
- assets: **ingest → dbt build → quality checks → publish**, all
  partitioned
- a **blocking** check, so a failed check stops publish
- a job that materialises one partition end to end

Acceptance: the asset graph shows **both leagues**, and **failed checks
block publish**.

✅ **Checkpoint:** a `definitions.py` with an empty `dg.Definitions()`

### 2. Define the partitions (30 min)

In `partitions.py`, define a multi-partition with a daily `date`
dimension and a static `league` dimension (`nba`, `wnba`).

Decisions to write as comments:

- **Start date.** The earliest date you'll ever backfill (M6.7 goes back
  to 2015).
- **Timezone.** Partition dates are **league-local game dates**, not UTC
  (see M6.2). `DailyPartitionsDefinition` takes a `timezone` argument;
  decide what it should be.
- **End offset.** Should today's partition exist before today ends?
  (`end_offset`: games finish late at night.)

```python
import dagster as dg

LEAGUES = ["nba", "wnba"]

league_date_partitions = dg.MultiPartitionsDefinition(
    {
        "date": dg.DailyPartitionsDefinition(start_date=___, timezone=___, end_offset=___),
        "league": dg.StaticPartitionsDefinition(LEAGUES),
    }
)
```

Inside an asset, read the dimensions with
`context.partition_key.keys_by_dimension["date"]` and `["league"]`.
Never split the key string.

</details>

### 3. The ingest asset (60 min)

Write `assets/ingest.py`: one asset, `raw_games` (name it after what
your extractor actually lands), partitioned by `league_date_partitions`,
that calls your M2/M6.2 extractor for **one league and one date**.

Rules for the asset body:

- It calls the extractor's library function, not a subprocess, so errors
  surface as Python exceptions with tracebacks in the UI.
- It returns `dg.MaterializeResult(metadata={"rows": ..., "raw_keys": ...})`
  so the UI shows what landed.
- A date with no games for that league is **success with 0 rows**, not a
  failure.

✅ **Checkpoint:** materialise `2025-07-15|wnba` and `2025-10-22|nba` (or
any dates with games) from the UI. Both succeed; the metadata shows row
counts that match the source.

### 4. dbt assets (90 min)

Load your dbt project as assets with `dagster-dbt`. Two things make this
the hard step:

1. **Partitions.** The dbt assets must use the same
   `league_date_partitions`, and the run must tell dbt *which* partition
   to build, usually through `--vars`, consumed by your incremental
   models' `is_incremental()` filters.
2. **Lineage.** The dbt staging models must depend on `raw_games`, so the
   graph is one connected pipeline rather than two islands. dagster-dbt
   links them through dbt **sources**: map your raw source to the
   `raw_games` asset key (look up `DagsterDbtTranslator` and the
   `meta.dagster.asset_key` source config).

<details>
<summary>Hint 1 · Nudge</summary>

`@dbt_assets(manifest=..., partitions_def=league_date_partitions)` gives
you one Dagster asset per dbt model. In its body you run `dbt build` and
stream the events back. How would your incremental models know the
date and league?

</details>

<details>
<summary>Hint 2 · Skeleton</summary>

```python
import json
import dagster as dg
from dagster_dbt import DbtCliResource, DbtProject, dbt_assets

dbt_project = DbtProject(project_dir=___)  # path to transform/
dbt_project.prepare_if_dev()  # builds manifest.json in dev


@dbt_assets(manifest=dbt_project.manifest_path, partitions_def=league_date_partitions)
def sideline_dbt(context: dg.AssetExecutionContext, dbt: DbtCliResource):
    keys = context.partition_key.keys_by_dimension
    dbt_vars = {"run_date": keys["date"], "league": keys["league"]}
    yield from dbt.cli(["build", "--vars", json.dumps(dbt_vars)], context=context).stream()
```

Then in your incremental models, filter on `var('run_date')` and
`var('league')` when `is_incremental()`. Remember M5's lookback: does a
single-day partition still need a 3-day lookback window?

</details>

✅ **Checkpoint:** the asset graph shows `raw_games` → staging → marts as
one connected graph. Materialising one partition runs dbt for that date
and league only (check the dbt log lines in the run).

understand the mechanism rather than relying on dbt's.

Pick a check that matters for this partition, for example: *every game
in this date and league has exactly two team rows in `fact_team_game`*.
Make it `blocking=True`.

### 6. Publish (60 min)

"Publish" means: make this partition visible to consumers (M11's API
and dashboard). Decide what that is. Two good options:

- Copy the partition's rows into a **serving table** in Postgres
  (`serving.team_game`), **atomically**: delete the partition's rows and
  insert the new ones **in one transaction**.
- Flip a pointer: an Iceberg tag or branch, or a view over the latest
  validated snapshot.

Whichever you pick, the publish asset depends on the checked mart. When
the blocking check fails, publish must not run.

✅ **Checkpoint (the acceptance test):** temporarily break the data
(insert a third team row for one game in a dev copy, or make the check
fail with a flag), materialise the partition, and confirm in the UI:
check failed, publish **skipped**, serving table unchanged. Revert.

<details>
<summary>Solution (open only after you have your own): the gating mechanism in isolation</summary>

A minimal, runnable version of the publish gate, with stub bodies. It
shows the mechanism, not your real pipeline:

```python
import dagster as dg

league_date = dg.MultiPartitionsDefinition(
    {
        "date": dg.DailyPartitionsDefinition(start_date="2015-10-01", timezone="America/New_York"),
        "league": dg.StaticPartitionsDefinition(["nba", "wnba"]),
    }
)


@dg.asset(partitions_def=league_date)
def raw_games(context: dg.AssetExecutionContext) -> dg.MaterializeResult:
    keys = context.partition_key.keys_by_dimension
    context.log.info(f"ingest {keys['league']} {keys['date']}")
    return dg.MaterializeResult(metadata={"rows": 0})


@dg.asset(partitions_def=league_date, deps=[raw_games])
def fact_team_game(context: dg.AssetExecutionContext) -> None: ...


@dg.asset_check(asset=fact_team_game, blocking=True)
def two_teams_per_game(context: dg.AssetCheckExecutionContext) -> dg.AssetCheckResult:
    bad_games = 0  # replace with a real query
    return dg.AssetCheckResult(passed=bad_games == 0, metadata={"bad_games": bad_games})


@dg.asset(partitions_def=league_date, deps=[fact_team_game])
def published_team_game(context: dg.AssetExecutionContext) -> None: ...


daily_league_job = dg.define_asset_job(
    "daily_league_job", selection=dg.AssetSelection.all(), partitions_def=league_date
)

defs = dg.Definitions(
    assets=[raw_games, fact_team_game, published_team_game],
    asset_checks=[two_teams_per_game],
    jobs=[daily_league_job],
)
```

Run one partition in a test with
`dg.materialize([...], partition_key=dg.MultiPartitionKey({"date": "2025-10-21", "league": "nba"}), raise_on_error=False)`.
When the check returns `passed=False`, the run fails at the check
step and `published_team_game` is never executed.

</details>

## Gotchas

- **Manifest freshness.** dagster-dbt reads `manifest.json`. After
  editing models, the manifest must be regenerated or the graph is stale.
  `prepare_if_dev()` handles it locally; CI and deploys need an explicit
  `dbt parse`.
- **DuckDB file locks.** If dbt writes to a DuckDB file, two partitions
  running at once will fight over the write lock. Note it now; M6.7's
  concurrency of 4 has to solve it (see that lab).
- **Mixed partitioning.** Unpartitioned dims (`dim_team`) downstream of
  partitioned staging need care. dagster-dbt can select subsets; decide
  which models run per partition and which run once a day.
- **Empty partitions are normal.** Most dates have games in only one
  league. Don't alert on 0 rows; alert on 0 rows *on a game day* (M6.6).
