# M6.2 · WNBA extractor following the NBA pattern

> **Ticket:** [#84](https://github.com/Dfscashline21/sideline/issues/84) ·
> **Mode:** agent: the agent drafts from your M2 pattern, you review every line ·
> **Time:** 3 to 4 hours · **Needs:** M2 merged (NBA extractor, raw zone, tests)

## Why this matters

The first extractor (M2) was hand-built because the *pattern* is the
skill: retries, watermarks, raw data landed unchanged, idempotent
restarts. The second extractor is where you find out whether that
pattern is actually reusable, or whether NBA assumptions are baked in
everywhere. A good agent draft that copies your pattern faithfully will
expose every hard-coded `"nba"`.

It's also the realistic version of agent work on a team: you own the
pattern and the review, the agent does the repetition.

## What you'll produce

- A WNBA extractor in `ingestion/sideline_ingestion/` that lands raw
  WNBA data in the raw zone, using:
  - **sportsdataverse season files** for completed seasons, and
  - **ESPN's public scoreboard/summary endpoints** for the current season
- The **same tests and idempotency guarantees** as the NBA extractor.
- Your review notes in the PR.

## Steps

### 1. Map what's league-specific in your M2 code (30 min, by hand)

Before any prompting, read your NBA extractor and list every place it
assumes NBA. Typical ones:

- source URLs and endpoints, request headers
- the league key in the raw path (`nba/...`)
- season naming and the date range of a season
- rate limits and retry settings for that source
- the watermark key

✅ **Checkpoint:** a written list. If it's long, consider a small
refactor (pull the league-specific values into a config object) **by
hand first**, so the agent extends a pattern rather than copying a mess.

### 2. Learn the two WNBA sources (30 min, by hand)

**Completed seasons:** the sportsdataverse releases you used in M1:

```
https://github.com/sportsdataverse/sportsdataverse-data/releases/download/espn_wnba_schedules/wnba_schedule_<season>.parquet
https://github.com/sportsdataverse/sportsdataverse-data/releases/download/espn_wnba_team_boxscores/team_box_<season>.parquet
https://github.com/sportsdataverse/sportsdataverse-data/releases/download/espn_wnba_pbp/play_by_play_<season>.parquet
```

**Current season:** ESPN's public JSON (no key, undocumented, so expect
it to change without notice):

```bash
curl -s "https://site.api.espn.com/apis/site/v2/sports/basketball/wnba/scoreboard?dates=20250715" \
  | python3 -m json.tool | less
```

Look for `events[].id`, `events[].date` and `events[].status.type`.
Note that `date` is **UTC**: a late game on 15 July is dated the 16th.

Decide and write down:

- Which "season boundary" moves a season from ESPN-live to
  sportsdataverse-files? (For example, once the season's final file is
  published.)
- What exactly lands in raw: the Parquet files as downloaded, the JSON
  responses as returned, or both? M2's ADR-001 says raw is landed
  unchanged. Does that still hold?
- How do raw keys look? Follow your M2.2 layout, e.g.
  `wnba/espn/scoreboard/ingest_date=2025-07-16/<run_id>.json` and
  `wnba/sportsdataverse/team_box/ingest_date=.../team_box_2025.parquet`.

### 3. Prompt the agent

Starter prompt. Paste in your list from step 1 and your decisions from step 2:

> Read AGENTS.md and `ingestion/sideline_ingestion/` (the NBA extractor
> and its tests). Build a WNBA extractor that follows the **same pattern**:
> same retry/backoff helper, same raw-zone writer, same watermark
> mechanism, same CLI flags (`--start/--end`), same logging of row counts.
>
> Sources: *(paste step 2)*. League-specific values I found: *(paste
> step 1)*.
>
> Reuse existing helpers; don't copy them. If a helper is NBA-specific,
> propose a minimal change to make it league-agnostic and show me that
> diff separately, first.
>
> Tests: mirror every NBA test for WNBA, including the injected 429/5xx
> test and the kill-and-restart idempotency test. Use recorded fixtures,
> not live HTTP, in unit tests.

### 4. Review it like a pull request

Read the diff before running it. Answer each question in the PR description:

| Review question | What a good answer looks like |
|---|---|
| Did it reuse your helpers or copy them? | Imports from the shared module; no second retry implementation |
| Is any `"nba"` still hard-coded in shared code? | `grep -rn '"nba"' ingestion/` shows only NBA-specific config |
| Where does the UTC → game date conversion happen, and in which timezone? | One function, tested on a late-night game |
| Is the raw payload written byte-for-byte as received? | No parsing or reformatting before the raw write |
| What happens when ESPN returns 200 with an empty `events` list? | Treated as "no games", not an error, and logged |
| What happens on a kill mid-season-backfill and a restart? | Same final raw objects, no duplicates: the M2.7 test proves it |
| Are watermarks per league? | Advancing WNBA's watermark can't move NBA's |
| Are new dependencies justified? | Ideally none beyond what M2 uses |

Ask the agent to explain anything you can't. You must be able to explain
every line.

### 5. Run it for real

```bash
make up
uv run python -m sideline_ingestion.wnba --start 2025-07-01 --end 2025-07-07
```

(Use your actual entry point.) Then check the raw zone in the MinIO
console (http://localhost:9001 → `sideline-raw` → `wnba/`), or with
whatever listing helper you wrote in M2.

✅ **Checkpoint:** objects for each day with games, nothing for days
without, and row counts in the logs that match the number of games ESPN
lists for those dates.

### 6. Prove the guarantees

1. Run the same range twice. The raw zone has no new duplicates (same keys, or
   the same logical content if keys include a run ID: check what your M2
   design promised).
2. Run the kill-and-restart test for WNBA.
3. `make test`: coverage at least the NBA extractor's.

### 7. Ship it

```bash
git switch -c m6.2-wnba-extractor
make lint && make typecheck && make test
git add ingestion/
git commit -m "M6.2: WNBA extractor on the shared ingestion pattern"
gh pr create --fill     # Closes #84; paste review answers
```

## Gotchas

- **UTC dates.** Partitioning or watermarking on the UTC date silently
  shifts late games to the next day. Decide on league-local game dates
  (WNBA teams span several US time zones; using US/Eastern for all is a
  common, documented convention).
- **Undocumented API.** ESPN's site API has no contract. Land responses
  raw and parse later, so a format change breaks staging (fixable),
  not ingestion (data lost).
- **Season files are re-published.** A sportsdataverse file for a
  completed season can be regenerated with corrections. Your
  idempotency design must say what happens when the same season is
  ingested again with different bytes.
- **Expansion teams.** New WNBA franchises appear mid-history. Don't
  assume a fixed team count anywhere.
