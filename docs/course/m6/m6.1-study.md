> **Ticket:** [#83](https://github.com/Dfscashline21/sideline/issues/83) ·
> **Mode:** hand · **Time:** 4 to 5 hours over several sessions ·
> **Needs:** nothing from M6. A scratch virtualenv is enough for the exercises.

## Why this matters

"How would you orchestrate this pipeline?" comes up in nearly every
data engineering loop. Weak answers name a tool. Strong answers talk
about **what** is being produced (assets and their partitions), **when**
it should be recomputed (schedules, sensors, upstream changes), and **how**
a rerun stays safe (idempotent, atomic writes). That vocabulary is what
this study session builds, before you write the real pipeline in M6.4.

## What you'll produce

- `docs/notes/m6-cheatsheet.md`: one page, your own words.
- The ability to compare Dagster and Airflow **in 2 minutes, out loud**
  (the acceptance criterion). You'll record yourself doing it.

## Session 1 · Tasks vs assets (60 min)

**Read:**
- Dagster: [Assets](https://docs.dagster.io/guides/build/assets) (the
  "defining assets" page).
- Airflow 3: [Assets](https://airflow.apache.org/docs/apache-airflow/stable/authoring-and-scheduling/assets.html)
  and the DAG concepts page.

The core distinction:

| | Task/DAG-centric (classic Airflow) | Asset-centric (Dagster; Airflow 3 assets) |
|---|---|---|
| You declare | Steps and the order they run in | The **data** that should exist, and what it's computed from |
| Dependencies | Task A >> task B | Asset B reads asset A |
| "Is it up to date?" | Did the last run succeed? | When was each asset (partition) last materialised, and is its upstream newer? |
| Lineage | Implied by the DAG | First class, shown in the UI |

### Exercise 1.1

Write `assets.py` with three assets (`raw_games` → `team_game` →
`published_team_game`) that just log a message, then:

```bash
dagster dev -f assets.py
```

Open http://localhost:3000, view the asset graph, materialise all three.
Then materialise **only** `team_game`. What does the UI say about
`published_team_game` afterwards?

<details>
<summary>Hint · Skeleton</summary>

```python
import dagster as dg


@dg.asset
def raw_games(context: dg.AssetExecutionContext) -> None:
    context.log.info("ingest")


@dg.asset(deps=[raw_games])
def team_game(context: dg.AssetExecutionContext) -> None: ...


# ...and a third, then:
defs = dg.Definitions(assets=[raw_games, team_game, ...])
```

</details>

## Session 2 · Partitions and backfills (60 min)

**Read:** Dagster [Partitioning assets](https://docs.dagster.io/guides/build/partitions-and-backfills/partitioning-assets)
and [Backfilling data](https://docs.dagster.io/guides/build/partitions-and-backfills/backfilling-data).

A **partition** is a slice of an asset you can compute independently,
usually a date. A **backfill** is materialising many partitions,
typically historical ones.

Sideline needs **two** dimensions: date and league. Dagster has a
`MultiPartitionsDefinition` for that.

### Exercise 2.1

Give your three assets this partitioning and materialise one partition:

```python
league_date = dg.MultiPartitionsDefinition(
    {
        "date": dg.DailyPartitionsDefinition(start_date="2025-10-01"),
        "league": dg.StaticPartitionsDefinition(["nba", "wnba"]),
    }
)
```

Inside the asset, log `context.partition_key` and
`context.partition_key.keys_by_dimension`. What string does the key
print as? Which dimension comes first, and why? (Try renaming `date` to
`zdate`.)

### Exercise 2.2: what makes a backfill safe?

Think it through, then write the answers on your cheat sheet:

1. Your asset **appends** a day's rows to a table. You backfill that day
   twice. What happens?
2. Your asset **deletes the day's rows, then inserts**. The process is
   killed between delete and insert. What do readers see?
3. What would make the write **atomic**: readers see either the old day
   or the new day, never a half-written one?

<details>
<summary>Explanation</summary>

1. Duplicates. Appends aren't idempotent.
2. A missing day until someone reruns it.
3. Options, in rough order of preference: write to a staging table or
   file and swap it in with one atomic step (a rename, or Iceberg's
   single-snapshot commit); `MERGE`/upsert on a natural key; delete and
   insert **in one transaction**. Iceberg (M4) gives you atomic
   overwrite of a partition for free: one snapshot commit, or none.

Interview phrase to have ready: **"idempotent per partition, atomic per write."**

</details>

## Session 3 · Schedules, sensors and asset checks (60 min)

**Read:** Dagster [Schedules](https://docs.dagster.io/guides/automate/schedules),
[Sensors](https://docs.dagster.io/guides/automate/sensors) and
[Asset checks](https://docs.dagster.io/guides/test/asset-checks).

- A **schedule** fires on a clock (cron).
- A **sensor** is a function Dagster calls every N seconds; it decides
  whether to request runs. Use it when the trigger is an *event* (a file
  arrived, a game ended) rather than a time.
- A **run key** de-duplicates: Dagster won't launch two runs with the same
  `run_key` from the same sensor. That's how a sensor that's evaluated
  every 30 seconds requests a run exactly once.
- An **asset check** tests an asset after it materialises. A check with
  `blocking=True` stops downstream assets in the same run if it fails.

### Exercise 3.1

Add a check on `team_game` that always fails, with `blocking=True`.
Materialise all three assets. What happens to `published_team_game`?
Change `blocking` to `False` and try again.

### Exercise 3.2

Write a sensor that requests a run for today's `nba` partition only if
today is in a hard-coded set of game days. Test it **without** the UI:

```python
with dg.instance_for_test() as instance:
    ctx = dg.build_sensor_context(instance=instance, definitions=defs)
    result = my_sensor(ctx)
```

What do you return when there are no games? (`dg.SkipReason`.) Why is
that better than returning nothing?

## Session 4 · Airflow 3 in practice (45 min)

**Read:** the Airflow 3 [release notes / upgrade guide](https://airflow.apache.org/docs/apache-airflow/stable/installation/upgrading_to_airflow3.html)
and the backfill section of the CLI docs.

Things that changed from Airflow 2 and that interviewers may probe:

- The task SDK lives in `airflow.sdk` (`dag`, `task`, `Asset`).
- "Datasets" were renamed **assets**. A DAG can be scheduled on assets
  (`schedule=[Asset("s3://...")]`), so it runs when upstream data updates.
- **Backfills are first class**: created through the API, UI or
  `airflow backfill create --dag-id ... --from-date ... --to-date ...
  --max-active-runs N`, and run by the scheduler rather than a CLI
  process you have to keep alive.
- Tasks talk to the API server rather than straight to the metadata
  database.

You don't need to install Airflow until M6.8.
