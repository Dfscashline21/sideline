# M6.5 · League calendar sensor and post-game run

> **Ticket:** [#87](https://github.com/Dfscashline21/sideline/issues/87) ·
> **Mode:** hand · **Time:** 4 to 5 hours ·
> **Needs:** M6.4 (`daily_league_job` and the date × league partitions)

## Why this matters

A cron schedule that runs every day at 6 a.m. is easy and wrong for
sports data. Most days have no games for a given league; the useful
moment to refresh is **after the last game ends**, and that moment moves
every night. Scheduling on events rather than clocks is a common
interview topic ("how would you trigger a pipeline when upstream data is
ready?"), and getting it right means handling three things: not firing on
off days, firing **exactly once**, and not losing track of games that
finish after midnight.

## What you'll produce

`orchestration/sideline_orchestration/sensors.py` with one sensor that,
for each league:

- requests the daily run **only on game days**
- requests one extra **post-game run two hours after the last game ends**

Plus tests proving **no runs on off days** and **the post-game run fires**.

## Steps

### 1. Decide where the schedule comes from (30 min)

The sensor needs, for a league and date: the games, and whether each is
finished. Options:

| Source | Pros | Cons |
|---|---|---|
| ESPN scoreboard (`site.api.espn.com/.../scoreboard?dates=YYYYMMDD`) | Live status (`STATUS_FINAL`), today's games | Network call every evaluation; undocumented API |
| Your staged schedule table (from M6.2's raw data) | Already in the warehouse; no extra calls | Only as fresh as the last ingest, so it can't see "final" in real time |
| Both: schedule table for "is it a game day", scoreboard for "are they final" | Cheap on off days | Two code paths |

Pick one and write the choice and reason at the top of `sensors.py`.

Whatever you pick, put it behind a function with a narrow signature:

```python
def fetch_games(league: str, game_date: date) -> list[Game]: ...
```

so tests can swap in a fake. **This is the design choice that makes the
sensor testable.**

### 2. Define "the last game ended" (20 min)

ESPN tells you a game is final, but not *when* it became final. Options:

- **Observed:** remember the first evaluation at which *all* games were
  final, and fire two hours after that. Needs state between evaluations:
  the sensor **cursor**.
- **Estimated:** last scheduled tip-off plus a typical game length plus
  two hours. No state, but overtime and delays make it wrong.

Write which you chose, and what error it allows (the observed approach
is late by at most one sensor interval).

### 3. Write the decision logic as a pure function (60 min)

Keep the "should we run?" logic **out** of the Dagster sensor, in a
plain function you can test without Dagster:

```python
def decide(league, game_date, games, now, all_final_since) -> (run_keys, new_all_final_since)
```

<details>
<summary>Hint 1 · Nudge</summary>

What makes a run happen **exactly once** even though the sensor is
evaluated every few minutes? Dagster de-duplicates by `run_key`. So the
function's real job is to return the right *keys*, deterministic for a
league, date and trigger. It doesn't decide *whether this is the first time*.

</details>

<details>
<summary>Hint 2 · Approach</summary>

- No games → no keys, and reset the state.
- Any games → key `"{league}|{date}|daily"` (requested every evaluation;
  Dagster launches it once).
- All games final → set `all_final_since` if not set; if
  `now - all_final_since >= 2 hours` → also key `"{league}|{date}|postgame"`.
- Not all final → `all_final_since = None` (a game went to overtime).

</details>

### 4. Wrap it in a sensor (45 min)

The sensor loops over leagues, calls `fetch_games`, calls `decide`,
turns keys into `RunRequest`s with the right `MultiPartitionKey`, and
stores `all_final_since` per league and date in the cursor (JSON).

Return `dg.SkipReason("no games ...")` when there's nothing to do, so the
UI shows *why* it didn't run.

### 5. Test it (60 min)

In `orchestration/tests/test_sensors.py`, with a fake `fetch_games` and
a fake clock:

1. **Off day:** no games in either league → `SkipReason`, no run requests.
2. **Game day, games live:** daily key only, no post-game key.
3. **Post-game fires:** all final at T; evaluate at T (no post-game), then at
   T + 2h 1m, passing the first result's cursor → post-game key present.
4. **Overtime reset:** a game goes from final back to "in progress"
   (it happens with stat corrections). The two-hour timer restarts.
5. **After midnight:** games on the 15th finish at 00:30 on the 16th.
   Evaluate at 02:31 on the 16th. The post-game run for the **15th**
   must still fire.

Test sensors without the UI:

```python
with dg.instance_for_test() as instance:
    result = league_calendar_sensor(dg.build_sensor_context(instance=instance, cursor=cursor))
```

✅ **Checkpoint:** all five tests pass. If test 5 fails, read Gotchas
before opening the solution. It's the bug this lab exists to teach.

<details>
<summary>Solution (open only after you have your own)</summary>

```python
POST_GAME_DELAY = timedelta(hours=2)


@dataclass(frozen=True)
class Game:
    game_id: str
    final: bool


def decide(
    league: str,
    game_date: date,
    games: list[Game],
    now: datetime,
    all_final_since: datetime | None,
) -> tuple[list[str], datetime | None]:
    """Return run keys to request and the updated 'all games final since' time."""
    if not games:
        return [], None
    keys = [f"{league}|{game_date.isoformat()}|daily"]
    if all(g.final for g in games):
        all_final_since = all_final_since or now
        if now - all_final_since >= POST_GAME_DELAY:
            keys.append(f"{league}|{game_date.isoformat()}|postgame")
    else:
        all_final_since = None
    return keys, all_final_since


@dg.sensor(job=daily_league_job, minimum_interval_seconds=300)
def league_calendar_sensor(context: dg.SensorEvaluationContext) -> dg.SensorResult | dg.SkipReason:
    state = json.loads(context.cursor) if context.cursor else {}
    now = clock()  # league-local "now"; injectable for tests
    requests = []
    # Late games finish after midnight, so yesterday's game date is still "open".
    for game_date in (now.date() - timedelta(days=1), now.date()):
        for league in ("nba", "wnba"):
            games = fetch_games(league, game_date)
            slot = f"{league}|{game_date.isoformat()}"
            since_raw = state.get(slot)
            since = datetime.fromisoformat(since_raw) if since_raw else None
            keys, since = decide(league, game_date, games, now, since)
            state[slot] = since.isoformat() if since else None
            pk = dg.MultiPartitionKey({"date": game_date.isoformat(), "league": league})
            requests += [
                dg.RunRequest(run_key=k, partition_key=pk, tags={"trigger": k.split("|")[-1]})
                for k in keys
            ]
    # Forget slots older than yesterday so the cursor doesn't grow forever.
    keep = {(now.date() - timedelta(days=1)).isoformat(), now.date().isoformat()}
    state = {k: v for k, v in state.items() if k.split("|")[1] in keep}
    if not requests:
        return dg.SkipReason("no games today in any league")
    return dg.SensorResult(run_requests=requests, cursor=json.dumps(state))
```

How `clock` and `fetch_games` get injected is up to you: module-level
functions you monkeypatch in tests, a factory that builds the sensor, or
a Dagster resource. The factory version is the easiest to test.

</details>

## Gotchas

- **Midnight.** Looping only over "today" means games on the 15th that end
  at 00:30 on the 16th never get a post-game run: at 02:30 the sensor is
  looking at the 16th. Evaluate yesterday's game date as well.
- **Time zones.** "Today" must be the league's local date, matching the
  partition timezone from M6.4. A sensor running in UTC on a server
  shifts every evening game.
- **Run keys must be deterministic.** A key containing `now()` or a
  random ID defeats de-duplication and launches a run every evaluation.
- **Cursor growth.** Prune old dates from the cursor, or it grows forever.
- **Network calls in sensors** run on the daemon every interval. Keep them
  cheap and time-boxed; a hanging HTTP call blocks the sensor.
