# M8.5 · Late events and dead-letter topic

> **Ticket:** [#111](https://github.com/Dfscashline21/sideline/issues/111) ·
> **Mode:** hand · **Time:** 4 to 6 hours ·
> **Needs:** M8.4 working on the clean test game

## Why this matters

A watermark is a promise with fine print: "I'll wait 30 seconds; after
that, I stop guaranteeing anything." A pipeline that silently drops what
falls outside the promise has a correctness bug nobody can see. A senior
pipeline makes the two outcomes explicit:

1. **Late but within the watermark:** the result is **corrected**.
2. **Too late:** the event is **kept and set aside** in a dead-letter
   topic (DLQ) where someone can see it, count it and replay it.

The ticket's criterion is a test that proves both. Writing a
*deterministic* test for a streaming job is the real skill here.

## What you'll produce

- A late-event router that sends events beyond the 30-second threshold to
  `game-events-dlq`, with the reason and how late they were.
- `streaming/tests/test_late_events.py`: a scripted scenario proving
  (a) a 20-second-late basket updates its window and (b) a 2-minute-late
  basket lands in the DLQ and not in the totals.

## Background: what Spark gives you and what it doesn't

From the [Spark guide's watermarking section](https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html#handling-late-data-and-watermarking),
two facts drive this lab:

- Data **within** the threshold is guaranteed to be aggregated.
- Data **beyond** it is *not guaranteed to be dropped*. It may or may not
  be counted, depending on timing. And Spark doesn't hand you the dropped
  rows: there's no built-in "late data" output.

So the DLQ is yours to build. (Flink has this built in, as a "side
output" for late data. Note that for M8.10.)

## Steps

### 1. Write the scenario on paper first (30 min)

A test you can reason about beats a random replay. Using events from
game 401584089, design a sequence in **arrival order**:

| Arrival | Event | Event time | Expected outcome |
|---|---|---|---|
| 1 to n | Normal events, in order | t₀ … t₀ + 3 min | Counted |
| n+1 | Basket A, held back | 20 s behind the newest event | **Counted**; its window's row is updated |
| … | More normal events | | Counted |
| m | Basket B, held back | 120 s behind the newest event | **DLQ**; never in the totals |

Write down the expected window totals for Basket A's minute, and the
expected DLQ message for Basket B, **before** writing any code.

✅ **Checkpoint:** you can say for each event which side of the
watermark it's on, and why, using `watermark = max event time seen − 30 s`.

### 2. Decide the lateness rule you'll enforce (30 min)

Spark's own watermark is global to the query and lags a micro-batch (see
the [module gotchas](README.md#know-these-before-you-write-any-streaming-code)),
so you can't read it from your code. Define your own, explicit rule:

> An event is late if its `event_time` is more than 30 seconds behind the
> newest `event_time` already seen **for that game**, in arrival (offset) order.

Write in `streaming/README.md` why "per game" (several games can replay
at once and shouldn't push each other's watermark) and why "arrival
order" (makes the decision deterministic, whatever the batch size).

### 3. Build the router (90 to 120 min)

A second streaming query on the same topic. It keeps a small state per
game (the max event time seen so far) and flags each event.

<details>
<summary>Hint 2 · Approach</summary>

1. Read `game-events`, decode it as in M8.4, and **keep the Kafka `offset`
   column**. Each game is in one partition (keyed by `game_id`), so offset
   order is arrival order.
2. `groupBy("game_id").applyInPandasWithState(route, out_schema,
   state_schema, "append", "NoTimeout")`.
3. In `route`: read `max_seen` from state, concatenate the batch's pandas
   frames, **sort by offset**, walk the rows: if
   `max_seen - event_time > 30 s`, mark late with `lateness_seconds`,
   else update `max_seen`. Save `max_seen` back to state and yield the late
   rows.
4. Write the late rows to `game-events-dlq` with the Kafka sink: key
   `game_id`, value = the original bytes, plus Kafka headers
   `reason=late` and `lateness_seconds`.

</details>

<details>
<summary>Solution · router (open only after you have your own)</summary>

```python
"""Route events more than 30 s behind the newest event of their game to the DLQ (M8.5)."""

from collections.abc import Iterator
from datetime import timedelta

import pandas as pd
from pyspark.sql import functions as F
from pyspark.sql.streaming.state import GroupState
from pyspark.sql.types import (
    BinaryType,
    LongType,
    StringType,
    StructField,
    StructType,
    TimestampType,
)

THRESHOLD = timedelta(seconds=30)
OUT = StructType(
    [
        StructField("game_id", LongType()),
        StructField("event_id", LongType()),
        StructField("value", BinaryType()),
        StructField("lateness_seconds", LongType()),
    ]
)
STATE = StructType([StructField("max_seen", TimestampType())])


def route(
    key: tuple[int], pdfs: Iterator[pd.DataFrame], state: GroupState
) -> Iterator[pd.DataFrame]:
    frames = list(pdfs)
    if not frames:
        return
    batch = pd.concat(frames).sort_values("offset")  # arrival order within the game's partition
    max_seen = state.get[0] if state.exists else None
    late = []
    for row in batch.itertuples():
        if max_seen is not None and max_seen - row.event_time > THRESHOLD:
            late.append(
                (
                    row.game_id,
                    row.event_id,
                    row.value,
                    int((max_seen - row.event_time).total_seconds()),
                )
            )
        else:
            max_seen = row.event_time if max_seen is None else max(max_seen, row.event_time)
    state.update((max_seen,))
    yield pd.DataFrame(late, columns=["game_id", "event_id", "value", "lateness_seconds"])


def start_router(events_with_offset):  # decoded events + Kafka `offset` and raw `value`
    late = events_with_offset.groupBy("game_id").applyInPandasWithState(
        route, OUT, STATE, "append", "NoTimeout"
    )
    return (
        late.select(
            F.col("game_id").cast(StringType()).alias("key"),
            "value",
            F.array(
                F.struct(
                    F.lit("reason").alias("key"), F.lit("late").cast(BinaryType()).alias("value")
                ),
                F.struct(
                    F.lit("lateness_seconds").alias("key"),
                    F.col("lateness_seconds").cast(StringType()).cast(BinaryType()).alias("value"),
                ),
            ).alias("headers"),
        )
        .writeStream.format("kafka")
        .option("kafka.bootstrap.servers", "localhost:19092")
        .option("topic", "game-events-dlq")
        .option("checkpointLocation", ".data/checkpoints/late_router")
        .start()
    )
```

Type annotations are trimmed in `start_router` for space. Yours should
pass mypy. Note the router decides lateness from **its own** state, not
Spark's watermark, so it gives the same answer whatever the batch sizes.

</details>

Keep the Kafka value **unchanged** in the DLQ (the original Avro bytes):
whoever replays the DLQ later should get the exact original event. Put
the "why" in headers, not in a modified payload.

### 4. Write the test (90 min)

Make it deterministic:

- A **scripted producer** in the test sends the step 1 sequence (use the
  M8.3 producer's serialisation, with `--late-fraction 0` and your own
  ordering, or a small helper that sends a list of events in order).
- A **fresh topic name** per test run (`game-events-test-<uuid>`) and a
  **fresh checkpoint** directory (`tmp_path`), so runs can't see each
  other's data.
- Run the queries with `trigger(availableNow=True)`: process what's
  there, then stop. No sleeping and hoping.
- Assert:
  1. Basket A's points are in its window's total (Postgres or whatever
     M8.4 writes to).
  2. The DLQ topic has exactly one message, Basket B's `event_id`, with a
     `lateness_seconds` header ≥ 90.
  3. Basket B's points are **not** in any window total.

<details>
<summary>Hint · Assertion 3 can flake. Why?</summary>

`availableNow` may process everything in **one** micro-batch. Spark's
watermark only moves *between* batches, so the aggregation query may
count Basket B (that's the "not guaranteed to be dropped" fine print).
Your router still DLQs it, so it's counted *and* dead-lettered.

Fixes, in order of honesty:
1. Set `maxOffsetsPerTrigger` small (e.g. 20) on the aggregation's Kafka
   source so the watermark advances between batches before Basket B
   arrives. Then the test exercises real watermark behaviour.
2. Have the aggregation read only events the router marked on-time.
   Stronger consistency, but more moving parts.

Pick one and explain the trade-off in the test's docstring. This exact
issue is a great interview story.

</details>

Mark it as an integration test (needs Redpanda and Spark running) with
a pytest marker, so `make test` without the stack doesn't fail. Add a
`make test-streaming` target that runs it.

✅ **Checkpoint:** the test passes three times in a row, and **fails** if
you change the threshold to 200 seconds (Basket B is no longer late).
Mutating the code to see a test fail proves the test can catch something.

## Gotchas

- **`pd.concat([])` raises.** A key can be called with no rows (for
  example on timeout). Guard for an empty iterator.
- **Event-time types.** Decoded `timestamp` columns arrive in pandas as
  `datetime64[ns]` (timezone-naive in UTC, depending on Spark's session
  time zone). Set `spark.sql.session.timeZone` to `UTC` in both jobs so
  comparisons don't shift by your local offset.
- **DLQs need an owner.** A dead-letter topic nobody watches is a slower
  way of dropping data. Note in `streaming/README.md` how you'd alert on
  DLQ volume (M9 will ask).
- **Retention.** Give `game-events-dlq` a longer retention than
  `game-events` if you mean to replay it later.
