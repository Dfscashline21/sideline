# M8.10 · ADR-006: Stream processor choice

> **Ticket:** [#116](https://github.com/Dfscashline21/sideline/issues/116) ·
> **Mode:** hand · **Time:** 2 to 3 hours ·
> **Needs:** M8.4, M8.5 and M8.7 built (you need first-hand evidence)

## Why this matters

"Flink or Spark Structured Streaming?" is a classic design question,
and the weak answer is a feature list copied from a blog. The strong
answer ties each difference to **this** workload and to things you
actually hit. You've now built the job, fought late data and tested a
sink; the ADR is where that experience becomes a decision someone else
can review.

## What you'll produce

`docs/adr/006-stream-processor.md`, in the same format as your earlier
ADRs (M2.8 onward).

## Steps

### 1. Write the forces before the options (30 min)

What does *this* use case need? List requirements with numbers where you
have them. Examples to adapt:

- **Latency:** stats within a few seconds; the win-probability feed
  within one second (M8.6 measured it).
- **Late data:** a 30-second watermark, and late events must be
  **captured** (M8.5), not silently dropped.
- **Sink:** exactly-once into Iceberg (M8.7).
- **Scale:** at most ~15 concurrent NBA games, a few hundred events per
  game: tiny.
- **Team:** one engineer who already knows PySpark from M7.
- **Ops:** runs locally in Compose, later on AWS (M10).

### 2. Research Flink for the same requirements (60 min)

You don't need to build it, but you need concrete facts, from the docs
rather than blogs:

| Concern | Where to look in Flink |
|---|---|
| Late data | [Side outputs](https://nightlies.apache.org/flink/flink-docs-stable/docs/dev/datastream/side_output/) and `sideOutputLateData` on windowed streams |
| Watermarks | Watermark strategies, `forBoundedOutOfOrderness`, idleness handling |
| Latency model | Record-at-a-time processing vs Spark's micro-batches |
| Exactly-once to Iceberg | The Iceberg Flink sink commits on checkpoints |
| Python | PyFlink's maturity compared with PySpark for your team |
| Running it | JobManager/TaskManager containers vs `spark-submit` / local mode |

Optional, and worth it if you have an evening: port M8.4's windowed
aggregation to PyFlink or Flink SQL and compare.

### 3. Fill in the comparison with your evidence (30 min)

<details>
<summary>Hint · A table that earns its place</summary>

Only include rows where the difference **matters for this use case**,
and cite your own evidence for the Spark column:

| Force | Spark Structured Streaming (built) | Flink (researched) |
|---|---|---|
| Late data capture | No built-in output; built a stateful router (M8.5); a micro-batch "grey zone" made a test flaky | Native side output for late records |
| Latency | Trigger interval plus batch overhead; fine for stats, chose a plain consumer for win probability | Per-record; sub-second without a separate consumer |
| Iceberg exactly-once | Verified by kill tests (M8.7) | Supported via checkpoint commits (not tested) |
| Team skills / reuse | Same engine as M7 batch jobs | New runtime and APIs |
| Ops footprint | Local mode, one process | Cluster of JobManager + TaskManager |

</details>

### 4. Decide, and say what would change your mind (30 min)

An ADR without consequences isn't finished. Write:

- **Decision:** one sentence.
- **Consequences:** what you accept by choosing it (e.g. the late-data
  router is your code to maintain).
- **Revisit when:** the specific trigger that would flip the decision
  (e.g. "if we need sub-second per-event processing for more than one feed",
  or "if the DLQ grey zone causes a real incident").

## Gotchas

- **Don't decide by popularity.** "Flink is the industry standard for
  streaming" is not a force for a 15-game, one-engineer system.
- **Separate facts you measured from facts you read.** Label them. An
  interviewer will ask which is which.
