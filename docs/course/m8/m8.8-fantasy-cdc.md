# M8.8 · Fantasy league DB and Debezium CDC

> **Ticket:** [#114](https://github.com/Dfscashline21/sideline/issues/114) ·
> **Mode:** mixed: schema and change-apply logic by hand, seeding and config by agent ·
> **Time:** 3 to 4 hours · **Needs:** M8.2 (broker), M0.3 (Postgres in Compose)

## Why this matters

Most company data starts in an application database, not in a feed.
**Change data capture** (CDC) reads the database's own write-ahead log
and turns every insert, update and delete into an event, without
touching the application and without hammering the database with
`select * where updated_at > …` polling.

The traps are exactly what interviewers probe:

- Polling misses **deletes** (the row is gone, so there's nothing to select).
- Polling misses updates that happen twice between polls.
- CDC handles both, but **deletes look different** (a tombstone, and a
  "before" image that may be incomplete). That's the ticket's
  "insert, update, delete all arrive downstream".

This lab is independent of M8.3 to M8.7: it only needs the broker.

## What you'll produce

- A small fantasy-basketball schema in Postgres (`fantasy` database or schema).
- `streaming/cdc/seed_fantasy.py`: seeds leagues, teams, players and rosters,

## Steps

### 1. Design the schema (by hand, 30 min)

Keep it small; the point is the changes, not the domain. A minimal design:

- `leagues (league_id pk, name, season)`
- `fantasy_teams (fantasy_team_id pk, league_id fk, owner_name, team_name)`
- `rosters (fantasy_team_id, athlete_id, slot, acquired_at, primary key (fantasy_team_id, athlete_id))`

`athlete_id` should be a real ESPN athlete ID from `nba_player_box` so
that later modules can join fantasy rosters to real stats. Every table
needs a primary key: why does CDC care? (See Gotchas.)

### 2. Enable logical replication (15 min)

Debezium reads Postgres's write-ahead log through **logical decoding**.
The Compose Postgres needs:

```yaml
postgres:
  command: ["postgres", "-c", "wal_level=logical"]
```

Restart Postgres and check:

```bash
docker compose exec postgres psql -U sideline -c "show wal_level;"   # logical
```

`pgoutput`, the plugin Debezium uses by default, is built into Postgres
10+; nothing to install.

### 3. Agent: Debezium Connect and seeding

> Add a Debezium Kafka Connect service to `compose.yaml` using image
> `quay.io/debezium/connect:3.7.1.Final`, connected to Redpanda at
> `redpanda:9092`, REST API on port 8083 (bound to 127.0.0.1). Configure
> its config, offset and status storage topics for a **single-broker**
> cluster. Then write `streaming/cdc/postgres-connector.json` for
> `io.debezium.connector.postgresql.PostgresConnector` with `plugin.name`
> `pgoutput`, `topic.prefix` `fantasy`, capturing only my three tables,
> credentials from environment rather than hard-coded. Add
> `make cdc-up` that registers the connector with
> `curl -X PUT .../connectors/fantasy/config` (idempotent).
>
> Also write `streaming/cdc/seed_fantasy.py` (psycopg, typed): creates my
> schema from `streaming/cdc/schema.sql`, seeds 2 leagues × 10 teams × 13
> roster spots using athlete IDs from `.data/practice.duckdb`
> `nba_player_box`, and has a `--moves N` flag that performs N random
> roster moves (add, drop, change slot) with a short sleep between.

Review checklist:

| Question | Good answer |
|---|---|
| Why does the connector config use `PUT …/config` not `POST /connectors`? | `PUT` creates or updates, so re-running is safe |
| Internal topics' replication factor? | 1 on a single broker; the default (3) fails to create topics |
| Which tables are captured? | Explicit `table.include.list`, not everything |
| Where do credentials come from? | Environment / `.env`, never in the committed JSON |
| Does the seed script use real athlete IDs? | Yes, read from the practice DB |
| Are moves random but reproducible? | A `--seed` flag |

### 4. Look at real change events (by hand, 30 min)

```bash
make cdc-up
uv run python streaming/cdc/seed_fantasy.py --moves 0
docker compose exec redpanda rpk topic list | grep fantasy
docker compose exec redpanda rpk topic consume fantasy.public.rosters -n 3
```

Topics are named `<topic.prefix>.<schema>.<table>`. Then, in `psql`, do
one of each by hand and watch the topic:

```sql
insert into rosters values (1, 3112335, 'BENCH', now());
update rosters set slot = 'G' where fantasy_team_id = 1 and athlete_id = 3112335;
delete from rosters where fantasy_team_id = 1 and athlete_id = 3112335;
```

For each message, write down `payload.op` (`c`, `u`, `d`, plus `r` for
rows read during the initial snapshot), `before` and `after`. After the
delete, notice **two** messages.

<details>
<summary>Hint · Why two messages for a delete?</summary>

The first is the delete event (`op: d`, `after: null`). The second has
the same key and a **null value**: a *tombstone*. It tells Kafka log
compaction "this key is gone", so a compacted topic eventually forgets
the row. Your consumer must accept null values without crashing.

</details>

<details>
<summary>Hint · Why is `before` almost empty on delete and update?</summary>

By default Postgres logs only the **primary key** of the old row
(`REPLICA IDENTITY DEFAULT`). If downstream needs the full old row
(e.g. "which slot was the dropped player in?"), run
`alter table rosters replica identity full;` and repeat. It costs more
WAL. Note whether you need it.

</details>

✅ **Checkpoint:** you've seen `r`, `c`, `u`, `d` and a tombstone with
your own eyes, and you can explain each.

### 5. Apply the changes downstream (by hand, 60 min)

`streaming/cdc/apply_changes.py` consumes `fantasy.public.rosters` and
maintains the **current** roster in a downstream table, say a DuckDB file
`.data/fantasy_replica.duckdb` table `rosters_current`.

Rules to implement:

- `r` / `c`: insert `after`
- `u`: replace the row by key with `after`
- `d`: delete by key (use the message **key**, which works whatever the
  replica identity)
- tombstone (null value): nothing to do (the delete already happened)

<details>
<summary>Hint · Make it idempotent</summary>

The consumer is at-least-once (M8.1): after a crash it may re-apply
events. "Insert" as an **upsert** by primary key, and "delete" of a
missing row as a no-op, make re-application harmless.

</details>

<details>
<summary>Solution · apply function (open only after you have your own)</summary>

```python
import json
from typing import Any

import duckdb


def apply_change(con: duckdb.DuckDBPyConnection, key: bytes, value: bytes | None) -> None:
    """Apply one Debezium change event to rosters_current. Safe to re-apply."""
    if value is None:  # tombstone: the delete event already ran
        return
    payload: dict[str, Any] = json.loads(value)["payload"]
    op = payload["op"]
    if op in ("r", "c", "u"):
        row = payload["after"]
        con.execute(
            """insert into rosters_current (fantasy_team_id, athlete_id, slot, acquired_at)
               values (?, ?, ?, ?)
               on conflict (fantasy_team_id, athlete_id) do update set
                 slot = excluded.slot, acquired_at = excluded.acquired_at""",
            [row["fantasy_team_id"], row["athlete_id"], row["slot"], row["acquired_at"]],
        )
    elif op == "d":
        pk = json.loads(key)["payload"]  # the key carries the primary key columns
        con.execute(
            "delete from rosters_current where fantasy_team_id = ? and athlete_id = ?",
            [pk["fantasy_team_id"], pk["athlete_id"]],
        )
```

This assumes the default JSON converter with schemas enabled (hence
`["payload"]`). `acquired_at` arrives as an epoch number in microseconds
by default, so convert it in your version; that's a classic CDC type gotcha.

</details>

### 6. Prove insert, update and delete all arrive (30 min)

1. Run `seed_fantasy.py --moves 200 --seed 7` while `apply_changes.py` runs.
2. Stop the moves. Compare source and replica:

   ```sql
   -- run against both and diff, or attach Postgres to DuckDB with its postgres extension
   select fantasy_team_id, athlete_id, slot from rosters order by 1, 2;
   ```

3. Count by `op` in what the consumer processed: the seed log says how
   many adds, drops and slot changes it made. The counts should match.
4. Kill the consumer mid-run, restart it, and repeat the comparison.

✅ **Checkpoint:** source and replica identical after 200 moves and a
restart; non-zero counts for `c`, `u` and `d`.

PR with `Closes #114`. Include the op counts and the comparison result.

## Gotchas

- **Tables without a primary key** produce change events without a usable
  key, and updates/deletes can't be applied reliably downstream. Debezium
  warns; your schema shouldn't need it to.
- **Replication slots hold WAL.** If the connector stops for a long time,
  Postgres keeps WAL for the slot and the disk grows. After the lab:
  `select slot_name, active from pg_replication_slots;` and drop unused ones.
- **Initial snapshot.** On first start, Debezium reads every existing
  row as `op: r`. Re-registering under a new name re-snapshots everything.
- **Types.** Timestamps, decimals and dates are encoded (epoch numbers,
  base64 bytes) depending on converter settings. Check one of each before
  writing the consumer.
