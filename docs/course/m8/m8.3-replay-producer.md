# M8.3 · Game replay producer with chaos

> **Ticket:** [#109](https://github.com/Dfscashline21/sideline/issues/109) ·
> **Mode:** agent: the agent drafts, you review it like a junior's PR ·
> **Time:** 2 to 3 hours · **Needs:** M8.2, practice data from M1.2 (or M4's `raw.pbp`)

## Why this matters

You can't wait for a real NBA game every time you test a streaming job.
A **replay producer** turns a finished game into a live feed you control:
play it at 10x, make it misbehave on purpose, and run it again with
exactly the same misbehaviour. Every lab after this one depends on it,
so the review matters more than usual.

The "chaos" part is the point. Real feeds are late and out of order; a
job that only works on a perfect feed is a job you haven't tested.

## What you'll produce

`streaming/producer/replay.py`, a CLI that publishes one historical game
to `game-events`:

```bash
uv run python streaming/producer/replay.py --game-id 401584089 --speed 10 \
    --late-fraction 0.05 --max-delay 60 --seed 42
```

- **Configurable speed** (1x, 10x, 60x…) and **disorder** (how many
  events are delayed, by how much, reproducible with a seed).
- **Event time in every message**: in the Avro body (`event_time`) and
  as the Kafka message timestamp.

## Steps

### 1. Write the spec (yourself, 20 min)

Decide these before prompting. Write them in `streaming/README.md`:

- **Source:** which table, which columns, how events are ordered
  (`game_play_number`) and what to do with a missing `wallclock` (there's
  one in the 2023-24 season).
- **Pacing:** sleep between events = (gap in `wallclock`) / speed. A
  timeout or review stoppage can leave a long gap: cap the sleep (say
  10 seconds of real time) or you'll stare at a silent feed.
- **Disorder model:** pick a fraction of events and hold each back for a
  random delay before sending. Is the delay measured in **real seconds** or
  **event seconds**? (See Gotchas: decide on event seconds.)
- **Key:** `game_id`, so one game stays in one partition.
- **End of game:** send a final marker event (`event_type = "End Game"`
  already exists in the data) so downstream windows can close.

### 2. Prompt the agent

> Write `streaming/producer/replay.py` for this repo. It replays one NBA
> game from `.data/practice.duckdb` table `nba_pbp` (columns: `id`,
> `game_id`, `game_play_number`, `wallclock` ISO-8601 UTC string, …) to
> Kafka topic `game-events` on `localhost:19092`, serialising values with
> the Avro schema in `streaming/schemas/game_event.avsc` via the schema
> registry at `http://localhost:18081`, using `confluent-kafka`'s
> `SerializingProducer` / `AvroSerializer`.
>
> Requirements: *(paste your spec)*. CLI flags with argparse: `--game-id`,
> `--speed`, `--late-fraction`, `--max-delay` (seconds of **event time**),
> `--seed`, `--dry-run` (print instead of sending). Set the Kafka message
> timestamp to the event time. Use `enable.idempotence=True`. Log one line
> per 50 events and a summary at the end (events sent, how many delayed,
> largest delay). Fully typed for mypy strict, no global mutable state,
> under ~150 lines. Explain how you schedule delayed events.

Add the dependency the right way: `uv add confluent-kafka[avro]`. Check
the lockfile diff is small and explainable.

### 3. Review it like a pull request

| Review question | What a good answer looks like |
|---|---|
| How are delayed events scheduled? | A priority queue (`heapq`) of `(release_time, event)`; each loop sends everything whose release time has passed. Not a thread per event, not `sleep(delay)` that blocks the whole feed |
| Is the delay in event time? | Real delay = event-time delay ÷ speed. At 10x, a 60-second event-time delay is held back 6 real seconds |
| Is it reproducible? | One `random.Random(seed)` instance passed around, not the global `random` |
| Where is event time set? | `event_time` field from `wallclock`, and `timestamp=` on `produce()` in milliseconds |
| What happens on exit? | `producer.flush()` before the process ends, and Ctrl-C handled cleanly. Otherwise the last events are lost |
| Delivery errors? | A delivery callback that logs failures. Silent `produce()` calls hide broker errors |
| Does pacing use real gaps? | Sleep is based on gaps between consecutive `wallclock`s, capped; not a fixed `sleep(0.1)` |

<details>
<summary>Hint · Why a heap and not threads</summary>

With threads, two delayed events can be released in a different order
every run (thread scheduling), so the run isn't reproducible. A
single-threaded loop over a heap releases them in a deterministic order
for a given seed. Reproducibility is what makes M8.5's test possible.

</details>

### 4. Verify the feed

Dry-run first, then for real:

```bash
uv run python streaming/producer/replay.py --game-id 401584089 --speed 600 --dry-run | head
uv run python streaming/producer/replay.py --game-id 401584089 --speed 60 --late-fraction 0.05 --max-delay 60 --seed 42
docker compose exec redpanda rpk topic consume game-events -n 5 -f '%k %d %v\n'
```

Then check the three properties with a small script or by eye:

1. **Count:** messages on the topic for this game = rows in `nba_pbp` for
   it (474 for game 401584089, which has one `wallclock` per row). Delete and
   recreate the topic between runs, or count only your run's offsets.
2. **Disorder:** with `--late-fraction 0` the arrival order matches
   `sequence`; with 0.05, about 5% arrive after events that happened later.
3. **Reproducible:** the same seed gives the same arrival order twice.

✅ **Checkpoint:** at 60x the game takes about two minutes; Redpanda
Console (or `rpk topic consume`) shows the message timestamp equal to
`event_time`.

## Gotchas

- **Event-time vs real-time delay.** If `--max-delay` were real seconds,
  changing `--speed` would silently change how late events are in event
  time, and your M8.5 tests would behave differently at 10x and 60x.
  Define chaos in event time; derive the real delay.
- **The source is already slightly out of order.** About 0.8% of
  2023-24 events have a `wallclock` earlier than the previous event.
  Don't "fix" this in the producer; sort by `game_play_number` and
  let the stream job cope.
- **A clock gap isn't an error.** Halftime is about 15 minutes of real
  time. At 10x that's 90 seconds of silence unless you cap sleeps.
- **`linger.ms` batching.** The client batches messages for a few
  milliseconds by default. Harmless here, but it's why `flush()` matters.
