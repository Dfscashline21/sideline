# M8.7 · Iceberg sink every minute

> **Ticket:** [#113](https://github.com/Dfscashline21/sideline/issues/113) ·
> **Mode:** hand · **Time:** 3 to 5 hours ·
> **Needs:** M8.1 session 3, M8.4, your Iceberg REST catalog from M4.2, M7.5 (Spark + Iceberg)

## Why this matters

"How do you get exactly-once into a lake?" is one of the most common
senior streaming questions. The honest answer has three parts, and this
lab makes you build and test each:

1. a **replayable source** (Kafka offsets, saved in a checkpoint)
2. a **deterministic** job
3. a sink that is either **transactional** (commits output and progress
   together) or **idempotent** (writing the same thing twice changes nothing)

The acceptance criterion is blunt: kill the job mid-stream, restart it,
and find **no duplicates**.

## What you'll produce

- `streaming/jobs/iceberg_sink.py`: appends `game-events` to the Iceberg
  table `raw.live_game_events` once a minute.
- A restart test showing every `event_id` appears exactly once.
- A short write-up of *why* it's exactly-once (or what makes it idempotent).

## Steps

### 1. Create the table (30 min)

Streaming writes to Iceberg need the table to exist first. Create
`raw.live_game_events` in your M4 catalog with the event columns from
`game_event.avsc`, plus `ingested_at` (timestamp) and the Kafka
`partition` and `offset`.

Decide the partition spec. Every minute adds one small commit, so the
spec decides how many small files you create. `day(event_time)` is a
sensible start. Why would `game_id` alone be a poor choice for a table
that will hold many seasons?

Spark configuration for a REST catalog (adapt the names and ports to
what you built in M4.2):

### 3. Break it on purpose (45 min)

The test that matters. Script it so you can rerun it:

1. Fresh topic, fresh table (or `delete from`), fresh checkpoint.
2. Start the producer at 10x and the sink job.
3. After two or three commits, **kill the sink job hard** (`kill -9` on
   the Spark driver's Python process, not Ctrl-C). A clean shutdown proves
   nothing.
4. Restart the sink with the same checkpoint. Let the game finish.
5. Check: total rows, distinct `event_id`s, and any `event_id` with
   `count(*) > 1`.

Kill at different moments over several runs, including right after a
"Committed" log line, the most dangerous moment.

<details>
<summary>Hint 1 · Where could a duplicate come from?</summary>

Spark records each micro-batch's offsets in the checkpoint **before**
running it, and marks it committed **after** the sink finishes. If the
job dies after the sink committed to Iceberg but before Spark wrote its own
"commit" marker, the restart re-runs that batch with the same batch ID.
What stops the second Iceberg append?

</details>

<details>
<summary>Hint 2 · Look inside the snapshots</summary>

```sql
select committed_at, snapshot_id, summary
from lake.raw.live_game_events.snapshots
order by committed_at;
```

Look in `summary` for properties naming the streaming query and its
epoch (batch) ID. A sink that records "batch N of query Q is committed"
**inside the same atomic commit as the data** can skip batch N if it's
replayed. That's the transactional pattern. Find the evidence yourself
and quote it in your write-up rather than trusting this hint.

</details>

✅ **Checkpoint:** after at least three hard kills, zero duplicate `event_id`s.

### 4. Build the idempotent version yourself (60 to 90 min)

Relying on a sink's internals is fine, but you should be able to build the
guarantee yourself. It's the version you'd need for a sink without it
(Postgres, an API), and the one interviewers want you to describe.

Rewrite the sink with `foreachBatch` and a `MERGE INTO` keyed on `event_id`.

<details>
<summary>Hint · Skeleton</summary>

```python
def write_batch(batch: DataFrame, batch_id: int) -> None:
    batch.dropDuplicates(["event_id"]).createOrReplaceTempView("incoming")
    batch.sparkSession.sql("""
        merge into lake.raw.live_game_events t
        using incoming s
        on t.event_id = s.event_id
        when not matched then insert *
    """)
```

`foreachBatch` is at-least-once by itself; the `MERGE` is what makes a
replayed batch harmless. Why is `dropDuplicates` inside the batch needed
as well?

</details>

Run the same kill test. Then compare the two versions in your write-up:
cost per minute (a `MERGE` has to find matches; an append doesn't), and
what each one depends on.

<details>
<summary>Solution · idempotent sink (open only after you have your own)</summary>

```python
"""Append game-events to Iceberg every minute, idempotent on event_id (M8.7)."""

from pathlib import Path

from pyspark.sql import DataFrame, SparkSession
from pyspark.sql import functions as F
from pyspark.sql.avro.functions import from_avro

SCHEMA = Path("streaming/schemas/game_event.avsc").read_text()
TABLE = "lake.raw.live_game_events"


def write_batch(batch: DataFrame, batch_id: int) -> None:
    # One micro-batch can contain the same event twice (producer retry): dedup first,
    # then MERGE so a replayed batch after a crash inserts nothing new.
    batch.dropDuplicates(["event_id"]).createOrReplaceTempView("incoming")
    batch.sparkSession.sql(f"""
        merge into {TABLE} t
        using incoming s
        on t.event_id = s.event_id
        when not matched then insert *
    """)


def main(spark: SparkSession) -> None:
    raw = (
        spark.readStream.format("kafka")
        .option("kafka.bootstrap.servers", "localhost:19092")
        .option("subscribe", "game-events")
        .option("startingOffsets", "earliest")
        .load()
    )
    events = raw.select(
        from_avro(F.expr("substring(value, 6, length(value) - 5)"), SCHEMA).alias("e"),
        "partition",
        "offset",
    ).select("e.*", "partition", "offset", F.current_timestamp().alias("ingested_at"))
    (
        events.writeStream.foreachBatch(write_batch)
        .trigger(processingTime="1 minute")
        .option("checkpointLocation", ".data/checkpoints/iceberg_sink")
        .start()
        .awaitTermination()
    )
```

The `MERGE` needs the column order of `incoming` to match the table for
`insert *`; select columns explicitly if yours differ. The cost of the
`MERGE` grows with the table. Narrowing the `on` clause with the
partition column (`and t.event_time >= <batch min>`) lets Iceberg prune
files. Try it and measure.

</details>

## Gotchas

- **Small files.** A commit every minute for a whole season is ~500k
  snapshots and many tiny files. Note that M4.7's compaction and snapshot
  expiry now need scheduling (M6 orchestration).
- **Deleting the checkpoint = replaying everything.** With the append
  version, that duplicates the whole table. With `MERGE`, it's slow but
  safe. Know which one you're running before you delete one.
- **`kill -9` the right process.** With local Spark, the JVM is a child
  of your Python process. Kill the Python process; check with `ps` that
  no orphaned `java` remains holding the checkpoint.
- **Version matrix.** The Iceberg runtime is per Spark minor version
  (`iceberg-spark-runtime-4.1_2.13`). A PySpark upgrade that outruns it
  fails at startup with class errors.
