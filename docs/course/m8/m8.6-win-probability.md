# M8.6 · Live win-probability feed

> **Ticket:** [#112](https://github.com/Dfscashline21/sideline/issues/112) ·
> **Mode:** mixed: model and ordering logic by hand, Kafka plumbing by agent ·
> **Time:** 3 to 4 hours · **Needs:** M8.3; M8.4 helps but isn't required

## Why this matters

This is the part of the demo people remember: a line that swings with
every basket. The engineering lessons are less flashy and more useful:

- **Latency budget.** "Within seconds of each event" rules out some
  designs (a Spark job with a 30-second trigger) and allows others.
- **Out-of-order events.** A late event carries an *old* score. Applied
  naively, it makes the probability jump backwards in time.
- **Model honesty.** A simple model you've measured beats a clever one
  you haven't. You'll backtest it on a full season before trusting it.

## What you'll produce

- `streaming/jobs/win_probability.py`: consumes `game-events`, emits one
  message per event to `win-probability`: `game_id`, `event_id`,
  `event_time`, `home_win_prob`, `margin`, `seconds_remaining`.
- `ml/win_prob_backtest.py` (or a notebook-free script): the model's
  calibration on a past season.
- A latency measurement showing updates arrive within seconds.

## Steps

### 1. The model (by hand, 60 min)

A classic, simple model treats the remaining score margin as a random
walk. With `m` = home margin now, `f` = fraction of regulation left
(`seconds_remaining / 2880`), `σ` = spread of final margins, and `h` =
home advantage in points:

```
P(home wins) = Φ( (m + h·f) / (σ·√f) )
```

`Φ` is the standard normal CDF. Intuition: early on, `√f` is large and a
10-point lead means little; with 30 seconds left, the same lead is nearly
certain.

Estimate `σ` and `h` yourself from `nba_team_box` (home rows, regular
season): the standard deviation and mean of final margin. Measured for
2022 to 2026: σ between 13.7 and 16.4, mean home margin between 1.6 and
2.5 points.

<details>
<summary>Hint 1 · Φ without SciPy</summary>

`Φ(x) = 0.5 · (1 + erf(x / √2))`, and `math.erf` is in the standard
library.

</details>

<details>
<summary>Hint 2 · The edges</summary>

At `f = 0` the formula divides by zero. End of regulation: return 1, 0,
or 0.5 for a tie (overtime). In overtime, treat each 5-minute period as
its own short game: what is `f`, and what's the right `σ`? A defensible
simplification is fine if you document it.

</details>

<details>
<summary>Solution · probability function (open only after you have your own)</summary>

```python
import math

REGULATION_SECONDS = 2880.0


def home_win_prob(
    margin: float, seconds_remaining: float, sigma: float = 15.0, home_edge: float = 2.0
) -> float:
    """Random-walk win probability for the home team, regulation only."""
    if seconds_remaining <= 0:
        return 1.0 if margin > 0 else 0.0 if margin < 0 else 0.5
    frac = seconds_remaining / REGULATION_SECONDS
    z = (margin + home_edge * frac) / (sigma * math.sqrt(frac))
    return 0.5 * (1.0 + math.erf(z / math.sqrt(2.0)))
```

</details>

### 2. Backtest it (by hand, 60 min)

Run the function over every regulation event of a season you **didn't**
use to pick σ (e.g. fit on 2022 to 2024, test on 2025). Report:

- **Brier score**: mean of `(p − outcome)²`. A coin flip scores 0.25.
- **Calibration table**: bucket predictions into tenths; compare the
  average prediction with the actual home-win rate in each bucket.

✅ **Checkpoint:** for reference, with σ = 15 and h = 2 on the 2024-25
regular season (575,664 events), the Brier score was 0.166 (coin flip
0.250) and σ = 18 did slightly better (0.165). The calibration table
showed the model **overconfident** at the edges: predictions near 0.75
won about 69% of the time. Get your own numbers; write one paragraph on
what you'd improve (possession, timeouts, team strength) and why you
won't yet.

### 3. The out-of-order rule (by hand, 30 min)

Each event carries the score **at that moment**, so the probability is
computable from one event, without state. But the *feed* needs a rule.
Suppose event 300 (score 98–95, 2:10 left) arrives after event 305
(score 100–97, 1:30 left). What should a viewer see?

Decide and implement one rule, then justify it in the module notes:

- emit only if `event_time` ≥ the last emitted `event_time` for this game
  (late events update nothing live, but still go to the Iceberg sink in M8.7), or
- emit everything and let the chart sort by event time.

<details>
<summary>Hint · Where the state lives</summary>

A dict `{game_id: last_emitted_event_time}` in the consumer process is
enough for a demo. Say in the notes what's lost on restart (the dict is
empty, so the first event after a restart is always emitted) and why
that's acceptable here.

</details>

### 4. Choose the runtime (decision, 20 min)

The criterion is "within seconds". Options:

| Option | Latency | Notes |
|---|---|---|
| Plain Python consumer (`confluent-kafka`) | Milliseconds per event | Stateless per event: no need for a big engine |
| Spark Structured Streaming, `processingTime` trigger | At least the trigger interval, plus batch overhead | Reuses M8.4 but adds latency |
| Spark real-time / continuous modes | Lower, with feature restrictions | Check what your Spark version supports for your operators before relying on it |

Pick one and write a sentence in `streaming/README.md`. The labs assume
the plain Python consumer. It's a good answer to "when *not* to use a
stream processor".

### 5. Agent: the plumbing

> Write `streaming/jobs/win_probability.py` for this repo: a
> `confluent-kafka` consumer of `game-events` (Avro, schema registry at
> `http://localhost:18081`, consumer group `win-probability`) that, for each
> event, calls `home_win_prob(margin, seconds_remaining)` from
> `streaming/jobs/win_model.py` (I wrote it) and my `should_emit(state,
> event)` rule, then produces an Avro message to `win-probability` keyed by
> `game_id` with fields game_id, event_id, event_time, home_win_prob,
> margin, seconds_remaining, emitted_at. Register the new schema. Commit
> consumer offsets **after** producing. Typed, under ~120 lines, graceful
> shutdown on Ctrl-C.

Review checklist:

| Question | Good answer |
|---|---|
| When are offsets committed? | After the output is produced (at-least-once): a crash can repeat a probability, never skip one. Is a repeated probability harmful here? |
| Is your code called, unchanged? | The model and the rule live in your module; the agent only imports them |
| Is `emitted_at` set by the job? | Yes: wall clock when producing. You need it for step 6 |
| `auto.offset.reset`? | `earliest` for replays, or you miss the start of a game you start consuming late |

### 6. Measure latency (45 min)

For each output message, latency = `emitted_at` − **arrival time of the
input** (the input's Kafka timestamp is event time, not arrival, so log
arrival in the job or use the broker's append time). Replay the test game
at 10x and report median and max latency.

✅ **Checkpoint:** median well under a second with the plain consumer;
max within a few seconds. If not, look for per-message `flush()` calls
or a schema-registry lookup per message (the serializer should cache).

PR with `Closes #112`, including the backtest numbers, calibration
table and latency numbers.

## Gotchas

- **`seconds_remaining` vs the clock string.** Use the numeric
  `start_game_seconds_remaining` (or your schema's equivalent), not
  `clock_display_value`, which resets every quarter.
- **Leakage in the backtest.** Fitting σ on the same season you test on
  flatters the result. Fit on earlier seasons. (M12 makes this rigorous.)
- **Overtime.** The regulation formula breaks after 0:00 of the 4th. Don't
  let a tie at the buzzer produce a division by zero in the live demo.
