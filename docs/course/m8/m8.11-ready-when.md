## Why this matters

The M8 promise: *explain step by step what happens to a go-ahead
three-pointer that arrives 45 seconds late.* It sounds like one question.
It's actually your whole pipeline, from producer to lake, under the one
condition that breaks naive designs. If you can walk it end to end
without notes, you understand streaming. If you can only describe pieces,
you've learned tools.

- **No AI, no notes, no code open** until you've finished talking.

- Record yourself (phone is fine). Aim for 5 to 8 minutes.

## The scenario

Fourth quarter, 0:40 left. Home trails 101–103. At **21:58:20** (event
time) the home team hits a three: 104–103, the go-ahead basket.

The courtside feed hiccups. The event reaches `game-events` at
**21:59:05** processing time, 45 seconds after it happened. Meanwhile the
events that came *after* it on court (a timeout at 21:58:35, a missed
shot at 21:58:50, a rebound at 21:59:04) all arrived on time.

Your system is the one you built: 30-second watermark, 1-minute
event-time windows, the late-event router, the win-probability consumer,
the Iceberg sink.

## Steps

### 1. Walk it out loud (closed-book, 10 min)

Cover, in order, and **draw the timeline** with both time axes:

1. How the event gets onto the topic: key, partition, timestamp.
2. The watermark at the moment it arrives: compute it.
3. What your **late-event router** does with it, and why.
4. What the **windowed team-stats aggregation** does with it. Careful:
   which window does it belong to, and is that window's state still there?
5. What the **live scoreboard and win probability** show, before and after
   it arrives.
6. What lands in **Iceberg**, and what a batch box score built from
   Iceberg tomorrow says.
7. What an on-call engineer sees, and what they'd do.

### 2. Stress questions (closed-book, 5 min)

Answer each in one or two sentences:

- What changes if the threshold were 60 seconds? 10 seconds?
- What if this were the **only** event for two minutes (the feed went
  quiet), and then it arrived?
- What if the producer retried and the event arrived **twice**?

<details>
<summary>Model walkthrough (open after you've finished talking)</summary>

**1. Onto the topic.** The producer serialises with the registered Avro
schema; key = `game_id`, so it lands in the same partition as the rest of
the game, **after** the rebound (offset order ≠ event-time order). The
message timestamp is the event time, 21:58:20.

**2. The watermark.** Newest event time seen before it: the rebound at
21:59:04. Watermark ≈ 21:59:04 − 30 s = **21:58:34**. In Spark, the
watermark computed at the end of the previous micro-batch is the one in
force, so it may be a little behind that. The event (21:58:20) is about
14 seconds behind the watermark: **late**.

**3. The router (M8.5).** Per-game max event time 21:59:04; the event is
44 seconds behind it, which is more than 30. It goes to `game-events-dlq`
with the original bytes and headers `reason=late`,
`lateness_seconds=44`. Decision made in offset order, so it's the same
whatever the batch boundaries.

**4. The windowed aggregation.** The event belongs to the window
**[21:58:00, 21:59:00)**. Spark keeps a window's state until the
watermark passes the window's **end**. The end, 21:59:00, is still
*after* the watermark (21:58:34), so the window is open and Spark
**does count** the 3 points, and the update-mode sink corrects that
window's row. The router also dead-lettered it. That's the grey zone from
M8.5: "late" per event vs "too late" per window are different tests.
Saying this unprompted is the senior signal. Your M8.5 write-up says
which rule you made authoritative.

**5. Scoreboard and win probability.** Before arrival, the scoreboard
already showed 104–103: the timeout, miss and rebound each carry the
running score, which includes the three. So the score was right; only
the *event itself* was missing from the play list. Win probability, too,
was computed from those later events' scores. When the late event
arrives, your `should_emit` rule (event time older than the last emitted)
suppresses it, so the line doesn't jump backwards to 0:40.

**6. Iceberg.** The sink doesn't use the watermark; it lands every event.
The event is in `raw.live_game_events` within a minute, once (the `MERGE`
on `event_id`, or the sink's commit metadata, prevents a duplicate). A
batch box score from Iceberg tomorrow is correct, which is why the lake,
not the live view, is the source of truth.

**7. On call.** The DLQ count goes from 0 to 1; dashboard panel and an
alert on DLQ rate (not a page for a single event; M9 is about alert
fatigue). The action: confirm the batch layer has it (it does), decide
whether the live window needs correcting (it was already counted), and
look at feed health if the DLQ rate keeps rising.

**Stress answers.** 60 s threshold: not late anywhere; counted
normally; more state held. 10 s: late for both router and window
(window end 21:59:00 < watermark 21:58:54), so dropped from live stats,
in the DLQ, still in Iceberg. Quiet feed: the watermark doesn't move
without new data, so with nothing newer seen, the event isn't late at
all. Watermarks are data-driven. Duplicate: counted twice in the windowed
stats (they're not idempotent per event; a dedup by `event_id` with a
watermark-bounded state would fix it), once in Iceberg (`MERGE`).

</details>
