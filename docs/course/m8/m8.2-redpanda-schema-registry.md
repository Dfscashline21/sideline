# M8.2 · Redpanda and Schema Registry in Compose

> **Ticket:** [#108](https://github.com/Dfscashline21/sideline/issues/108) ·
> **Mode:** agent: the agent drafts, you review it like a junior's PR ·
> **Time:** 2 to 3 hours · **Needs:** M0.3 (Compose), M8.1 session 3

## Why this matters

A streaming system is only as reliable as its **contract**. Without a
schema registry, a producer can rename a field on a Friday and every
consumer breaks over the weekend. With one, the bad schema is
**rejected at publish time**. That's the second acceptance criterion,
and it's the exact story interviewers want: "how do you stop producers
breaking consumers?"

Redpanda speaks the Kafka API and ships a Confluent-compatible schema
registry in the same binary, so one container replaces Kafka, ZooKeeper
or KRaft, and a separate registry.

## What you'll produce

- `redpanda` (and optionally `redpanda-console`) services in `compose.yaml`.
- `streaming/schemas/game_event.avsc`: the Avro schema for `game-events`.
- A topic `game-events` (plus `game-events-dlq`) with the schema
  registered under subject `game-events-value`.
- Proof that an incompatible change is rejected.

## Steps

### 1. Design the event schema first (by hand, 30 min)

The agent can write YAML; it can't decide what a game event *is*. Write
`streaming/schemas/game_event.avsc` yourself. Fields to decide, from the
[replay data columns](README.md#the-replay-data):

- `event_id` (long): the ESPN `id`, unique per event, used for dedup later
- `game_id`, `sequence` (`game_play_number`)
- `event_time`: Avro `long` with `logicalType: timestamp-millis`, from `wallclock`
- `period`, `clock` (string), `seconds_remaining` (double)
- `team_id` (nullable: some events have no team)
- `event_type` (`type_text`), `scoring_play` (boolean), `score_value` (int)
- `home_score`, `away_score`, `home_team_id`, `away_team_id`
- `league` (string, default `"nba"`), ready for WNBA

<details>
<summary>Hint · Avro nullable fields</summary>

A nullable field is a union with `null` **first**, plus a default of
`null`: `{"name": "team_id", "type": ["null", "int"], "default": null}`.
Getting the order wrong makes the default invalid.

</details>

✅ **Checkpoint:** you can say, for every field, what consumer needs it.

### 2. Decide the compatibility rule

Read the [Confluent schema evolution rules](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)
(Redpanda implements the same API). Pick one for `game-events-value` and
write why in `streaming/README.md`:

- `BACKWARD` (the default): consumers on the **new** schema can read data
  written with the **old** one. Upgrade consumers first.
- `FORWARD`: old consumers can read new data. Upgrade producers first.
- `FULL`: both.

For a live feed where the replay producer and several jobs evolve at
different speeds, which one do you want?

### 3. Prompt the agent

> Add Redpanda to this repo's `compose.yaml` for local development. Use
> image `docker.redpanda.com/redpandadata/redpanda:v26.2.7` in
> `--mode dev-container` with `--smp 1`. Two Kafka listeners: internal
> `redpanda:9092` for other containers and external `localhost:19092` for
> my laptop. Enable the schema registry on internal 8081 / external 18081.
> Add a healthcheck using `rpk cluster info`, a named volume, and follow
> the existing style (comments per service, ports from `.env` with
> defaults, update `.env.example`). Optionally add Redpanda Console
> (`docker.redpanda.com/redpandadata/console:v3.14.0`) on port 8080.
>
> Then write `streaming/setup_topics.sh` that is safe to re-run: creates
> topics `game-events` and `game-events-dlq` (3 partitions, 1 replica) with
> `rpk`, sets compatibility for subject `game-events-value` to
> *(your choice)*, and registers `streaming/schemas/game_event.avsc`.
> Add `make streaming-up` in the Makefile's style. Don't add a
> Python dependency for this step.

Read `AGENTS.md` into the session first so it follows your conventions.

### 4. Review it like a pull request

| Review question | What a good answer looks like |
|---|---|
| Why two listeners and two advertised addresses? | Clients connect to the address the broker **advertises**. A laptop can't resolve `redpanda`; a container can't reach your `localhost` |
| Does `make up` still work and stay fast? | Redpanda is added to the stack, or behind a Compose profile so non-streaming work doesn't start it. Either is defensible: say which and why |
| Is the setup script idempotent? | Creating an existing topic doesn't fail the script; registering the same schema twice returns the same ID |
| How is the schema registered? | `rpk registry schema create game-events-value --schema streaming/schemas/game_event.avsc`, or a `curl` `POST /subjects/game-events-value/versions` |
| Are ports bound to `127.0.0.1`? | M0's known limitation #2. Worth fixing for new services |
| Any `latest` tags? | None. Exact versions only |

<details>
<summary>Hint · What dev-container mode does</summary>

It turns on settings meant for a laptop: relaxed fsync, auto topic
creation, small memory use. Never use it in production. Your ADR or
`streaming/README.md` should say so in one line.

</details>

### 5. Prove criterion 1: topic with a registered schema

```bash
make streaming-up
docker compose exec redpanda rpk topic list
docker compose exec redpanda rpk registry subject list
curl -s localhost:18081/subjects/game-events-value/versions/latest | python3 -m json.tool
```

✅ **Checkpoint:** both topics listed; subject `game-events-value` has
version 1 with your fields.

### 6. Prove criterion 2: an incompatible change is rejected

Make a copy of the schema with a **breaking** change for your chosen
rule. Under `BACKWARD`, adding a new field **without a default** breaks
it (new readers can't fill that field for old data). Test it without
registering, then try to register it:

```bash
# test only: should report is_compatible: false
curl -s -X POST -H 'Content-Type: application/vnd.schemaregistry.v1+json' \
  --data "$(jq -n --rawfile s /tmp/game_event_bad.avsc '{schema: $s}')" \
  localhost:18081/compatibility/subjects/game-events-value/versions/latest

# real attempt: should fail with HTTP 409
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  -H 'Content-Type: application/vnd.schemaregistry.v1+json' \
  --data "$(jq -n --rawfile s /tmp/game_event_bad.avsc '{schema: $s}')" \
  localhost:18081/subjects/game-events-value/versions
```

Then make a **compatible** change (a new nullable field with a default)
and show it registers as version 2. Save the commands and outputs in
`streaming/README.md` as evidence.

✅ **Checkpoint:** 409 for the bad schema, version 2 for the good one.

### 7. Ship it

```bash
make lint && make test
git switch -c m8.2-redpanda
git add compose.yaml .env.example Makefile streaming/
git commit -m "M8.2: Redpanda with schema registry and game-events schema"
gh pr create --fill        # Closes #108
```

Paste your review answers into the PR description.

## Gotchas

- **Port clashes.** Redpanda Console's default 8080 and the external 18081
  can clash with other local tools. `lsof -i :8080` before blaming Compose.
- **Wrong content type.** The registry API expects
  `application/vnd.schemaregistry.v1+json`. The schema itself is a JSON
  *string* inside the body, which is why `jq --rawfile` is used above.
- **Compatibility is per subject.** Setting a global default doesn't help
  if the subject already has its own override. Check with
  `GET /config/game-events-value`.
- **Machine resources.** Redpanda wants a few GB of memory per core in
  production. `--smp 1` and dev-container mode keep it small, but your
  stack now runs MinIO, Postgres, the catalog and a broker. Watch
  Docker's memory limit.
