# M8.1 · Study: event time, watermarks, delivery semantics

> **Ticket:** [#107](https://github.com/Dfscashline21/sideline/issues/107) ·
> **Mode:** hand · **Time:** 5 to 6 hours over several sessions ·
> **Needs:** nothing from M8. Paper and a pen are the main tools.

## Why this matters

Streaming interviews almost always come down to two questions: "what
happens to late data?" and "can you guarantee each event is counted
exactly once?" Most candidates answer with product names. Strong
candidates answer with a timeline drawn on a whiteboard. This lab gives
you the vocabulary and the drawings; M8.4 to M8.7 make you build them.

## What you'll produce

- `docs/notes/m8-cheatsheet.md`: one page in your own words.
- The ability to explain **at-least-once vs effectively-once** out loud,
  with a concrete failure, without notes. That's the ticket's acceptance
  criterion.

## Session 2 · Windows, triggers and watermarks (90 min)

Read Ch. 2 and Ch. 3, or "Streaming 102".

The four questions from the book, in your words:

- **What** are you computing? (sum of points)
- **Where** in event time? (1-minute tumbling windows; per game)
- **When** in processing time do you emit results? (triggers, watermark)
- **How** do later results relate to earlier ones? (replace, add, retract)

### Exercise 2.1: a watermark by hand

A watermark with a 30-second threshold: `watermark = max event time seen − 30 s`.
Using the five events above, in **processing order**, fill this table:

| Processing time | Event arriving | Max event time seen | Watermark after it | Is this event behind the watermark? |
|---|---|---|---|---|
| 19:10:02 | Jump ball | | | |
| 19:10:21 | Layup | | | |
| 19:10:56 | Foul | | | |
| 19:11:06 | Free throw | | | |
| 19:11:30 | 3-pointer | | | |

<details>
<summary>Check your table</summary>

Max event time seen goes 19:10:00 → 19:10:20 → 19:10:55 → 19:11:05 →
19:11:05 (the 3-pointer's 19:10:41 is older). Watermarks:
19:09:30, 19:09:50, 19:10:25, 19:10:35, 19:10:35.

The 3-pointer (19:10:41) arrives when the watermark is 19:10:35. It is
**not** behind the watermark, so it's on time for the system even though
it arrived 49 seconds after it happened. That's the subtle bit: lateness
is measured against **other events**, not against the wall clock. If the
feed had been quiet, even a very delayed event could still be "on time".

Now redo it with a 5-second threshold. The 3-pointer is late.

</details>

## Session 3 · Delivery semantics (90 min)

Read Ch. 5 and the Kafka semantics section.

The three guarantees, as the *effect* on your output:

| Name | Each event affects the result… | How you get it |
|---|---|---|
| At-most-once | 0 or 1 times | Commit the input offset **before** processing. Crash = lost |
| At-least-once | 1 or more times | Commit the offset **after** processing. Crash = reprocessed |
| Effectively-once ("exactly-once") | exactly 1 time, *as observed in the output* | At-least-once delivery **plus** dedup, an idempotent write, or a transaction that commits output and offset together |

"Exactly-once **delivery**" over a network isn't possible: a message can
always be resent after a lost acknowledgement. Systems that claim
exactly-once mean the *effect*. That's why many people say
"effectively-once".

### Exercise 3.1: the crash timeline

Draw a timeline for a consumer that reads event 41 (a 3-pointer), adds 3
to the home score in a database, and commits offset 42. Mark three crash
points:

1. after reading, before the database write
2. after the database write, before the offset commit
3. after the offset commit

For each crash point, and for each of "commit before" vs "commit after"
processing, what is the home score after restart?

<details>
<summary>Check your answer</summary>

Commit **after** processing (at-least-once): crash 2 replays event 41
and the score goes up by 6. That's the double-count. Crashes 1 and 3 are
fine.

Commit **before** processing (at-most-once): a crash after the commit
but before the write loses the 3 points.

Fix for crash 2: make the write idempotent (store `event_id`, upsert by
it, or set the score to the event's `home_score` instead of adding 3),
or write the result and the offset in **one** transaction. M8.7 builds
exactly this.

</details>

### Exercise 3.2: where Spark fits

The Spark guide says end-to-end exactly-once needs: a **replayable
source** (Kafka offsets), a **deterministic** computation, **checkpointed**
offsets and state, and an **idempotent or transactional sink**. For each
of these sinks, say whether it gives exactly-once output and why:
console, Kafka, a file/Iceberg sink, `foreachBatch` writing to Postgres.

<details>
<summary>Hint</summary>

The Kafka sink is at-least-once: a replayed micro-batch writes its
messages again. `foreachBatch` is at-least-once unless *your* code is
idempotent per `batch_id`. Iceberg's Spark streaming writes commit each
micro-batch as a snapshot; check in M8.7 how a replayed batch is
recognised.

</details>
