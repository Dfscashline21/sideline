# M1.7 · Read a query plan and make it 2x faster

> **Ticket:** [#32](https://github.com/Dfscashline21/sideline/issues/32) ·
> **Mode:** hand · **Time:** 2 to 3 hours ·
> **Needs:** M1.1 session 4, M1.6 merged

## Why this matters

"This query is slow, what do you do?" is a senior-level interview
question, and the wrong answer is "add an index" before you've looked at
anything. The right answer is a loop: **measure → read the plan → find
the expensive operator → change the work it does → measure again.** This
lab is one full turn of that loop, written up.

## What you'll produce

`docs/notes/m1.7-query-plan.md` with:

- before and after timings (median of several runs, conditions stated)
- the relevant parts of both plans
- one paragraph on what changed in the plan and why it's faster

Plus the faster query (and any supporting table) in `sql/problems/`.

## Steps

### 1. Measure properly (30 min)

A single timing is noise. Write a tiny harness, `sql/practice/bench.py`,
that runs a SQL file N times against `.data/practice.duckdb` and prints
the median. Write it yourself; it's about 15 lines with `time.perf_counter`
and `statistics.median`.

<details>
<summary>Hint · What the harness must do</summary>

- Run the query once to warm up (first runs pay for loading data into
  memory) and throw that timing away.
- Then run it 7 to 9 times, call `.fetchall()` so the result is actually
  produced, and report the median.
- Optional flag to run with `SET threads = 1`, which makes CPU cost
  easier to compare (see Gotchas).

</details>

Run your M1.6 query through it. Record: median time, thread setting,
your laptop model, and whether other heavy apps were running.

✅ **Checkpoint:** on a recent laptop expect tens of milliseconds
multi-threaded, and several times that single-threaded. DuckDB is fast.
That's why you have to be precise about measurement.

### 2. Read the plan (45 min)

```sql
explain analyze <your M1.6 query>;
```

Read it **bottom-up**. For each operator, note:

| Operator | Rows in → out | Time | What it's doing |
|---|---|---|---|
| `TABLE_SCAN` | | | |
| `FILTER` | | | |
| `HASH_GROUP_BY` | | | |
| `WINDOW` | | | |
| … | | | |

Questions to answer in your notes:

1. How many rows does the scan read, and how many survive to the window?
   (Roughly: 3.3M in the table, ~2.2M out of the scan, ~45k into the
   window, 57 out.)
2. Did the `season_type = 2` filter get pushed down into the scan? Look
   for it inside the `TABLE_SCAN` box rather than as a separate `FILTER`.
3. Which operator costs the most? Is it the window function you were
   worried about, or something earlier?

<details>
<summary>Hint · Reading the times</summary>

Per-operator times in DuckDB's `EXPLAIN ANALYZE` are **CPU time summed
across threads**, so they can add up to more than the "Total Time" at
the top. Compare operators with each other, not with the total. Running
with `SET threads = 1` makes them add up more intuitively.

</details>

### 3. Form a hypothesis (15 min)

Write one sentence before changing anything: *"Most of the time goes to
X, because it processes Y rows; if I change Z, X will do less work."*

<details>
<summary>Hint 1 · Nudge</summary>

The window function only sees ~45k rows. What sees all 3.3M? Does that
work need redoing every time you run the query? The underlying games
from 2008 to 2026 don't change.

</details>

<details>
<summary>Hint 2 · Approach</summary>

The scan and the aggregation (game rows → player-season rows) dominate.
They produce the same answer every time. **Precompute them once** into a
summary table (`ncaa_player_season`: one row per player per season),
then point the ranking query at that table. The query's plan then
starts from ~150k rows instead of 3.3M.

This is exactly what a dbt mart is (M5): a table built once by the
pipeline so every consumer query is cheap. In testing, this cut a ~18 ms
query to ~9 ms multi-threaded, and ~70 ms to ~10 ms single-threaded.

</details>

### 4. Make the change and re-measure (30 min)

Implement your hypothesis. Run the same harness under the same
conditions. Then run `EXPLAIN ANALYZE` again and compare the trees: which
operators disappeared, and how did the row counts change?

Check the results are **identical** before you celebrate:

```sql
(select * from (<old query>)) except (select * from (<new query>));
-- and the reverse direction
```

Zero rows both ways. (If TS% differs in the last decimal places, round
both to 4 places before comparing. Floating-point sums can differ in
the last bits depending on the order rows are added.)

✅ **Checkpoint:** median at least 2x faster, identical results.

### 5. Try at least one lever that *doesn't* help

You learn as much from a hypothesis that fails. Pick one, measure it and
record it in the notes:

- Group by IDs only and look names up after ranking (moves string work
  later). Does it matter here?
- Query a Parquet file instead of the DuckDB table (`COPY ncaa_player_box
  TO 'x.parquet'`, then `read_parquet`). Faster or slower, and why?
- If your M1.6 first draft used a correlated subquery, time that version
  against the window version. It's often 4 to 5x slower.

### 6. Write it up

`docs/notes/m1.7-query-plan.md`. A structure that works:

```markdown
# M1.7: Speeding up the TS% top-3 query

## Setup
Laptop, DuckDB version, threads, runs per measurement, data size.

## Before
Median: __ ms. Plan excerpt (the operators that matter). Most expensive: __.

## Hypothesis
One sentence.

## Change
What I did.

## After
Median: __ ms (__x). Plan excerpt. What disappeared from the plan and why.

## What didn't help
Lever, numbers, why.

## Trade-off
What the faster version costs. (Hint: the summary table must be rebuilt
when data changes. Who does that, and how stale can it be?)
```

Commit the summary-table SQL and the faster query alongside your M1.6
file. PR with `Closes #32`.

## Gotchas

- **The cache is warm after the first run.** Always discard the first timing.
- **Laptop noise.** Close the browser, plug in power (battery saver
  throttles the CPU), and run before/after back to back.
- **Read-only connections.** Open `.data/practice.duckdb` with
  `read_only=True` in the harness so it can't lock the file while you
  rebuild tables in another shell.

## Done when

- [ ] Before and after medians recorded, conditions stated, ≥2x faster
- [ ] Results proven identical (`EXCEPT` both ways)
- [ ] Write-up explains what changed in the plan, with excerpts
- [ ] One lever that didn't help, measured
- [ ] PR merged with `Closes #32`
