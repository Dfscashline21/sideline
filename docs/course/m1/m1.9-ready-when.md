# M1.9 · Ready-when check (closed-book)

> **Ticket:** [#34](https://github.com/Dfscashline21/sideline/issues/34) ·
> **Mode:** hand, closed-book · **Time:** 45 min ·
> **Needs:** M1.8 done (all 25 problems)

## Why this matters

The M1 promise: *solve a medium window-function problem in 15 minutes on
a whiteboard and explain its plan.* That's a live interview round. If
you can only do it with the docs open, the module hasn't stuck yet, and
it's far better to find that out now than in an interview.

## The rules

- **No AI, no notes, no docs, no running queries** until the timer stops.
- Paper or a whiteboard (or a plain text editor with no autocomplete).
- Talk out loud as you go, as you would to an interviewer. Record it on
  your phone if you can bear to; it's the best feedback you'll get.

## Steps

### 1. Pick a problem you haven't seen

Three sealed problems below. Pick **one** without reading the others
(roll a die: 1–2 → A, 3–4 → B, 5–6 → C). Save the other two for IP.2 practice.

Use the table definitions from memory. If you need a column name, say
what you'd assume, as you would in an interview.

<details>
<summary>Problem A</summary>

For each NBA team in the 2024 regular season, find its **longest run
of consecutive games scoring 120 or more points**. Return team, run
length, first and last date. Ties: return all.

</details>

<details>
<summary>Problem B</summary>

For each NBA player in 2024 (min 50 games played), find the game where
their points **exceeded their own previous-10-game average by the most**.
Return player, date, points, the trailing average, and the difference.
Games with fewer than 10 prior games don't count.

</details>

<details>
<summary>Problem C</summary>

For each WNBA season, rank teams by **point differential per game**
(regular season). Return the top 2 per season with their win %. Then add
a column showing how far (in point differential) each is behind the
season leader.

</details>

### 2. Solve it: 15 minutes, timed

Start the timer when you start reading. In the first two minutes, say
out loud: the pattern, the grain of your output, and any decisions
(playoffs? DNPs? ties?).

### 3. Explain the plan: 5 more minutes, still closed-book

Without running anything, sketch the plan your query would produce,
bottom-up: scan → filters → aggregates → windows → qualify → sort. For
each step, estimate the rows in and out. Name the most expensive step and
one way to make it cheaper.

### 4. Now check it

Timer off. Type your query into DuckDB exactly as written. Then:

- Does it run? Count syntax errors; they matter less than logic errors,
  but note them.
- Is it right? Verify one row by hand.
- Run `EXPLAIN ANALYZE`. How close was your sketch?

### 5. Score yourself honestly

| Result | Meaning |
|---|---|
| Correct logic in ≤ 15 min, plan roughly right | **Pass.** Close the ticket. |
| Correct logic in 15 to 25 min | Not yet. Redo two M1.8 problems of the same pattern, retry with another sealed problem in 2 days. |
| Wrong pattern or stuck | Repeat the lab for that pattern (M1.3, M1.4 or M1.6) from a blank file, then retry. |

### 6. Write the notes

Append to `docs/notes/m1.md`:

```markdown
## Ready-when check (YYYY-MM-DD)
- Problem: A/B/C · Time: mm:ss · Result: pass / retry
- Mistakes: logic __, syntax __
- Plan sketch vs actual:

## Hardest part of M1
<three sentences: what was hardest and why>
```
