# M1.4 · Rolling 5-game scoring average

> **Ticket:** [#29](https://github.com/Dfscashline21/sideline/issues/29) ·
> **Mode:** hand · **Time:** 90 min ·
> **Needs:** M1.1 session 2 (frames), M1.2 (`nba_player_box`)

## Why this matters

"Rolling N-period average" is the most common window-frame interview
question, and it's also a real feature-engineering task: in M12 you'll
build rolling features for a model, and **including the current game**
in a feature that predicts the current game is *leakage*. This lab
trains the habit of choosing a frame on purpose.

## What you'll produce

`sql/problems/002_rolling_scoring_avg.sql` with, per player per game:

- `avg_last5_incl`: average points over this game and the 4 before it
- `avg_last5_excl`: average points over the 5 games **before** this one

Plus a comment explaining each frame clause.

## Steps

### 1. Decide what counts as a "game"

Look at one player's rows first:

```sql
select game_date, season, season_type, did_not_play, minutes, points
from nba_player_box
where athlete_display_name = 'Nikola Jokic' and season = 2024
order by game_date
limit 20;
```

Decisions to write in your header:

- **DNP rows** (`did_not_play = true`) have `points = NULL`. Is a game
  he didn't play one of "his last 5 games"? For a scoring average,
  almost certainly not. Filter them out *before* the window.
- **Season boundaries.** Should game 1 of a new season average in the
  last 4 games of last season? Pick one and say why.
- **Playoffs.** Same question.

### 2. Write the "including" version

You want the current row and the 4 physical rows before it. `ROWS` or
`RANGE`? (Think: is "4 before" a count of rows or a distance in values?)

</details>

```sql
avg(points) over (
    partition by ___
    order by game_date, game_id
    rows between ___ preceding and ___

```

✅ **Checkpoint:** check one row by hand. Pick a game in the middle of the
season, average the five `points` values yourself, compare.

### 3. Write the "excluding" version

The frame must end **before** the current row.

<details>
<summary>Hint</summary>

Both ends of the frame are `PRECEDING`: from 5 rows back to 1 row back.

</details>

### 4. Handle the start of a series

For a player's first game, the excluding window is empty, and for games 2
to 5 it holds fewer than 5 games. What does `avg()` return for each?
Is a "5-game average" over 2 games misleading?

Add a column `games_in_window` (hint: `count(points)` with the same
frame) and decide whether to show `NULL` until there are 5 games. Many
real feature pipelines do exactly that.

<details>
<summary>Solution (open only after you have your own)</summary>

```sql
-- Problem:  Rolling 5-game scoring average per player, including and excluding the current game
-- Pattern:  window frames (ROWS BETWEEN)
-- Tables:   nba_player_box
-- Decisions: regular season only; DNPs removed before windowing; windows reset each season
with played as (
    select athlete_id, athlete_display_name, season, game_date, game_id, points
    from nba_player_box
    where season_type = 2 and not did_not_play
)
select *,
    -- ROWS, not RANGE: "last 5 games" is a count of rows. RANGE would work on
    -- game_date values, so "4 preceding" would mean 4 days, not 4 games.
    avg(points) over w_incl as avg_last5_incl,
    -- Frame ends 1 row back so the current game can't leak into its own feature.
    avg(points) over w_excl as avg_last5_excl,
    count(points) over w_excl as games_in_excl_window
from played
window
    w_incl as (partition by athlete_id, season order by game_date, game_id
               rows between 4 preceding and current row),
    w_excl as (partition by athlete_id, season order by game_date, game_id
               rows between 5 preceding and 1 preceding)
order by athlete_id, game_date;
```

</details>

### 5. Prove ROWS was the right choice

Rewrite the including version with
`range between interval 4 days preceding and current row` (order by
`game_date` only). Compare it to your `ROWS` version for one player. Why
do the two differ, and when would a date-based window actually be the
better feature? (Think about back-to-back games and fatigue.)

`sql/problems/002_rolling_scoring_avg.sql`, header plus frame comments,

## Gotchas

- **Default frame.** `avg(points) over (partition by p order by d)`
  without a frame is a running average from the start, not a rolling one.
  It's the most common wrong answer.
- **Integer division.** `points` is an integer. DuckDB's `avg()` returns
  a double, but if you ever compute `sum(points) / count(*)` yourself in
  another database, you may get integer division.
- **Traded players.** Partition by player, not by player and team, or a
  mid-season trade restarts the window. Is that what you want?
