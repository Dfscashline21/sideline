# M1.2 · Load practice data into DuckDB

> **Ticket:** [#27](https://github.com/Dfscashline21/sideline/issues/27) ·
> **Mode:** agent: the agent drafts, you review it like a junior's PR ·
> **Time:** 90 min · **Needs:** the [module overview](README.md) (table spec)

## Why this matters

This is your first `mode:agent` ticket, so the skill being practised
isn't writing a loader. It's **specifying** work clearly and
**reviewing** it hard. "You must be able to explain every line" is the
acceptance bar, and the interviewer version is "walk me through this
code".

It's also deliberately *not* real ingestion. M2 builds the
production-grade extractor (retries, watermarks, raw zone in MinIO). This
is a quick, honest practice loader. Keep it small.

## What you'll produce

- `sql/practice/load_practice_data.py`: one command that builds
  `.data/practice.duckdb` with the five tables in the
  [module overview](README.md#tables-m12-should-build).
- The script committed; the database **not** committed.

## Steps

### 1. Branch and make a place for it

```bash
git switch -c m1.2-practice-data
mkdir -p sql/practice
```

### 2. Write the spec before you prompt

Write down, in your own words, what "done" looks like, so you can judge
the agent's output against it. At minimum:

- the five tables, their source releases and season ranges (from the overview)
- the output path, and that the parent folder must be created if missing
- safe to re-run: running twice gives the same database, not double rows
- prints one line per table: name, row count, min and max season
- passes `make lint` and `make typecheck` (mypy is strict here: every
  function needs annotations)
- standard library plus `duckdb` only, so no new dependencies

### 3. Prompt the agent

A starting prompt you can adapt. Paste your spec where indicated:

> Write `sql/practice/load_practice_data.py` for this repo. It builds a
> local DuckDB practice database from public Parquet files in the
> `sportsdataverse/sportsdataverse-data` GitHub releases. The URL
> pattern is
> `https://github.com/sportsdataverse/sportsdataverse-data/releases/download/<release>/<prefix>_<season>.parquet`.
> DuckDB can read these URLs directly with `read_parquet`.
>
> Requirements: *(paste your spec)*
>
> Keep it under ~80 lines. Use a data structure for the table list
> rather than five copies of the same code. Don't add dependencies.
> Explain any DuckDB feature you use that isn't plain SQL.

Read `AGENTS.md` (M0.7) into the session first, or check the agent
picked it up, so it follows your conventions.

### 4. Review it like a pull request

Don't run it yet. Read it first, line by line, and answer each question
in writing (PR description or a scratch file):

| Review question | What a good answer looks like |
|---|---|
| Where does the output path come from? Is it under `.data/`? | Path built from the repo root, not the current directory, so it works from anywhere |
| What happens on a second run? | `CREATE OR REPLACE TABLE`, or drop then create. Not `INSERT` into an existing table |
| How does it pass a list of URLs to `read_parquet`? | A list parameter, or a list literal. Not one query per file followed by `UNION ALL` built from strings |
| What if a season's file is missing (404)? | Fails loudly with the URL in the error, rather than skipping silently |
| What does `union_by_name=true` do, and is it needed? | Columns are matched by name across files whose schemas drift between seasons. Look it up if the agent used it |
| Is any SQL built by f-string from data? | Table names from a constant list are fine; never values from outside |
| Are all functions typed? | `def main() -> None:` and so on |

Ask the agent to explain anything you can't. Then ask yourself: could
you explain it to someone else? If not, you're not done.

<details>
<summary>Hint · Things agents often get wrong here</summary>

- Downloading files with `requests`/`urllib` first, then loading them.
  This works, but it's twice the code and adds a dependency. DuckDB's
  `httpfs` extension reads HTTPS directly (it auto-loads on first use).
- Hard-coding `season` 2027. That season is in progress and its file
  changes daily, so practice results won't be reproducible.
- `os.chdir` or relative paths that only work from the repo root.
- Writing to `data/` instead of `.data/` (only `.data/` is ignored).

</details>

### 5. Run it and check the numbers

```bash
time uv run python sql/practice/load_practice_data.py
```

Expect roughly 15 to 60 seconds depending on your connection, and a file
of about 650 MB. Then verify the data independently: don't trust the
script's own printout alone.

```bash
uv run python - <<'EOF'
import duckdb
con = duckdb.connect(".data/practice.duckdb", read_only=True)
con.sql("""
    select 'nba_team_box' t, count(*) n, min(season), max(season) from nba_team_box
    union all select 'wnba_team_box',   count(*), min(season), max(season) from wnba_team_box
    union all select 'nba_player_box',  count(*), min(season), max(season) from nba_player_box
    union all select 'nba_pbp',         count(*), min(season), max(season) from nba_pbp
    union all select 'ncaa_player_box', count(*), min(season), max(season) from ncaa_player_box
""").show()
EOF
```

✅ **Checkpoint:** counts close to these (the source is occasionally
re-published, so exact counts can drift slightly):

| Table | Rows | Seasons |
|---|---|---|
| `nba_team_box` | ~64,400 | 2002 to 2026 |
| `wnba_team_box` | ~11,300 | 2003 to 2026 |
| `nba_player_box` | ~173,000 | 2022 to 2026 |
| `nba_pbp` | ~1,880,000 | 2024 to 2026 |
| `ncaa_player_box` | ~3,300,000 | 2008 to 2026 |

Then run three sanity checks of your own. Write the SQL yourself (it's
hand work):

1. `(game_id, team_id)` is unique in `nba_team_box`.
2. Every NBA team has 82 regular-season games in 2024. Ignore the
   All-Star rows. Two teams don't: find out why. (The
   [module overview](README.md#know-these-before-you-write-any-query)
   has the answer once you've looked.)
3. Run the script a second time. Do the counts stay identical?

### 6. Make it easy to re-run

Add a Make target so you (and M0.8's stranger) don't need to remember
the path. Follow the existing style: a `## comment` so `make help` lists it.

```make
practice-data: ## Build .data/practice.duckdb for the M1 SQL labs
	$(UV_RUN) python sql/practice/load_practice_data.py
```

Remember to add it to the `.PHONY` list. Mention it in `sql/README.md`.

### 7. Ship it

```bash
make lint && make typecheck && make test
git status                        # make sure .data/ isn't listed
git add sql/ Makefile
git commit -m "M1.2: practice data loader for M1 SQL labs"
git push -u origin m1.2-practice-data
gh pr create --fill               # Closes #27
```

In the PR description, paste your review answers from step 4. That's
the evidence that you reviewed it, not just accepted it.

## Gotchas

- **`check-added-large-files` hook.** If `git status` ever shows a
  `.duckdb` or `.parquet` file, stop. The pre-commit hook will block it,
  but don't rely on that.
- **Schemas drift between seasons.** The 2026 WNBA team-box file has a
  `lead_changes` column that earlier seasons don't. Loading all seasons
  without `union_by_name=true` fails with a column mismatch (or, worse,
  silently lines up the wrong columns if you load by position).
- **Two connections, one file.** DuckDB allows one writer at a time. If
  the loader fails with a lock error, close any other DuckDB shell open
  on `.data/practice.duckdb`.
