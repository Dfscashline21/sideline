## Session 1 · Window function basics (60 min)

**Read:** [DuckDB window functions](https://duckdb.org/docs/stable/sql/functions/window_functions)
(the sections on `PARTITION BY`, `ORDER BY` and the function list).

The mental model: a window function computes a value **for each row**
from a set of related rows (its *window*), **without collapsing rows**
the way `GROUP BY` does.

```
function(...) OVER (
    PARTITION BY <which rows are related>     -- like GROUP BY, but rows stay
    ORDER BY     <order inside each partition>
    <frame>      <which of those rows to use for this row>
)
```

Use this toy table for sessions 1 to 3:

```sql
create table scores as select * from (values
    ('Alice', 1, 10), ('Alice', 2, 20), ('Alice', 2, 30), ('Alice', 3, 40),
    ('Bob',   1, 25), ('Bob',   2, 25), ('Bob',   3, 15)
) t(player, game_day, pts);
```

### Exercise 1.1: the three rankings

Predict, then run:

```sql
select player, game_day, pts,
       row_number() over w as rn,
       rank()       over w as rnk,
       dense_rank() over w as drnk
from scores
window w as (partition by player order by pts desc)
order by player, pts desc;
```

<details>
<summary>Check your understanding</summary>

For Bob: two rows have 25 points.

- `row_number`: 1, 2, 3. Ties broken arbitrarily: **non-deterministic**
  between the two 25s.
- `rank`: 1, 1, 3. Ties share a rank, then it **skips**.
- `dense_rank`: 1, 1, 2. Ties share a rank, **no gap**.

Interview question: "top 3 per group, ties included". Which one? (You'll
need this answer for M1.6.)

</details>

### Exercise 1.2: LAG and LEAD

Write a query that shows each player's points and the change from their
previous game. What does the first game show, and how would you make it
show 0 instead?

<details>
<summary>Hint</summary>

`lag(pts) over (partition by player order by game_day)`. Look up its
optional second and third arguments.

</details>

`sum(pts) over (partition by player)` vs

## Session 2 · Frames: ROWS vs RANGE (60 min)

**Read:** the "Framing" section of the window functions docs.

The **frame** is the subset of the partition used for the current row.
The rule that catches everyone:

> If you write `ORDER BY` and no frame, the default frame is
> `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`.

**`ROWS`** counts *physical rows*. **`RANGE`** works on *values* of the
`ORDER BY` column, so all rows with the same value (*peers*) are in or out
together.

### Exercise 2.1: the canonical difference

```sql
select player, game_day, pts,
  sum(pts) over (partition by player order by game_day
                 rows  between unbounded preceding and current row) as rows_running,
  sum(pts) over (partition by player order by game_day
                 range between unbounded preceding and current row) as range_running
from scores
order by player, game_day;
```

Predict Alice's two `game_day = 2` rows in both columns before running.

<details>
<summary>Explanation</summary>

Alice has two rows on day 2 (20 and 30).

- `rows_running` gives them **different** totals (30 and 60, or 40 and
  60, depending on which tied row comes first). Order among ties isn't
  guaranteed, so this column is non-deterministic.
- `range_running` gives **both** rows 60, because both day-2 rows are
  peers and are included together.

Write this example on your cheat sheet. It's the answer to the ticket's
acceptance criterion.

</details>

### Exercise 2.2: sliding frames

Write a "last 2 games including this one" points sum using `ROWS`. Then
a version **excluding** the current game. Which frame clause does each use?

<details>
<summary>Hint</summary>

`rows between 1 preceding and current row` vs
`rows between 2 preceding and 1 preceding`. You'll use exactly this
shape in M1.4.

</details>

### Exercise 2.3: RANGE with an offset

`range between 1 preceding and current row` on `game_day`: what does
"1 preceding" mean here, compared to `ROWS`? When would value-based
windows be what you want (hint: dates with gaps between games)?

## Session 3 · QUALIFY and CTEs (45 min)

**Read:** [DuckDB QUALIFY](https://duckdb.org/docs/stable/sql/query_syntax/qualify)
and [WITH clause](https://duckdb.org/docs/stable/sql/query_syntax/with).

SQL runs clauses in a logical order:
`FROM → WHERE → GROUP BY → HAVING → WINDOW → QUALIFY → SELECT → ORDER BY → LIMIT`.
You can't filter on a window function in `WHERE` because windows haven't
been computed yet. `QUALIFY` is the `WHERE` for window results.

### Exercise 3.1

Return each player's single best game using `QUALIFY`. Then write the
same query **without** `QUALIFY`, using a CTE. Many interview platforms
run Postgres or SQL Server, which don't support `QUALIFY`, so you need
both forms.

### Exercise 3.2: recursive CTE

**Read:** the recursive CTE section of the WITH docs.

Generate every date from 2024-10-22 to 2024-10-31 with a recursive CTE
(no `generate_series`). Then explain, in one sentence, the two parts of
every recursive CTE and how it knows when to stop.

<details>
<summary>Skeleton</summary>

```sql
with recursive days(d) as (
    select date '2024-10-22'          -- anchor: the starting row(s)
    union all
    select ___ from days where ___    -- recursive step: next row(s), with a stop condition
)
select * from days;
```

</details>

Where recursive CTEs show up in real work: hierarchies (org charts,
tournament brackets: a game's winner feeds the next game), and
filling gaps in time series.

## Session 4 · Reading query plans (60 min)

**Read:** [DuckDB EXPLAIN](https://duckdb.org/docs/stable/guides/meta/explain)
and [EXPLAIN ANALYZE](https://duckdb.org/docs/stable/guides/meta/explain_analyze).

- `EXPLAIN` shows the plan the optimizer **intends** to run.
- `EXPLAIN ANALYZE` **runs** the query and shows actual time and row
  counts per operator.

Plans are trees: read them **bottom-up**. Data flows from scans at the
bottom, through filters, joins, aggregates and windows, up to the result.

### Exercise 4.1

```sql
create table big as
select i % 1000 as player, i as game, (random() * 40)::int as pts
from range(5000000) t(i);

explain analyze
select player, game, pts
from big
qualify rank() over (partition by player order by pts desc) <= 3;
```

Find in the output: the scan, the `WINDOW` operator, and the `FILTER`.
How many rows went *into* the window, and how many came *out* of the
filter?

Now change `rank()` to `row_number()` and run it again. The `WINDOW`
operator disappears: DuckDB recognises "top N per group with
`row_number`" and rewrites it as an aggregate plus a join. The optimizer
is allowed to change *how* your query runs, as long as the result is the
same. Always read the plan rather than assuming it follows your SQL.

### Exercise 4.2

The window is now inside a subquery, and the filter is outside it. Run
both and compare where the filter ends up:

```sql
explain analyze
select * from (
    select player, game, pts, rank() over (partition by player order by pts desc) as rk
    from big
) where player < 10 and rk <= 3;

explain analyze
select * from (
    select player, game, pts, rank() over (partition by player order by pts desc) as rk
    from big
) where pts > 5 and rk <= 3;
```

In the first, `player < 10` moves down into the `TABLE_SCAN` and the
window sees 50,000 rows. In the second, `pts > 5` stays above the window,
which sees all 5,000,000. Why is the optimizer allowed to move one and
not the other?

<details>
<summary>Explanation</summary>

Filtering on a partition column removes whole partitions, which can't
change any other partition's window result, so the optimizer pushes it
down to the scan. Filtering on `pts` would remove rows *inside* a
partition and change the ranks, so it must stay above the window (if you
*meant* to filter first, put it in the inner `WHERE`; that's a different
question with different answers). This idea ("can I filter before the
expensive step?") is most of M1.7.

</details>
